# Peak Share 产品线：Share、Review、Forms 与 Portal

**Status:** 产品线概念已整理，进入调研候选；尚未完成市场、技术、安全与商业验证，未进入实施 spec  
**Date:** 2026-07-22  
**读者:** Peak Assistant owner、产品规划者和后续调研 / 原型负责人  
**关联:** [Roadmap · 调研候选](../../roadmap.html#researching) · [Peak Composer 编辑视图](../../superpowers/specs/2026-07-09-peak-composer-editing-view.md)
**更新:** 2026-07-28 补充 Composer 本地评论、外部分享评论与 Copilot 引用源的统一兼容约束

## 结论先行

这个方向已经不只是“一键分享一篇笔记”，而是一条可以逐层形成价值的产品线：

```text
Peak Share
单篇发布与持续更新的技术底座，也是低门槛获客入口
        ↓
Peak Review
把评论升级成批注、修改请求、审批、签收和有版本的操作记录
        ↓
Forms（候选能力 / 候选独立产品）
让外部用户提交结构化数据和附件，并安全回流到 Vault
        ↓
Peak Portal
把多篇文档、进度、决策、文件、Review 和 Forms 组合成长期客户空间
```

当前最强的商业假设是 **Peak Portal**：把 Obsidian 项目文件夹变成私密、专业、可评论、可审批的客户交付空间。`Share` 是基础设施与获客入口，`Review` 是最直接的付费理由，`Forms` 是由外向发布之外的第二条数据闭环，`Portal` 则有机会成为承担主要收入的产品。

工程构建顺序和产品验证顺序不应混为一谈。工程上必须先有可靠的 Share 发布底座；产品上应该直接用一个窄范围的自由职业者 Portal 验证真实客户是否愿意进入、查看、评论和确认，而不是只验证“用户会不会偶尔生成分享链接”。

## 证据边界

本文主要整理 owner 提供的产品设想，不等于市场研究、法律意见、成本测算或已接受架构。

本轮只核实了两项官方背景：

- [Obsidian Bases](https://obsidian.md/help/bases) 是 core plugin，可以基于本地 Markdown 文件及其 properties 建立可查看、编辑、过滤和排序的数据库式视图，因此适合作为 Portal 本地项目视图的候选基础。
- [Obsidian 官方定价页](https://obsidian.md/pricing) 在 2026-07-22 显示 Publish 为每站点 US$8/月（年付）或 US$10/月（月付）。它只能作为网页发布价格的背景锚点，不能直接证明 Portal 的支付意愿。

“Bases 的 Kanban 正在开发”、客户门户市场价格区间、下面的套餐价格和目标用户支付意愿尚未在本轮独立验证，因此都保持为假设。

## 四个层次不是四套重复产品

| 层次 | 用户要完成的事 | 核心单位 | 主要付费价值 | 关系 |
| --- | --- | --- | --- | --- |
| Peak Share | 把当前笔记发给别人并持续更新 | 一篇共享笔记 | 长期链接、密码、版本、去品牌 | 所有外部页面的发布底座 |
| Peak Review | 对内容给出可追踪的正式反馈 | 文档版本上的 review | 审批、修改请求、签收、审阅记录 | 可独立售卖，也被 Portal 复用 |
| Forms | 从外部收集结构化信息和附件 | 一次 submission | 自动入 Vault、可查询、可进入 Bases | 可独立验证，也被 Portal 复用 |
| Peak Portal | 给一个客户持续存在的交付空间 | 一个 client project | 专业呈现、减少邮件、客户行动、品牌与域名 | 组合 Share、Review、Forms、Files、Notifications |

不要为四个名字建立四套发布、身份、附件、事件和计费系统。研究阶段就应把它们视为一组共享领域能力上的不同产品包装。

## 最值得先切入的人群

### 第一目标：有真实客户项目的自由职业者

- 独立开发者。
- 网页与 UI/UX 设计师。
- 品牌、内容、营销和 SEO 顾问。
- 独立研究者、摄影师和视频制作人。

他们的资料通常散落在邮件、网盘、聊天软件、本地文件和不同文档工具中，也很在意客户看到的专业程度。第一批验证应进一步收窄到 owner 最熟悉的“独立开发者交付网站 / 软件项目”场景。

### 第二目标：顾问与专业服务人员

- 商业、技术、职业和留学顾问。
- 教练、导师和私人教师。
- 研究与内容咨询人员。

这些场景反复需要展示分析、进度和行动计划，同时等待客户提供资料或作出决定。

### 后期目标：小型工作室与代理机构

两到十人的工作室有更高付费潜力，但会立即带来成员权限、审计、模板、多品牌和集中计费问题，不适合进入第一个产品验证。

## Peak Portal：最看好的商业产品

Peak Portal 的工作定义是：

> 以 Obsidian 为作者后台的客户门户 SaaS。作者继续在本地 Vault 工作，客户只看到经过筛选的专业项目空间，并在其中查看、评论、确认和提交资料。

### 客户空间不是文件列表

一个 Portal 可以由若干明确发布的内容组成：

```text
Project Alpha
├── 项目说明
├── 当前进度
├── 设计方案
├── 会议纪要
├── 待确认事项
├── 文件与交付物
└── 反馈与提交
```

首页只回答四个客户问题：

1. 项目现在进行到哪里？
2. 最近发生了什么？
3. 现在有什么事情需要我处理？
4. 下一步是什么？

因此 Portal 不能只是把一个文件夹里的 Markdown 平铺到网页。它需要一个面向客户的首页，把最新更新、待审批、待决策、下一里程碑和新文件聚合出来。

### 明确的发布 allowlist

用户本地可能同时拥有 `Requirements.md`、`Internal Notes.md`、成本测算和未完成草稿。Portal 只能发布用户明确选择的内容，例如：

```yaml
---
peak-portal: acme
publish: true
order: 3
client-title: Website Requirements
---
```

是否采用这一 frontmatter 形状仍属后续 spec 决策，但产品边界必须保持：**未明确发布的文件默认不离开设备。** 发布前还应提供最终内容和附件清单预览，避免嵌入内容或内部链接把未选择的信息带出去。

### Portal 的核心模块

- 客户首页：状态、最近更新、下一步和待客户行动。
- 多篇文档：导航、版本和可控的内容降级。
- Review：评论、批注、审批、签收和选项决策。
- Files：交付物下载、客户上传、版本和状态。
- Forms：客户资料收集并回流 Vault。
- Notifications：邮件和 Obsidian 未读提示，默认支持摘要。
- Access：Secret link、密码；需要可信身份时升级 magic link。
- Branding：Logo、品牌色、邮件发件人、自定义域名和去品牌。

### 第一垂直模板

独立开发者 Portal 可以固定在一个很窄的内容结构：

```text
Project Overview
Requirements
Technical Decisions
Progress
Meeting Notes
Deliverables
Feedback
```

先验证这一种真实项目，再考虑顾问 Portal 和需要强图片 / 画布批注的设计师 Review Portal。

## Peak Review：从评论工具变成工作流产品

普通评论表达“有人说了什么”，Review 还要表达“客户对哪个版本采取了什么正式动作”。首批结构化动作可以包括：

- `Approve`。
- `Request changes`。
- `Acknowledge receipt`。
- `Choose option A / B / C`。

适用场景包括 PRD 审核、设计方案确认、合同草案反馈、会议纪要确认、客户验收、内容发布审批和论文导师批注。

### 统一批注域：Composer 与 Share 不能各建一套评论

Composer 本地评论、分享网页上的朋友评论、Portal 客户反馈和 Peak Review 应复用同一个批注领域模型。它们可以使用不同存储和同步 adapter，但不能分别发明锚点、线程、状态与身份语义，否则同一条反馈无法在作者本地、外部页面、Copilot 和后续 Review 之间稳定流转。

这是一项未来兼容约束，不表示 Share、Portal 或远程同步已经进入实施。进入正式 spec 前至少要覆盖以下能力：

- **统一目标锚点：**评论可以绑定整个文档、Block、文字选区或对象子目标。对象子目标要为表格单元格、图片区域、PDF 页码 / 选区和 Canvas 节点预留可扩展形状。
- **稳定身份与版本：**每条批注和线程拥有稳定 ID，并记录文档 ID、创建时的本地 source revision 或已发布 `PageVersion`、原始引用文字和上下文指纹。不能只靠当前文本位置或临时 Block ID。
- **版本迁移与失效：**正文更新后，批注要区分仍可定位、已映射到新版本、仅属于旧版本和锚点失效。失效批注不能静默消失或被错误重绑，用户应能查看旧版本并手动重新锚定。
- **右侧批注体验：**本地 Composer 和网页阅读器都支持选中文字评论、整块 / 对象评论、正文高亮、右侧批注卡和双向定位。宽度不足时降级为贴边抽屉，而不是把评论表单插进正文流。
- **线程生命周期：**支持回复、编辑记录、删除墓碑、解决、重新打开、未读和按线程静音。`resolved` 是讨论状态，不能替代版本化的 `Approve` 或 `Request changes`。
- **参与者与权限：**区分作者私人批注、作者公开批注、受邀朋友 / 客户反馈和 Copilot 产出。查看、评论、回复、解决、重新打开和执行正式 Review 动作需要分别授权；Secret link 下的展示身份不能被误报为可信实名。
- **发布隐私：**发布正文不会自动上传作者的本地私人评论。分享确认面必须让作者选择是否公开既有批注、是否允许新评论以及谁能看到线程；关闭或撤销分享后仍需定义评论保留、导出和删除策略。
- **离线与双向同步：**外部评论首先成为可靠的云端协作事件，插件在线后以游标、幂等事件 ID 和删除墓碑同步到本地投影。不能使用整文件覆盖或客户端时间戳的最后写入获胜来合并线程。
- **通知与治理：**支持新评论、回复、提及、解决和 Review 动作的站内 / 邮件摘要，以及限流、举报、封禁、垃圾内容处理和审计记录。第一版可以缩减通知渠道，但不能忽略公开链接的滥用面。
- **Copilot 引用源：**评论与线程可以作为显式、可定位的 Copilot source chip；冻结上下文时携带评论 ID、锚点、原文、线程和版本。朋友 / 客户输入属于外部不可信内容，必须与作者指令分层，防止评论被当成系统指令或提示注入。
- **AI 行为边界：**Copilot 可以总结讨论、起草回复或依据评论生成正文候选修改，但不得自动发送回复、修改正文、解决评论或批准版本。每个结果必须保留“引用了哪些评论”的 receipt，并由作者明确确认。
- **可携带与可恢复：**用户需要能够导出批注 / Review 记录，重新连接同步后恢复线程，并在删除账号、Portal 或分享链接时看到明确的数据处理结果。

最小的数据关系应保持清楚：

```text
Document / PageVersion
        └── AnnotationTarget（document / block / selection / object）
                └── CommentThread
                        ├── CommentEvent（author / guest / customer）
                        ├── ResolutionEvent
                        └── CopilotSourceRef（显式引用，不自动执行）

ReviewAction（approve / request changes / acknowledge / choose）
        └── 单独绑定 PageVersion 与可信身份记录
```

普通评论是围绕内容的讨论；Review action 是对特定版本采取的正式动作。两者可以出现在同一右侧批注体验中，但数据与权限不能混成一个 `status` 字段。

### Review 的基本记录

审批不能只把 `review-status: approved` 覆写进当前 frontmatter。最小可信记录还需要：

- 稳定的文档 ID 和被审阅的版本 ID。
- 动作类型、结果和可选说明。
- 审阅人身份及身份验证方式。
- 操作时间。
- 后续是否被新版本取代或撤销。

Vault frontmatter 可以保存方便用户查看的最新投影：

```yaml
---
review-status: approved
reviewed-by: Alice
reviewed-at: 2026-07-22T10:32:00+12:00
reviewed-version: 4
---
```

但云端不可变 review event 与本地投影的 source-of-truth 关系必须在 spec 中单独决定。第一版只能称为“有身份和版本记录的确认”，不能宣称法律级电子签名。

### 为什么 Review 更适合收费

审批、签收和修改请求能减少“我没有同意过”的争议，也能形成项目记录。它比普通评论更贴近收入、交付和责任，因此可以作为独立的 Peak Review 套餐，也可以成为 Portal 的核心付费层。

## Forms：结构化信息回到 Vault

Forms 让用户在 Obsidian 中定义需要收集的字段，发布成网页表单；提交后形成结构化 Markdown，并可被 Bases 或其他 Vault 工作流继续使用。

候选定义形状：

```yaml
---
peak-form:
  id: project-intake
  fields:
    - key: name
      type: text
      required: true
    - key: email
      type: email
      required: true
    - key: budget
      type: number
    - key: requirements
      type: long-text
---
```

同步到 Vault 后可以形成：

```yaml
---
submission-id: sub_01
form-id: project-intake
name: Alice
email: alice@example.com
budget: 5000
currency: NZD
status: new
submitted-at: 2026-07-22T14:20:00+12:00
---
```

候选用途：

- 客户需求与项目 onboarding。
- 活动报名、研究问卷和意见反馈。
- Bug report、招聘申请和联系表单。
- 课程作业提交和客户文件收集。

### 自动写回不能假装永远在线

网页提交无法直接写入用户本地 Vault。服务端需要先可靠保存 submission；插件在线后再拉取、去重并写入用户批准的目录。必须处理重复投递、字段演进、恶意附件、文件名冲突和部分同步失败。

Forms 可以作为 Portal 的“客户资料收集”模块，也值得单独验证成“表单 → Markdown / Bases”的产品入口。是否命名为 `Peak Forms`、独立收费或仅随 Portal 提供，目前不做决定。

## Source of truth 边界

“Markdown 是唯一源文件”只适用于作者正文，不能笼统覆盖所有协作数据。推荐在后续设计中区分四类真值：

| 数据 | 推荐 canonical source | Vault 中的形态 |
| --- | --- | --- |
| 作者文档正文 | 本地 Markdown | 原始笔记 |
| 已发布内容 | 云端不可变 PageVersion | 本地正文发布后的快照引用 |
| 评论、审批、访问与通知 | 云端事件记录 | 插件缓存或用户可读投影 |
| 表单提交与客户上传 | 云端接收队列，完成同步后进入 Vault | submission note 与受控附件目录 |

这不是已接受的数据架构，但它暴露了一个不能回避的问题：客户在作者设备离线时仍可能评论、批准和提交，因此云端协作事件不能只依赖本地 Markdown 存在。

## MVP：产品验证和工程底座分开看

### 工程底座：Share primitive

- 发布一篇明确选择的笔记。
- 固定链接持续更新。
- 删除和过期。
- 受约束 schema、固定模板、HTML 清洗与 CSP。
- 基础图片 / 附件支持和兼容性降级。

这一层是 Portal 必需的技术前提，但不需要先作为独立产品完整发布。

### 第一个产品验证：单客户 Portal

Obsidian 端：

- 从一个项目文件夹创建 Portal。
- 明确选择 3–5 篇客户可见笔记。
- 一键同步、更新、查看状态和删除 Portal。
- 查看普通评论。

客户端：

- 一个客户首页。
- 多篇文档导航与查看。
- 普通评论。
- 文件下载。
- Secret link 或密码访问。
- 基础品牌信息。

服务端：

- User、Portal、Page、PageVersion、Asset、Comment 和 AccessToken。
- 容量 / 数量限制、自动删除和最小运营管理能力。

这个版本只证明一件事：**用户愿不愿意把一个真实客户邀请到由 Obsidian 驱动的 Portal，并在整个项目周期持续使用。**

### 第二阶段：验证付费工作流

- Review：审批、修改请求、签收和版本绑定。
- Forms：资料收集、附件上传和 Vault 回流。
- 邮件通知和摘要。
- 自定义品牌与域名。
- 版本差异和客户决策事项。

### 明确不做

- 在线正文编辑、CRDT / OT、实时光标和冲突合并。
- 法律电子签名。
- 发票、收款、合同、会计、CRM 和工时管理。
- 团队空间、复杂成员权限和 SSO。
- 全 Vault 发布、Digital Garden、Newsletter 和 SEO 站点。
- AI 摘要、页面问答或自动翻译作为成立前提。
- 允许上传任意 HTML、JavaScript 或通用托管内容。
- 承诺兼容所有第三方 Obsidian 插件。

核心产品规则始终是：**作者在 Obsidian 工作，客户在 Portal 查看并采取行动。**

## 安全、隐私与访问边界

### 页面与附件

服务端只接受受约束的数据包和允许的附件类型，使用固定模板渲染。至少需要内容清洗、CSP、附件白名单、大小限制、病毒 / 恶意内容处理、热链防护、限流、举报和下架流程。

### 发布隐私

分享确认面需要明确展示：

- 哪些笔记、嵌入和附件会上传。
- 链接是否公开、是否允许索引。
- 何时过期，删除后何时完成清理。
- 评论和客户上传是否开启。
- 服务运营者是否可能访问内容。

### 身份与审批

Secret link 和共享密码适合低风险阅读，但不足以可靠回答“谁批准了哪个版本”。当 Review 需要实名操作记录时，应升级到 email magic link 或其他可验证身份方式。

## 商业模式假设

用户不是为“存储 100 MB”付费，而是为专业呈现、减少邮件往返、客户确认、项目记录、自定义品牌和域名付费。

| 产品 / 套餐假设 | 价格假设 | 价值 |
| --- | --- | --- |
| Peak Share Personal | US$4–6/月 | 高频分享、更新原链接、密码、基础评论 |
| Peak Review | US$7.99/月或 US$59–79/年 | 批注、修改建议、审批、版本差异、完成状态 |
| Portal Freelancer | US$9–15/月 | 多个客户空间、Review、Files、Forms、通知、去品牌 |
| Portal Studio | US$25–49/月 | 团队、权限、多品牌、域名、审计、模板、API / Webhook |

这些数字只用于访谈和定价测试，不是 roadmap 承诺。后续需要分别验证：用户愿意为 Review 单独付费，还是只愿意购买完整 Portal；Forms 是独立产品、获客入口，还是套餐功能。

## 最大的产品陷阱

### 变成第二个 Notion

一旦开始建设在线编辑器、数据库、看板、日历和实时协作，产品就会失去“Obsidian 是作者后台”的边界。

### 变成完整业务管理软件

合同、发票、支付、CRM 和工时管理可能提高客单价，也会把产品带入完全不同的竞争和运营范围。早期只聚焦内容交付、客户行动和记录回流。

### 只做漂亮网页

如果客户没有需要完成的动作，Portal 只是加强版发布站点。长期价值来自客户评论、批准、提交资料，以及这些状态安全地回到作者工作流。

### 过度承诺 Obsidian 还原度

主题、Callout、Mermaid、Math、Dataview、内部链接、嵌入笔记和动态插件是不同的兼容问题。实施前必须建立“支持 / 静态快照 / 降级 / 禁止”的矩阵。

### 把确认误报成法律签名

身份、时间、版本和事件记录可以提供清晰确认，但在法律与合规要求未完成专项调研前，产品不能宣传电子签名或不可否认性。

## 进入实施 spec 前必须回答的问题

### 产品

- 独立开发者会不会把真实客户邀请进 Portal，而不仅自己打开演示页面？
- 客户最有价值的动作是评论、批准、提交资料还是下载交付物？
- Share、Review、Forms 应独立售卖还是作为 Portal 的 acquisition / expansion 路径？

### 内容与同步

- 首版支持哪些内容类型，如何显示降级和发布预览？
- 如何处理删除、重命名、版本回滚、内部链接和被嵌入笔记？
- Review 与 submission 同步回 Vault 时，如何去重、冲突处理和保留事件历史？

### 身份、安全与运营

- 阅读、评论、审批、上传分别需要什么身份强度？
- 举报、下架、审计、备份清理、账号封禁和数据导出由谁处理？
- 如何防止钓鱼页面、恶意附件、热链和免费层自动化滥用？

### 商业

- 支付意愿来自 Portal 的专业形象，还是 Review 带来的责任记录？
- 每 Portal、每客户、每作者、存储量和团队席位哪一种计费单位最自然？
- Portal 是否应作为 Peak Assistant 的内置服务，还是共享账号体系的独立 SaaS？

## 推荐验证顺序

1. **5–8 位目标用户访谈：**只找有真实客户交付经历的独立开发者 / 顾问，收集最近一次项目的邮件、文档和确认路径。
2. **竞品实测：**覆盖 Share / Publish、client portal、review/approval 和 form-to-notes 四类，不用功能列表代替真实流程。
3. **内容与安全 spike：**用真实复杂笔记建立支持矩阵，并验证 allowlist、嵌入泄露、固定模板、清洗、CSP、删除和过期。
4. **Portal 可点击原型：**围绕“最近更新 → 待我确认 → 查看版本 → 评论 / 确认”设计客户首页，不先做通用 dashboard。
5. **单项目技术原型：**一个作者、一个 Portal、3–5 篇笔记、一个真实客户、普通评论和密码访问。
6. **Review 实验：**增加一个与版本绑定的 `Approve / Request changes`，观察它是否替代邮件确认。
7. **Forms 实验：**增加一个 project intake form，验证 submission 是否可靠进入 Vault 并被实际继续处理。
8. **定价测试：**分别测试 Share、Review 和 Portal 价值叙事，不用存储空间作为主卖点。
9. **spec gate：**只有真实客户使用、内容边界、安全治理、身份模型和回写策略足够清楚，才进入 `docs/superpowers/specs/`。

## 当前判断

这是一个值得优先调研的独立产品战线，不是局部 UI 小需求，也不是已经接受的实施计划。当前最值得保留的判断是：

> **Peak Share 是低门槛入口，Peak Review 是付费理由，Forms 是结构化回流入口，Peak Portal 是最有机会承担主要收入的产品。**

下一步不应同时实现完整四层，而应使用同一套底座做一个自由职业开发者 Portal 的真实客户验证，再由行为证据决定 Review、Forms 和更高阶 Portal 套餐的顺序。
