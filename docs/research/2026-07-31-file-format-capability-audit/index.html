结论：当前是 Markdown-first 多格式工作台

Peak Assistant 今天最强的故事不是“所有文件都能编辑”，而是以 Markdown Composer 为主工作面， 将多种文件纳入不同深度的知识工作流。不同格式停在不同层级，不能只用一个“支持”概括。

最完整：Markdown

可打开、解析、直接修改并完成 AI 审阅写回，覆盖常见 Markdown 块与 Obsidian 扩展语法。

覆盖最广：读取与索引

Loader 已覆盖部分文档、数据与 Obsidian 原生画布格式，但多数默认关闭；Office 内部分支不算产品支持。

差异化：嵌入对象修改

在 Markdown Composer 中，可对引用的 .base、.canvas 与 Excalidraw 文件做受控结构化写回。

未来故事：File Workspace 与 Peak Sheet

独立图片/HTML/PDF 工作区和 Peak Sheet 都已有设计或调研，但仍未成为生产功能。

当前最诚实的产品定位

“Markdown 为核心的多格式知识工作台”已经成立；“全格式 AI 编辑器”还没有成立。 这一区分会直接决定宣传可信度。

目标：每种文件都有合适的 AI 合同，而不是同一种编辑器

目标能力按用户任务组织：有些格式需要完整工作面，有些只需复用轻量文本编辑， 还有一些应保留 Obsidian 或生态插件的原生 renderer，由 Peak 增加 context-aware AI companion。 共同部分是当前文件、选区、revision、候选审阅与保存边界，而不是扩展名本身。

01完整 AI 文件工作面

Markdown、HTML、Code Source、Peak Sheet、Image。支持选区/当前视图上下文、格式动作、候选 review 和可靠写回。

02轻量文本与数据工作面

TXT、JSON。TXT 复用 Markdown 的纯文本子集；扁平 JSON 可进入 Peak Sheet，嵌套 JSON 保持 source/tree。

03原生 viewer + AI companion

PDF、Canvas、Excalidraw、Bases。不复制成熟 renderer，Peak 负责页/节点/元素/视图 context 与结构化写回。

04媒体理解与生成 integration

Audio、Video、draw.io 等。精确声明转录、时间轴问答或生成，不用“全格式支持”掩盖没有编辑 surface。

Owner 筛选后：真正值得补的是 Code Source Workspace

Markdown code block 适合记录和展示代码，但不能替代独立的 Python、TypeScript 等 native source files。 真正有产品价值的是：源码能单独打开、保留原扩展名、理解 import/reference，并与 Markdown 笔记和其他源码共同进入 AI context。

HTML project / bundle 入口 HTML + CSS/JS + JSON/WASM + assets；folder/manifest 是 bundle boundary 从 rendered element 定位源码；解释依赖与 console；一次审阅多文件修改 安全预览；运行、network 和外部 action 单独授权
源码“可编辑”和“可执行”必须分开

File Workspace 默认只负责查看、上下文、AI candidate 和 source patch。 Run/Test/Build、shell、安装依赖、network 与外部进程属于另一类 permissioned action； .env、credential、private key 和 ignore 文件默认不进入模型。

Jupyter：保留规划位，暂不实施

.ipynb 未来可做 cell-aware companion，但现在不预建 notebook runtime、kernel 或专用 UI。

JSONL：已有内部实现

PartitionedJsonlStore 已承载 conversation、receipt、media job、Hub 与 Composer history 等 machine records；不再重复建设 JSONL Workspace。

用户 JSONL 与内部 JSONL 要分开

DataStore/records/**/*.jsonl 不进入普通文件 surface 或知识索引。未来若需要 NDJSON → Peak Sheet，只做窄 import adapter。

其他格式全部降级

EPUB、字幕、邮件日历、地理数据、Parquet、Archive、设计/CAD 等先留 research backlog；没有真实任务就不扩展 Loader。

当前源码事实

当前没有 Code Source file view、代码 Loader、symbol/reference index 或 multi-file review。 仓库里已有 CodeMirror 组件和代码展示能力，但不能据此把源码文件工作区标记为已交付。

先定义“支持”到底指什么

一个扩展名出现在类型列表里，只能证明插件认识它。对外表达时至少要说明能力停在哪一步， 否则“支持 PDF”“支持 CSV”会被用户自然理解成可打开、可问 AI、可编辑和可保存。

  • Loader 支持不等于文件工作区。Loader 负责读取、切块、摘要和索引，不负责独立 View、编辑器或保存体验。
  • 附件可上传不等于模型已读取。文件可以被保存和显示，但还要确认实际字节或转文本内容是否进入模型请求。
  • 能生成不等于能回读和编辑。例如 .drawio 可以生成，但 Peak 没有对应 Loader 或独立编辑面。
  • 宿主能打开不等于 Peak 能修改。PDF、Bases、Canvas 与 Excalidraw 的原生显示能力来自 Obsidian 或生态插件。

这些文件今天是怎么被修改的

当前不存在一个“任意文件编辑器”。实际修改路径分为五种，每种都有不同的 source of truth 和保存边界。

01Markdown 主文件

Composer 直接读取和写回 .md。确定性操作与 AI 候选都经过 transaction/review 语义。

02Markdown 内结构化块

表格、图表、Mermaid、代码等仍保存回 Markdown 源文件。CSV 在这里是导入/导出格式，不是独立工作区。

03被引用的原生文件

.base、.canvas、Excalidraw 在 Markdown 内被引用时，可通过 typed patch 修改原文件，并带 revision guard。

04媒体生成与图片编辑

图片编辑读取 Vault 引用图，产出新的图片文件。音频和视频生成同样创建新产物，不是原文件原位编辑。

05结构化产物生成

Chat 可创建 Markdown、Bases、Excalidraw、draw.io 等文件，并记录 receipt。能创建不代表 Peak 也能完整编辑。

06Loader-only 文件

Loader-only 文件当前主要用于读取、摘要或索引。修改仍要回到外部或 Obsidian 原生工具。

聊天附件的 AI 直读链路目前不能作为卖点

默认配置选择 direct attachment，但当前最近消息渲染器没有把资源字节构造成模型消息 part。 转文本模式可以借助 Loader/转录生成摘要，但“把任意 PDF 或图片拖进来直接问”尚缺闭环证据；Office 不在产品支持范围。

宣传口径：哪些话现在能说

建议使用的总定位

Peak Assistant 是以 Markdown 为核心、面向 AI 时代文件的知识工作台。当前可深度编辑 Markdown， 提取和检索 PDF 文本、与 CSV 互操作，并协作处理部分 Obsidian 原生对象和图片产物。 JSON、HTML 与 TXT 当前仍以可选或内部读取基础为主； HTML、Peak Sheet、Image 与原生对象 companion 是已定义目标，但在交付前不会冒充当前支持。

可以直接说

  • Markdown 的完整编辑与 AI 协作
  • PDF 文本提取、索引和悬浮预览
  • Markdown 表格的 CSV 导入与导出
  • 生成与编辑 PNG/JPEG/WebP 图片
  • 生成 Bases、Excalidraw、draw.io 等 Vault 产物

带条件说

  • 启用后索引多种文本、数据与 Obsidian 原生对象格式
  • Canvas/Base/Excalidraw 修改发生在 Markdown 嵌入对象场景
  • 音频转录取决于已配置的 provider
  • 生态格式的最终渲染依赖 Obsidian 或社区插件

现在不要说

  • 支持 Word / PowerPoint，或声称 XLSX 已经可用
  • 支持独立编辑 CSV、JSON、HTML 或 PDF
  • 支持独立打开、引用和重构 Python/TypeScript 等源码文件
  • 支持所有图片的语义搜索
  • 任何附件都能被模型直接理解
  • Peak Sheet 已经可用

容易误导的短句

  • “支持 Office”与已锁定的产品范围直接冲突
  • “支持 HTML”会被理解为浏览器式预览与修改
  • “支持图片”会把预览、索引、理解和改图混成一件事
  • “支持 CSV”会被理解为电子表格工作区
  • “支持多模态附件”会越过当前 direct part 缺口

影响可信宣传的关键缺口

下面这些不是“以后可以更好”的普通增强，而是会让产品页、设置页和真实行为相互矛盾的合同问题。

XLSX 是最明显的假阳性

类型、Loader 扩展名和设置 UI 都出现 XLSX，但读取分支直接返回 null。当前应视为不支持。

HTML/XML 类型合并造成开关漂移

XML 由同一 Loader 读取，却产生 HTML 类型；设置页又没有 XML 开关，真实启用语义不清晰。

TXT 有 Loader，却没有设置入口

默认配置包含 TXT，但 Knowledge Index 的文件类型 chips 不包含它。用户无法从当前 UI 理解或控制这项能力。

图片索引不是真多模态理解

Image Loader 会读取二进制并计算 hash，但描述函数明确没有把图片字节发送给模型，通常只留下占位文本。

附件 direct mode 没有构造模型内容

模型路由会识别 vision/PDF 能力，但最近消息 slot 的 direct 分支没有追加 image/file part。

Loader 缺少格式级回归测试

当前有表格、原生对象、媒体相关 focused tests，但没发现覆盖全部 Loader 的 fixture/E2E 测试面。

图片格式清单不一致

Loader、附件分类、UI 图标和 AI 改图白名单各自维护扩展名，HEIC/AVIF/SVG 等处于不同状态。

File Workspace 仍是 implementation pending

当前 ViewManager 没有扩展名接管；Composer 入口也明确只接受 Markdown。

Code Source 尚无产品链路

现有代码块、CodeMirror 组件和附件展示不等于源码文件工作区；还没有语言扩展注册、reference graph 或 multi-file review。

建议把文件能力分成四条产品线

宣传重点不应等待所有格式都达到同一成熟度。更稳妥的做法是保留一个统一总定位， 同时把当前、下一阶段和远期能力明确拆开。

  1. 完整 AI 文件工作面。 Markdown 已是当前基线；HTML、Code Source、Peak Sheet 和 Image 按各自 context 与写回合同推进。
  2. 轻量文本与数据工作面。 TXT 复用 Markdown 纯文本子集；JSON 使用 source/tree，扁平数组可进入 Peak Sheet。
  3. 原生 viewer + Peak AI companion。 PDF、Canvas、Excalidraw 与 Bases 保留原生/生态 renderer，Peak 提供格式感知的上下文和写回。
  4. 媒体理解与生成 integration。 Audio、Video、draw.io 等按转录、时间轴问答或生成任务精确表达，不承诺通用编辑器。

DOC/DOCX、PPT/PPTX 不进入上述产品线。XLSX 与 CSV 一样归入 Peak Sheet 互操作路线， 但当前源码仍没有 XLSX 解析和导入闭环。

未来需要一个机器可读的文件能力清单

本次调研发现扩展名散落在多套类型、运行时与 UI 注册点中。 后续应由一个 app-owned capability manifest 生成用户设置和宣传矩阵，至少记录：

  • 扩展名与 MIME；
  • 读取与索引能力；
  • 预览、直接 AI 输入与独立编辑能力；
  • 嵌入编辑、生成与导出能力；
  • 默认开关、依赖的 provider 或生态插件；
  • 对应 fixture、自动化测试和真实 Obsidian 验收状态。
本轮不建议马上扩大格式数量

先修正 XLSX、附件 direct mode、图片索引和类型清单漂移，能够显著提高现有宣传的可信度。 在这些合同收口前继续添加扩展名，只会让“识别了”与“真的可用”之间的落差更大。
