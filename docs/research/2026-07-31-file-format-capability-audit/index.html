Peak Assistant 文件格式能力审计

这份报告回答两个容易被混在一起的问题：插件今天到底能对哪些文件做什么， 以及哪些能力已经足够成为宣传卖点。结论以当前代码、配置、测试和已登记设计为依据， 不把文件图标、扩展名识别或未来方案算成已交付能力。

结论：当前是 Markdown-first 多格式工作台

Peak Assistant 今天最强的故事不是“所有文件都能编辑”，而是以 Markdown Composer 为主工作面， 将多种文件纳入不同深度的知识工作流。不同格式停在不同层级，不能只用一个“支持”概括。

最完整：Markdown

可打开、解析、直接修改并完成 AI 审阅写回，覆盖常见 Markdown 块与 Obsidian 扩展语法。

覆盖最广：读取与索引

Loader 已覆盖常见文档、数据、Office 与 Obsidian 原生画布格式，但多数默认关闭。

差异化：嵌入对象修改

在 Markdown Composer 中，可对引用的 .base、.canvas 与 Excalidraw 文件做受控结构化写回。

未来故事：File Workspace 与 Peak Sheet

独立图片/HTML/PDF 工作区和 Peak Sheet 都已有设计或调研，但仍未成为生产功能。

当前最诚实的产品定位

“Markdown 为核心的多格式知识工作台”已经成立；“全格式 AI 编辑器”还没有成立。 这一区分会直接决定宣传可信度。

先定义“支持”到底指什么

一个扩展名出现在类型列表里，只能证明插件认识它。对外表达时至少要说明能力停在哪一步， 否则“支持 PDF”“支持 CSV”会被用户自然理解成可打开、可问 AI、可编辑和可保存。

识别知道扩展名和图标
预览悬浮或宿主查看
读取提取文本或二进制
索引进入搜索与摘要
修改直接或 AI 写回
生成创建或导出新文件
  • Loader 支持不等于文件工作区。Loader 负责读取、切块、摘要和索引，不负责独立 View、编辑器或保存体验。
  • 附件可上传不等于模型已读取。文件可以被保存和显示，但还要确认实际字节或转文本内容是否进入模型请求。
  • 能生成不等于能回读和编辑。例如 .drawio 可以生成，但 Peak 没有对应 Loader 或独立编辑面。
  • 宿主能打开不等于 Peak 能修改。PDF、Bases、Canvas 与 Excalidraw 的原生显示能力来自 Obsidian 或生态插件。
可作为当前卖点 可宣传但要限定 内部基础能力 暂不宣传 仅设计或调研

这些文件今天是怎么被修改的

当前不存在一个“任意文件编辑器”。实际修改路径分为五种，每种都有不同的 source of truth 和保存边界。

01Markdown 主文件

Composer 直接读取和写回 .md。确定性操作与 AI 候选都经过 transaction/review 语义。

02Markdown 内结构化块

表格、图表、Mermaid、代码等仍保存回 Markdown 源文件。CSV 在这里是导入/导出格式，不是独立工作区。

03被引用的原生文件

.base、.canvas、Excalidraw 在 Markdown 内被引用时，可通过 typed patch 修改原文件，并带 revision guard。

04媒体生成与图片编辑

图片编辑读取 Vault 引用图，产出新的图片文件。音频和视频生成同样创建新产物，不是原文件原位编辑。

05结构化产物生成

Chat 可创建 Markdown、Bases、Excalidraw、draw.io 等文件，并记录 receipt。能创建不代表 Peak 也能完整编辑。

06Loader-only 文件

Loader-only 文件当前主要用于读取、摘要或索引。修改仍要回到外部或 Obsidian 原生工具。

聊天附件的 AI 直读链路目前不能作为卖点

默认配置选择 direct attachment，但当前最近消息渲染器没有把资源字节构造成模型消息 part。 转文本模式可以借助 Loader/转录生成摘要，但“把任意 PDF、图片、Office 文件拖进来直接问”尚缺闭环证据。

宣传口径：哪些话现在能说

建议使用的总定位

Peak Assistant 是以 Markdown 为核心的多格式知识工作台。它能提取与检索 PDF、DOCX 和 PPTX 的文本， 并可按设置读取 CSV、JSON、HTML 与 TXT。在 Composer 中，用户可以审阅式修改 Markdown 与嵌入对象， 再把 AI 结果保存为可继续使用的 Vault 文件。

可以直接说

  • Markdown 的完整编辑与 AI 协作
  • PDF 文本提取、索引和悬浮预览
  • Markdown 表格的 CSV 导入与导出
  • 生成与编辑 PNG/JPEG/WebP 图片
  • 生成 Bases、Excalidraw、draw.io 等 Vault 产物

带条件说

  • 启用后索引多种文本、数据、Office 与 Obsidian 原生对象格式
  • DOCX/PPTX 仅提取文本，不保留原始版式
  • Canvas/Base/Excalidraw 修改发生在 Markdown 嵌入对象场景
  • 音频转录取决于已配置的 provider
  • 生态格式的最终渲染依赖 Obsidian 或社区插件

现在不要说

  • 支持 Excel / XLSX
  • 支持独立编辑 CSV、JSON、HTML 或 PDF
  • 支持所有图片的语义搜索
  • 任何附件都能被模型直接理解
  • Peak Sheet 已经可用

容易误导的短句

  • “支持 Office”会把文本提取误解为版式查看与编辑
  • “支持 HTML”会被理解为浏览器式预览与修改
  • “支持图片”会把预览、索引、理解和改图混成一件事
  • “支持 CSV”会被理解为电子表格工作区
  • “支持多模态附件”会越过当前 direct part 缺口

影响可信宣传的关键缺口

下面这些不是“以后可以更好”的普通增强，而是会让产品页、设置页和真实行为相互矛盾的合同问题。

XLSX 是最明显的假阳性

类型、Loader 扩展名和设置 UI 都出现 XLSX，但读取分支直接返回 null。当前应视为不支持。

HTML/XML 类型合并造成开关漂移

XML 由同一 Loader 读取，却产生 HTML 类型；设置页又没有 XML 开关，真实启用语义不清晰。

TXT 有 Loader，却没有设置入口

默认配置包含 TXT，但 Knowledge Index 的文件类型 chips 不包含它。用户无法从当前 UI 理解或控制这项能力。

图片索引不是真多模态理解

Image Loader 会读取二进制并计算 hash，但描述函数明确没有把图片字节发送给模型，通常只留下占位文本。

附件 direct mode 没有构造模型内容

模型路由会识别 vision/PDF 能力，但最近消息 slot 的 direct 分支没有追加 image/file part。

Loader 缺少格式级回归测试

当前有表格、原生对象、媒体相关 focused tests，但没发现覆盖全部 Loader 的 fixture/E2E 测试面。

图片格式清单不一致

Loader、附件分类、UI 图标和 AI 改图白名单各自维护扩展名，HEIC/AVIF/SVG 等处于不同状态。

File Workspace 仍是 implementation pending

当前 ViewManager 没有扩展名接管；Composer 入口也明确只接受 Markdown。

建议把文件能力分成三条产品线

宣传重点不应等待所有格式都达到同一成熟度。更稳妥的做法是保留一个统一总定位， 同时把当前、下一阶段和远期能力明确拆开。

  1. 当前：Markdown 与多格式知识摄取。 以 Markdown Composer、PDF/文本/数据/Office 读取索引、CSV 互操作、原生对象协作为主。
  2. 下一阶段：Peak File Workspace。 图片、HTML 和 PDF 获得一致的打开、AI 协作与版本保存体验。
  3. 远期：Peak Sheet。 将现有表格基础升级为可计算的 Sheet 与结构化 Dataset 系统。

未来需要一个机器可读的文件能力清单

本次调研发现扩展名散落在多套类型、运行时与 UI 注册点中。 后续应由一个 app-owned capability manifest 生成用户设置和宣传矩阵，至少记录：

  • 扩展名与 MIME；
  • 读取与索引能力；
  • 预览、直接 AI 输入与独立编辑能力；
  • 嵌入编辑、生成与导出能力；
  • 默认开关、依赖的 provider 或生态插件；
  • 对应 fixture、自动化测试和真实 Obsidian 验收状态。
本轮不建议马上扩大格式数量

先修正 XLSX、附件 direct mode、图片索引和类型清单漂移，能够显著提高现有宣传的可信度。 在这些合同收口前继续添加扩展名，只会让“识别了”与“真的可用”之间的落差更大。
