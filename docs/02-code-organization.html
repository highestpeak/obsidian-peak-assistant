这页解决什么

Peak Assistant 大约 13 万行 TypeScript，分四个顶层目录（app/ / service/ / core/ / ui/）加一个根 main.ts 入口。第一次打开仓库很容易犯两个错：

  1. 按字母顺序逐个目录读——读到一半就忘了自己在追什么。
  2. 从 UI 组件切入——以为看到 useState 就找到了业务真相，结果 truth 其实在 service 的 runtime 里。

这页把"按能力追踪"的读法固化下来，让你打开文件的顺序总是对的。

本文读者 已经读过 01 架构与边界、能理解 app 层为什么可以 import Obsidian 而 service/core/ui 不行；正准备打开代码，为一个具体能力或一个具体修改追踪文件顺序。
本文不做什么
  • 不重复架构层次的动机——那是 01 架构与边界 的题目。
  • 不列举 src/**/*.ts 每个文件——那种清单半年后就过期。
  • 不解释具体能力的业务逻辑——Chat 看 11、Search 看 12、Agent Harness 看 21、Settings 看 04。
01 与 02 的分工
  • 01 讲"为什么"——四层为什么这么切、port/adapter 为什么必要、Runtime Registry 为什么放 app 层。
  • 02 讲"怎么读"——按什么顺序打开文件、哪些目录不能互相越界、改一个开关从哪儿动。

两页配套使用；本页所有"依赖方向"的规则都可以在 01 找到原理性解释，本页只把它翻译成阅读动作。

4 层一眼

四个顶层目录不是平级的“功能分区”，而是依赖方向严格单向的分层。把它们的允许/禁止关系刻在脑子里，任何“这个 import 应该放哪”的犹豫都能立刻解决。

层可以 import禁止 import存在感
app/
composition		 obsidian、service、core、ui；任何 concrete host API。 无禁止（它是最外圈，本来就要粘所有真实依赖）。 约 100 个文件；main.ts + 各 compose*.ts + adapters。
service/
capabilities		 core、其它 service 模块、obsidian 的 类型（有限）。 禁止 @/app/**、@/ui/**；禁止直接触碰 Obsidian concrete API。 业务能力主战场：chat / search / copilot / ambient / lint / usage / agents / mcp / skills。
core/
substrate		 只 import 其它 core/ 子模块、第三方库。 禁止 @/app/**、@/service/**、@/ui/**；甚至 obsidian 也基本不出现（个别遗留 duck-typed handle 除外）。 底座：storage / providers / ports / schemas / types / template / utils。
ui/
projection		 service（通过 ServiceContext）、core 的类型和 ports。 禁止 @/app/**；禁止直接 import obsidian；禁止把 Zustand store 当长期业务 truth。 React 视图、hooks、stores、shared components。

为什么 app 可以 import 一切 app/ 是 Composition Root。它的唯一职责是把 Obsidian、SQLite、LLM、workspace 这些 concrete 依赖装配成窄 port，交给 service/ui。所以它必然需要看到所有层；但反过来说，任何一段“为了拿到某个 host 能力而想 import app”的 service/ui 代码，一定是设计错了——正确姿势是让 app 层把那个能力包成 port 传下去。

按能力读代码

读代码永远不要从 src/ 的字母序开始。先选一个具体用户能力（Chat、Search、Copilot、Ambient、Vault X-Ray、Usage Dashboard），沿“入口 → 装配 → runtime → port → adapter → UI projection”这条骨架读下去，一次只追一条线。下面 4 条 recipe 是最有代表性的读法，覆盖了当前所有能力的形态。

依赖规则

四层架构的红线不是靠代码审查靠的，是靠 npm run audit:boundary 扫描 + 一批 test/*-source-guard.test.ts 守的。改代码前理解这些规则，能省下大量“为什么这样 import 会报错”的困惑。

1 · service/ui 禁 @/app/**
service 和 ui 不能 import app 层的任何文件。要拿 host 能力就走 port。npm run audit:boundary 会扫这条；test/ambient-source-guard.test.ts、copilot-action-runtime-source-guard.test.ts、copilot-action-surface-source-guard.test.ts 等专项测试守着特定 runtime。
2 · service/core 禁 obsidian concrete
service/core 只能 import 类型（type），不能 import 真正会跑代码的 Obsidian API。T11R 已把 Obsidian import 清到 0；剩下少量 duck-typed 访问走 src/core/ports/AppHandle.ts 与 src/core/storage/vault/vault-ops.ts，这两个是过渡桥，未来会继续收窄成更强类型 port。
3 · 不做 service-layer 模块 singleton
禁止 let currentRuntime = null; export function setRuntime() 这种 service 内部藏 singleton 的写法。runtime 的 owner 是 src/app/context/AppRuntimeRegistry.ts（bind/read/try/clear 四态语义）。如果 service 需要拿到某个 runtime，只能通过依赖注入或 ServiceContext——不能自己 static 一份。
4 · 不扩张 AppContext.getInstance()
AppContext.getInstance() 是历史遗留，不允许在 service 侧继续新增使用。新代码通过 constructor、port 或 RunEnvelope 边界传依赖。rg AppContext\\.getInstance src/service src/core src/ui 定期跑一遍，看新增是不是回潮。
5 · UI store 是投影，不是 truth
Zustand store（src/ui/store/ + src/ui/view/<feature>/store/）只保存 UI 显示状态。业务真相在 service runtime / repo / RunEnvelope。判断依据：如果这段状态在“重启插件”后必须恢复，它就不该只活在 store 里。
6 · Templates / config 强制外置
docs/conventions/configurability.md 明确：i18n、regex、label map、颜色、阈值、权重、timing 都不许硬编码在逻辑文件里，必须走 templates/config/ + 一个文档化的 domain fallback。改动前先确认新配置属于哪个已有 JSON。跨切面小常量放 src/core/constant.ts；大 domain 配置表不许倒进 constant.ts。
7 · 加新层前先问“它是不是 port”
诱惑：在 service 和 core 之间加一个 “helper 层”。90% 的情况下，这个 helper 要么是一个新 port（放 src/core/ports/），要么是一个新 compose 页（放 src/app/<cap>/）。别开新目录。
为什么这些规则存在 四层依赖方向被打破的代价是重构成本呈指数增长——不是审美问题。audit:boundary = 0 findings 是当前的稳定状态；每一处新的“service reach app”都会让下一次 provider 或 UI 重构多花一天。这是 01 详细论证的结论，本页只做规则的操作化。

Regression test/t11r-*.test.ts T11R 边界重构的回归护栏（Obsidian import zero、vault-ops 收敛等）。

Runner 长什么样：run-test.js 用 esbuild 把 *.test.ts 编成临时 JS 跑 Node，结束后清理。跑全部：npm run test；跑单个：npm run test -- test/<name>.test.ts。所以每个 test 文件必须是可独立运行的模块，不要跨文件共享全局状态。

怎么找相关测试：看到能力代码找不到测试时，先按能力名 ls test/ | grep <capability>；再看 port 名 ls test/ | grep -i port。source-guard 类跑在 CI，本地也应该跑一遍（npm run audit:boundary）。

维护规则

这份文档最容易过期的地方：目录搬家、能力增删、port 改名。按下面几条维护，能撑住半年不脱钩。

目录搬家 = 同步 3 处。 目录改名或迁移必须同步：本页 目录职责表 + 改动入口手册 的相关行 + docs/gstack/codebase-reading-map-2026-06-28.html（source of truth）。仅改一处就是埋雷。
新增能力 = 新增一条 Recipe。 加了新的用户能力（不是内部 helper），补一条 recipe 到 按能力读代码。如果新能力和已有 recipe 同构（例如又一个 RunEnvelope adopter），可以只在 Recipe D 后面加一句“XX 也按这个读”。
新增 port = 补入口表。 加了新 port（src/core/ports/<Name>Port.ts），在 改动入口手册 的“加一个新 capability port”样例后加一行具体路径。port 命名要 stable，别频繁改。
依赖规则 7 条不许扩张。 “依赖规则”这 7 条不是随手加的：每一条都对应 audit:boundary 或 source-guard 测试。想加第 8 条前先让规则落进 CI，否则它只是纸面约定。
测试地图跟随 test/ 命名。 不列具体 test 文件（那会过期），只维护命名模式。加新测试请沿用现有模式：*-source-guard、*-ports、<capability>-*、t11r-*。
不要在这页塞架构原理。 “为什么四层单向”、“为什么 port/adapter 存在”这些是 01 的题目。这里出现的每一句“为什么”都应该能删掉后不影响读者按顺序打开文件——否则就抢了 01 的活。
