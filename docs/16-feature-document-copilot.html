Open Copilot 的 Document lane：会看什么、会写什么、什么时候要按 Apply。

这份文档只讲 Copilot 的 Document lane：当你在一篇笔记里想让 AI 做五类事情时——

  • 润色
  • 审稿
  • 找链接
  • 补标签
  • 拆分文档

怎么选、按下去会发生什么、结果最终以什么方式落回你正在编辑的文件。用户视角在前——先说“打哪个按钮”“会不会改到我的文档”“怎么撤销”；维护者视角在后——action 是怎么注册、怎么拿到文档上下文、怎么调 Copilot role 的模型的。Vault lane 和 Setting lane 不在这一页。

这页解决什么

用户对 Copilot 的第一个疑问不是“功能强不强”，而是 "我按下去，它会不会把我文档改坏"。这页把 Document lane 的每一个 action 拆开：它读什么（整篇 / 选区 / 关联笔记）、结果长什么样（结构化面板 / 流式改写 / 建议列表）、是否直接落笔（几乎全部不是）、Apply 按钮按下去之后又发生了什么。

核心结论 Document lane 的所有 action 先出结果、再等你按 Apply。除了 Suggest Tags 的 frontmatter 写入是显式的“Add Tags to Frontmatter”按钮，没有任何一个 action 在“执行完”那一刻就把改动落回你的文件。文档改动全部走确认面板。
本文读者 正在写笔记、想用 Copilot 但又怕它乱改的 Obsidian 用户；打算加一条新 action 的维护者；正在排障“为什么按了 Apply 却没变化”的 coding agent。
本文不做什么 不重复 Chat / Search / Vault Intelligence 的用户手册（分别在 11 / 12 / 13）。不讲 Vault lane 的 Vault Health、Extract Todos、Smart Connections 等（那些属于 Vault Intelligence）。不展开 Copilot 底层 agent loop 的实现（在 21 Agent Harness）。
当前文档的结构上下文归 File Atlas 当前文档属于哪些 hub、入链 / 出链和 local graph 已经是 File Atlas 的上下文行与 Graph 子视图，不再放进 Document Copilot panel。原生编辑器里的 Copilot Intelligence modal 负责当前文件 / 选区问答；Vault Search inspector 只负责选中结果并 handoff 到 File Atlas。边界与迁移决策见 File Atlas surface。
Composer 中的 Block AI 不等于这 17 条 Document action Composer 还需要按块类型区分固定编辑操作、由证据触发的 Copilot Review 建议，以及 Mermaid / Base / Canvas / Excalidraw 等对象的增量生成。当前生产实现从点击、Prompt、等待到预览写回的完整说明见 19 · Composer 里的 AI 到底怎么工作；目标类型矩阵、预览方式和写回边界见 Composer Block AI Capability Contract；未落生产的部分统一进入 Roadmap。

Document lane 动作清单

Document lane 里一共 17 条 action：12 条 document category + 5 条 writing category。下面这张表按“怎么用”排序——最上面 6 条是核心的润色 / 审阅 / 链接 / 标签 / 拆分，往下是辅助性的写作与阅读工具。三个核心列：读什么、结果面板长什么样、Apply 会做什么。所有 action 都从当前文档拿 DocumentContext；scope 为 selection 时优先用选区，否则用整篇。

与 Composer 的关系：这里记录现有 Document lane action；编辑视图里每类 block 应该稳定出现什么、什么只能由 Review 证据触发、什么必须流式重渲染，以 Block AI 能力契约 为准。

相关系数（relevance）决定排序：Picker 会按 action.relevance(ctx) 排序。有选区时 Polish / Rewrite Selection 排前面；没有链接时 Suggest Links / Suggest Semantic Links 排前面；文档 > 2000 词时 Suggest Split 排前面。所以“该给我推什么 action” 完全由当前文档形状决定，不是随机。

用哪个模型跑：Copilot role 这 17 条 action 全部走 ProfileRegistry.getActiveCopilotConfig()——也就是 04 Configuration 里那张 6 role 表格里的 activeCopilotConfig。没绑就回落到 Conversation。想让 Copilot 走另一个 model：Settings → AI Setup → AI behavior → Copilot。想给单条 action 换 model：目前不支持，只能整块 Copilot 换。

4 条常用 recipe

下面 4 条是我们观察到的最高频用法。每条都写清 入口 → 面板长啥样 → Apply 时会改到文档的哪部分。

Document → Polish重写

Recipe 1 · 润色当前一段 / 一整篇 Polish Document

怎么做
  1. 打开笔记；想润色单段的话，先在编辑器里选中那段。
  2. Command Palette → Open Copilot。
  3. Document tab → Polish Document。
  4. 面板里出现流式改写和双栏 Diff。等它跑完，检查 Diff。
  5. 按 Apply Changes。
会写到文档吗

不会——直到你按 Apply Changes 那一刻。Apply 后，如果 scope 是 selection 就替换选区；如果 scope 是 full 就整篇覆盖。Ctrl-Z 可以撤销（Obsidian 的 native undo）。

小心：整篇覆盖时如果 Apply 前你又手动改了几行，你的改动会被覆盖。习惯上：跑 Polish 前不要边改边等。

Document → Review Article审阅 + 定点 Fix

Recipe 2 · 审阅整篇，再让它逐条修 Review + inline Fix

怎么做
  1. 打开长文（≥ 500 词效果最好）。
  2. Open Copilot → Review Article。
  3. 拿到一份 overall + N 条 findings（error / warning / info）。
  4. 看到不满意的 finding，按它旁边的 Fix——面包屑跳到嵌套的 PolishPanel，展示针对该条建议的改写。
  5. 按 Accept Fix 落笔；不喜欢就按 Skip 退回 Review。
会写到文档吗

Review 本身不改。它只是评审报告。改动发生在你按 Fix 之后进入的 Polish 面板里，那里再按 Accept Fix 才真的落笔——所以你能针对每条 finding 独立决定。

面板底部的 Copy Feedback 会把 overall + findings 拼成 markdown 复制到剪贴板。适合把审阅意见发给合作者而不动原文。

Document → Suggest Links / Suggest Links (Graph)补链接

Recipe 3 · 给一篇“孤儿笔记”补 [[links]] Suggest Links + Suggest Links (Graph)

怎么做
  1. 打开一篇看起来没什么 backlinks 的笔记（isOrphan 会让这两条 action 排到最前）。
  2. 先试 Suggest Links (Graph)——它从索引图上找“语义上很近但没连上”的笔记，需要该文档已被索引；Fast 档位没有语义边。
  3. 再试 Suggest Links——它走 agent，不依赖索引，agent 会自己去 vault 里搜。
  4. 面板里挑选想插入的 outgoing 建议，按 Insert N Links。
会写到文档吗

Insert 会把 [[target]] 直接嵌进当前文档。Suggest Links 精准到 context——link 会插在建议里给出的 context 短语后面；Suggest Links (Graph) 粗一些——会在文档末尾新加一段 ## Related Notes。

区别选择：写文中链接选 Suggest Links；只想在文末列个“Related notes”块选 Suggest Links (Graph)。

Document → Suggest Split最重的写入

Recipe 4 · 拆分一篇写太长的笔记 Suggest Split

怎么做
  1. 打开一篇 > 2000 词的笔记（< 500 词的会被 guard 拒绝）。
  2. Open Copilot → Suggest Split。
  3. 面板给出 N 段 (lineRange, newTitle, reason)。仔细读 reason，看 line range 是不是真的按你希望的地方切。
  4. 不满意就直接关掉——不按 Split 什么都不会变。
  5. 确认后按 Split into N Notes。
会写到文档吗

会，而且是最“重”的一次。会在原 folder 下新建 N 个笔记；把原文件里被切走的部分替换成 → [[newTitle]] 单行链接。不能用一次 Ctrl-Z 撤销——那是多文件的改动。

撤销策略：看不满意就手动删除新生成的 N 个 note，把原文件从 Obsidian 的 File Recovery 恢复。习惯上：跑 Suggest Split 前先做一次 Git commit 或 Vault 快照。

"会不会直接改我的文档"

用户对 Copilot 的头号疑问。逐条 action 给出确定答案：只有 Suggest Tags 的 frontmatter 写入是"直觉上直接"的（因为它没有 Diff 面板），其它全部走"结果面板 + 明确 Apply 按钮"两步。

Summarize 不改。流式摘要。 Insert at Top：在 frontmatter 之后插 > [!summary] callout。 Ctrl-Z 一次撤销。

Rewrite Selection 不改。流式改写。 Replace Selection：只改当前选区。 Ctrl-Z 一次撤销。
Add Evidence / Writing Plan / Write Article 不改。Agent 流。 用户复制或选择插入；无一 Apply-then-overwrite。 Ctrl-Z（如果用户选择插入）。
Safety mode 目前不阻挡 Document lane 的 Apply 04 里的 permission mode（read / acceptEdits / bypassPermissions）是给 Agent Harness 用的。Document lane 的 Apply 是用户在 UI 上按下去的显式动作，不走 Harness 的 permission gate。这意味着：即使把 Safety 调到 Read only，你按 Suggest Split 的 “Split into N Notes” 还是会真的拆。Safety 保护的是 agent 无人监督执行的场景；Copilot 结果面板的 Apply 按钮不在保护范围内。
Agent 流的 action 是例外 Suggest Links、Add Evidence、Knowledge Gaps、Writing Plan、Write Article、Detect & File 等走 agent.runAgentStream()——它们在 生成结果 的过程中会真的调用 vault 搜索工具、可能读多份笔记。如果 permission mode 拒绝 read，这些 agent 会直接卡住。这里 permission mode 起作用，但作用点是 “agent 能不能读”，而不是 “能不能改”。

失败与降级

Copilot action 会以三种方式“不成功”：guard 挡住、依赖没准备好、模型 / 网络出错。UI 表现各不同——搞清是哪一种能少走弯路。

Guard 挡住：文档不符合 action 前提。 Picker 里 action 仍可见但被禁用，鼠标悬停显示原因。举例：Correct Content“Document is too short to check for errors (minimum 50 words).”、Suggest Split“Document is too short to split (< 500 words)”、Rewrite Selection“Select text to rewrite”。这不是 bug，是设计上防止无意义调用。
索引未就绪：语义类 action 走不动。 Suggest Links (Graph)、Smart Connections、Find Related 依赖已构建的 semantic graph 或 vector index。当前文档未被索引时结果面板显示“Document not indexed yet. Run indexing first.”，或返回 searchUnavailable。解决方法：04 · Knowledge Index 切到 semantic/full 档并重建索引。
Copilot role 未绑定：回落到 Conversation。 ProfileRegistry.getActiveCopilotConfig() 返回 null 时会走 Chat role；日志里没有特殊提示，用户可能只是感觉“质量不太对”。Overview 卡片会显示 Needs attention。修法：AI Setup → AI behavior → Copilot 选一个 provider + model。
Agent 流的 action 需要工具权限。 Suggest Links、Add Evidence、Writing Plan、Write Article、Detect & File 会调 vault 搜索工具、读取多份笔记。permission mode 是 read 时能跑；工具被显式禁用会直接 error。
模型 / 网络出错：Panel 显示 Notice。 Streaming 中途中断会保留已流式的文本、Apply 时会拿部分结果——注意 Diff 双栏可能只显示半段。Notice（Obsidian 右上角吐司）会显示 “Fix failed: ...” / “Failed to apply: ...”。
Apply 之后 diff 没变：source 已经不在原文档里。 Correct Content 逐条 Accept 是做字符串 replace。如果你在生成后又手动改了那段原文，Accept 会找不到 before，静默失败（applyCopilotBlocksPure 里 if (!next.includes(block.before)) continue;）。UI 上表现为“按了 Accept 但文档没变”。解决：先关闭面板，重新跑一次。

加新 action 的规则

Document lane 目前已有 17 条，Vault lane 10 条。以后加新 action 请按下面这条最小契约走。

1 · 在 src/service/copilot/actions/index.ts 里加 CopilotAction，不要绕过 factory。 Action 必须只用 CopilotActionPorts——不要直接 AppContext.getInstance()、不要碰 obsidian。execute() 是 async generator，返回 ActionResult（stream 或 structured）。
2 · category 决定 lane。 document 或 writing ⇒ Document lane；vault ⇒ Vault lane。想放某条“Document 里的 vault 操作”，走 DOCUMENT_ACTION_IDS 白名单或显式设 intentTab: 'document'——但要写清为什么打破默认。
3 · 有 guard 就写 guard；不要用文档不符时静默返回空结果。 Picker 会给出 disabled 状态 + 悬停提示。这是用户能预期到的行为，比“跑了但空”好得多。
4 · Prompt 走 PromptId，不要拼串。 需要 LLM 就用 ai.queryStream / queryStructured / renderPrompt 配合 PromptId.*；提示词落在 templates/prompts/。结构化输出要在 copilot-schemas.ts 里新增 zod schema。
5 · UI 面板注册到 copilot-action-surfaces.tsx。 结果 modal 通过 action.id → PanelComponent 查表；漏了这一步 modal 会显示 “This is a Copilot wiring bug — the action ran but no UI is bound.”
6 · 一次 Apply = 一次编辑器 transaction。 批量改动尽量拼成一个 vault.modify 调用（applyCopilotBlocksPure 就是这样组装的），让 Ctrl-Z 一次撤销。多文件 action（如 Suggest Split）必须在文档里明确说“不可 Ctrl-Z 撤销”，或提供撤销脚本。
7 · Copilot role 决定用哪个模型；不要在 action 里 hardcode provider。 如果新 action 需要“更强的 planning 能力”，考虑给它走 agent 路径（agent.runAgentStream）；agent 会独立走 activeAgentConfig。
