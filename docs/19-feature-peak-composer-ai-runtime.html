2. 已确认的新原则：AI 是一个过程，不只是一段答案

这次明确要改的方向 包括文字在内，所有 Composer AI 操作都要走统一 Agent 流程；步骤要看得见；所有生成结果都要进生成历史，未采用也能找回。
统一 Agent Run

文字也不能只是一轮裸模型调用

简单润色可以只调用一次模型，但仍要记录上下文、步骤、校验、结果和完成状态。

复用现有 stream

不只是逐字输出

已有的步骤、工具、来源、权限、状态和结构化事件都应接进 Composer，而不是只留下 text-delta。

生成历史

未采用不是删除

每个初次生成、重新生成、失败前的部分结果和媒体产物都要保留，并且下次打开还能恢复。

不展示内部思维

展示真实操作步骤

界面显示“正在读上下文、调用工具、校验结果”等事实，不显示模型隐藏的 chain-of-thought。

3. 当前点下按钮后，到底发生了什么？

这一节讲当前生产实现。无论点“润色文本”还是“补一列”，系统都会先把任务需要的内容打包，再交给 AI。

先记住你正在处理哪一块 系统保存当前文档版本、目标段落或选区，以及它在原文里的准确位置。这样结果回来后不会写错地方。
准备给 AI 的任务说明 任务说明由固定规则、当前内容、少量上下文和你输入的定向指令组成。这个完整任务说明就是 Prompt。
调用当前启用的 AI 模型 当前普通 Composer AI 只做一轮任务，不会自己搜索 Vault，也不会调用其他工具。这正是上面记录的待改问题。
把结果放进预览区 文字可以一边生成一边显示。表格、图表和原生对象要等完整结果通过格式检查以后才显示。
等你决定是否采用 按“接受”才写回；当前“丢弃”会关闭建议。目标是改成“未采用”：原文不变，但生成结果永久进入生成历史。

窄上下文本身没错，错的是所有能力都被压成同一种窄上下文

润色一句话不需要读取整个 Vault；但公式要理解附近变量，图片 Caption 要看真实图片和所在段落，Frontmatter 要理解全文，Copilot 建议还要带上它的证据与相关材料。正确方向不是“越多越好”，而是每个 AI 能力明确自己必需、可选和需要时再读取的上下文。

目标：Composer 复用 Chat 的上下文方法，但按编辑能力选材料

Chat 已经把上下文拆成一格一格的材料（代码里叫 slot）：每格可以单独排序、压缩或省略，并由总预算控制。Composer 不应复制 Chat 最终拼好的 Prompt，也不应另造第二套系统；它应复用这套装配和预算方法，再增加“目标块、文档结构、对象材料、Copilot Brief”这些编辑专用材料。完整 Chat 现状见 11 · Chat 上下文。

Copilot / Ambient 发起的任务 它最初发现的问题（finding）与证据、Brief 快照、用户显式“带入协作”的相关材料、当前 Copilot 会话和已有反馈。 Ambient 一刷新就改写正在运行的上下文，或未征得用户选择便把所有后台发现送进模型。
Copilot 和 Ambient 在这条链里的分工

Ambient 负责在后台感知和排序，把“接下来值得处理什么、相关材料、还没安放的想法”投影到 Copilot Brief。用户点“讨论 / 带入协作”后，Copilot 才把对应 finding、证据和资料引用装进 session；真正发送时再冻结成 Agent Run。Ambient 不是第三个 tab，也不是另一套 Prompt 系统。

每次运行还要留下“上下文收据”

生成历史除了保存 Prompt 身份、模型和结果，还要记录本次请求了哪些上下文材料、实际使用了哪些来源、哪些可选材料被压缩或省略。这样恢复一个未采用结果时，用户能知道它当时依据了什么，而不是只剩一段孤立文本。正式合同见 Composer AI Agent 流程与生成历史。

4. 结果可以等，过程不能空白

所有 AI 操作都必须马上给出反馈，并持续显示当前步骤和运行动画。不同操作之间唯一的区别，是生成中的半成品能不能安全给你看。

表格、图片等结果不能逐字显示，用户就只能看着空骨架等吗？ 不能。内容可以等完整结果，但运行过程必须一直可见：现在做到哪一步、是否还在工作、已经等了多久，都要看得见。

运行反馈

每一种 AI 操作都有

点击后立即出现“已锁定目标、正在准备上下文、正在调用模型、正在校验结果”等真实步骤。暂时没有新事件时，当前步骤仍保持动画和已用时间。

内容预览

按结果类型决定

文字可以边生成边展示。表格、JSON、原生对象和图片要等结果完整或文件准备好以后再展示，避免把不能使用的半成品闪给用户。

动画是运行心跳，不是假进度

没有新文字或新步骤时，界面继续显示动态圆点、微光或进度轨迹，并保留当前阶段与已用时间。系统不能编造“正在思考第 3 步”或虚假的百分比；收到真实事件才切换步骤。若正在等待用户授权、已经失败或已经取消，动画必须停止并显示下一步操作。

5. 固定能力目录，不等于全部 AI 建议

下面三张表列的是 Composer 预先注册的固定操作：它们的能力名称、适用对象和写回方式保持稳定。除此之外，Copilot 和 Ambient 还会随着正文、焦点和相关材料变化，不断产生新的动态建议。

固定操作

稳定、随时可点

例如润色、补例子、转成表格。它们来自统一能力目录，按块类型显示，不需要先调用模型判断该放什么按钮。

动态生成

随着当前工作持续变化

Ambient 持续整理下一步、相关材料和未安放想法；Copilot 继续生成建议、追问、任务和候选版本。它们带着证据和上下文，不受下面固定按钮表格限制。

动态建议不等于随意创造一段不可执行的按钮代码

一条动态建议可以推荐某个已有能力并预填指令，也可以让 Copilot 用已注册的能力和工具组合一次新任务。建议内容可以不断变化，但真正执行仍进入统一 Agent Run，继续经过权限、步骤、校验、预览和生成历史。

6. 为什么按钮固定，但 Copilot 建议还会继续生成？

它们其实是两条同时存在的来源 块旁边的常用按钮本来就是固定能力；Copilot / Ambient 则在另一条持续感知链里生成真正适配当前内容的建议。动态建议不是用来替换固定按钮的。

当前段落操作栏只检查“这是不是一个非空段落”。只要适用，就稳定显示：

  • 润色文本
  • 补一个例子
  • 转成表格

这条固定入口不会先问 AI “现在该显示什么按钮”，所以操作位置和含义不会来回跳动。与此同时，Ambient 可以根据正文变化反复刷新 finding；Copilot 可以围绕这些 finding 继续讨论，生成新的任务、追问和候选版本。

当前生产只接通了动态链的一部分

Brief 已经有 finding store、持续感知模式、相关材料和 session 投影，但当前 finding producer 主要按规则发现未完成任务项，完整 AI 建议生成与 Copilot 执行链还没有接通。目标中同一个 finding 会同时投影到正文附近和 Copilot Brief，不是两套互不相认的数据。

固定入口与动态生成同时存在 两条来源，共用执行与历史
flowchart LR Document["正文、焦点和相关材料"] --> Type["块类型与适用性"] Type --> Fixed["固定快捷操作
稳定显示 · 随时可点"] Document --> Sense["Ambient 持续感知与排序"] Sense --> Finding["动态 finding
证据 · 位置 · 为什么现在"] Finding --> Brief["Copilot Brief"] Brief --> Session["讨论或带入协作"] Session --> Dynamic["动态任务

读图：固定的是 capability 目录，不是 AI 能提出的问题清单。Ambient 可以不断产生和更新 finding，但不会自动写正文；用户选择讨论或运行后，Copilot 才冻结上下文并进入 Agent Run。如果 finding 本身由模型生成，它也要留下 run 和生成记录；“忽略”只改变展示状态，不删除生成事实。

7. 什么时候才会真的改文档？

生成完成不等于已经写入。正常的 Composer AI 修改都要经过“预览 → 接受”。

你的操作发生什么原文状态
生成中AI 正在准备一个修改版本。原文不变。
接受把当前预览版本写入准确位置，并记录到 History / Undo。原文被修改，可以撤销。
当前“丢弃”关闭这个建议；候选只在当前运行时内存中暂存。原文不变，但还没有可靠的跨会话恢复。
目标“未采用”关闭当前预览，同时把 run、variant 和产物保留在生成历史。原文不变，以后可以恢复。
重新生成增加一个新版本，旧版本仍可切回。原文不变。
源内容已经变化旧建议会变成过期状态，系统拒绝猜测新的写入位置。原文不变，需要重新运行。
两个需要知道的例外

原生对象：Base、Canvas 和 Excalidraw 写入的是另一个文件，因此不会进入当前 Markdown 的 History / Undo。

AI 改图：新图片文件在你接受之前就已经生成到 Vault。当前丢弃建议不会自动删除这个新文件，但也没有统一生成历史解释它来自哪次运行；目标设计会补齐这条记录。

8. 当前还没接完整的地方

下面这些界面或底层能力已经有一部分，但不能当成完整功能来理解。

功能现在实际做到哪里还缺什么
统一 Agent Run
当前是单轮模型流		 Composer 经过共享 AI 服务和 CapabilityRunner，但实际模型调用是单轮、无工具。 文字、结构化对象和媒体都要进入同一 Agent Loop，并拥有统一 run、receipt 和步骤生命周期。
自定义 stream 事件
只保留文字分片		 共享 stream 已有步骤、工具、来源、权限、状态等格式。 Composer 适配器目前只转发 text-delta，需要把运行事件和 typed result 事件完整接进 review UI。
Generation History
没有持久化事实源		 当前 candidate、variant 和公式解释主要保存在内存；Document History 只收已接受事务。 所有生成、重新生成、未采用、失败和取消前的部分结果都要持久保存，并能跨会话恢复。
Copilot Sidecar 的 Send
没有完成调用		 会记住当前上下文，创建一条“正在准备”的运行记录。 没有生产模型执行器继续生成答案或修改建议，所以流程停在“准备中”。
Copilot / Ambient 动态生成
只接通部分链路		 固定按钮正常投影；Brief 可以保存 finding、相关材料和未安放想法。当前 producer 主要按规则发现未完成任务项。 还缺完整 AI finding producer、同一 finding 的正文与 Brief 投影，以及从动态任务到 Agent Run、候选和生成历史的端到端链路。
图片智能布局
没有生产入口		 底层生成、校验和测试链路存在。 当前 React 界面没有按钮调用它。
图片 Caption
不是视觉理解		 会根据图片块源码生成 Caption。 没有把真实图片作为视觉输入交给模型。
正式记录已经建立

Composer AI Agent 流程与生成历史 记录了根因、目标 Mermaid 流程、Generation History 数据边界、恢复规则和十条验收标准。它是设计决定，不代表代码已经实现。

开发者附录 A：前面出现的术语是什么意思？

如果只想使用功能，可以跳过后面的附录。

Agent Run
一次有开始、步骤、结果和结束状态的完整 AI 任务。它可以只调用一次模型，不等于一定要多轮或使用工具。
生成历史
保存 AI 每次生成过的结果和版本，包括未采用、失败前的部分结果和媒体产物。代码设计中叫 Generation History。
文档 History
只记录真正写入 Markdown 或独立对象文件的修改，用于查看变更和撤销。它不等于生成历史。
Prompt
交给 AI 的完整任务说明。它包含固定规则、当前内容、附近内容和你的指令。
流式生成
AI 每生成一小段文字就立刻传回来，所以你能看到预览逐步增长。
候选修改
AI 已经提出、但还没有写入文档的预览版本。代码里叫 candidate。
当前内容快照
点击那一刻保存的目标内容、文档版本和准确位置。代码里叫 snapshot。
AI Provider
真正执行模型请求的服务，例如 OpenAI、Anthropic、Google 或其他兼容服务。
格式检查
把 AI 返回的表格、图表或对象修改解析成程序能安全执行的结构。代码里叫 materialize / schema validation。
写回
用户接受后，把预览修改应用到 Markdown 或独立对象文件。代码里叫 writeback。

为什么同样叫“润色文本”，可能走两个不同 Prompt？

段落上可见的固定“润色文本”使用 composer-prose-transform.md。选区润色和文字块的自由“指令”入口通常使用 doc-polish.md。两者显示名称接近，但前者是固定的一块式改写，后者允许把用户自己的指令直接附加到润色任务。

图片和公式为什么不完全走这张图？

公式：共用同一个 AI executor，但结果进入每个公式自己的详情 store，不进入通用候选写回。

Caption：共用文字 executor，但图片协调器会等待完整句子再准备候选。

AI 改图：调用 MediaGenerationService.produce()，等待图片任务返回文件，不经过文字流和 Prompt 模板。
