怎么使用这份报告

不要从目录树开始读。这个代码库已经重构成 app composition、service runtime、core substrate、ui projection 四层；正确读法是先找用户入口，再沿 runtime 和 ports 往下追。

先看入口

从命令、view、modal、setting tab 找用户如何触发能力。入口不等于业务逻辑。

再看 composition

`compose*.ts` 和 `ReactElementFactory` 通常是一页版依赖图，说明谁把 concrete 变成 port。

然后看 runtime

runtime/manager/service 回答“状态真相在哪里、流程怎么跑、并发如何处理”。

最后看 UI projection

Zustand、React hooks、panel 负责展示和交互，不应该反向拥有业务 truth。

3 分钟读法 如果你只想快速找方向：先读“关键入口地图”，再读“全局运行图”，然后跳到对应用户功能的流程图。不要先读代码量表；代码量表只用于判断认知负担，不决定阅读顺序。

总心智模型

不要把这里理解成传统 “UI 调 service，service 调 core” 的单向小项目。Peak Assistant 现在更像一个 Obsidian host 上的 capability platform：`app/` 是 composition shell，负责接 Obsidian；`service/` 是能力 runtime 和业务编排；`core/` 是可复用底座、类型、存储、provider；`ui/` 是 React projection 和用户操作面。
Obsidian Host加载 `main.js`，提供 `App`、workspace、vault、views、commands。
`main.ts`插件入口和 boot sequence，创建 app context、services、runtimes。
`src/app/**`唯一允许直接组合 Obsidian concrete APIs 的 shell。
`src/service/**`能力逻辑：chat/search/copilot/ambient/lint/usage/agents。
`src/ui/**`React views、stores、hooks；应消费 narrow ports，不再进口 `@/app/**`。

现代化主线

T11 系列的核心目标是把“隐藏依赖”和“host 类型泄漏”赶回 app shell。当前 T11R 已经把 scanner 看到的 `service/core -> Obsidian`、`service -> app`、`ui -> app`、`service -> ui` 清到 0。

Capability按用户能力命名，而不是按老服务残留命名。
Runtime单一执行路径，放进 `AppRuntimeRegistry`。
Portsservice/core 只看接口，不看 Obsidian concrete。
Adaptersapp 层把 Obsidian/SQLite/Notice/Workspace 接进来。
ProjectionUI store/hook 只投影运行状态，不做长期 truth owner。
Guardssource scan / regression test 锁边界。

关键入口地图

读这个代码库时，入口分三类：插件生命周期入口、用户触发入口、React 服务注入入口。不要从 feature 目录里随机打开文件；先用下面这张表定位“用户怎么进来”。

插件启动入口 boot

  1. `main.ts`：从 `onload()` 开始，看 settings、template、manager、AppContext、runtimes、views、commands 的顺序。
  2. `main.ts`：跳到 `initSqlite()`，看 SQLite、SearchClient、Usage、VaultLint、VaultReview 的初始化。
  3. `main.ts`：最后看 `onunload()`，确认 runtime、store、sqlite、manager 如何被清理。

用户命令入口 palette

  1. `src/app/commands/Register.ts`：9 个 top-level command。
  2. `PeakCommandActions.ts`：命令如何打开 view/modal 或触发 runtime。
  3. 看到 command 后不要停在 action：继续追 view/modal 的 React mount 和 ServiceContext。

View / Modal 入口 screen shell

  1. `ViewManager.ts`：注册 Chat、Ambient、Usage、Vault X-Ray、Chat Studio 等 Obsidian views。
  2. `QuickSearchModal.tsx`、`HarnessOnboardingModal.tsx`：modal shell。
  3. 这些 shell 的职责是挂 React，不应该承载业务 runtime。

React 注入入口 ports into UI

  1. `ReactElementFactory.tsx`：唯一把 app-owned ports 送进 React 的地方。
  2. `ServiceContext.tsx`：UI 能拿到哪些 manager/runtime/ports。

阅读时问这 5 个问题

  1. 入口：用户从 command、view、modal、setting tab 还是 startup 进来？
  2. composition：哪个 `compose*.ts` 或 factory 把 concrete dependency 包成 port？
  3. state truth：状态是真在 runtime/manager，还是只是 UI projection？
  4. side effect：vault、workspace、Notice、SQLite、LLM 调用通过哪个 adapter 出去？
  5. 验证：有 build、boundary audit、regression test，还是只有人工判断？
最容易读错的地方 `src/ui/**` 很多文件看起来像业务逻辑，因为有 hooks 和 stores；但现代化后的规则是 UI 只做 projection 和 orchestration。真正的长期 truth 要回到 service runtime、AppRuntimeRegistry、storage repo 或 RunEnvelope。

代码加载路径

第一次读时先沿 boot path 走一遍。`main.ts` 很长，但它不是业务逻辑大杂烩，它是 composition root。

1. plugin load`main.ts` `MyPlugin.onload()`。
2. settings/templates`normalizePluginSettings`、`TemplateManager`、model registry。
3. AI manager`AIServiceManager` 组合 chat storage、prompt、context slots。
4. AppContext`AppContext` 持有 app-owned ports 与 runtime registry。
5. SQLite/search`initSqlite()` 创建 search/index/usage/lint review runtimes。
6. views/commands`ViewManager` + command palette。

启动里最值得看的文件

`main.ts`先看 `onload()` 的 composition 顺序，再看 `initSqlite()`，最后看 `onunload()` 清理顺序。
`src/app/context/AppContext.ts`看哪些东西是 app-owned：runtime registry、vault/navigation/preview/editor/chat/stats ports、copilot review history。
`src/app/runtime/AppRuntimeRegistry.ts`看 runtime bind/read/try/clear 的统一语义。
`src/app/react/ReactElementFactory.tsx`看 React UI 如何拿到 services/ports，而不是自己 import app shell。
`src/ui/context/ServiceContext.tsx`看 UI 可用的能力 surface。这里没有 raw `app` 和 `viewManager` 是 T11P 后的重要成果。

模块分类

App Shell composition

`src/app/**` 是 Obsidian concrete 的合法区域。读这里不要问“为什么 import Obsidian”，要问“它有没有把 Obsidian 包到 port/adapter/runtime 里”。

viewscommandsadaptersruntime wiring
  • `ViewManager` 注册 Obsidian ItemView。
  • `VaultPortAdapter` 等 app adapters 是 host 边界。
  • `composeAmbientRuntime` 这类文件是单能力 composition page。

Service capabilities

`src/service/**` 是业务能力和 runtime。当前应避免 import `@/app/**`、`obsidian`、`@/ui/**`。

chatsearchcopilotambientlint
  • 读某个功能时，从 runtime/manager 进，不要从组件进。
  • 看到 `Port` 类型，顺着 app adapter 找 concrete 行为。
  • 看到 singleton，要确认是不是历史兼容还是明确 owner。

Core substrate

`src/core/**` 是底座：SQLite repo、document loader、provider/profile、ports、types、utils。现代化后 core 不应该依赖 service/app/ui。

storageprovidersportstypes
  • `AppHandle` 是当前 neutral escape hatch。
  • `vault-ops` 是 T11R 后 service/core 的 duck-typed vault helper。
  • 长期更优方向是从 `AppHandle` 再收窄成更强类型 ports。

UI projection

`src/ui/**` 是 React views、hooks、Zustand stores 和 shared components。它可以 import service/core types/runtime ports，但不应该 import `@/app/**`。

ReactstoresviewsCSS
  • 读 UI 时先找 `useServiceContext()`，再找 port/runtime。
  • Zustand store 是 projection，不应成为长任务 truth。
  • 共享 UI/CSS 是当前最大阅读噪音之一。

设计模式速查

模式看哪里怎么判断对不对
Composition Root`main.ts`、`src/app/context/AppContext.ts`、`src/app/**/compose*.ts`concrete dependency 是否只在 app 层被装配。
Port / Adapter`src/core/ports/*`、`src/service/**/ports/*`、`src/app/adapters/*`service/core 是否只依赖接口；adapter 是否拥有 Obsidian/SQLite/Notice 细节。
Runtime Registry`src/app/runtime/AppRuntimeRegistry.ts`runtime 是否 fail-loud double bind、soft accessor、clear on unload。
RunEnvelope`src/service/run-envelope/*`、`src/service/lint/VaultLintRun.ts`run 是否有 session、events、artifact ref；UI 是否从 trace 投影。
Registry / Catalog`RetrieverRegistry`、`CopilotActionRuntimeImpl`、`SkillRegistry`、`ProfileRegistry`新增类型是否注册一次，调用方是否只看统一 catalog。
Pipeline / Slots`ContextPipeline`、`QueryService`每个阶段是否小而可替换，阶段顺序是否清楚。
Template / Config externalization`TemplateManager`、`TemplateRegistry`、`templates/config/*`大文案、模型、阈值、规则是否不要散在逻辑文件。
Projection Store`src/ui/store/*`、feature storestore 是否只是 UI 状态投影，不拥有长期业务 truth。
Duck-typed transitional bridge`src/core/storage/vault/vault-ops.ts`、`AppHandle`这是 T11R 的 containment，不是终局；未来可继续收窄成 typed ports。

用户功能岛与技术支撑层阅读指南

下面不是“目录说明”，而是两层阅读路线。先读用户功能岛，理解产品能力怎样跑起来；再读技术支撑层，理解这些能力共同依赖的 UI、storage、agents、tools、app shell 和 cross-cutting glue。

每张功能卡都按同一个问题集阅读。 先找用户入口，再找 app composition，再找 runtime/state truth，再找 side effect 通过哪个 port/adapter 出去，最后才看 UI 组件和样式。这样读的好处是：你不是在目录树里迷路，而是在追一条能解释行为的调用链。

用户功能岛：从用户入口追到 runtime

Quick Search + Search 21,368 lines

这是最大功能岛，包含即时检索、AI 分析、图谱生成、后台 session、保存分析结果。

阅读顺序
  1. `Register.ts` 里看 `peak-quick-search` 命令。
  2. `app/modals/QuickSearchModal.tsx` 了解 Obsidian modal shell。
  3. `composeQuickSearchHost.ts` 看 app-owned facade 暴露了哪些操作。
  4. `useSearchSession.ts` 看一次搜索/AI 分析的 UI orchestration。
  5. `SearchClient.ts` 和 `QueryService.ts` 看 parser、retrievers、RRF、PPR、rerank。
  6. `QuickSearchBackgroundRuntimeImpl.ts` 看关闭 modal 后后台继续跑的 runtime。
理解重点

`composeQuickSearchHost` 比较宽，它把 raw Obsidian app 操作留在 app 层。service/search 负责检索逻辑，UI stores 只投影 session 状态。Review 时重点看有没有新 `src/ui/** -> @/app/**` 或 service 直接摸 UI。

Copilot 19,213 lines

Copilot 是动作 catalog + runtime + result panels 的组合，不要从某个 panel 开始读，否则会被 20 多个 action 淹没。

阅读顺序
  1. `composeCopilotActionRuntime.ts` 看 app 层如何组装 action ports。
  2. `CopilotActionRuntimeImpl.ts` 看 built-in/custom prompt catalog、rank、lookup。
  3. `actions/index.ts` 看 built-in actions 怎么创建。
  4. `copilot-action-surfaces.tsx` 看 action 到 UI panel 的绑定。
  5. `CopilotReviewSession.ts` 看 Auto Review 这种长路径如何接 deps。
理解重点

现在动作执行的 dependency 都应该通过 `CopilotActionPorts`。阅读时把 action body 和 result panel 分开：前者回答“做什么”，后者回答“怎么展示”。后续瘦身最好从 generic panel/action factory 收敛重复形态，而不是删功能。

Chat 14,128 lines

Chat 是产品主路径之一，也是 context assembly 最复杂的地方。读它时要从 manager 和 pipeline 进，不要从单个 message component 进。

阅读顺序
  1. `ChatStudioView.ts` / `ChatView.ts` 看 Obsidian view shell。
  2. `AIServiceManager` 看 storage、prompt、profile、context services 怎么被组装。
  3. `src/service/chat/context/slots/*` 逐个看上下文片段：system prompt、profile、summary、working context、previous analysis。
  4. `ConversationService` 看发送、streaming、usage event、storage 写入。
  5. `ChatStorageService` 看 chat data 如何落到 vault。
  6. `src/ui/view/chat-view/*` 最后读，理解 UI 如何消费 manager 和 stores。
理解重点

Chat 的关键不是某个组件，而是 context pipeline。任何改动都要问：会不会改变 prompt/context 顺序？会不会让 UI store 变成业务 truth？会不会绕开 `ChatVaultWriterPort` / app-owned composition？

Usage Dashboard 8,635 lines

Usage 是用户可见的成本与效果保护面：它连接 usage tracking、outcome、optimization、dashboard UI、curator push。

阅读顺序
  1. `UsageDashboardView.ts` 看 view shell。
  2. `UsageTrackingService.ts` 看 AI 调用记录。
  3. `UsageOutcomeService.ts` 看 saved/adopted outcome。
  4. `src/service/usage/optimization/*` 看 recommendation/rules/prompt/schema。
  5. `composeCuratorPushRuntime.ts` 和 `CuratorPushRuntime.ts` 看 usage nudges。
  6. `src/ui/view/usage-dashboard/*` 最后读 UI screens。
理解重点

这里不要默认删 dashboard。可优化方向是 chart primitive 和 CSS 重复、fallback string 组织、recommendation renderer 复用。

Settings + Onboarding 8,346 lines

这是用户修复 capability readiness 的入口，覆盖模型/profile/MCP/skills/search/usage/harness setup。

阅读顺序
  1. `PluginSettingsLoader.ts` 看 settings normalize/sanitize/migration。
  2. `settings/types.ts` 看 persisted shape。
  3. `MySetting.ts` 看 Obsidian setting tab shell。
  4. `src/ui/view/settings/*` 看分 tab UI。
  5. `HarnessOnboardingModal.tsx` 和 `src/ui/view/onboarding/*` 看初次配置。
  6. `templates/config/*` 看外置 strings/config。
理解重点

这里的风险是把大配置表和文案写回 TS。Review 时看新增设置是否有 migration/default/sanitize，是否通过 template/config 外置。

Vault Lint / X-Ray 2,494 lines

体量小，但这是用户可见的 vault inspection 能力，同时也是 RunEnvelope 首个真实 adopter。

阅读顺序
  1. `composeVaultLintRuntime.ts` 看 lint ports/adapters。
  2. `VaultLintContract.ts` 看 capability contract。
  3. `VaultLintRun.ts` 看 RunEnvelope session/events/artifact。
  4. `VaultLintService.ts` 看 detector execution。
  5. `useVaultLintRunState.ts` 看 UI 如何从 event trace 投影。
理解重点

这是读 `RunEnvelope` 的最佳样本。任何新 long-running capability 都应该参考它的 runner、event trace、artifact ref、UI projection 边界。

Ambient + Morning 2,475 lines

这是用户可感知的 proactive assistance 能力，也是 ports/adapters 模式的清爽样本。

阅读顺序
  1. `composeAmbientRuntime.ts` 看 ports 如何被 app adapters 填充。
  2. `AmbientPorts.ts` 看 runtime 需要什么。
  3. `AmbientPushRuntime.ts` 看 trigger/search/projection/briefing 的主流程。
  4. `src/app/ambient/*Adapter.ts` 看具体 Obsidian/SQLite/UI store 接入。
  5. `src/ui/view/ambient-push/*` 和 `src/ui/view/morning-briefing/*` 看呈现层。
理解重点

它是理解“service runtime 不摸 host”的好入口。未来 Current Work State 不应该和旧 Ambient 平行双系统并存。

Shared UI + CSS 16,564 lines

这是技术支撑层的一部分，不是独立用户功能。它支撑所有用户功能的视觉 primitive、shared component、layout 和 CSS token。

阅读顺序
  1. `docs/conventions/ui-design.md` 先读设计系统约束。
  2. `src/ui/components/primitives/*` 看真正跨功能 primitive。
  3. `src/ui/component/*` 看旧 shared component 和 feature-ish component。
  4. `peak-components.css` 看 CSS primitive/token 的实际承载。
  5. 再回到各 feature view，看它们是否重复实现 Button、Pill、Card、Modal、Row。
理解重点

这里要按“谁能复用”分类：primitive、shared composite、feature-local。Review 时不要只看行数，重点看同一种 UI 语义是不是有两套实现。

Core storage 13,210 lines

这是 SQLite、vault chat storage、repo、DDL、native module 的底座。它不是用户功能，但所有高价值能力都依赖它。

阅读顺序
  1. `SqliteStoreManager.ts` 看 DB 初始化、backend selection、repo access。
  2. `src/core/storage/sqlite/ddl.ts` 看数据表语义。
  3. `src/core/storage/sqlite/repositories/*` 按 feature 找 repo。
  4. `ChatStore.ts` 看 vault-side chat persistence。
  5. `vault-ops.ts` 看 T11R 后 service/core 如何避免 import Obsidian。
理解重点

storage 是多能力共享底座。Review 时优先看 schema/migration/backward compatibility，不要用“这个文件大”作为删除理由。

Agents + Harness 9,071 lines

这是 agent 基础设施层，承载 VaultSearchAgent、GraphAgent、DocSimpleAgent、report orchestrator、agent loop、tool/hook/memory/permission。

阅读顺序
  1. `AgentLoop.ts` 看通用 agent loop。
  2. `src/service/agents/harness/tool/*` 看 tool registry / adapter。
  3. `src/service/agents/core/*` 看 Agent SDK bridge、message adapter、pool。
  4. `DocSimpleAgent.ts`、`VaultSearchAgent*`、`GraphAgent.ts` 按具体 agent 看。
  5. `ReportOrchestrator.ts` 看报告生成 session。
理解重点

先分清“agent framework”与“具体 agent”。具体 agent 不应该重新定义 runtime ownership；它应该复用 tool/schema/loop/port 体系。

MCP + Skills + Tools 5,888 lines

这是外部工具与 skill 系统：MCP client、tool adapter、skill parser/registry、search graph inspector tools。

阅读顺序
  1. `MCPClientManager.ts` 看 stdio/SSE server 连接管理。
  2. `MCPToolAdapter.ts` 看 MCP tool 怎么变成 agent tool。
  3. `SkillRegistry.ts` 和 `SkillParser.ts` 看 vault skill 加载。
  4. `src/service/tools/*` 看内置工具，尤其 content reader、search memory、search graph inspector。
  5. `templates/tools/*` 看工具提示词/输出模板。
理解重点

这类代码要重点看权限、输入 schema、错误降级、tool result 是否适合给 agent 消费。不要让 tool 直接跨层拿 UI 或 app concrete。

Boot/App shell 3,951 lines

虽然行数不大，但它决定全系统怎么被装起来。任何“我看不懂模块怎么连”的问题，先回这里。

阅读顺序
  1. `main.ts`：`onload()`、`initSqlite()`、`initializeSearchService()`、`onunload()`。
  2. `AppContext.ts`：app-owned services、ports、runtime registry。
  3. `AppRuntimeRegistry.ts`：所有 runtime bind/read/clear 语义。
  4. `ViewManager.ts`：view registration 和 activation。
  5. `ReactElementFactory.tsx`：UI service context 的唯一注入点。
理解重点

`app/` 可以知道 Obsidian；它的职责是把 concrete 变成 ports/adapters/runtime。Review 时看是否出现第二个 composition root 或 service-side runtime owner。

Other / cross-cutting 13,878 lines

这里不是一个功能，而是常量、事件、types、utils、small services、cross-feature glue。不要从这里开始读。

阅读顺序
  1. 先从某个功能岛遇到引用时再回来。
  2. `core/constant.ts` 只看 cross-cutting constants，不要往里继续塞大配置。
  3. `eventBus.ts` 看 view event/usage event 的横向通信。
  4. `src/core/types/*` / `src/core/search/*` 看 neutral domain types。
  5. `src/core/utils/*` 只按调用链读，不要全量硬啃。
理解重点

这个岛的 review 原则是“避免变成垃圾桶”。新增跨功能东西时，要问它到底是 port、type、config、utility，还是应该留在 feature 内部。

你应该怎么读和 Review

  1. 先定能力，不要先定目录。例如你要看 Quick Search，就从 command/modal/host/runtime 开始，不要直接冲进 `src/ui/view/quick-search`。
  2. 每条路径都问三个问题。入口在哪里？runtime/state truth 在哪里？side effect 通过哪个 port/adapter 出去？
  3. 读 app composition，再读 service runtime。`compose*.ts` 往往是一页版依赖图，能帮你避开在 service 内迷路。
  4. 看到 `AppHandle` 要标记为 transitional bridge。这不是失败，是 T11R 后的 containment；未来优化方向是把它缩成更窄的 ports。
  5. 看到 Zustand store，不要默认它是业务真相。检查是否只是 projection；长任务真相应该在 runtime / envelope / persistence。
  6. 用扫描命令代替直觉。边界类判断先跑 `npm run audit:boundary`，再用 `rg` 查 `@/app`、`obsidian`、`AppContext`。

每次看一个能力的固定模板

1. Command / view entry 2. app compose file 3. runtime or manager 4. ports interface 5. app adapter implementation 6. UI hook/store projection 7. tests / regression guard 8. old path deletion evidence

审阅提醒

提醒位置为什么值得看
`AppHandle` 仍是过渡桥`src/core/ports/AppHandle.ts`、`src/core/storage/vault/vault-ops.ts`T11R 把 Obsidian import 清到 0，但一些 service/core 仍通过 duck-typed app handle 访问 vault。下一步若继续优雅化，应把这些缩成更窄的 typed ports。
Quick Search host 仍比较宽`src/app/quick-search/composeQuickSearchHost.ts`它把文件操作、agent factory、markdown persistence、chat interop 都打包给 UI。边界合法，但阅读时要把它当作一个 app-owned facade。
Shared UI/CSS 是阅读噪音大头`src/ui/component*`、`src/ui/components/*`、`src/styles/*`它不是边界问题，而是命名、重复 primitive、feature/shared 混放带来的 owner cognition cost。
有小清洁点但不阻断构建`src/service/chat/service-manager.ts`当前文件里 `ProfileRegistry` 被重复 import；`npm run build` 通过，但后续整理 import 时可以顺手清掉。
