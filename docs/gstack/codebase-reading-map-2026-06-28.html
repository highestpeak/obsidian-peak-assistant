阅读与 Review 路线

这份报告按“你打开代码时真正会怎么追”的顺序组织。先选一个用户能力，再沿着入口、装配点、运行对象、状态、外部副作用读下去；如果你只是想理解底座，再跳到技术支撑层报告。

总心智模型

你可以把 Peak Assistant 想成一个挂在 Obsidian 里的能力平台。Obsidian 负责把插件加载起来；`app/` 负责把 Obsidian、SQLite、Notice、workspace 这些真实依赖接进来；`service/` 负责让能力运行；`core/` 放可复用底座；`ui/` 把运行状态展示给用户。
Obsidian 加载插件`main.ts` 从 `onload()` 开始，把 settings、views、commands、SQLite、runtime 装起来。
app 层接真实依赖`src/app/**` 可以知道 Obsidian 和宿主 API，但要把它们包成更窄的对象。
service 层跑能力Chat、Search、Copilot、Ambient、Lint、Usage 的主流程在这里。
core 层放底座存储、provider、类型、工具函数、ports，不应该反向依赖 app 或 UI。
UI 层做投影React 组件、hooks、stores 展示状态和接用户动作，不反向拥有长期 truth。

读代码时记住这条线

一条健康路径应该是：用户触发入口很薄，app 层装配真实依赖，service/runtime 拥有流程和状态，副作用通过 port 或 adapter 出去，UI 只展示和发起动作。T11 系列的边界工作，就是把隐藏的宿主依赖赶回 app 层。

用户能力先问“用户要做什么”，不是先问“这个目录叫什么”。
入口command、view、modal、setting tab 或 startup path。
装配点`main.ts`、`AppContext`、`ReactElementFactory`、`compose*.ts`。
运行对象runtime、manager、service、RunEnvelope 或 repo。
副作用出口vault、workspace、SQLite、LLM、MCP、filesystem。
验证build、boundary audit、regression test、局部 `rg`。

阅读时问这 5 个问题

  1. 入口：用户从 command、view、modal、setting tab 还是 startup 进来？
  2. composition：哪个 `compose*.ts` 或 factory 把 concrete dependency 包成 port？
  3. state truth：状态是真在 runtime/manager，还是只是 UI projection？
  4. side effect：vault、workspace、Notice、SQLite、LLM 调用通过哪个 adapter 出去？
  5. 验证：有 build、boundary audit、regression test，还是只有人工判断？
最容易读错的地方 `src/ui/**` 很多文件看起来像业务逻辑，因为有 hooks 和 stores；但现代化后的规则是 UI 只做 projection 和 orchestration。真正的长期 truth 要回到 service runtime、AppRuntimeRegistry、storage repo 或 RunEnvelope。

代码加载路径

第一次读时先沿 boot path 走一遍。`main.ts` 很长，但它不是业务逻辑大杂烩，它是 composition root。

1. plugin load`main.ts` `MyPlugin.onload()`。
2. settings/templates`normalizePluginSettings`、`TemplateManager`、model registry。
3. AI manager`AIServiceManager` 组合 chat storage、prompt、context slots。
4. AppContext`AppContext` 持有 app-owned ports 与 runtime registry。
5. SQLite/search`initSqlite()` 创建 search/index/usage/lint review runtimes。
6. views/commands`ViewManager` + command palette。

启动里最值得看的文件

`main.ts`先看 `onload()` 的 composition 顺序，再看 `initSqlite()`，最后看 `onunload()` 清理顺序。
`src/app/context/AppContext.ts`看哪些东西是 app-owned：runtime registry、vault/navigation/preview/editor/chat/stats ports、copilot review history。
`src/app/runtime/AppRuntimeRegistry.ts`看 runtime bind/read/try/clear 的统一语义。
`src/app/react/ReactElementFactory.tsx`看 React UI 如何拿到 services/ports，而不是自己 import app shell。
`src/ui/context/ServiceContext.tsx`看 UI 可用的能力 surface。这里没有 raw `app` 和 `viewManager` 是 T11P 后的重要成果。

模块分类

App Shell composition

`src/app/**` 是 Obsidian concrete 的合法区域。读这里不要问“为什么 import Obsidian”，要问“它有没有把 Obsidian 包到 port/adapter/runtime 里”。

viewscommandsadaptersruntime wiring
  • `ViewManager` 注册 Obsidian ItemView。
  • `VaultPortAdapter` 等 app adapters 是 host 边界。
  • `composeAmbientRuntime` 这类文件是单能力 composition page。

Service capabilities

`src/service/**` 是业务能力和 runtime。当前应避免 import `@/app/**`、`obsidian`、`@/ui/**`。

chatsearchcopilotambientlint
  • 读某个功能时，从 runtime/manager 进，不要从组件进。
  • 看到 `Port` 类型，顺着 app adapter 找 concrete 行为。
  • 看到 singleton，要确认是不是历史兼容还是明确 owner。

Core substrate

`src/core/**` 是底座：SQLite repo、document loader、provider/profile、ports、types、utils。现代化后 core 不应该依赖 service/app/ui。

storageprovidersportstypes
  • `AppHandle` 是当前 neutral escape hatch。
  • `vault-ops` 是 T11R 后 service/core 的 duck-typed vault helper。
  • 长期更优方向是从 `AppHandle` 再收窄成更强类型 ports。

UI projection

`src/ui/**` 是 React views、hooks、Zustand stores 和 shared components。它可以 import service/core types/runtime ports，但不应该 import `@/app/**`。

ReactstoresviewsCSS
  • 读 UI 时先找 `useServiceContext()`，再找 port/runtime。
  • Zustand store 是 projection，不应成为长任务 truth。
  • 共享 UI/CSS 是当前最大阅读噪音之一。

`AmbientPorts.ts`先看 runtime 需要哪些能力，而不是先看实现。port 是否窄？有没有把 whole app 或 store 塞进去？
`AmbientPushRuntime.ts`读 trigger、search、abort stale run、projection、briefing。并发和取消是否清楚？startup path 是否可降级？
app adapters + UI stores确认 runtime 不 import UI，只通过 projection adapter 写入。未来 Current Work State 不应与旧 Ambient 形成双系统。

模式它解决什么问题先看哪里怎么判断对不对
Composition Root把真实依赖集中装配，避免 service/UI 自己到处找 host。`main.ts`、`AppContext`、`src/app/**/compose*.ts`Obsidian、SQLite、Notice、workspace 这些 concrete 是否只在 app 层接入。
Port / Adapter让 service/core 只看自己需要的窄能力。`src/core/ports/*`、`src/service/**/ports/*`、`src/app/**/*Adapter.ts`port 是否窄；adapter 是否拥有 host 细节；有没有把 whole app 传下去。
Runtime Registry让长期 runtime 有统一 owner、bind/read/clear 语义。`src/app/runtime/AppRuntimeRegistry.ts`double bind 是否 fail loud；unload 是否清理；调用方是否只读 registry，不偷偷 new runtime。
RunEnvelope给长任务提供 session、event trace、artifact、UI projection 的统一形状。`src/service/run-envelope/*`、`VaultLintRun.ts`UI 是否从 trace 投影；run 是否能取消、失败、产出 artifact。
Registry / Catalog避免新增类型散落在 switch 和 if 里。`RetrieverRegistry`、`CopilotActionRuntimeImpl`、`SkillRegistry`、`ProfileRegistry`新增项是否注册一次；调用方是否通过 catalog lookup。
Pipeline / Slots让复杂流程按阶段读，而不是在一个函数里追迷路。`QueryService`、`ContextPipeline`、chat context slots阶段顺序是否清楚；每段是否可替换；错误和 fallback 是否有位置。
Template / Config externalization把大文案、默认模型、规则、阈值从业务逻辑里拿出去。`TemplateManager`、`TemplateRegistry`、`templates/config/*`新增配置是否可读、可替换；有没有把 prompt 或长文案塞回 TS。
Projection Store让 UI store 表达显示状态，而不是接管业务 truth。`src/ui/store/*`、feature stores、hooksstore 是否只保存 UI 状态；长期 truth 是否仍在 runtime/repo/envelope。
Transitional Bridge在边界收敛期间隔离旧 host access，不把重构一次做爆。`AppHandle`、`vault-ops.ts`、Quick Search hostbridge 是否被 containment；有没有继续扩张成新的 god-port。

审阅提醒

提醒位置为什么值得看
`AppHandle` 仍是过渡桥`src/core/ports/AppHandle.ts`、`src/core/storage/vault/vault-ops.ts`T11R 把 Obsidian import 清到 0，但一些 service/core 仍通过 duck-typed app handle 访问 vault。下一步若继续优雅化，应把这些缩成更窄的 typed ports。

Shared UI/CSS 是阅读噪音大头`src/ui/component*`、`src/ui/components/*`、`src/styles/*`它不是边界问题，而是命名、重复 primitive、feature/shared 混放带来的 owner cognition cost。
