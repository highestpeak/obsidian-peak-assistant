PKM 产品类别分析：从信息获取到输出

创造一个知识库，其实是大脑的延伸。大脑可以把更多精力用于思考，知识库负责存储、记忆、检索和组织；真正有效的工具要让资料、笔记、图谱、表格和输出在同一个工作流里形成闭环。

这个 Composer 视图不是要把 Obsidian 改造成另一个协作文档产品，而是把当前正在编辑的 Markdown 变成更顺手的工作台：文字保持可写，图片可以直接检查，表格可以像小型 spreadsheet 一样调整，公式可以阅读，Base、Canvas、Excalidraw 也能作为文档里的真实块继续被 AI 理解。

1. 知识库不是单一目录，而是多种结构叠加

知识库的结构，是根据想要存储的知识来设计的。碎片化思想、阅读摘录和灵感更适合网络结构；一门技术、一组课程或一本书的读书笔记更适合树状结构。

真正难的不是把内容收进来，而是让它在之后还能被重新找到、重新组合、重新输出。一个“舒服”的编辑器要允许用户边写边整理：有时候补一段解释，有时候把一组项目拆成表格，有时候让 AI 把当前段落改写成行动计划，但所有变化都应该可以回到原始 Markdown。

  • 网络结构：承接滑箱笔记、论文旁批、公众号想法和临时判断。
  • 树形结构：承接系统学习、技术专题、书籍章节和项目文档。
  • 跨库链接：当一个知识库裂解成多个知识库时，保留来源、引用和迁移差异。

这里的 AI 不应该像一个远处的聊天窗口，而应该像贴在当前块旁边的编辑伙伴：它知道当前块的源范围、知道它会写成什么语法，也知道这次建议只是一个 patch，用户接受之前不会真的写回文件。

“区分资料库、笔记和大脑”可以看成区分高速缓存、内存和硬盘。[1]

2. 找回信息的四条路径

这四条路径其实对应四种用户心智：搜索、浏览、联想和索引。Composer 要能在同一个页面里承接这些心智，例如把搜索结果转成 checklist，把反向链接摘要转成卡片，把专题索引转成 Canvas 或 Base 预览。

这一节的判断主要来自 [[知识库]]、[[信息管理]] 和 [[表格工具]]；更早的结论在 [[Z-旧版-PKM分类草稿]]，该笔记已被合并删除。

4. 原地编辑必须能回到 Markdown 事务

真正危险的地方不是渲染，而是写回。Composer 可以让段落、图片、表格、公式和 native embed 都变得好编辑，但每一次修改都应该知道自己对应哪一段 Markdown、哪一个附件引用、哪一个 Canvas 节点或哪一段 Excalidraw JSON。

  • 文本块写回普通 Markdown range，保持标题、段落、列表、引用、callout 的源语法。
  • 表格块写回 pipe table，并保留对齐、排序、转置和公式预览的审阅历史。
  • 图片块写回附件引用、尺寸、图注和非破坏性标注，不直接覆盖原图。
  • Native 块写回原文件，不把 Base / Canvas / Excalidraw 转成 Peak 私有格式。
写回原则
AI 永远先给候选 patch，用户接受后才进入 Obsidian undo stack。拒绝、关闭、重试都不应该污染原始文件。

5. AI 建议应该贴在块旁边，而不是把用户拉到远处聊天

对写作者来说，最自然的 AI 不是一个万能聊天框，而是当前块的候选动作。标题需要改名、段落需要扩写、列表需要补项、表格需要总结、公式需要解释、图片需要重新生成或标注。用户把鼠标悬到哪里，AI 就应该把最可能有用的动作带到哪里。

Composer 的目标不是隐藏 Markdown，而是让 Markdown 在复杂对象面前也能保持可编辑、可理解、可回滚。
