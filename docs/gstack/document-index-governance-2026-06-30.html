1. 核心答案

这个项目现在不缺文档，缺的是索引规则。最优解不是搬目录，也不是把全部文档合并成一本书，而是在现有 docs 上方加一个清晰的控制平面。

推荐办法：双层索引

第一层：人看的入口。使用 `docs/index.html` 作为唯一入口，让 owner 和 coding agent 能按任务进入：ground truth、当前状态、最近证据、设计参考、调试手册、历史考古。

第二层：机器可维护的 registry。后续新增 `docs/doc-registry.json` 或 `docs/doc-registry.yml`，给关键文档记录 status、role、canonicalFor、supersedes、lastVerified、readWhen、tags。HTML 是阅读形态，registry 是维护形态。

HTML first 先加索引 再做归档 不要按日期盲删

为什么不直接重组目录

很多文档是证据链：handoff、implementation note、owner review、audit、HTML map 之间互相解释。如果只按目录清理，很容易把“过期文档”和“历史证据”混在一起删掉。

更安全的做法是先给文档加语义标签，跑一轮索引验证，再决定哪些移动到 archive、哪些保留为 evidence。

2. Ground Truth 文档族

你列的四类应该升级成项目的最高解释层。它们不是普通目录文档，而是所有后续代码阅读、refactor、handoff 和 review 的引用入口。

Canonical 1

架构文档

回答“系统为什么这样分层、运行时归谁拥有、边界在哪里”。建议正稿路径：`docs/ground-truth/architecture.html`。内容必须覆盖 app/service/core/ui、Capability Contract、Run Envelope、runtime ownership、禁止双系统双代码共存。

Canonical 2

代码组织文档

回答“我要改某个能力时先看哪里、哪些 import 合法、目录名代表什么责任”。建议正稿路径：`docs/ground-truth/code-organization.html`。它应该是读代码地图，不是简单文件树。

Canonical 3

功能与算法文档

这里不要写成营销式功能介绍，而要写重要能力的算法逻辑：Chat context 如何堆叠、Search 如何检索和重排、Agent loop 如何推进、Ambient signal 如何进入 review surface。建议正稿路径：`docs/ground-truth/capabilities-and-algorithms.html`。

Canonical 4

配置项与用户视图文档

回答“哪些东西可配置、默认值从哪里来、用户在 Vault 里会看到什么 folder/file 形状”。建议正稿路径：`docs/ground-truth/configuration-and-user-views.html`。重点覆盖 `templates/config/`、settings UI、provider/model/profile、用户侧项目/聊天/历史文件结构。

3. 建议目录形状

docs 根目录应该从“所有东西都摊开”改成“只有入口和少数控制文件”。旧文档先不删，先降级成 evidence、design reference 或 archaeology。

区域责任
`docs/index.html`唯一人工入口。只回答“现在应该读哪几份”。
`docs/ground-truth/`四份正稿 HTML：架构、代码组织、功能算法、配置项和用户视图。
`docs/current/`当前阶段、当前 roadmap、当前 issue pool。可以由 `progress.md` 逐步迁成 HTML。
`docs/evidence/`implementation notes、owner review packets、audit findings、issue maps。保留证据链，但不当正稿。
`docs/design/`gstack/mockup/UX flow 报告。作为设计参考，不和架构正稿混层。
`docs/archive/`明确 superseded 或 historical 的旧路线、旧任务板、旧探索。
`docs/registry/`后续放 registry、link check 输出、生成索引脚本的输入数据。

6. 文档索引模型

索引的目标不是记录所有路径，而是让每份重要文档回答：它现在是什么身份，什么时候该读，能不能覆盖别的文档，是否已经被替代。

字段作用
`id`稳定短 id，例如 `architecture-handbook-2026-06-01`。
`path`相对路径，方便跨机器和仓库内链接。
`status``current`、`draft`、`evidence`、`historical`、`superseded`、`archive`。
`role``status-source`、`canonical`、`operating-rule`、`evidence`、`design-ref`、`debug-ref`。
`tier`0 到 6，对应真相源梯子。
`canonicalFor`这份文档对哪个主题拥有最高解释权。
`supersedes` / `supersededBy`显式记录替代关系，不靠读者猜。
`lastVerified`上次确认仍然可信的日期。
`readWhen`一句话告诉 reader 什么时候打开它。
`tags`能力、surface、阶段、文档类型标签。

8. 维护流程

文档治理要轻。每次新增或重写重要文档，只需要过一个短流程，不要让索引本身变成新负担。

Step 1

写状态横幅

每份重要文档顶部写明：`current`、`draft`、`evidence`、`historical`、`superseded` 或 `archive`。HTML 文档也应该在 hero 或 meta 区展示。

Step 2

登记 registry

只登记高价值文档。普通截图、局部 mock、一次性输出可以挂在父文档下面，不必都变成一条 registry record。

Step 3

标替代关系

不要让读者猜哪个文档覆盖哪个文档。用 `supersedes` 和 `supersededBy` 记录旧稿、正稿和后续修订。

Step 4

更新入口

`docs/index.html` 只列最重要入口。细节留给 registry、ground truth 文档内部目录和按主题归档的 evidence。

Step 5

链接校验

至少跑本地 link check，确保 registry 和 HTML report 里的路径存在。上一版打不开的问题就应该由这个门拦住。

Step 6

定期清理

按 `status` 和 `lastVerified` 清，不按日期粗暴清。老文档可以是 historical evidence，不一定要删。

9. 落地路线

建议先做索引覆盖，不要先移动文件。目录搬迁应该发生在 registry 跑通之后。

P0 - 入口固定

新增 `docs/index.html`，只放少数入口：ground truth、current status、architecture source、active evidence、code reading maps、design refs、debug refs。

P1 - Ground truth HTML

先写四份正稿 HTML：架构、代码组织、功能算法、配置项和用户视图。旧 Markdown 只能作为证据引用，不继续承担正稿责任。

P2 - Registry seed

新增 `docs/registry/doc-registry.json`，先登记 40 到 60 份高价值文档。每条记录有 status、role、tier、readWhen、supersedes。

P3 - 归档与 guard

给 stale docs 加 `supersededBy`，再移动到 archive。添加 link check 和 registry shape check，防止新文档继续漂移。

10. 不要做什么

文档治理最容易失败在“看起来更整齐，但实际更难找真相”。下面这些动作应该避免。

不要按日期批量归档 老文档可能是证据链。先标 status 和 supersededBy，再决定移动。
不要把所有文档合成一本 这个项目需要分层索引，不需要一本巨大的 architecture bible。
不要让 README 变成 500 行目录 README 应该是入口，完整列表交给 registry 和生成报告。
不要把设计图和正稿混成同一层 gstack 视觉材料很重要，但多数是 design reference，不是 current source of truth。
不要只靠文件夹表达状态 同一文件夹里可能有正稿、draft、证据和历史。状态必须进 metadata。
不要让 AI 只按路径猜文档价值 索引要告诉 agent 读什么、什么时候读、不要被什么旧稿误导。
