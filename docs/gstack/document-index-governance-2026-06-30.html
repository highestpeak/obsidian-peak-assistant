Documentation playbook

把 docs 写成能用的系统，不写成聊天纪要。

这页不再试图列出所有文档。它只回答四件事：哪些文档值得写成正稿；每份正稿该怎么写；现有文档如何归位；以后代码变了怎么维护文档。

核心判断 Peak Assistant 需要 4 份 ground truth HTML，不需要一份越来越长的“总目录”。`docs/superpowers/` 和 `docs/gstack/` 原位保留，只做索引标注。
写作口径 每份文档只服务一个读者任务。架构文档解释边界；代码组织文档指导改代码；功能文档说明能力和算法；配置/用户手册说明用户能看见和修改什么。

1. 结论

当前问题不是“文档不够”，而是不同类型的文档混在一起。正稿、探索稿、实现记录、视觉报告、用户手册、配置参考承担了不同任务，不能都塞进同一种页面。

先拆类型

用 Diataxis 的思路区分解释、操作指南、参考和教程。我们的 ground truth 多数是解释 + 参考，不应该写成流水账或任务列表。

再写正稿

先写 `architecture.html` 和 `code-organization.html`。这两份决定后面所有功能、配置和用户文档的词汇和边界。

旧文档不搬

`docs/superpowers/` 与 `docs/gstack/` 是既有工作流目录。保留位置，只在索引里标成 canonical、evidence、design-ref、historical 或 superseded。

少写 AI 口吻

每段只回答一个问题。少用“治理”“体系”“全景”“沉淀”这类空泛词，多写读者下一步该打开哪个文件、看哪个图、更新哪份正稿。

2. 外部范式给我们的启发

下面不是照搬模板，而是把成熟文档体系裁剪成适合这个项目的规则。

来源它解决什么在本项目怎么用
Diataxis 把文档分成 tutorial、how-to、reference、explanation。每类文档服务不同读者需要。 不要让一份 HTML 同时承担架构解释、操作指南、历史归档和配置参考。每份正稿先写清它属于哪类。
arc42 给架构文档一个稳定骨架：目标、约束、上下文、方案、building blocks、runtime、决策、质量、风险。 `architecture.html` 用 arc42 的骨架，但只保留对当前重构有用的章节。
C4 model 用不同 zoom level 解释系统：Context、Container、Component、Code。 架构文档不画一张巨图。先画系统边界，再画 app/service/core/ui，再画 Chat/Search/Ambient 的关键 runtime。
Kubernetes docs 明确 Concept、Task、Tutorial、Reference 等页面类型。 配置与用户手册拆成“概念解释、任务步骤、参考表”。不要把用户操作和内部架构混在一起。
Google developer style 强调面向开发者的清晰、一致、可扫描写法。 标题用读者问题写；链接文字说清目的；句子短；不要把报告写成 AI 生成的抽象总结。
ISO/IEC/IEEE 29148 需求工程强调目的、范围、角色、需求、约束、验收和生命周期。 功能需求文档不用完整 SRS，但每个能力必须写用户目标、输入输出、约束、验收和测试证据。

4. 四份正稿怎么写

每份正稿都要短、有边界、有维护触发器。不要从“背景介绍”开始，先告诉读者这份文档帮他做什么。

架构文档

docs/01-architecture.html
读者问题
  • 系统现在的目标架构是什么？
  • 哪些 runtime 归 app 层拥有？
  • 为什么不能双系统双代码共存？
第一版目录
  • 当前结论和不变量
  • C4：边界、容器、组件
  • arc42 裁剪版：目标、约束、building block、runtime、决策、风险
  • 当前偏离和 T0-T12 执行线
不要写
  • 不要写成所有历史讨论合集。
  • 不要列完整文件树。
  • 不要把未实现能力写成已完成事实。

代码组织文档

docs/02-code-organization.html
读者问题
  • 我要改 Chat/Search/Settings/Agent，先看哪里？
  • 哪些 import 合法？
  • 哪些目录只是 adapter，不该放业务逻辑？
第一版目录
  • Boot path：main.ts 到 AppContext
  • 按能力读代码：Chat、Search、Indexing、Settings、Agent/Tool
  • 层级规则：app/service/core/ui
  • 改动检查表和测试入口
不要写
  • 不要生成 directory dump。
  • 不要复述每个文件名。
  • 不要把旧 boundary leak 当成规范。

功能与算法文档

docs/03-function-map.html
读者问题
  • Chat context 到底怎么堆？
  • Search 从 query 到 result 怎么走？
  • Agent loop 和 tools 如何交互？
能力卡模板
  • 用户目标和 entry point
  • 输入、context sources、pipeline、输出
  • ranking/merge/selection 规则
  • 配置项、测试、失败模式
第一版先写
  • Chat context stack
  • Search retrieval / rerank
  • Indexing lifecycle
  • Agent loop / ToolDef

配置项与用户视图文档

docs/04-configuration-and-user-views.html
读者问题
  • 用户能配置什么？
  • 默认值从哪里来？
  • Vault 里会出现哪些 folder/file？
第一版目录
  • 用户可见模型
  • 配置来源优先级：settings、templates/config、fallback
  • 任务步骤：如何改 provider/model/profile
  • 参考表：key、默认值、来源、影响面
不要写
  • 不要只写开发者内部配置。
  • 不要把用户 folder shape 藏在实现细节里。
  • 不要硬编码多语言 regex/label 这类规则。

6. 维护机制

文档维护要跟代码变化绑定。不要靠“整理一下 docs”这种大扫除。

变化必须更新只登记索引完成标准
runtime owner 或层级边界变化架构文档、代码组织文档相关 superpowers audit / implementation note正稿能解释新 owner、旧路径是否仍允许。
Chat context 或 Search pipeline 变化功能与算法文档tests、issue map、handoff能读到 input、source、pipeline、output、测试证据。
新增配置项或默认值配置项与用户视图文档config governance evidence说明用户在哪里看见它，默认值来自哪里，fallback 如何生效。
新增 gstack HTML report通常不用改 ground truthdocs/index.html 或 registry标成 reading map、design-ref 或 QA evidence。
新增 superpowers plan/audit/handoff除非改变事实，否则不用改 ground truthregistry status、readWhen、canonicalFor能判断它是 active evidence、operating rule、historical 还是 superseded。

HTML report QA 规则

这条来自 `technical-doc-architect` skill：文档类 HTML 只验证真实阅读环境，不做额外设备宽度检查。

代码阅读报告

主场景是桌面阅读。验证记录写“主阅读视口 1440px 已验证”。除非用户明确要求，或者报告本身是产品界面，否则不跑其他设备宽度。

产品 UI / public 页面

只有当页面真实需要多个目标环境时，才按那些环境验证。不要把所有 HTML report 都默认写成多环境 QA。

已归档证据

codebase-reading-map 和 technical-support-layer-report 的验证记录也应只记录主阅读视口。

7. 写作规则

这部分专门防止“AI 味”。重点不是让文字更花，而是让读者愿意继续读。

标题回答问题

不要写“治理方案”“能力沉淀”。写“打开 docs 先看哪份？”、“改 Search 先读哪里？”、“这个配置用户在哪里看见？”

一段只做一件事

如果一段里同时出现历史、现状、风险、下一步，就拆开。长段落会让文档像聊天总结。

图和表各有工作

架构图说明边界和 runtime；表格说明 contract、配置项、状态；卡片说明并列入口。不要为了好看堆卡片。

事实和建议分开

用轻量标签：Confirmed from code、Inferred、Risk、Needs verification。不要把推断写成事实。

不要这样写

建立一个能判断真相、证据、历史和下一步的文档索引控制平面。

改成这样

打开 docs 时先做两件事：看 `docs/index.html`；确认要读的文档是 canonical、evidence 还是 historical。
