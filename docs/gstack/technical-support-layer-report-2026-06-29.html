技术支撑层阅读报告

这份报告只讲技术支撑层：Boot/App shell、Shared UI/CSS、Core storage、Agents/Harness、MCP/Skills/Tools、Other/cross-cutting。 它的目的不是评价代码多不多，而是帮你知道从哪里进、怎么追流程、哪些地方是状态真相、哪些地方只是 glue。

62,562技术支撑层 raw lines，占当前统计口径 44.9%。
6支撑子层：UI、storage、agents、tools、boot、glue。
1推荐入口：先读 Boot/App shell，再向下追 ports。
0目标不是新功能，而是降低读代码时的迷路成本。

报告定位

核心判断：技术支撑层不是“剩下来的杂项”。它是所有用户功能共同站在上面的运行底座。你读用户功能时，如果看不懂依赖、状态、端口、持久化、工具执行，通常不是功能代码本身的问题，而是支撑层路径没先建立。
本文读者

代码 owner 或 reviewer，知道 Peak Assistant 是 Obsidian 插件，但不想在重构后的模块里靠猜。

本文目标

读完后能追一条能力从 Obsidian 入口到 React ports、service runtime、SQLite/tool/agent 的路径。

本文不做什么

不重新解释每个用户功能的业务逻辑；不为 Current Work State、Chat 或 Command Gateway 提前设计新架构。

3 分钟读法

  1. 先看 按问题进入，决定你现在是在追启动、UI、存储、agent、tool，还是跨功能 glue。
  2. 再看 Boot/App shell，因为所有支撑层对象几乎都从这里被装配出来。
  3. 最后按你正在读的用户能力跳到 UI、storage、agents 或 tools，不要按目录树从上往下硬啃。

按问题进入

技术支撑层的正确读法不是“从最大目录开始”。你先判断自己卡在哪个问题，再跳到对应层。

你卡住的问题先读哪一层第一批文件读完应该能回答什么

总心智模型

技术支撑层可以理解成四条主线：启动装配、UI 注入、持久化底座、工具执行底座。`Other / cross-cutting` 不应该作为第一入口，它只在调用链需要时回看。

最重要的边界

`src/app/**` 可以知道 Obsidian concrete API；`src/service/**` 应该靠 ports/runtime；`src/ui/**` 通过 `ServiceContext` 拿 narrow ports，不再直接进口 `@/app/**`。

最容易误读的地方

代码量最大的支撑层不一定最先读。Shared UI + CSS 最大，但理解全局运行收益最高的是 Boot/App shell 和 `ReactElementFactory`。

Boot / App Shell

这一层回答：插件什么时候创建全局对象？哪些 runtime 在 boot 期间绑定？React tree 怎么拿到服务？卸载时谁负责清理？

启动流程：从 Obsidian onload 到 runtime 可用

flowchart TB
  onload["main.ts onload()"]
  settings["loadData + normalize settings<br/>ProfileRegistry + TemplateManager"]
  manager["AIServiceManager + AppContext"]
  early["early runtimes<br/>QuickSearchBackground · CopilotAction"]
  sqlite["initSqlite()"]
  repos["SqliteStoreManager<br/>usage · search · repos"]
  bind["bind runtimes<br/>VaultLint · VaultReview · SessionContext"]
  views["ViewManager + commands + setting tab"]
  react["ReactElementFactory injects ServiceContext"]
  unload["onunload clears runtimes/stores/sqlite"]

  onload --> settings --> manager --> early --> sqlite --> repos --> bind --> views --> react
  onload -. "hot reload / plugin unload" .-> unload

阅读顺序

  1. `main.ts`：先找 `onload()`、`initSqlite()`、`initializeSearchService()`、`onunload()`。
  2. `AppContext.ts`：看 app-owned services、ports、runtime registry。
  3. `AppRuntimeRegistry.ts`：看 fail-loud、double-bind、clear 语义。
  4. `ReactElementFactory.tsx`：看 UI service context 的唯一注入点。
  5. `ViewManager.ts` 和 `Register.ts`：看 views 与 palette command 的暴露面。

你要带着这些问题读

  • composition root 在哪里？如果一个 runtime 需要 Obsidian、SQLite、Zustand store，它应该由 `app/compose*.ts` 或 `main.ts` 组合。
  • runtime 什么时候可用？有些 runtime 在 `onload()` 早期可用，有些必须等 `initSqlite()`。
  • 清理是否对称？`onload()` bind 的对象，`onunload()` 要 clear/dispose。
Review 重点：不要新增第二个 composition root。看到 service 或 UI 自己去拿 `AppContext.getInstance()`、动态 import `@/app/**`、或者自己 new app adapter，要停下来检查边界。

Shared UI + CSS

这一层不是用户功能。它负责把同一套视觉 token、primitive、shared component 和 React service port 注入方式应用到不同 feature surface。

UI 支撑路径：app composition 到 React projection

flowchart LR
  appctx["AppContext<br/>manager · searchClient · runtimeRegistry · ports"]
  factory["ReactElementFactory<br/>compose ports once"]
  service["ServiceContext<br/>narrow ports only"]
  primitives["Primitives<br/>Button · Row · Pill · Modal · Segmented"]
  css["CSS tokens<br/>peak-tokens · peak-components"]
  surface["Feature surfaces<br/>chat · settings · usage · quick search"]

  appctx --> factory --> service --> surface
  primitives --> surface
  css --> primitives
  css --> surface
先读这些
  • `docs/conventions/ui-design.md`：设计系统规则和 Obsidian CSS 防线。
  • `peak-tokens.css`：颜色、间距、radius、shadow 的源头。
  • `peak-components.css`：`.pk-*` primitive 样式。
  • `src/ui/components/primitives/*`：生产 wrapper。
  • `ServiceContext.tsx`：UI 能拿到哪些 service/port。
怎么理解

现在的 UI 支撑层有两条线：一条是视觉 primitive，一条是 service port 注入。前者管样式一致性，后者管 UI 不越界碰 app concrete。

旧的 `src/ui/component/shared-ui/*` 和新的 `src/ui/components/primitives/*` 同时存在，review 时要判断新增 UI 应该落在哪套 primitive 上，避免继续扩大双系统。

常见误读

误读正确读法
Shared UI 行数最大，所以先全读 UI。先读 `ServiceContext` 和 primitive catalog，再按 feature surface 回看具体组件。
Zustand store 是业务真相。多数 store 是 projection；runtime、repo、RunEnvelope、持久化层才更接近 truth。
一个新 button 随手写 class 就行。先查 primitive，缺 primitive 才扩展；不要新增 per-surface button/pill 体系。

Core Storage

Core storage 是整个插件的持久化底座。它分成 SQLite tenant/repo 体系和 vault markdown 文档体系。理解它，就能知道 search、chat、usage、ambient、lint 的数据到底落在哪里。

Storage 结构：两个 SQLite tenant + vault markdown

flowchart TB
  init["main.initSqlite()"]
  manager["SqliteStoreManager"]
  vaultDb["vault.sqlite<br/>search/index/graph/lint/ambient"]
  chatDb["chat.sqlite<br/>chat/project/AI analysis/usage"]
  vaultDocs["Vault markdown docs<br/>chat transcripts · analysis docs"]
  reposA["IndexedDocumentRepo · DocChunkRepo · EmbeddingRepo · GraphRepo"]
  reposB["ChatProjectRepo · ChatConversationRepo · UsageLogRepo · AIAnalysisRepo"]
  chatStore["ChatStorageService"]
  vaultOps["vault-ops<br/>temporary AppHandle helpers"]

  init --> manager
  manager --> vaultDb --> reposA
  manager --> chatDb --> reposB
  chatStore --> vaultDocs
  chatStore --> reposB
  chatStore --> vaultOps

阅读顺序

  1. `SqliteStoreManager.ts`：看开库、backend selection、tenant-aware repo getters。
  2. `ddl.ts`：看表语义，尤其 `mobius_node`、`doc_chunk`、chat tables、usage tables。
  3. `src/core/storage/sqlite/repositories/*`：按 feature 找 repo，不要全量读。
  4. `ChatStore.ts`：看 chat markdown 与 SQLite meta 如何双写/回读。
  5. `vault-ops.ts`：看 T11R 后暂时保留的 duck-typed vault helper。

Review 重点

  • Schema first：先看 schema 和 repo contract，不要从 UI query 开始猜数据结构。
  • Tenant 意识：`vault` tenant 和 `chat` tenant 共用部分 index repo，但落在不同 SQLite 文件。
  • AppHandle 是 containment：`vault-ops.ts` 不 import Obsidian，但它仍是过渡桥，不应该无限扩张。

Agents + Harness

Agent Harness 是工具执行和多步推理的底座。具体 agent 是使用者，harness 才是共用框架：loop、tool registry、permission、tier、hooks、memory、subagent、trace。

AgentLoop：一次 agent run 的骨架

flowchart LR
  cfg["AgentLoopConfig<br/>model bindings · tools · hooks · memory · budget"]
  start["loop_start + session_start hook"]
  tier["TierController<br/>local-fast → local-deep → online"]
  tools["ToolRegistry slice<br/>allowed tools per tier"]
  model["AI SDK generateText<br/>one step at a time"]
  trace["TraceBus<br/>step/tool/context events"]
  stop["stop conditions<br/>max steps · tokens · final answer · abort"]

  cfg --> start --> tier --> tools --> model --> trace --> stop
  stop -- "continue" --> tier
  stop -- "finish" --> result["AgentLoopResult"]
框架入口

`AgentLoop.ts` 是主干；它控制 step、tool call、trace、budget、stop condition。

工具入口

`ToolRegistry` 管工具注册和 tier filter；具体工具不应绕开 registry。

安全入口

`PermissionGuard` 是 deny-first，不应被 bypassPermissions 覆盖 explicit deny。

阅读顺序

  1. `src/service/agents/harness/loop/*`：先理解 loop 和 stop condition。
  2. `tool/registry.ts`、`permission/PermissionGuard.ts`、`tier/TierController.ts`、`hook/HookBus.ts`：理解共用控制面。
  3. `memory/*`、`subagent/*`、`trace/*`：按你要 debug 的现象回看。
  4. 最后读具体 agent：`DocSimpleAgent`、`VaultSearchAgent`、`GraphAgent`、`ReportOrchestrator`。
不要混淆：Copilot action runtime 是 Copilot 功能自己的 action catalog；Agent Harness 是多步 agent 执行底座。它们可能都调用 AI 和工具，但 ownership 不一样。

MCP / Skills / Tools

这一层是 agent 能力的外部扩展面：MCP server、vault skill、内置工具。读它时要先看 registry/adapter，再看具体 tool 的实现和权限边界。

工具供给链：从外部 server / vault skill 到 agent tool

flowchart LR
  mcpServer["External MCP server<br/>stdio / SSE"]
  mcpManager["MCPClientManager<br/>connect · listTools · callTool"]
  mcpAdapter["MCPToolAdapter<br/>JSON schema → Zod · namespaced tool"]
  skills["SkillRegistry<br/>built-in + vault _skills"]
  parser["SkillParser<br/>markdown → SkillDefinition"]
  builtin["Built-in tools<br/>content-reader · search graph · memory"]
  agentTools["Agent tool surface"]
  loop["AgentLoop"]

  mcpServer --> mcpManager --> mcpAdapter --> agentTools
  skills --> parser --> agentTools
  builtin --> agentTools
  agentTools --> loop

阅读顺序

  1. `MCPClientManager.ts`：连接、发现 tools、callTool、dispose。
  2. `MCPToolAdapter.ts`：MCP JSON Schema 到 AgentTool/Zod 的转换。
  3. `SkillRegistry.ts` 和 `SkillParser.ts`：built-in / vault skill 加载与 hot reload。
  4. `src/service/tools/*`：按 tool 名称读，重点看输入 schema、返回 envelope、错误降级。

Review 重点

  • 工具名命名空间：MCP tool 会被命名成 `mcp_{serverName}_{toolName}`，避免和内置工具撞名。
  • 输入要 schema 化：外部 JSON Schema 会被转成 Zod；新增工具不应只靠自由文本参数。
  • 权限不能后补：会编辑 vault 或调用外部系统的工具，要先看 `PermissionGuard` 和 tool kind。

Other / Cross-Cutting

这是最容易变成“杂物桶”的层：constants、types、EventBus、utils、ports。正确读法是按调用链回看，不要把它当一个功能模块顺序阅读。

Cross-cutting 的正确打开方式

  feature["你正在读的 feature/runtime"]
  types["core/types<br/>neutral DTO / domain shape"]
  ports["core/ports<br/>host-neutral handles"]
  constants["core/constant.ts<br/>shared policy constants"]
  events["EventBus<br/>view communication events"]
  utils["core/utils<br/>path · markdown · hash · concurrency"]

  feature --> types
  feature --> ports
  feature --> constants
  feature --> events
  feature --> utils

  utils -. "read caller first" .-> feature
子类代表文件阅读规则
Event bus`src/core/eventBus.ts`先看事件枚举，再找 emit/on 调用方；不要把 EventBus 当业务 runtime。
Constants`src/core/constant.ts`适合放真正跨功能的 policy；不适合塞 feature 文案、UI label、巨大配置。
Neutral types`src/core/types/*`先看对应 feature 的 service，再回看类型；不要从 types 目录开始读。
Ports / handles`src/core/ports/*`用于隔离 Obsidian concrete；新增 port 要窄，不要变成 god-port。
Utils`src/core/utils/*`按调用链读，重点看是否真的通用，还是应该留在 feature 内部。

设计模式怎么读

技术支撑层里的模式不是抽象名词，它们是读代码时的路标。先识别实现形状，再判断改动有没有顺着这个形状走。

模式它解决的问题实现形状Review 判断
Composition Root防止真实依赖在 service/UI 里乱窜。`main.ts`、`AppContext`、`compose*.ts` 集中创建 runtime 和 ports。新增依赖是否在 app 层装配？unload 是否能清理？
Ports / Adapters让业务 runtime 不知道 Obsidian、SQLite、Notice、workspace 的细节。service 定义 port interface，app adapter 连接 concrete。port 是否足够窄？有没有把 raw app、viewManager、store 传下去？
Runtime Registry让长期 runtime 有唯一 owner。`AppRuntimeRegistry` 负责 bind/read/try/clear。是否 fail-loud double bind？是否有第二个 hidden singleton owner？
Repository把 SQLite 表访问集中管理。`ddl.ts` 定义表，`repositories/*` 负责 query。上层是否散落 raw SQL？schema 变更是否有兼容路径？
RunEnvelope让长任务有 session、events、artifact、UI projection。`VaultLintRun` 是当前最清楚样本。UI 是否从 trace 投影，而不是重新拥有运行状态？
Facade / Host Bundle在迁移期间把宽 host access 关在 app-owned bundle 里。`composeQuickSearchHost` 这种 facade 可以存在，但必须有边界。facade 是否继续变宽？能否逐步拆成更窄 ports？
Deny-first Guard工具和 agent 权限默认保守。`PermissionGuard` 先 explicit deny，再看模式和 allow。`bypassPermissions` 是否仍不能覆盖 explicit deny？危险工具是否有 kind/schema？

你应该怎么 Review 技术支撑层改动

按路径 Review
  1. 确认改动属于哪个支撑子层，不要把用户功能和技术底座混在一张 diff 里看。
  2. 找到 composition root：是 `main.ts`、`AppContext`、`ReactElementFactory`、还是某个 `compose*.ts`。
  3. 找到 state truth：runtime、repo、RunEnvelope、SQLite、vault markdown，还是 UI projection。
  4. 找到 side effect：Obsidian workspace/vault、SQLite、MCP server、AI provider、filesystem。
  5. 跑边界和浏览器检查，不要只靠类型通过。
不要做这些
  • 不要让 `ServiceContext` 重新发布 raw `app` 或 `viewManager`。
  • 不要在 `src/service/**` 新增 app-layer ownership 或 UI store import。
  • 不要把 `core/constant.ts` 当 feature 配置桶。
  • 不要扩张 `AppHandle` 或 vault god-port 来快速过边界。
  • 不要把 Shared UI 的局部样式复制成第三套 primitive。
