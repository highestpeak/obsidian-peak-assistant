# Vault Intelligence workspace V2 mock

This is a design-only, standalone `file://` prototype for owner review.

For the consolidated design decisions and next-task boundary, start with [the continuation handoff](./continuation-handoff.md). For the complete Follow-up source model, all current and future finding examples, every owner action example, file-write boundary, and exit condition, use the canonical [Vault Scan Follow-up and Work queue contract](../../superpowers/specs/2026-08-15-vault-scan-follow-up-and-work-queue-contract.md).

- It does not import or modify plugin production code.
- Most numbers, findings, files, costs, and run events are illustrative mock data. The Vault contents knowledge graph is the exception: it uses a read-only representative projection of five maintained knowledge roots (2,106 Markdown notes and 1,839 uniquely resolved Wikilinks at the time of inspection).
- Knowledge Index is part of Vault Intelligence rather than a fourth top-level workspace. Overview shows its current readiness and downstream impact; first setup, normal re-entry, and recovery all use one `Scan Vault`-owned setup page.
- `Scan Vault` simulates setup or resume → visible execution stages → actionable completed result.
- Top-level navigation contains only `Overview`, `Vault map`, and `Work queue`. The title-row `Last scan` entry reopens the latest completion summary; while a scan is active, the primary action becomes `View progress`.
- The lower-right Mock state control includes `Completed` so the owner can jump directly to the completion state during review. No prototype-only completion action is mixed into the proposed run header.
- Proposal actions never write files; Apply only demonstrates the review state.

## Scan setup and recovery

- The mock-state control in the lower-right previews `Changes`, `First setup`, and `Recoverable` entry conditions.
- The same standalone setup page owns all three conditions; only its evidence, default scope, estimates, and primary action change. It belongs to the `Scan Vault` flow, so Cancel and Back return to Overview.
- First setup defaults to the entire Vault and explains what is missing before the first successful run. It does not claim that choosing settings means Search or Vault Intelligence is already ready.
- A returning incremental run defaults to changed objects plus dependency closure, while keeping the current Vault projection usable until the new run publishes.
- A recoverable run preserves its run identity, completed Search work, frozen input, and partial evidence. `Resume scan` begins at the saved Vault-map checkpoint rather than silently restarting.
- Setup exposes only owner decisions: scope, four understandable task groups covering the 19 local maintenance tasks, the current run's Knowledge Index outputs, five readable AI groups, the ten underlying AI operations, their actual routed models, and typical token/cost totals. Hovering or focusing a task group highlights the AI groups it supports; `Content health` correctly highlights none because it is local-only.
- Task selection and AI authorization are different controls. Step 2 decides which maintenance outcomes Peak should pursue. Step 3 groups the related AI functions for readability, but only the ten expanded operations have switches. Turning one operation off preserves its selected local task and immediately recalculates the operation count, estimated time, token estimate, cost estimate, and group summary.
- Required local facts are separated from AI work. AI planning, embeddings, file summaries, machine-only AI Tags, relationship discovery, semantic review, Community/Hub/bridge analysis, proposal preparation, and maintenance synthesis run only after Setup authorization. The Index output plan and the AI operation switches share one state, so an output cannot appear enabled while its supporting AI operation is disabled.
- The setup is read-only. User-file changes still require a separate, reviewable proposal after findings exist.

## Knowledge Index inside Vault Intelligence

- Knowledge Index is the reusable Search and machine-knowledge layer maintained by Vault scans. It powers Vault Search, AI Search, file context, relationship signals, and Vault map analysis; those consumers do not each build a private index.
- Overview answers `What is ready now?` and `Which product surfaces are affected?`. It never becomes a second setup form. `Review next Index plan` enters the normal Scan setup and expands the relevant plan in place.
- Step 1 owns input scope once. The Index plan inside Step 2 inherits that exact scope and chooses only this run's outputs: Full-text, Embeddings, Summaries, Tags and entities, Relationships, and Content understanding. It never repeats folder or Community selection.
- The detailed four-group generated-knowledge matrix is retained from the earlier Knowledge Index workspace. Automatic local outputs, optional available outputs, and unavailable `Later` capabilities remain visibly distinct instead of disappearing from the product model.
- Step 3 owns AI authorization and model routing for the selected tasks and Index outputs. Shared controls are synchronized: changing Embeddings, Markdown summaries, AI Tags, Semantic similarities, or Community signals updates the supporting AI operation, and changing that operation updates the Index plan.
- Estimated time is run-specific rather than decorative copy. It combines the selected scope's measured local-throughput range with the longest parallel AI path and a bounded share of all enabled AI work. Every available Index output, AI operation, and routed model recalculates the visible range; the tooltip exposes the simple formula and conservative rounding rule.
- Durable defaults remain in Knowledge Index settings: background refresh, batching, retries, exclusions, chunking, and default model policies. Scan setup owns only the current run.
- Progress does not launch a second Index workflow. `Discover → Build Index → AI work → Publish` is one pipelined DAG rather than four strictly serial boxes. Each document first produces readable text, Full-text, and deterministic facts; enabled Embeddings, Summary, and machine-only AI Tags then follow that document as Index enrichment. Vault-level relationship, semantic, Community, Hub, and bridge analysis starts only after enough indexed evidence exists, but may overlap the tail of the Index pipeline.
- Overall progress and Knowledge Index progress are different visible measures. Overall progress covers the entire Scan DAG; Index progress covers the selected Index-layer work units and separately reports Core Search-ready documents and AI-enriched documents. During live indexing, the detailed workbench retains the earlier Index design's own progress bar, connected internal rail, document queue, current file, six per-file steps, remaining time, and throughput.
- Publish is layer-aware. Core Search can publish after its layer verifies even when an optional enrichment operation stopped or failed; verified vectors, summaries, and AI Tags publish by their own layer receipt. A partial optional layer never silently blocks refreshed Search or claims full completion.
- Completion reports observable effects by Index layer and names the affected consumers. Only failed or unresolved outputs with a real owner action and verifiable exit condition enter Work queue; successful Index refreshes remain completion effects and receipts.

## Run navigation and retention

- A scan is an operation, not a permanent workspace section. `Scan Vault` opens setup, changes to `View progress` while active, and lands on the completed result when publishing finishes.
- Setup, progress, and completion form one uninterrupted route: `Scan setup → Run progress → Completed`. These operation screens do not claim the `Overview` top-level tab, and their breadcrumbs move through the scan flow rather than jumping sideways into Overview.
- Progress puts Overall completion, advanced objects, elapsed and remaining time, throughput, and actual AI tokens/spend in one top band. A continuous four-stage rail (`Discover / Build Index / AI work / Publish`) is clickable: its state can show Build Index and AI operations running concurrently. The lower surface follows the primary live stage by default or lets the user inspect another stage without changing execution.
- AI work exposes two different execution scopes instead of presenting five equivalent rows. Per-document Index enrichment follows each eligible document and contributes directly to Index progress. Vault-wide analysis starts only after an evidence threshold and then runs its own overlapping lifecycle: assemble changed + affected + current-graph evidence, discover candidates, review them against sources and Community history, and prepare guarded follow-up. Index enrichment may finish while Vault-wide review continues.
- Vault-wide work is one continuous timeline rather than a second summary rail followed by unrelated AI cards. Its four nodes retain the run history in place: completed nodes collapse to a concrete result summary, running nodes auto-expand and receive a one-time centered scroll focus, and waiting nodes state their required input. Parallel running nodes may remain open together. Ordinary progress refreshes never keep stealing the scroll position; if the user is inspecting another Run stage, focus waits until the AI stage becomes visible. Clicking any node reveals its process without changing execution.
- `Assemble evidence` has its own observable four-step trace for selected input, affected context, the complete current graph, and provenance boundaries; it is not a decorative label. The remaining timeline nodes contain the actual Vault-level operations. Each operation shows a four-step process timeline, current or required input, concrete evidence produced, output counts, routed model/provider, receipt-backed tokens and spend, and individual Stop/Skip control. Relationship discovery visibly builds a candidate pool, compares links/vectors/summaries across the complete graph, ranks and deduplicates candidates, then attaches source passages; semantic review separately checks direction, meaning, contradictions, existing history, and retained/rejected evidence. The UI never exposes or claims hidden chain-of-thought.
- Prototype-only `Mock state → Indexing` and `Mock state → AI work` shortcuts freeze the run at those two live states so both progress measures and every operation detail can be reviewed without waiting for the demo timer.
- The header keeps one compact result entry: `Last scan`. It opens the latest completed scan directly without making the user search a run list.
- Older run receipts are still retained for citations, comparison, debugging, cost, and audit. They are not deleted; they are simply not promoted to a top-level historical browser in the daily workflow.
- `Work queue` is not run history. It contains only durable Vault-maintenance work that Peak cannot finish safely without an owner: a choice, a review, a guarded proposal, or recovery with a verifiable exit condition.
- `Work queue` is an action surface, not a statistics dashboard. `All`, `Needs your choice`, `Ready for review`, and `Needs recovery` are lightweight filters, not permanent result types. Proposal review sits inside `Ready for review`; ordinary successful receipts, temporary run states, and unrelated saved Projects or Chats do not become queue items.
- The product Work queue shows only the unresolved follow-up that actually exists in the current Vault. The Mock does not add an Action catalog, preview selector, second Work queue mode, or grouped card wall. Its Completed state renders the full 48-item synthetic Follow-up dataset as one continuous top-to-bottom result list. Every row keeps its situation, expected result, evidence, boundary, and primary action visible. Opening the primary action routes into one of six real interaction archetypes rather than one generic “Choose outcome” Modal: restore a saved review at its exact position; open a read-only evidence surface; review an AI operation before start and then inspect progress, actual usage, and result; make a genuine product decision; configure and run a scoped recovery or verification; or enter a user-file Proposal workspace with per-file diffs and source guards. Only genuine decisions show outcome cards. Each path renders the actual inspectable work surface—file rows and ranges, metadata or Markdown diffs, AI answer sections and citations, graph membership or coverage, parser logs, provider batches, write receipts, or verification scope/results. A result sentence plus metric chips is not sufficient. Open [`index.html#completed`](./index.html#completed) to review all 48 directly.
- Every Follow-up archetype now follows the same reading and navigation contract learned from Property review without borrowing the wrong domain actions. Completed is a one-line, three-column result list—`Follow-up / Affected / Next action`. Affected shows exactly one primary object count per row—files, notes, nodes, Communities, PDFs, Hubs, or another object the owner will actually handle. Secondary quantities stay in the task title when essential or inside the opened task; they never compete as an unlabeled second metric. Rows do not repeat family labels, provenance badges, IDs, explanatory copy, impact chips, or a separate Evidence summary. Complete evidence, impact, and write boundaries appear only after opening the task. The complete row remains the primary click target. The resumed Property workspace also uses one title region rather than a generic Modal header followed by the same task title again. Inside the task, the first summary strip answers how much work, evidence, cost, or recovery is in scope; every meaningful object group uses its complete header row for collapse/expand with Enter/Space support; controls inside a header do not collapse it. AI, read-only inspection, product decisions, recovery, verification, and Proposal work keep their own action vocabulary. Accept/Reject and bulk actions appear only when the underlying object set is genuinely independently selectable, never as a generic decoration for AI or inspection work.
- Property work uses one owner-facing maintenance task over a canonical set of independently selectable Property changes. `Batch` and `File` are interchangeable grouping projections inside one Git-style continuous diff, not nested navigation levels: Group by Batch explains why changes were proposed, while Group by File collects every change that will affect the same file—even when those changes originate in several batches. `Group by` and `Show` sit together as view controls; global Accept/Reject stays separate. Every Batch header promotes its file and change counts into dedicated metrics, while every File header promotes its change count and, when relevant, cross-batch count. Revision appears once at File-header level; individual Property rows contain only Property, current value, proposed value, and actions. Repeated evidence sentences are not printed under every change. File grouping adds only a compact source-Batch label where provenance would otherwise be lost. The complete Batch or File header row toggles collapse without changing decisions; its Accept/Reject controls remain independent. Accept/Reject exists at batch, visible file group, and individual-change levels and always updates the same underlying decision state; the active button is the row state, so the UI does not repeat `accepted` or `rejected` badges. A decision must be unmistakable without rereading the buttons: the selected control becomes solid, the whole change row gains a matching tint and left rail, the proposed value reflects accepted or rejected treatment, and the unselected opposite action recedes while remaining available. `Accept all` accepts every non-conflicting suggestion in the canonical set, while `Reject all` rejects the complete set, including conflicts; all bulk Accept actions skip conflicts. The saved example has 43 changes across 28 unique files; `Customer interview 07.md` combines `type / source / status` suggestions from three batches, and zero accepted changes are written until the final combined diff passes explicit Apply and revision verification.
- Broken links follow the same canonical-set and interchangeable-grouping principle without pretending to be Property changes. One `Broken-link maintenance` task owns every broken reference from the Scan, and every choice remains attached to the exact reference regardless of grouping. Repair choice is hierarchical: a Target choice sets the default for every matching reference; a File choice may override that default for all matching references in one file; and an individual occurrence may override both at its exact source location. Bulk selection makes a scope uniform by clearing its lower-level exceptions, while later lower-level choices create deliberate exceptions. The available actions remain domain-correct—redirect to a maintained target, create or restore the missing destination, remove link syntax while keeping visible text, or leave unresolved; ambiguous targets expose evidence-backed destinations. `Target` and `File` are interchangeable views over the same decision state, not separate work items. `All`, `Needs repair`, `Needs target`, and `Already repaired` filter one continuous list, with `All` as the default. Collapsed rows show the broken target, named impact, and next action. Expanded Target rows show the group default first, then a file list whose complete rows open a file-level choice and every exact source reference with its own choice control. File path and revision stay in hover metadata; exact line numbers and excerpts appear only after opening a file. Automatic repairs remain read-only rows in the same list with a compact verified receipt. In the review dataset, 63 broken references span 18 unique files: 21 deterministic rename or heading repairs were pre-approved in Scan Setup, applied with revision guards, re-indexed, and detector-verified; 31 references await a repair choice; and 11 references have ambiguous targets. Target, file, and exact-reference disclosures use one animated expansion contract.
- Reuse the interaction grammar, not the domain controls. Before adding another Scan item, define its canonical atom, stable identity, interchangeable projections, real action scopes, domain outcomes, suggestion-correction behavior, write boundary, and verification. Counts and CTA labels are derived live from the same canonical decision state. Natural-language `Update suggestions` may recompute every unapplied suggestion but never overwrites an owner choice; model and cost details stay in expandable receipts instead of adding another local model picker. File Property still needs cross-Batch collision handling, custom proposed values, full Property operation types, schema validation, evidence on demand, partial stale recovery, a final per-file combined diff, and Apply/Verify results. The durable rules live in [Scan maintenance review 共享规则](../../superpowers/specs/2026-08-15-vault-scan-follow-up-and-work-queue-contract.md#scan-maintenance-review-shared-rules) and the [File Property review contract](../../superpowers/specs/2026-08-15-vault-scan-follow-up-and-work-queue-contract.md#file-property-review-contract).
- The Property, Broken-link, and Community iterations also establish a state-and-copy contract, not merely a layout pattern. During review, the current owner choice outranks the current Peak suggestion, which outranks historical suggestions and evidence; after Apply and Verify, the verified result becomes the visible truth. An override or rejection must update the row, explanation headline, live counts, CTA, and final result together, while the superseded suggestion moves to history. User-facing nouns name the actual domain object—Community, Property, File, broken target, Bridge—not a vague internal `Context`. Secondary copy remains only when it distinguishes outcomes, explains evidence or uncertainty, states the write boundary, or identifies a blocker. The canonical contract now includes a cross-domain regression matrix for overrides, rejection, suggestion recomputation, projection switching, staleness, and automatic verified results; a visual change is incomplete until those scenarios pass.
- Repeatable owner decisions aggregate before they reach Completed. The nine illustrative notes with uncertain Community membership now form one `Community membership` task rather than nine singleton `Decide where this note belongs` rows. `Suggested Community` and `File` are interchangeable projections over the same note-level decisions. `Accept all / Reject all` are symmetric bulk actions for existing suggestions. A Community group and an individual note use the same inline dropdown grammar—use the suggested Community, choose another Community, or keep the note outside Communities—and both write the same note-level decision state, so a note can override its group. Dropdown options are compact one-line choices containing only the action and Community name; repeated explanatory microcopy is forbidden. Expansion is state-aware: an untouched or accepted suggestion may show `Why <suggested Community>`, but an owner override switches to `Changed to <chosen Community>` and a rejection switches to `No Community`; stale rationale for the superseded suggestion must never remain the headline. Detailed prior evidence stays available through `Open evidence in File Atlas`. Expansion never introduces evidence cards, a second choice surface, or outcome buttons. Owner guidance may recalculate every unapplied suggestion without replacing saved decisions. Saving changes only Peak-owned Community membership. Moving a file to another folder or editing Markdown, frontmatter, or Wikilinks remains a separate user-file Proposal.
- A completed scan materializes only actionable outcomes into Work queue. Successful projections are summarized on the completed scan; the immutable receipt is retained internally for comparison and debugging rather than shown as another user-facing result.
- Follow-up coverage is deliberately broader than the product filters. Durable items can originate from Peak continuation, a pending owner decision, readiness, missing or stale enrichment, structure, content quality, tags and metadata, semantic review, runtime interruption, or a guarded proposal. These sources span seven maintenance capability domains—Structure, Content, Freshness, Machine knowledge, User metadata, AI diagnosis, and Materialization—and include the 19 currently executable deterministic detectors. Source, domain, lifecycle state, and next owner action remain separate dimensions rather than one compressed taxonomy.

## Completed run

- Completion is one decision page, not four tabs named `Observed facts`, `AI insights`, `Files & enrichment`, and `Run evidence`.
- Each actionable result keeps one owner decision, one short explanation, one or two decisive facts, and the next action together. Citations and AI reasoning stay available inside the relevant review flow instead of becoming extra status chips on the completion page. A stale bridge goes directly to its bridge notes, while an import cluster goes directly to its evidence. The former standalone AI Review summary page is intentionally removed.
- Prepared file changes are first-class run outputs. A ready proposal is shown beside the finding and opens its per-file diff directly; users do not traverse a separate AI Review page to discover it.
- The completion page follows the causal order the user experienced. Its hero says the Scan finished and keeps both `48 follow-ups below` and `7 files updated by pre-approved repairs` visible. A compact, collapsed `Peak finished automatically` disclosure comes first so users can see what changed and which product surfaces now consume it. The review Mock then renders all 48 synthetic Follow-up examples as ordinary result rows in one list. Family is only a small provenance badge, not a grouping container or taxonomy. This deliberately exhaustive dataset is for owner design review; a real Scan would show only the unresolved items supported by that run's evidence.
- Successful automatic effects stay in the first collapsed disclosure for Core Search, generated Index knowledge, the Vault map, and the 21 deterministic broken-link repairs that the user authorized in Setup. Automatic file edits must show affected-file counts, revision guards, write receipts, re-indexing, and fresh detector verification. AI-inferred or ambiguous targets are never included in that automatic path; they remain reviewable proposals or target decisions. Scan counts, duration, task count, actual models, token usage, spend, and completed/stopped/skipped operation state stay in a separate collapsed `Run details` disclosure after the follow-ups. Both remain inspectable without turning the default page into another audit dashboard.
- Peak-owned visible map text is maintained separately from graph facts. When membership changes, the map can still be structurally correct while its Community descriptions, topic labels, or Hub descriptions are outdated. The completed run and Work queue therefore create one understandable `Vault map text needs review` item, split into those three visible text groups. Users review the exact wording with `Publish / Try another / Keep old`; no abstract Community-profile object and no user-file proposal are exposed.
- The automatic-effects disclosure begins immediately after the completion hero, followed by the owner decision list; there is no expanded audit table, second summary dashboard, or `View updated overview` escape action. The fixed Mock state control includes `Completed` for direct access to this screen during review.
- Each decision row shows only the decision, one explanatory sentence, a few owner-readable facts, and the next action. Internal formation chains remain in the product-model document and do not appear in the owner UI.
- Run ID, scope, check versions, citations, and low-level call receipts remain in the internal audit model. Model names, total/per-group token usage, actual cost, and partial/stopped/skipped status are owner-visible because the user authorized and paid for those AI operations; there is still no separate default `Run record` page.
- The data and interaction rationale is documented in [`activity-and-run-result-model.md`](./activity-and-run-result-model.md).

## Icon system

- Navigation and section headings are text-led; decorative icons are intentionally removed.
- Action icons are bare 14–16 px line icons.
- File and work-object icons use one neutral outlined container.
- Accent and semantic colors are reserved for selection, AI, warnings, failures, and completion—not object categories.
- Continue work rows do not guess an object icon. They use an explicit source label such as `Project`, `Composer`, `AI Graph`, `Finding`, or `Proposal`, followed by the retained-state reason and the next action.

## Overview object families

- The top inventory contains only `Files`, `Chats`, `Projects`, and `Composer`.
- Hover or keyboard focus opens a preview popover; the summary itself does not navigate or open a drawer.
- AI Graph (`.peakaigraph`) and Peak Sheet (`.peaksheet`) are file types under Files, not peer object families.
- The Files popover pairs a Vault-wide pie chart with 16 actual file formats/extensions and their exact counts; it does not substitute semantic groups for file types.
- Chats, Projects, and Composer use the same pie-plus-breakdown pattern, but each keeps its own correct dimension: Conversation Type, explicit project lifecycle state, and durable Composer activity result.
- Every popover pie is an interactive SVG rather than a decorative CSS background. Hovering or focusing a slice highlights the matching legend row, and hovering or focusing a row highlights the matching slice.
- Clicking a Files slice or legend row opens `Vault contents` with that exact file type selected. The detail page repeats the same 16-type pie, then projects the selected type onto the Vault knowledge structure below it.
- The selected type updates Community counts, bridge evidence, applicable capabilities, readiness, next actions, and an evidence-linked AI interpretation. The default page does not repeat the inventory as a long, non-actionable file-type table.
- Orthogonal work status stays outside the pie when necessary: for example, Chat pending work is not misrepresented as a Conversation Type.
- The Composer pie is aggregate evidence only and never chooses a navigation target. The popover separately exposes the one exact pending record, including its saved Composer session, Change Set, file scope, and frozen source revisions.
- Only that concrete record can show `Open saved review`. The handoff restores the existing Composer review with the saved Change Set selected; it does not create a new Composer session or infer a target from the aggregate count. Missing or stale locators remain recoverable work items in Vault Intelligence.
- Full navigation only happens from an explicit link inside a popover or a dedicated page action.
- `Vault contents` and `Activity` share one persistent, left-aligned local navigation row. Right-aligned controls are page actions only, so the entry and return target never jumps across the page; the top-level `Vault map` tab stays active in both views.

## Vault map: contents and activity

- The top-level Vault Intelligence `Overview` contains a structural preview and a separate full-width, GitHub-style one-year activity heatmap. The heatmap is deliberately long rather than compressed into the graph's side column: it answers when explicit Vault activity occurred and exposes longer rhythms across months. Selecting a recent day prepares the detailed Activity view around that day's evidence. Color means record count only—not time spent, productivity, or inferred importance. It does not introduce another map subpage.
- The Overview structural preview is a second, read-only Cytoscape projection over the same maintained community, topic, bridge-document, and resolved-link data as `Vault contents`. It is not a screenshot-within-a-card and does not introduce a second taxonomy. The summary projection hides workbench chrome, keeps only five communities, five representative topics, and three important bridge documents, fits the whole graph into a horizontal 270 px stage, and pairs it with a short evidence-grounded interpretation. Clicking its explicit action opens and focuses the full interactive graph.
- Vault map has only two sibling views: `Vault contents` and `Activity`. Structure is not a third destination because file inventory and document structure are the same Vault-wide content model.
- `Vault contents` owns actual file types and the hierarchy `Community → Topic → File`. Selecting a type changes the structural projection, capability state, explanation list, and AI interpretation below the Pie. Communities connect only through real bridge documents; there are no unexplained community-to-community lines.
- The knowledge graph is implemented with the repository's installed `cytoscape` 3.34.0 and `cytoscape-fcose` 2.2.0, not React Flow and not a hand-positioned SVG. `vault-graph-cytoscape.ts` is bundled locally into `vault-graph-cytoscape.js`, so the prototype still opens through `file://` with no CDN.
- The graph never tries to render every file at once. Its resting state is a medium-density 18-object skeleton: five communities, nine representative topics, four real bridge documents, and readable authored relationships. Clicking a Community expands that node in place, adds its remaining Topic / Hub nodes around it, and keeps the rest of the graph as spatial context; it never replaces the canvas with a hidden second graph. Expansion uses three visual levels: the selected Community and Topics stay fully legible, directly connected Bridge evidence remains at medium strength, and unrelated nodes plus edges fade into the background. Clicking the same Community again, clicking the canvas, pressing Escape, or resetting the graph collapses it.
- Relationship labels are horizontal evidence pills rather than tiny text rotated along an edge. Both projections keep only high-signal edges labelled at rest and reveal the selected neighborhood labels on hover, avoiding text collisions without hiding the underlying relationships.
- The preset is collision-checked against rendered node sizes: side communities are pulled away from the Technology hull, the RAG bridge sits below rather than on top of the `Other technical topics` node, and the graph reserves vertical space for the shared toolbar. Only the strongest authored edge labels stay visible at rest; neighboring labels return on hover.
- The Vault-wide graph reuses the four production `AtlasGraphCanvasImpl` layouts that answer useful Vault-wide questions: `Constellation` uses fCoSE clustering, `Flow →` and the arrow-only `↓` control use Dagre reference flow, and `Orbit` places Communities toward the center with Topics and bridge documents around them. Switching changes only the layout of the same graph; it preserves the file-type projection and restores an expanded Community in the new layout instead of navigating to another graph. Orbit enables the optional semantic layer, matching Vault Search behavior. Community and Folders are intentionally omitted here because the graph already represents computed Communities and this surface is not a folder browser.
- The graph toolbar otherwise follows the production `AtlasGraphCanvasImpl` order and geometry: the shared layout segmented control, `GraphSemanticToggle`, `PanelRightOpen + Nodes`, Mermaid icon, image icon, fullscreen-only zoom/Fit/Readable controls, and fullscreen icon. A production implementation must reuse the shared `Button`, `IconButton`, and `GraphSemanticToggle`; the standalone mock only reproduces that contract because it cannot import the React surface through `file://`.
- Ordinary hover gives the target and its real neighborhood the existing orange Graph highlight without washing out unrelated content. Holding Shift opens a compact local inspect card; `I` pins it, and Escape closes inspect, the Nodes list, then full screen in that order.
- There is no persistent right-hand Graph selection inspector or separate File-type context sheet. The Community summary remains directly under the graph; its right column follows the active graph selection and shows the evidence-linked interpretation. The file-type Pie controls the projection from above.
- Semantic edges are an explicit optional layer and never masquerade as authored Wikilinks. When enabled, four dashed machine-inferred relationships appear with their own similarity evidence and update the visible link count from 20 to 24.
- `Activity` is one linked workspace rather than a chart plus detached `Current focus`, `Direction change`, and Events cards. Its default `Recorded activity` mode shows timestamped File edits, Chat contexts, Composer activity, Project changes, and Peak-native revisions without asking AI to guess a topic.
- `AI work themes` is an optional, explicitly generated projection over inspectable work sessions. It exposes generated/stale state, unclassified records, a complete searchable theme picker, top-theme lanes, and an `Other N themes` aggregate rather than pretending the Vault always has four themes.
- The current illustrative sample contains 111 explicit records across 36 days. Each record is counted once. Work sessions are deterministic groupings over shared objects and nearby timestamps; AI themes label those sessions and retain citations, confidence, source revision, and generation time.
- Both date handles resize the visible period, and dragging the selected window moves it. Source/theme lanes, period totals, event sessions, theme mix, and the previous equal-period comparison update from the same selection state. The former fixed seven-day `Current focus` and arbitrary four-week-versus-seven-day `Direction change` cards are removed.
- Large activity histories should aggregate according to the visible range in production: day → week → month. The mock demonstrates the daily level and preserves exact events behind topic, range, and event-group selection.
- Structural problems appear as annotations when they change how the map should be read, while full evidence and resolution remain in Work queue. Raw changes appear only when they explain a focus or direction shift.
- The former `Peak work`, `Needs attention`, and `Recent changes` map views are removed: continuation belongs in Work queue, findings belong in Work queue and structural annotations, and uncontextualized change counts do not explain the user's work.

- Objects without a stable row anchor—such as Vault map nodes and Overview cards—open a centered modal instead.
- Deep work still hands off to its owner surface or dedicated review page; the inline detail and modal are orientation surfaces, not replacement editors.
