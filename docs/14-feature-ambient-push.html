14 · Feature · Ambient Push · 编辑时后台送来的相关笔记

你在写笔记，Ambient 在旁边找关联，只有你看它一眼时才发言。

Ambient Push 是 Peak 唯一一条 用户没点也会发生 的 AI 通路。它在你写作、切文档或手动触发时读取当前段落，去找可能相关的笔记，并把结果放在固定、可忽略的位置：

  • 当前实现：右侧 Related Notes 面板；规划形态：Obsidian 窗口内置顶的 Ambient floating panel
  • 可选的编辑器行首 ? 提示（默认关闭，只适合极少数高置信度意外邻居）
  • 规划中的面板内刷新入口，用来主动找当前段落邻居

全程 不写你的文档——它只呈现，不落笔。这份文档讲这条通路里被推的是谁、什么信号让它排到前面、怎么关掉、以及维护者应该盯什么。

这页解决什么

Ambient Push 的争议不在“有没有用”，在 “它会不会烦我”。这页把这条通路拆开：什么时候触发、拿什么去搜、候选怎么打分、结果应该落到哪个固定位置，以及怎么全关或只留一部分。

核心结论 Ambient Push 是只读 + 只呈现的通路。它不改任何笔记；只有当你按下推荐里的 Link，系统才会在当前段末尾插入 [[wikilink]]。主呈现应固定在 Related Notes / Ambient 面板里，行首 ? 只是高置信度的辅助手势，不应该靠状态栏闪动或启动弹窗打断写作。
本文读者 正在写作、不确定“右下角那个提示是谁在推”的 Obsidian 用户；打算调 trigger 阈值或加一种新 signal 的维护者；正在排障“为什么一天了都没有推荐”的 coding agent。
当前产品缺口 现有代码里真正可找的入口是 Command Palette 的 Open Related Notes panel，它打开右侧 sidebar leaf；状态栏 N related 和行首 ? 都不是主入口，默认也应保持安静。下一步需要补一个 Obsidian 窗口内置顶的 Ambient floating panel：写作时不消失，点 × 后关闭，只在 Obsidian 里悬浮，不变成系统级 always-on-top 窗口。需求登记在 Planned Requirements，低保真稿见 Ambient Floating Panel。
本文不做什么 不重复 12 Search 的语义搜索原理；不讲 23 Search Index 里 SQLite 表的建表脚本；不覆盖 13 Vault Intelligence 的 Vault Health / Extract Todos 等用户主动跑的 vault-scope 分析。Ambient 只关心 你现在这一段的邻居。
产品形态 这条能力的主界面应该是固定位置的相关笔记面板，而不是反复出现的启动卡片或状态栏提示。本文按长期形态描述：一个可见、可关闭、可停靠的推荐面。

固定呈现通路

Ambient 计算得到的候选笔记应该先进入一个固定面板。用户想看的时候它一直在那里；用户不想看的时候，它不弹窗、不闪动、不抢编辑器焦点。当前实现是右侧 Related Notes leaf；更贴近写作场景的下一步是 Obsidian 窗口内置顶的 floating panel。

悬浮面板规划

可以做成“只悬在 Obsidian 里面”的窗口：实现上是 Obsidian 主窗口 DOM 内的 overlay / workspace companion surface，不是 macOS/Windows 的系统级 always-on-top。这样用户在 Obsidian 里写作时它不消失；切到别的应用时它不会盖住别的窗口。

需求设计约束为什么
Obsidian 内置顶 绑定在当前 Obsidian window / workspace root，不使用 OS-level always-on-top。 保持写作上下文，但不污染其它应用窗口。
可关闭、可重新打开 面板右上角有 ×；关闭只隐藏 UI，不停 runtime。Command Palette / Copilot 后续可以重新打开。 用户要有明确控制权，不要变成甩不掉的通知。
刷新入口可见 header 放 Refresh / Find related；调用 runtime 的 manual trigger。 解决“我想主动触发，但找不到入口”。
替代右下角提示 状态栏 N related 不作为主成功路径；最多保留为高级设置里的兼容开关。 右下角短文本不可解释、不可展开，也不适合承载推荐。
低保真稿 详细线框图和验收点放在 Ambient Floating Panel。这仍是规划需求，不代表当前版本已经实现。

什么时候会跑

Runtime 在 三种情况 下会触发一次搜索。每种都有 cooldown 保护，不会连续开火。

触发判定
canRun = enabled && contextReady && triggerCooldownPassed && triggerSpecificCondition
  1. writing_pause：停止输入超过 writingPauseMs，且当前段落新增字符数 ≥ minCharDelta。
  2. doc_switch：活动文件变化，且距离上次 doc switch 搜索超过 docSwitchCooldownMs。
  3. manual：用户主动刷新，不受普通 cooldown 限制，但仍需要当前 editor/context 可读。
  4. 段落过短、没有活动文件、索引不可用时直接跳过；这是安静策略，不是故障。
Trigger触发条件默认阈值用意
writing_pause 你停止敲键盘且当前段落字符增量足够 writingPauseMs = 5000ms；minCharDelta = 30 字符 写完一段就查一下有没有可以引的笔记，不打扰下一段思考。
doc_switch 切换到新文件 docSwitchCooldownMs = 5000ms 冷却 打开一篇旧笔记时提醒“这块内容你近期也写过”。
manual Runtime 支持手动触发；当前缺清晰 UI。规划入口是 floating panel / Related Notes header 的 Refresh。 无 cooldown 逃生舱：任何情况下都能强触发一次。
Cooldown 是 trigger 级别，不是 UI 级别 两次搜索最短间隔 triggerCooldownMs = 30s。这意味着：写作时你连续停顿两次，第二次并不会真的搜。这是刻意的，避免连续 push 造成阅读疲劳。想更激进？调低 triggerCooldownMs；想更安静？调到 5 分钟以上，几乎只在切文档时才有 push。

触发之后 Runtime 会从当前编辑器抽出一份 AmbientContext：当前段落 + 光标所在标题 + 文档标题 / 标签 / 已有 outlinks + 最近编辑增量。段落长度 < 10 字符会被 handleTrigger 直接跳过——不搜太短的东西。

currentParagraph
光标所在的段落原文；用于关键词 + 嵌入检索。
cursorSection
光标当前所在的 ## 标题路径；用于给结果排序时对齐主题。
documentTitle / Tags / Headings
整篇上下文摘要，用于图查询和 hub_member 信号判定。
existingOutlinks
已经在本文档里出现过的 [[wikilink]]；会被从候选里剔除，避免推“你早就链过的”。
recentEditDelta / editSessionDuration
最近编辑增量与本次写作持续时长；供未来的模式学习使用（当前排序主要看信号而非会话长度）。

候选怎么上榜

从 vault 检索到的候选笔记会同时挂上一到多种 AmbientSignal。Runtime 用信号强度打分，最终排序 + 只留 maxPushItems 条（默认 5）。同一个 AmbientPushItem 通常带 2-3 个信号，展示时选 优先级最高 的那个渲染成人话解释。

信号意味着什么数据来源展示例
shared_tag 那篇笔记和当前文档共享至少一个 tag vault 索引；mobius_node.tags “共享标签 #research”
graph_neighbor
hop=1/2		 在语义/结构图上距离 1 或 2 跳 graph traversal port（mobius_edge） “图上一跳的邻居”
co_citation 存在第三方笔记同时引了当前笔记与这篇候选 反向索引 + 图查询 “A.md 同时引用了它和当前文档”
hub_member 候选是当前文档所在结构 hub 的一员 Vault Intelligence 的 hub 识别 “同属 hub Reading queue”
text_overlap 候选与当前段落在 chunk-level 有强关键词/嵌入重合 SearchClient hybrid 检索 “主题很近：attention · self-supervised”
recency 近期编辑过；作为 boost 附加 vault mtime “3 天前刚改过”
排序公式
score = baseSearchScore + Σ signalStrength × signalWeight + patternBoost + recencyBoost
  1. baseSearchScore 来自当前段落的关键词 / embedding 检索。
  2. signalStrength 来自 shared tag、graph neighbor、co-citation、hub member、text overlap 等信号。
  3. patternBoost 只来自用户历史 co-open 行为；它不是 LLM 判断。
  4. 同一个候选可以带多个 signal；展示时选择优先级最高、最容易解释的一条。

除了这 6 种基础信号，还有两条 后处理 会调整最终排序：

Pattern boost：从你的 co-open 历史学出的加分 PatternLearningService 每 10 分钟聚一次 ambient_push_action 表里最近 30 天的行为，找出 “打开 A 之后 < 10 分钟又打开了 B” 重复出现 ≥ 2 次的 pair。当 A 是当前文档、B 是候选时，PatternLearner.getPatternBoost 给候选一个 0 - 0.4 的加分。这就是所谓“学到你的习惯”：不是你手动配置，也不是 embedding，是纯经验统计。
关掉：Settings → Ambient Push → feedbackLearning。
Serendipity：图上远但嵌入近，塞给你一个惊喜 SerendipitySearcher 做的是 2-hop 图遍历 + 嵌入距离 < 阈值，找出 “语义上很像但没被链过” 的候选，最多注入 1 条到最终列表。它是 行首 ? 提示 提示的直接来源；如果 enableSerendipityGutter 关掉，仍然可能进入状态栏 top 1。这种候选往往和当前段主题只沾一点边，用来打破“同温层”。

候选来源

Ambient 的主候选来自当前段落邻居，不来自启动弹窗。下面这些来源只说明候选从哪来，不代表一定要把它们做成单独 UI。

Unresolved Connections
被多人引用（doc_incoming_cnt ≥ 2）但自己 outgoing 很少（< incoming × 0.5）的笔记——说明它是个 话题磁铁，但还没被主动延展。
Changed Hubs
hub 类文档（Vault Intelligence 已识别）在过去 14 天被编辑过：“你有个中心节点又动了，想重新翻看一下吗”。
Decaying Engagement
PageRank 高但 last_open_ts 距今 > 14 天：“这些一直很重要的笔记，你有阵子没看了”。

每类最多返回 5 条候选，最终按 score 降序合并。BriefingItemBuilder 负责三类的分类策略；SqliteAmbientBriefingReadAdapter 只做 SQL 抽取，不判定归属。

不要把候选来源等同于通知形式 PageRank 高、长期未打开、hub 变化这些信号可以进入固定面板的候选解释，但不需要包装成一个每次启动都出现的卡片。用户要的是持续可见的相关笔记面板，不是打开 Obsidian 时再处理一张新任务。

会不会打扰我 / 会不会改文档

用户对 Ambient Push 的两大疑问：“它会不会一直在角落弹东西”、“它会不会在我不知情时写笔记”。答案是两个都不会——但值得逐条说清楚。

担心的事情实际行为控制手段
面板一直占空间 主通路是固定面板；用户可以把它收起、停靠到右侧，或拆到独立 leaf。 隐藏 Ambient view，或关闭 enabled。
行首 ? 老是跳出来 只在 serendipity 候选存在时才亮；不出现在每一行。 enableSerendipityGutter: false。
启动时弹窗打断我 长期形态不依赖启动卡片。相关候选应该进入固定面板，不作为每次打开 Obsidian 的待处理任务。 关闭旧启动卡片入口；保留固定面板。
它会不会写我的笔记 不会。runtime 只调 projection 与 persistence 端口；前者写 Zustand store，后者写自己的 ambient_push_log / ambient_push_action 表；vault 文件从头到尾没有 write path。 ——
它是不是暗中调 LLM 花我的 token 默认 不调。enableLlmExplanation 打开后才走 tier-2 micro-explanation：在 top 1 出现时 非阻塞 请一句话解释，冷却 llmExplanationCooldownMs = 120s。 enableLlmExplanation: false（默认）。
它会不会把我在写的段落传给 LLM 只有当 enableLlmExplanation: true 时，才会把 currentParagraph + 候选标题 + 候选 excerpt 发给 Chat role 配置里的 provider。关掉就完全不出你的机器。 ——
“完全不弹” 是通过 enabled: false 达到的 设置里的顶层 enabled 关掉后，composeAmbientRuntime 那一步就会跳过——runtime 干脆不启动，也不订阅任何事件。这是最彻底的关掉方式；只隐藏 UI 只是不呈现，runtime 仍可能写 SQLite 的 push log，占用一点 CPU / disk。

关掉它 / 只留一部分

下面这张是常见组合的“食谱”——对应到 04 · 配置项与用户视图 里的 Ambient Push 段落。

“我只想要固定面板，不要行首提示” enabled: true，隐藏/关闭行首 ? 提示，保留 Related Notes / Ambient 面板。这样结果持续可见，但不会在编辑器正文旁边闪出提示。
“我要行首的意外发现，但不要其它提示” 保留行首 ?，隐藏固定面板的常驻区域。注意：serendipity 只在 2-hop 有远近似候选时才有产出——如果 vault 还没建好语义边（04 · Knowledge Index 处于 Fast 深度），行首提示会很少出现。
“我要每一次 push 都给我一句 AI 的解释” enableLlmExplanation: true + 把 llmExplanationCooldownMs 调到很短（例如 10s）。代价：每 top 1 一次 LLM 请求，累积 token 消费；在 12 Search 的 Model role 里被计到 chat.role 上，Usage Dashboard 会看到。
“完全静音” 顶层 enabled: false。Runtime 不会被 composeAmbientRuntime 起起来，也不会 occupy event bus。想再打开：改设置后需要重启插件（重新走 onload()）。

为什么 handleTrigger 用 AbortController 触发很密（用户可能在 5s 内切两次文档），后到的触发要 放弃 前一次的搜索结果——否则会有“上上一次的 push 覆盖上一次”的抖动。每次进入 handleTrigger 都新建一个 AbortController，前一次持有的 pendingSearch 立即 abort()。这不是网络优化，是 UI 一致性。

技术附录 · 写进 SQLite 的两张表

Ambient 自己拥有两张表；其余读取都是从 23 Search Index 的 mobius_node / mobius_edge / embedding 取。

ambient_push_log — 每一次 push 的原始记录

Fire-and-forget 写入。用来供 17 Usage Dashboard 与 Pattern learning 反溯。

timestamp
push 时的 monotonic 时间戳。
triggerType
writing_pause | doc_switch | manual。
sourceFilePath
被 push 的文档（你正在写的那篇）。
contextParagraph
被搜的当前段（用于事后 debug / 优化 signal 时看命中原因）。
pushedFilePath / pushedScore
推荐的候选与它的排序分。
explanationType / explanationText
template（RelevanceExplainer 生成）或 llm（tier-2 micro-explanation）。

ambient_push_action — 你有没有点进去

走 runtime.recordAction()。用来给 Pattern learning 提供正样本 / 负样本，并让后续 push 的排序偏向你真的会点开的候选。

sourceFilePath / pushedFilePath
成对的“你在这篇上被推了那篇”。
action
opened | linked | dismissed | ignored；opened 与 linked 是正样本，dismissed 与 ignored 是负样本。
actionTs
动作时间；Pattern learning 只统计 30 天内的记录。
为什么 push_log 和 push_action 分两张表 Push 每次触发都写 log（可能一次 5 条），几乎不查。Action 只在用户真的点了推荐时才写，读频繁（Pattern learning 每 10 分钟聚一次）。分表让写频繁的那张 不带索引 / 只 append，读频繁的那张 加 index 优先按 sourceFilePath 查。schema 本身在 23 Search Index 的建表段。

当前思考线索

Ambient 的长期形态应该固定在 Related Notes / 当前思考线索这类可停留的面板里：一面显示“跟当前笔记语义相关的其他笔记”，另一面显示“你现在正在思考的问题”。后者由 SessionContextService.workingTheme.llmInferred 承载。

数据源

WorkingThemeInferrer（src/service/context/WorkingThemeInferrer.ts）读最近 20 条 ActivityEntry（编辑 / chat / 搜索 / 打开笔记），30s 防抖 + 10 次活动阈值触发一次 LLM 推断，产出 { summary, relatedFiles, updatedAt }。UI 层只消费这个结果，不重新推断用户正在想什么。

显示优先级

条件面板显示
llmInferred.summary 非空显示 thinking summary；展开后可看 relatedFiles。
无 summary，AmbientPushStore 有 items显示相关笔记列表。
无 summary 也无 items保持安静空态，不闪烁提醒。

刷新可以由定时与 store 事件共同驱动，但 UI 不应该用状态栏闪烁来抢注意力；它应该是一块稳定的、用户愿意一直开着的侧栏区域。

避免把 Ambient 做成通知系统 Related Notes 面板可以长期存在；gutter 只适合极少数高置信度提示；Morning Briefing 不应变成每次打开都弹出的例行卡片。Ambient 的原则是可见、可忽略、可停留，而不是不断打断。

失败与降级

当 Ambient 一整天都没给你任何推荐时，八成是下面这几种情况之一——诊断顺序按“可能性”排。

顶层 enabled 关了 → runtime 根本没起。 症状：Command Palette 里搜不到 Open Related Notes panel，或打开后一直没有任何候选。修：Settings → Ambient Push → Enable；如果只是状态栏没有 peak-ambient-status，不一定是故障，因为状态栏默认不作为主入口。
Vault 尚未被索引 → search 返回空。 症状：runtime 起了，但每次触发 handleTrigger 都最终走到 items.length === 0。SearchClient 需要 vault SQLite 里有 chunk + embedding。修：04 · Knowledge Index 切到 semantic/full 档并等索引跑完。Fast 档缺 embedding，语义信号全空。
段落太短 → 被 currentParagraph.length < 10 挡住。 症状：写单行笔记时永远没 push。修：写完一个完整句子（含标点）通常就够。
Cooldown 未到 → 触发但不搜。 症状：明明感觉“我停了很久”仍无推荐。triggerCooldownMs 30s 是最短间隔；30s 内两次 writing_pause 只有第一次真会跑。
Existing outlinks 把所有候选 filter 光了。 症状：候选表很小的段落（例如你正在写“笔记学习目录”）——因为候选早就被链过，剔除后一个不剩。修：改到写正文段试试。
LLM explanation 慢 / 拒绝 → tier-2 静默失败。 症状：状态栏和 push 都在，但一直用 template 解释（“共享标签 #xxx” 这种），从没出现过流畅的一句 AI 解释。LlmAmbientExplanationAdapter 是 非阻塞 的，失败时静默——不会打扰你，但也没有明显提示。诊断：devtools 里看 LlmAmbientExplanationAdapter 相关 error。
旧启动卡片入口没有出现。 把它当兼容入口排查即可，不要把它作为 Ambient 的主成功标准。主路径应该看固定面板是否有候选、候选是否能打开、信号解释是否合理。
Pattern boost 依赖 你之前用过 Ambient PatternLearner.getPatternBoost 只有在 ambient_push_action 里累积了 ≥ 2 次相同 pair 才会给分。新装的插件 / 一直关着 Ambient 的用户不会有 pattern boost，排序完全依赖基础信号。这不是 bug，是学习类特性的启动成本。
