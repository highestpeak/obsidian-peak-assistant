先理解用户场景

用户在 Obsidian 里问 AI 时，通常不是在问一个孤立问题。他可能刚上传了一份 PDF，正在某个项目 folder 里整理笔记，前面已经聊了十几轮，还打开了 web search 或 vault search 开关。

所以 Chat 的产品价值不是“把最后一句话发给模型”。真正的价值是把这次回答需要的工作现场组装出来：

  • 当前用户消息
  • 最近会话
  • 附件引用
  • 会话级 prompt
  • focus folder
  • recent activity / activity-index
  • 模型能力
  • 输出控制
  • 内部执行策略

这个组装过程就是本文的主线。

一句话结论 Chat 回答 = 用户消息 + conversation state + resource handling + ChatProfile slots + budget governance + provider streaming。任何改动如果绕过这条路径，都容易制造第二套 prompt 系统。

Chat 由哪些能力组成

Chat 是 Obsidian 里的工作区能力，不是一块孤立网页聊天框。主聊天视图和 Chat Studio 只是两个入口；真正影响回答质量的是会话、资源、上下文和能力开关如何一起进入请求。

入口 surface Open Peak Assistant 打开主聊天视图；Open Chat Studio 打开三栏工作区。它们是不同阅读/操作布局，不是两套 Chat 能力。
会话记忆 同一个 conversation 里的最近消息会进入 context stack。上下文过大时，旧内容会被压缩。
资源和附件 composer 上传或引用的文件会转成 resource ref；非 direct 模式会先走摘要或文本降级。
Vault / Web 能力 能力开关和 profile 决定系统能不能使用 Vault Search、Web Search 或其他工具；用户不应该先理解内部 mode 分支。
focus folder focus folder 是回答偏好和搜索范围提示，不是数据库层硬过滤。
输出约定 Chat 可以输出普通回答，也可以生成图、数据视图、代码块或可保存的结构化内容；具体能力由系统 prompt 和 renderer 支持决定。
使用时的判断 继续追问就留在同一个 conversation；需要材料就附文件或明确引用；需要查库或查网页就打开对应能力；需要计划就直接说“先给计划”。不要把这些都理解成同级入口。

Chat Studio UI/UX：独立阅读

左栏项目、项目内会话、独立会话、搜索、刷新、收起与右键管理；以及它如何改变当前选择。
中栏Home / 项目页 / 列表 / 当前会话的状态切换，消息、流式运行、附件、Composer 和消息级操作。

Chat Studio：当前三栏不是三个子产品

Chat Studio 是一个单独的三栏 React 工作面，不是 Obsidian 左、中、右三个独立 leaf 的并排版。它把同一份 chatDataStore 和 chatViewStore 同时交给三栏：左栏改变选中对象，中栏读取并编辑这段会话，右栏从中栏的消息重新推导索引。

正确的心智模型 左栏管理“我在什么项目 / 哪段会话里”；中栏管理“现在该看哪一种 Chat 页面，以及怎么继续工作”；右栏管理“当前这段会话里有哪些可回看的线索”。它们不是三个独立页面，也没有三份会话数据。

左栏：项目树和会话历史放在同一个入口

挂载时的准备 加载项目与全局会话，按创建时间倒序放进共享 store；没有 active conversation 时，会把最新一段设为当前选择。这个选择会决定中栏和右栏第一次看到什么。
顶端操作 Studio 传入的是非 compact 版本，因此当前会显示产品标识、Home、刷新、收起全部项目，以及单独一行“Find chat or project”搜索。搜索只在这个栏内过滤项目名与会话名，不是全局 Vault 搜索。
项目路径 展开项目会加载该项目的会话；项目行可打开项目概览，项目内有“New conversation”和“See more”。项目与项目内会话都有重命名 / 删除等右键管理入口。
独立会话路径 不属于项目的会话和项目内会话都能成为 active conversation。点选会话后，导航层会切到对应会话模式；改名、打开源 Markdown、删除等动作在会话菜单里完成。

中栏：ChatView 的六种阅读状态

Studio 的中心不是“永远显示聊天”。它复用完整的 ChatViewComponent 路由，所以同一块中心区域会替换成以下状态；这决定了为什么用户在 Studio 里有时会感觉自己从聊天跳进了一个首页或列表。

Home继续最近会话、总结笔记、研究主题、最近会话和项目入口。
All projects / conversations完整项目或会话列表，作为浏览与挑选页面。
Project overview查看一个项目的范围，并从项目上下文继续工作。
Project conversations当项目内会话超出侧栏的有限展示时，展开为中心列表。
Pending conversation“Start a new conversation”提示和居中的 Composer；不再先让用户挑 Chat / Agent / Plan。
Active conversation标题、可滚动消息、转项目建议和底部 Composer；这是通常被理解为“聊天页”的状态。

中栏当前会话：一条消息链上已经有的能力

Header展示会话标题；有源 Markdown 时可打开源文件；可请求重生成会话标题。删除没有放在 header，而是通过左栏会话的右键菜单处理。
消息与滚动切换会话时把 active conversation 的 messages 同步到消息 store，进入时滚到底；流式文本、reasoning 和工具调用会驱动自动滚动。消息按日期插入分隔线。
用户消息支持 Markdown 渲染、时间信息、资源附件簇和发送状态。附件不是独立右栏文件库，而是挂在产生它的消息上。
助手消息支持富 Markdown / 代码、流式输出、reasoning 折叠内容、工具调用摘要，以及模型、工具数、token 数和耗时等元信息。最后一条正常回答可带 capability suggestion 和建议追问。
消息级操作复制、重新生成、收藏、从此消息分支；还能复制 trace。More 菜单可查看 raw JSON、复制 Markdown / JSON、保存到 Vault、在消息下方直接追问。保存默认写入 Peak Chat Saves（可由文案配置覆盖）。
转项目建议当一段独立对话具有持续工作的形态时，中栏会给出把它归入项目的建议；这是把临时聊天转成有组织工作空间的桥。

Composer：输入、附件和运行配置

输入与提交文字输入和附件由 PromptInput 统一管理。发送开始时清空本轮文字和附件；有文字才出现发送按钮，流式时发送位变为停止按钮，并显示 “Planning and writing…” 状态。
附件入口底部左侧的 + 打开文件选择器。没有第二个纸夹、第二个上下文按钮或重复的搜索开关；它们被有意收进一个入口或 Run chip。
Run chip显示当前模型（或 Auto）与当前 context tag 数。弹层包含 role、模型路由摘要，以及 Vault Search / Web Search 两个实际可切换的上下文开关。
可见但不应误读的元素role 目前只在 Composer 本地显示，尚未传入消息 dispatch；弹层里的模型项也是当前路由摘要，不是模型选择器；麦克风按钮始终禁用。这三者不能被写成“已经影响本轮回答”的能力。

右栏：会话检索与产物回跳

Overview按相邻且同名的 message.topic 把消息折成可开合 topic；没有 topic 的消息保留在时间线。topic 内把消息和同一位置的 artifact 交错展示，点任一行都会平滑滚到中栏原消息。
Artifacts按 Images、Diagrams、Files、Code 分组。它从消息的 resources 和 Markdown fence 中即时推导；这是一份会话索引，不是另建的持久产物仓库。
局部搜索搜索范围只是当前内存里的时间线或 artifact 名：Overview 匹配 topic / 消息正文，Artifacts 匹配名称。它不搜索其它会话，也不搜索整个 Vault。
信息边界artifact 行的点击行为是“定位产生它的消息”，而不是直接打开、预览或管理该文件。代码块也会被列为 artifact，因此右栏的“产物”含义比用户直觉更宽。

三栏怎样完成一轮工作

下面的流程写的是当前实现的真实联动，不是理想化的产品流程。每一步都能解释一个可见变化来自哪里。

打开 Studio
Command: Open Chat Studio→复用现有 Chat leaf 或创建 tab→卸下旧项目栏 / 旧会话索引 leaf→尝试移入独立窗口；失败则留在 tab
切换工作对象
左栏点击项目或会话→更新 active project / conversation 并发出 selection event→中栏读取会话、选择 viewMode、同步 messages→右栏从新的 messages 重建 timeline 与 artifacts
继续一段对话
输入文字 / 加附件→Run chip 选择实际启用的 Vault / Web context→submit 把本轮交给聊天流→中栏显示 reasoning、工具和文本流→保存消息后右栏可回跳
把结果带走
消息级 Copy / Regenerate / Star / Branch→More 中可保存为 Markdown 到 Vault→建议追问直接复用同一会话 submit

关键边界：右栏不向中栏写入新的 Chat 内容；它只有“定位”能力。左栏不渲染会话正文；它只决定当前工作对象。中栏才是请求、流式、持久化和最终用户操作的主面。

当前 UX 负担：为什么三栏仍会显得复杂

这不是下一版的设计方案，而是当前 UI 里已经存在、会影响用户判断的事实清单。后续改中栏时，应先以这些边界为准，不要只替换颜色、圆角或图标。

品牌层重复Studio 本身已经是独立 Chat 工作面，但左栏使用非 compact 的 ProjectList，因此仍显示 “Peak Assistant” 标识、图标和工具栏。用户在进入一段会话之前先看到产品身份与导航控制，而不是当前工作对象。
两种导航语义混在一栏Projects 是长期工作容器，Conversations 是一次次对话；它们共用搜索、排序与选中态，却没有显式说明“当前在按项目浏览”还是“在找一段独立历史”。项目展开又会引入第二层会话列表。
中栏不是单一 chat thread同一块中心区域在 Home、项目概览、列表、新会话、当前对话间切换。功能上完整，但阅读任务会突然变化：用户以为自己在“聊天”，实际有时进入的是浏览器、项目页或空状态。
运行控件有真有假Vault / Web Search 是真实开关；role 只改变本地视觉选择，模型项只显示当前路由，麦克风禁用。把它们同时放在 Run chip 会让用户难以判断哪些动作会改变这次请求。
右栏“Artifacts”并不等于文件成果它会把附件、图片、图、文件和代码 fence 全部列出，点击只回跳到消息。用户可能以为这里是可管理的输出库，实际它是“从消息中抽出的导航索引”。
空间偏好不持久左右栏宽度可拖，但关闭 / 重新挂载后回到默认值；Studio popout 也会因平台能力不同而回退。这意味着布局本身目前不是用户可长期定制的工作环境。
后续 UI 设计应先回答的一个问题 Studio 的主对象到底是“会话线程”、还是“项目中的 AI 工作台”？现在两种模型同时存在：左栏偏项目容器，右栏偏线程回忆，中栏则在两者之间切换。只有先确定中栏服务哪一种主对象，三栏才能真正收敛。

用户能感知到的行为

如果用户不看代码，他会感受到的是一组连续行为，而不是一堆内部开关。

继续追问能接上 最近会话会被带入本轮请求；太长时会压缩旧内容，不承诺逐字保留所有历史。
附件会变成线索 上传或引用文件后，Chat 会把资源引用和摘要放进上下文，而不是把所有文件原文粗暴塞进 prompt。
focus folder 会改变偏好 回答会优先考虑这个 folder 的材料和搜索范围；它是强提示，不是硬过滤。
最近活动能提示工作状态 活动索引会记录最近打开文件、搜索和相关操作，让模型知道用户刚才在做什么。
能力开关决定能不能调用工具 Vault / Web / MCP 等能力要同时满足 profile、模型能力和权限，才可能进入工具调用路径。

上下文堆叠：模型回答前到底看到了什么

Chat context 不是一段大字符串，而是一摞有顺序的 slot。越靠近底部，越接近用户当前输入；越靠上，越像补充线索。

图 1 · Chat context stack slot stack
provider request最终发给模型的 messages
resource-index附件、资源摘要、资源引用 · optional · 300 tokens
prev-analysis上一轮分析结果或长期任务线索 · optional · 600 tokens
user-profile用户画像和偏好 · optional · 400 tokens
activity-index最近打开、搜索、操作记录 · optional · 200 tokens
conv-summary旧对话压缩摘要 · optional · 800 tokens
working-contextfocus folder、当前文件、工作现场 · optional · 500 tokens
recent-messages最近会话轮次 · required · maxRecentMessages 20
system-prompt角色、能力开关、custom prompt、focus folder · required · 1500 tokens

读图：required slot 不会被 drop；optional slot 会按预算被压缩或丢弃。新增上下文应该进入这一摞，而不是绕开 pipeline 直接拼到 provider message 里。

requiredsystem-prompt 和 recent-messages 是主干：它们定义角色、能力、当前会话和最近追问。
work stateworking-context 与 activity-index 负责让模型知道用户当前在哪里、刚才做过什么。
retrievable contextresource-index、prev-analysis、conv-summary 留线索，不把所有原文都塞进本轮。
budget ruleChatProfile.slots 决定顺序、required、priority、maxTokens 和 maxCompressionLevel。

一次请求的代码路径

一次请求分两段：先把用户消息、附件和 context stack 准备好，再按执行策略决定是否带工具、是否加 planning prompt，最后交给 provider stream。具体文件入口放在文末“代码证据”。

上下文太大时会怎样

ChatProfile 的总预算是 auto。实际预算由模型上下文窗口决定：maxCtx - 8192 - 5%。在这个预算内，系统先处理每个 slot 自己的上限，再压缩低优先级 non-required slot，最后才 drop。

压缩不等于永久丢失 好的 compact 结果应该保留“压缩了什么、哪些原文可重新取回”的线索。旧消息可以被变成摘要，附件和 Vault 内容可以只留下引用；后续如果 agent 需要细节，再通过 Search、resource loader 或上下文工具取回原文。这比简单丢弃更符合长期方向。

辅助上下文可牺牲 resource、prev-analysis、activity-index 这类 optional slot 会先压缩，仍超预算才 drop。

执行策略：少让用户选模式

产品心智应该是一套 Chat：用户表达意图，系统根据能力、权限和当前请求选择执行策略。

当前诚实状态 代码里仍有历史兼容分支：agent 路径会注入 tools；/plan 这类单次 planning intent 会追加 planning prompt。文档记录这个事实，是为了维护者读代码时不迷路，不是把 Chat / Agent / Plan 当成三个长期并列产品模式。
  • 共享边界：所有路径都先准备同一套 context。
  • 工具边界：只有满足模型能力、profile、开关和权限时才带 tools。
  • 计划边界：planning 是单次意图，不应该要求用户维护一个长期“Plan mode”。

富生成：结构化输出能力

富生成不是“只支持 Mermaid 和 Bases”。它的核心是：Chat 可以按约定生成可渲染、可复制、可保存的结构化结果。

Mermaid 图 适合让 Chat 把 Vault 里的概念关系、流程或依赖画出来。只有上下文里明确出现的笔记，才应该加可点击 wikilink。
Obsidian Bases 适合输出 .base 文件源码，让用户复制到 Obsidian 后交给原生 Bases 引擎渲染。Chat 视图本身不预览 Bases。
后续可扩展项 同一框架可以继续容纳表格、任务列表、canvas、dataview-like 查询、导出文件或 agent 产物。新增类型时，先定义输出约定、渲染/保存方式和失败时的降级文本。
边界 模型可以生成结构化内容，但不能凭空声称某个 vault note 存在。任何 click-through、文件引用或资源链接，都应该来自当前上下文或工具返回结果。

调研与验收入口：2026-07-01 rich-generation in Chat；Chat Studio 能力测试清单记录已上线、部分接入与尚未接入能力。

Bad cases：回答不像你预期时

忘了很久以前的内容 原因通常是上下文超过预算，旧消息被压缩。处理方式：把关键事实重新说明一次，或把重要材料作为当前附件/当前消息引用。
附件没有被完整理解 原因通常是附件处理模式不是 direct，或资源摘要失败/过短。处理方式：切换 direct / degrade_to_text 策略，或把关键段落贴进当前消息。
Web Search 没有参与 原因通常是没有 Web Search profile，或工具注入条件没满足。处理方式：配置 profile，打开 web search 开关，并确认当前请求允许工具调用。
Focus folder 没有像硬过滤一样生效 原因是 focus folder 是 system prompt 偏好，不是 Search 层强制过滤。处理方式：在用户消息里明确“只使用这个 folder”，或后续补硬 scope 设计。

维护规则：不要重开一条 prompt 小系统

不要这样做应该怎么做原因
在 UI store 里拼完整 prompt。 通过 app/service port 传状态，让 SystemPromptSlot 或新 slot 处理。 当前系统已经用 ChatRuntimeStatePort 把 UI toggles 从 service 里隔离出来。
把新上下文直接塞进 recent messages。 新增 slot，并定义预算、压缩、render 规则。 slot 才能被 BudgetGovernor 治理。
看到注册过某个 slot 就说它已启用。 以 ChatProfile.slots 为准。 注册表只是可用组件；profile 决定当前 prompt 组成。
把 agent 工具逻辑塞进 context pipeline。 context 只准备模型该看的信息；工具由 mode 分支和 Harness/ToolDef 处理。 上下文装配和工具授权是两条边界，混在一起会变成双系统。
