11 · Feature · Chat Context

Chat 的关键不是“模型更聪明”，而是每次回答前给它看什么。

面向用户，这份文档解释 Peak Assistant 的 Chat 为什么能带着当前会话、附件、focus folder 和能力开关一起回答。面向维护者，它把一次请求如何进入 context pipeline、哪些 slot 真正启用、预算如何压缩讲清楚。

先理解用户场景

用户在 Obsidian 里问 AI 时，通常不是在问一个孤立问题。他可能刚上传了一份 PDF，正在某个项目 folder 里整理笔记，前面已经聊了十几轮，还打开了 web search 或 vault search 开关。

所以 Chat 的产品价值不是“把最后一句话发给模型”。真正的价值是把这次回答需要的工作现场组装出来——八项一起：

  • 当前用户消息
  • 最近会话
  • 附件引用
  • 会话级 prompt
  • focus folder
  • 模型能力
  • 输出控制
  • 模式差异（Chat / Agent）

这个组装过程就是本文的主线。

一句话结论 Chat 回答 = 用户消息 + conversation state + resource handling + ChatProfile slots + budget governance + provider streaming。任何改动如果绕过这条路径，都容易制造第二套 prompt 系统。

本文读者、目标和不做什么

对象读完应该知道什么不需要在这里解决什么
Obsidian 用户 Chat 会参考哪些信息；什么时候旧消息会被压缩；附件和 focus folder 对回答有什么影响。 不需要理解每个 TypeScript class 的实现。
维护者 一次 chat request 的主路径、当前启用的 slots、预算治理和 mode 分支。 不在这里设计新的 agent harness；多步 agent 见 21。
Coding agent 新增上下文应该加 slot，不应该在 UI 或 provider adapter 里临时拼 prompt。 不把 22 Context Pipeline 的独立基础设施文档提前写完。

入口和结果

Chat 是 Obsidian 里的工作区能力，不是孤立网页聊天框。这里说明入口、需要条件和每个入口会带来的结果。

你想做什么从哪里开始需要条件预期结果
打开主聊天视图 左侧 ribbon 的 Open Peak Assistant 图标。 至少有可用的 chat profile / provider。 打开 Peak Assistant chat view，可以选择项目、会话并输入消息。
打开三栏聊天工作区 Obsidian Command Palette → Open Chat Studio。 适合同时看会话列表、当前聊天和索引/产物。 打开 Chat Studio 视图。
让 Chat 使用 Vault / Web 线索 在 Chat 运行设置或能力开关里启用对应能力。 Vault Search 需要索引可用；Web Search 需要配置 Web Search profile。 系统 prompt 会包含 capability 状态；agent mode 才会注入可用工具。
附加文件 使用 composer 的 attachment 入口。 附件处理模式可能是 direct 或 degrade_to_text。 附件进入本轮消息资源；非 direct 模式会先生成或读取摘要。

常见任务和预期结果

任务怎么做成功时应该看到什么注意
继续追问同一件事 留在同一个 conversation 里输入下一条消息。 回答会承接最近对话，而不是只看最后一句。 很长的历史会被预算治理压缩。
让回答围绕某个 folder 在会话支持的 focus folder 控制里设置 folder。 回答会更偏向该 folder 的材料，搜索指令也会默认提到这个范围。 这是模型偏好，不是硬过滤。
让 AI 先给计划 直接说明“先给计划，不要执行”。 回答更偏计划说明；默认不注入 tools。 内部可以映射到 planning prompt，但用户不需要理解一个单独 mode。
让 AI 调用工具 说明目标，并打开需要的 Vault / Web / MCP 能力。 如果模型、权限和开关允许，stream 中可能出现工具调用。 内部执行策略应由能力和意图共同决定，不应逼用户理解所有分支。

用户能感知到的行为

如果用户不看代码，他会感受到四件事：Chat 会记住最近对话；附件会变成上下文线索；focus folder 会改变回答偏好；模式切换会改变工具能力。

Conversation memory

继续追问时，最近几轮会被带上

RecentMessagesSlot 从当前 conversation messages 里取最近消息。当前 ChatProfile 给它的参数是 maxRecentMessages: 20。

Resources

附件不是简单塞进 prompt

legacy attachments 会被转成 ChatResourceRef。非 direct 模式会先确保资源摘要存在；render 时旧资源主要以 attached marker 进入消息。

Focus folder

focus folder 是回答偏好，不是硬过滤器

SystemPromptSlot 会把 focus folder 追加到 system prompt，让模型优先考虑该 folder 的笔记和搜索范围。

Mode

Chat、Agent、Plan 共享上下文，但能力不同

三种模式都先走 prepareChatRequest。只有 agent mode 会注入 tools；plan mode 会把 planning system prompt 加到 system message 前面。

用户操作系统实际行为用户需要知道的限制
在同一个 conversation 里继续问 当前用户消息会和已有 conversation messages 合并，再交给 context pipeline。 上下文过大时，旧内容可能被压缩，不承诺逐字保留全部历史。
上传或引用文件 附件会转成 resource ref；非 direct 模式会触发 summary generation 事件。 direct / degrade_to_text 模式看到的信息量不同；当前 render 对非最新资源偏引用标记。
设置 custom system prompt 自定义 prompt 会 prepend 到默认 conversation system prompt 前面。 它影响整段 conversation，而不是只影响当前一条消息。
设置 focus folder system prompt 会追加一段 Focus Mode 指令。 这是模型侧偏好，不是数据库搜索层的强制 folder filter。

上下文堆叠：模型回答前到底看到了什么

Chat context 不是一段大字符串，而是一组 slot。每个 slot 有顺序、预算、是否 required、最大压缩等级。这个结构让系统可以在上下文太大时有规则地牺牲低优先级内容。

当前启用的 slots

Context stack 和 slots 是同一件事的两个视角：stack 讲模型最终看到的顺序，slot 讲每一层是谁负责、能不能压缩、预算是多少。服务层注册了更多 slot，但当前 ChatProfile 只启用下面这一组。

1 · system-prompt · required · 1500 tokens 渲染 conversation system prompt；叠加 custom prompt、focus folder 和 capability toggles。不压缩。
2 · recent-messages · required · 100000 tokens 保留最近消息。当前 profile 传 maxRecentMessages: 20；允许最多 L3 压缩，但不会被 drop。
3 · working-context · optional · 500 tokens 当前工作上下文，优先级高于 summary/resource 这类辅助信息；最多 L2 压缩。
4 · conv-summary · optional · 800 tokens 会话摘要，让旧上下文在预算紧张时仍留下一段可读概要；最多 L2 压缩。
5 · activity-index · optional · 200 tokens 最近活动索引；最多 L1 压缩。
6 · user-profile · optional · 400 tokens 用户画像和偏好；最多 L1 压缩。
7 · prev-analysis · optional · 600 tokens 上一轮分析结果或长期任务线索；最多 L2 压缩。
8 · resource-index · optional · 300 tokens 附件、资源摘要和资源引用的索引；最多 L1 压缩。

上下文太大时会怎样

ChatProfile 的总预算是 auto。实际预算由模型上下文窗口决定：maxCtx - 8192 - 5%。在这个预算内，系统先处理每个 slot 自己的上限，再压缩低优先级 non-required slot，最后才 drop。

压缩不等于永久丢失 好的 compact 结果应该保留“压缩了什么、哪些原文可重新取回”的线索。旧消息可以被变成摘要，附件和 Vault 内容可以只留下引用；后续如果 agent 需要细节，再通过 Search、resource loader 或上下文工具取回原文。这比简单丢弃更符合长期方向。

用户能感知到的现象代码事实维护者含义
不同模型能带的上下文不同。 ContextPipeline.resolveBudget() 读取 modelCapabilities.maxCtx。 不要硬写全局 chat token limit；模型切换会影响预算。
旧对话可能被缩短。 RecentMessagesSlot L1 保留后一半；L2 保留最后 3 条原文，旧消息变成 100 字符摘要。 如果用户抱怨“忘了前面”，优先看 compression/budget，而不是 provider。
辅助上下文可能消失。 BudgetGovernor 只 drop non-required slots。 新增 slot 时要认真设置 required、priority、maxTokens 和 maxCompressionLevel。

执行策略：少让用户选模式

当前代码里仍有 chat / agent / plan 分支，但它们共享 context 准备。产品方向应该是用户表达意图、系统根据能力和权限选择执行策略，而不是让用户先理解三个模式。

维护者视角 这里保留 mode 表，是为了读代码时知道分支在哪里；不是说 UI 必须永远暴露三个同级按钮。真正稳定的边界是：context 先装好，之后再决定是否加 tools、是否使用 planning prompt。
内部策略上下文Tools特殊处理
chat 走同一套 prepareChatRequest。 不传 tools。 纯对话。
agent 走同一套 prepareChatRequest。 buildChatTools 根据 UI toggles 和 model capabilities 构建。 当前 web search 会在模型没有 native web search 且 toggle 开启时注入。
plan 走同一套 prepareChatRequest。 不传 tools。 渲染 PromptId.PlanModeSystem，并 prepend 到 system message。

富生成：Mermaid + Obsidian Bases（2026-07-03 shipped）

Chat 系统 prompt（templates/prompts/conversation-system.md）加了两块领域约定，让模型能生成 vault-aware 的图表和数据视图——而不是通用图/通用表。

Mermaid · vault-link click-through

给 mermaid 节点加 click NodeId "peak://wikilink/Note%20Title" 指令。peak://wikilink/ 是 Peak 自定义 scheme，由 AppWikilinkAdapter.parseHref 解析、由 streamdown-isolated CSS 直接样式化。前提是 StreamdownIsolated.findLinkInPath 也识别 SVG anchor（mermaid 的 click 编译成 SVG <a>），这本轮已改为大小写不敏感、HTMLElement+SVGElement 都覆盖。

模型不能凭空生成 wikilink prompt 明确"只对已知存在的笔记加 click 指令"。判断依据是对话上下文里给了引用（[[...]] 或 attached resource），不是模型幻觉。

Bases · .base YAML 生成

Obsidian 1.9+ 支持 .base 数据视图。prompt 里内嵌完整 schema：filters（and:/or:/not: + 操作符 ==/!=/>/</contains/startsWith/endsWith/taggedWith）、properties（displayName）、views（table/cards/board/calendar + order/sort/groupBy/dateProperty）、built-in file.name/file.path/file.folder/file.ext/file.mtime/file.ctime/file.size/file.tags/file.links/file.inlinks/file.outlinks。输出走 ```base code fence 让用户复制到 .base 文件。

不做内联渲染 没在 chat 视图里预览 .base 结果，只输出源码。理由：.base 依赖 Obsidian 内部数据引擎，隔离 shadow DOM 里预览等于自己实现一份 Bases 引擎——收益不抵成本。用户复制到文件里，Obsidian 原生渲染更真实。

排障：回答不像你预期时先看这里

现象可能原因先检查处理方式
它好像忘了很久以前的内容。 上下文超过预算，旧消息被压缩。 当前模型的 context window、conversation 长度、是否有大型附件。 把关键事实重新说明一次，或把重要材料作为当前附件/当前消息引用。
附件没有被完整理解。 附件处理模式不是 direct，或资源摘要失败/过短。 conversation attachment handling、资源摘要是否生成。 切换 direct/degrade_to_text 策略，或把关键段落贴进当前消息。
Web Search 没有参与。 没有 Web Search profile，或 mode/toggle 不满足工具注入条件。 Settings → Profiles 是否配置 Web Search；当前 mode 是否为 Agent。 配置 profile，打开 web search 开关，必要时切到 Agent mode。
Focus folder 没有像硬过滤一样生效。 focus folder 是 system prompt 偏好，不是 Search 层强制过滤。 本轮回答是否真的需要严格 folder scope。 在用户消息里明确要求“只使用这个 folder”，或后续把 Search/Context 文档补成硬 scope 设计。

维护规则：不要重开一条 prompt 小系统

不要这样做应该怎么做原因
在 UI store 里拼完整 prompt。 通过 app/service port 传状态，让 SystemPromptSlot 或新 slot 处理。 当前系统已经用 ChatRuntimeStatePort 把 UI toggles 从 service 里隔离出来。
把新上下文直接塞进 recent messages。 新增 slot，并定义预算、压缩、render 规则。 slot 才能被 BudgetGovernor 治理。
看到注册过某个 slot 就说它已启用。 以 ChatProfile.slots 为准。 注册表只是可用组件；profile 决定当前 prompt 组成。
把 agent 工具逻辑塞进 context pipeline。 context 只准备模型该看的信息；工具由 mode 分支和 Harness/ToolDef 处理。 上下文装配和工具授权是两条边界，混在一起会变成双系统。
