13 · Feature · Vault Intelligence · 让 Vault 显影

Vault Intelligence 告诉你哪些笔记正在腐烂，哪些地方缺连接，哪些可以修。

Search（12）帮你找回一篇具体笔记。Vault Intelligence 处理另一个问题：把整个 Vault 当成一张有健康度、断裂点、失效枢纽的知识图，把肉眼看不到的信号显影出来。这份文档面向两个读者：想理解 Health / Hubs / Structural holes / Lint / Bridge 各自意味着什么并且知道下一步怎么做的 Obsidian 用户；以及要维护这条管线的开发者。用户视角在前，技术附录在后。

这页解决什么

Peak Assistant 的 Vault Intelligence 不是一个独立功能开关，而是几条管线（Vault Lint、Hub discovery、Structural holes、Vault Review 摘要）合起来把 Vault 的“形状”和“健康度”显影给用户。它回答的是那类你自己不写脚本就答不出来的问题：“这周我有没有产出孤儿笔记？”、“我关于 X 的 hub 是不是已经过期了？”、“这两个话题之间是不是缺一座桥？”

本文读者 想理解 Peak 提示的 Vault 健康指标怎么读、怎么行动的 Obsidian 用户；要在 lint / hub / holes 上新增信号或改阈值的维护者；想搞清楚 Vault Review 报告里那些数字从哪来的开发者。
本文不做什么 不重复 Search（12）；不解释 Chat / Copilot 的对话形态（11）；不定义索引数据库结构（那是 23-infra-search-index）。当 Vault Intelligence 的信号是靠索引才能算出来时，本文会说明依赖，但不重写索引本身。
读法 先把五类维度当成“Vault 健康的五个视角”来读：结构、内容、语义、时间、标签。概览只解释每类问什么问题；具体 signal、阈值、误判场景和修复动作放在 每类信号细看，避免把整页变成一张状态表。

分数怎么合成
dimensionScore = 100 × (1 - Σ severityWeight × signalWeight × affectedRatio)
vaultHealth = Σ dimensionScore × dimensionWeight
  1. severityWeight：error = 3.0，warning = 1.5，info = 0.5。
  2. dimensionWeight：Structural 0.30、Semantic 0.25、Content 0.20、Temporal 0.15、Tags 0.10。
  3. 例子：Structural 里有 2 个 broken link warning，影响 4% 文档；另有 1 个 hard orphan error，影响 2% 文档。惩罚大约是 1.5 × signalWeight × 0.04 + 3.0 × signalWeight × 0.02，再乘 Structural 0.30 进入总分。
  4. 解释分数时不要只看总分：70 分可能是 tags 很乱，也可能是 structural 断裂。用户真正要看的通常是“哪个 dimension 拉低了分”。

Vault Intelligence 没有独立视图。用户从 Open Copilot（Vault tab）、Quick Search（AI Analysis）、AI Graph 三个入口触碰这些信号。理解不同入口拿到的是同一份数据的不同投影是关键。

Recipe A · 我想知道 Vault 现在有多健康

  1. Command Palette → Open Copilot，切到 Vault 标签。
  2. Vault Context 一行会显示 fingerprint / 最近一次 review 的 freshness。
  3. 点 “Scan now” 触发一次 full lint。等 scanning → cleared。
  4. 查看 dimensions 分数 + 排序后的可修复建议（见 Fixable）。

成功结果：5 个 dimension 分数 + Health 综合分（0–100）+ 一组 HealthInsight（默认按 severity 排序）。

Recipe B · 我想让 AI 围绕 Vault 做主题分析

  1. Command Palette → Quick Search，切 AI Analysis，选 Vault Analysis 预设。
  2. 输入主题（例如“我关于 attention head 的笔记结构”）。
  3. Peak 会调 VaultDigestBuilder：里面同时用 lint 最新 snapshot、top hubs、top structural holes 构造 digest 传给 meta-agent。
  4. 流式返回结构化报告；用户可选择保存到 ChatFolder/AI-Analysis/。

成功结果：拿到的不只是关键词摘要，而是带有 Vault 结构感知的答案：AI 知道你的 hub、你的孤儿、你的 stale 区域是什么。

Recipe C · 我想修一批 broken links

  1. 在 Vault tab 跑一次 scan。
  2. 在 Fixable 区域找 “Broken-link repair” 或 “Missing targets are referenced repeatedly” insight。
  3. 点 Ask AI to repair：Peak 会用 PromptId.LintBrokenLinkRepair 组装 prompt 并交给 Copilot lane。
  4. Copilot 提出改动，用户在 acceptEdits 或 read 模式下决定是否落地。

成功结果：issue 数量下降；重复出现的 missing target 变成 create-note / redirect 的批量提案。

为什么合并到 Copilot Picker 而不是独立面板 用户不需要记住“扫 lint”这个内部动作，用户需要的是“Vault 现在如何 + 下一步做什么”。所以 lint 应作为 Vault Intelligence 的数据 provider，而不是一个需要用户单独学习的功能孤岛；扫描、解释、修复和后续对话应该在 Copilot Vault tab 里衔接。

下面按维度展开。每个 signal 只回答三件事：它意味着什么、触发条件是什么、什么时候该相信或忽略它。尚未成为 UI finding 的信号，先写成“需要设计成形”的规则草案，不在概览里抢注意力。

Semantic · 话题结构层

整层 待设计成形：M-COVERAGE-GAP、M-LOW-COHESION、M-CONTRADICTION、M-PHANTOM-NODE、M-SEMANTIC-ISOLATION、M-REDUNDANT-HUBS 都还没 detector。阈值已定义：contradictionMinSimilarity = 0.80、phantomNodeMinReferences = 3、lowCohesionMaxDensity = 0.30、redundantHubMinOverlap = 0.70；scan.contradictionBatchSize = 20、contradictionConcurrency = 2——一看就知道这一层是给 LLM detector 预留的（LintSignalDetector.requiresLlm 字段），做全量扫描要有节流。

在 detector 落地之前，semantic 维度的“话题地图”感受主要来自 AI Graph（community layout + hub 高亮）和 VaultDigestBuilder 内部的 top structural holes 抽取；用户看到的信号还没有。

用户看到的“可修复建议”不是逐条 finding，而是 buildVaultHealthInsights 聚合出的六类 HealthInsight。每一类都对应一段渲染好的 prompt 模板；点“Ask AI”后 Copilot 拿到的就是这段 prompt。

用户可见		 S-BROKEN-LINK 的 top repeated targets（≥ 2 files 引用同一 target） target 数 × 总 file 引用数。 PromptId.LintMissingTargets

每个 finding 自身还带一个 fixActions: FixActionId[]（枚举定义在 @/core/types/lint）：suggest-links、delete-note、redirect-link、create-note、remove-link、insert-backlink、bridge-to-main、strengthen-connections、draft-content、suggest-split、merge-notes、link-as-alias、add-frontmatter、rename-with-prefix、review-update、mark-current、snooze、archive-cluster、update-neighborhood、create-hub、review-cluster、reconcile-contradiction、create-phantom-note、suggest-tags、merge-tag、review-taxonomy。这套动作是给 未来 的 finding-level UI 用的；今天进入 Copilot 的路径主要还是 6 类聚合 insight。

Bridge note 是特殊的可修复建议 templates/config/bridge-note-template.hbs 是 handlebars 模板，用于 bridge-to-main / create-hub 类动作：当 signal 检测到两个 community 之间缺一座桥时，Peak 用这个模板生成一个 seed note（frontmatter tags: [bridge-note, communityA, communityB]，加上两侧 top nodes 的 [[wikilink]]）。今天这个模板存在，但生成 flow 还挂在 semantic 层的 spec detector 上；只有当 Copilot 手动请求“帮我生成一座桥”时才会用到。
Dismissal 是持久化的 用户 dismiss 一个 finding 后，dismissal 会写入 VaultLintRepo 并在后续 scan 里以 ${signalId}:${filePath} 为 key 过滤掉。LintDismissal.reason 支持 'false_positive' | 'wont_fix' | 'snoozed'，snoozed 还带 snoozeUntil 时间戳。策略是：永远不要在扫描器里过滤掉“可能是噪声”的 finding——留给用户去判断并 dismiss，Peak 记住这次判断。

Runtime 归属：VaultLintRuntime 由 composeVaultLintRuntime 一次性构造，存在 app 层的 AppRuntimeRegistry；service 层不再有 module-scope singleton。见 VaultLintContract.ts 的 dependency inventory 及 CLAUDE.md 项目约定“Runtime ownership”。

Full scan 频率
scan.fullScanIntervalHours = 168（一周）——今天只是 建议值，因为 startup / scheduled trigger 不属于手动 scan 的当前路径。用户不点 “Scan now” 就不会扫。
Incremental debounce
scan.incrementalDebounceMs = 30000——同上，未实装的 incremental 模式预留值。
Detector 失败隔离
每个 detector 都用 .catch() 隔离；失败只走 console.warn + onDetectorWarning callback，返回空数组，不阻塞其他 detector。
Health score 归零保护
totalNotes === 0 时每个维度返回 100（空 Vault 视为满分，避免除零）。
Signal counts
LintScanResult.signalCounts 是 Partial<Record<LintSignalId, number>>，方便 digest / dashboard 只看某一 signal 的数量而不必遍历 findings 列表。

Hub Generation Agent（2026-07-03 shipped）

Hub doc（社区综述文档）的生成从"1-hop 邻居拼接"或"stub warning"升级为 两 agent 串联：HubCuratorAgent 决定 vault 该有哪些 hub、要不要合并/淘汰；HubMaterializationAgent 负责给每个 hub 起草综述并写回 vault。

为什么不用 1-hop 拼接

最初 HubDocService.regenerateHubByNodeId 是 stub，一个直觉方案是拼接 hub node 的 1-hop 邻居。用户否决：1-hop 混杂"引用了但不重要"的噪声、忽略 2-hop 桥接结构、无中心性权重、无覆盖率自检。方向 C 用整体网络图 + PageRank/Louvain + LLM agent 自评替代——基建已经全在，只是没被这样组合过。

LLM 自决 · 覆盖率 · 冲突处理

  • 数量 — 由 hubCurationSubmitSchema 决定（hubs 数组），LLM 看 coverage.uncoveredHighValue 自评是否再补
  • 合并 / 淘汰 — action: 'create' | 'keep' | 'merge' | 'retire'；merge 遇 peak_user_owned=true 源即拦截整个 merge（不静默丢用户手写）；retire 归档到 _archive/hub/，永不物理删除
  • 覆盖率 — Curator submit 里 coverage_pct = coveredMembers / totalMembers，Materializer critique 里 overallCoverage（core 成员 2× 权重）
  • Single-hub fallback — stale-triggered regen（例如某个 hub 的成员改了）不用等 Curator 跑完，HubGenerationRuntime.buildRegenerateFn() 会合成一个单-hub decision 现场喂给 Materializer
用户手写的 hub 永远不被 AI 覆盖 ObsidianVaultHubDocAdapter.readPeakUserOwned() 读 frontmatter；peak_user_owned: true 直接跳过写回。同时 skeleton 保留 <!-- USER_SECTIONS_BELOW --> marker 之下的手写区，AI 只覆盖上方结构化 section。

触发点

  • 命令 Curate Hubs Now — 手动跑 Curator + Executor
  • 命令 Materialize Hub for Active Note — 从当前笔记的社区反查代表节点，直接跑 Materializer
  • 命令 Show Latest Hub Curation Plan — 打开 HubCurationPlanModal 看最近一份决策
  • HubCurationScheduler — opt-in 定时（默认 7 天关），hubCurationSchedulerEnabled 打开
  • hub_regen_queue — HubStalenessDetector 检测到 constituent 变化时入队，HubRegenService 排空

失效模式与恢复

Vault Intelligence 依赖索引和 Vault Lint 两条管线；两边都有会让信号“看起来不对”的失效模式。这一节告诉你怎么复位。

症状常见原因怎么恢复
Health 分数明显偏低但 Vault 看起来还行 索引深度 = fast；或 C-STUB 在 daily notes 批量触发 Index depth 升到 semantic/full；不适用的 signal 批量 dismiss（wont_fix）
S-ORPHAN 数量突增 fast 深度没有 semantic edges；或新导入了大批未链接笔记 看 orphan-reconnect insight 样本，若属导入把目录加进 search.ignorePatterns
S-BROKEN-LINK 集中在单一文件夹 该文件夹是 imported / generated 材料 Peak 会升级为 noise-source insight；采纳 “Review ignore rule”
digest 显示 stale hubs 为 0，但你认为不是 Hub 材化尚是 stub（regenerateHubByNodeId 仅 warn）；staleness 检测跑，但 hub markdown 未生成 今日无自愈；digest 数字随索引重跑刷新，hub 摘要仍需手动
“Scan now” 一直转不出结果 某 detector 抛异常不阻断其他；但 getSemanticNeighbors 在 embedding 不可用时抛，orphan 分支退化。看 console 是否有 [VaultLintService] detector … failed Advanced → Diagnostics 查 embedding 连通；或临时关 semantic 深度跑一次
Dismiss 的 finding 又冒出来 Dismissal key = ${signalId}:${filePath}；移动文件即命中新路径 手动 dismiss 新路径；或标记 wont_fix
AI Analysis 说“没看到你的 Vault 信息” getVaultHealth() 在 loadLatestScan() 抛 / 返回 null 时 catch，报告不 fail，但 digest 少 lint 段 Copilot Vault tab 手动 “Scan now” 后重跑
不要清 vault.sqlite 来“重置”Vault Intelligence DataStore/vault.sqlite 同时装载全部搜索索引、embedding、graph、lint scan、dismissal。删掉 = 前面所有指标一起归零、下次扫全部要重算。要“重来一次 lint”，正确做法是 Copilot Vault tab 里再点一次 “Scan now”，会重写 latest scan 但保留 dismissal 历史。

维护规则

这条管线的形状是被“契约”和“配置文件”约束的。新增一个信号要动的地方非常多，容易漏。按下面这几条来。

加新 signal = 5 处同步。 1) src/core/types/lint.ts 的 LintSignalId 枚举；2) HealthScoreEngine 的 SIGNAL_WEIGHTS + DIMENSION_OF 两张表；3) 写一个新的 LintSignalDetector 放到 src/service/lint/signals/<dimension>.ts；4) 在 composeVaultLintRuntime 的 registry 注册；5) 如果要暴露 fixable insight，在 buildVaultHealthInsights 里加一段，并在 templates/prompts/lint-*.md 补 prompt。任一步漏掉都会造成“Health score 悄悄降但 UI 显示不出来”。
阈值要放 vault-lint-config.json，别硬编码。 项目 docs/conventions/configurability.md 明确不允许硬编码阈值。detector 从 context 拿 VaultLintConfig（content.ts 里的 buildContentDetectors(config) 就是范例：接收 config、返回按当前阈值构造的 detector）。
Detector 不许拿 AppContext / sqliteStoreManager。 当前边界要求所有 Vault / metadata / graph 访问必须走 context.detectorContext（VaultLintDetectorContextPort）。想读新的东西？先在 ObsidianVaultLintDetectorContextAdapter 加接口。test/vault-lint-contract.test.ts 会源码扫描防止回退。
新的 fix action 要落枚举，不能自由字符串。 FixActionId 是闭合联合。UI 侧根据 kind 分派动作类型。加新 action = 更新枚举 + 更新对应 insight builder + 更新 Copilot 侧的 dispatcher。
自动触发必须先进入能力契约。 VaultLintCapabilityInput.trigger 当前以 'manual' 为主；如果要加入 'startup' 或 'scheduled'，先扩展契约和 UI 说明，不要绕开它自己新起一条“自动扫描”的定时任务。
新增 detector 时同步用户说明。 每个新 signal 都可能改变 Health 分数。只要 detector 进入健康分计算，就要同步阈值、公式例子和用户解释，否则用户会以为分数突然下降是 bug。
