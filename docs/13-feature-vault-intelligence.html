13 · Feature · Vault Intelligence · 让 Vault 显影

Vault Intelligence 告诉你哪些笔记正在腐烂，哪些地方缺连接，哪些可以修。

Search（12）帮你找回一篇具体笔记。Vault Intelligence 处理另一个问题：把整个 Vault 当成一张有健康度、断裂点、失效枢纽的知识图，把肉眼看不到的信号显影出来。这份文档面向两个读者：想理解 Health / Hubs / Structural holes / Lint / Bridge 各自意味着什么并且知道下一步怎么做的 Obsidian 用户；以及要维护这条管线的开发者。用户视角在前，组装链路和证据入口在后。

这页解决什么

Peak Assistant 的 Vault Intelligence 不是一个独立功能开关，而是几条管线（Vault Lint、Hub discovery、Structural holes、Vault Review 摘要）合起来把 Vault 的“形状”和“健康度”显影给用户。它回答的是那类你自己不写脚本就答不出来的问题：“这周我有没有产出孤儿笔记？”、“我关于 X 的 hub 是不是已经过期了？”、“这两个话题之间是不是缺一座桥？”

本文读者 想理解 Peak 提示的 Vault 健康指标怎么读、怎么行动的 Obsidian 用户；要在 lint / hub / holes 上新增信号或改阈值的维护者；想搞清楚 Vault Review 报告里那些数字从哪来的开发者。
本文不做什么 不重复 Search（12）；不解释 Chat / Copilot 的对话形态（11）；不定义索引数据库结构（那是 23-infra-search-index）。当 Vault Intelligence 的信号是靠索引才能算出来时，本文会说明依赖，但不重写索引本身。
读法 先把五类维度当成“Vault 健康的五个视角”来读：结构、内容、语义、时间、标签。概览只解释每类问什么问题；具体 signal、阈值、误判场景和修复动作放在 每类信号细看，避免把整页变成一张状态表。

Vault Lint 的五个 dimension 就是 Vault Intelligence 对用户显影的五个视角。它们不是并列的功能开关，而是同一次扫描算出来的五组分数。

分数怎么合成
dimensionScore = 100 × (1 - Σ severityWeight × signalWeight × affectedRatio)
vaultHealth = Σ dimensionScore × dimensionWeight
  1. severityWeight：error = 3.0，warning = 1.5，info = 0.5。
  2. dimensionWeight：Structural 0.30、Semantic 0.25、Content 0.20、Temporal 0.15、Tags 0.10。
  3. 例子：Structural 里有 2 个 broken link warning，影响 4% 文档；另有 1 个 hard orphan error，影响 2% 文档。惩罚大约是 1.5 × signalWeight × 0.04 + 3.0 × signalWeight × 0.02，再乘 Structural 0.30 进入总分。
  4. 解释分数时不要只看总分：70 分可能是 tags 很乱，也可能是 structural 断裂。用户真正要看的通常是“哪个 dimension 拉低了分”。

用户如何触发

Vault Intelligence 的主入口已经是 Quick Search → AI workspace selector → Vault Intelligence。进入该 mode 只读取结构摘要、hub、结构缺口与 review history，不会自动扫描；用户通过 Quick review 或 Complete review 显式启动复核。旧 Copilot Vault tab 不再承担这套产品界面。

当前入口：AI Search → Vault Intelligence Quick Search 顶层只保留 Vault Search 与一个 AI workspace selector；普通打开默认 AI Search，Vault Intelligence 与 AI Graph 从同一下拉进入。选择 Vault Intelligence 只切换页面内容，不自动触发 review。实现契约见 AI Search 统一模式入口，关闭批次见 PR-VAULT-GRAPH-SEGMENT。
旧草图与当前归属 Vault Maintenance Graph Segment 记录了早期 Copilot Vault tab 草图；当前 stats、overview graph、hubs、current note 与 recent reviews 已归入 Vault Intelligence。当前文档的 hub / link / local graph 归 File Atlas；Vault Search inspector 只做结果解释与 handoff。

Recipe A · 我想知道 Vault 现在有多健康

  1. Command Palette → Quick Search，从 AI workspace selector 选择 Vault Intelligence。
  2. 先看 stats、overview graph、hubs 与最近一次 review。
  3. 点 Complete review 触发完整复核；需要更轻量时选 Quick review。
  4. 查看 dimensions 分数 + 排序后的可修复建议（见 Fixable）。

成功结果：5 个 dimension 分数 + Health 综合分（0–100）+ 一组 HealthInsight（默认按 severity 排序）。

Recipe B · 我想让 AI 围绕 Vault 做主题分析

  1. Command Palette → Quick Search；普通打开 AI workspace 时默认是 AI Search。主题分析直接输入问题，不再选择旧的 Vault Analysis preset。
  2. 输入主题（例如“我关于 attention head 的笔记结构”）。
  3. Peak 会调 VaultDigestBuilder：里面同时用 lint 最新 snapshot、top hubs、top structural holes 构造 digest 传给 meta-agent。
  4. 流式返回结构化报告；用户可选择保存到 ChatFolder/AI-Analysis/。

成功结果：拿到的不只是关键词摘要，而是带有 Vault 结构感知的答案：AI 知道你的 hub、你的孤儿、你的 stale 区域是什么。

Recipe C · 我想修一批 broken links

  1. 从 Vault Intelligence 运行一次 Complete review。
  2. 在 Fixable 区域找 “Broken-link repair” 或 “Missing targets are referenced repeatedly” insight。
  3. 点 Ask AI to repair：Peak 会用 PromptId.LintBrokenLinkRepair 组装 prompt 并交给 Copilot lane。
  4. Copilot 提出改动，用户在 acceptEdits 或 read 模式下决定是否落地。

成功结果：issue 数量下降；重复出现的 missing target 变成 create-note / redirect 的批量提案。

为什么归入 Quick Search 的 AI workspace 用户需要的是“Vault 现在如何 + 下一步做什么”，而不是再记一个 Copilot Vault 面板。Vault Intelligence 因而与 AI Search、AI Graph 共用 selector；结构摘要保持只读，复核必须由 Quick / Complete review 显式触发。

每类信号细看

这节按维度展开。每个 signal 行里直接解释名字、例子和处理方式，避免读者在单独 glossary 和真正规则之间来回跳。

Structural · 图上有没有断裂

Signal怎么理解触发与处理
S-BROKEN-LINKerror · 用户可见 某篇笔记里有指向不存在 target 的 wikilink。 直接来自 Obsidian unresolved links，无阈值。优先 create / redirect / remove；如果集中在导入目录，先看是不是应该 ignore。
S-ORPHANwarning · 用户可见 硬孤儿：图上没有任何 in/out edge。 可直接相信。semantic 深度可提供 revival suggestion；fast 深度只能列出孤儿本身。见 Index depth。
S-SOFT-ORPHANdetector 已落地 · UI 解释待加强 软孤儿：链接数量很少，但不是 0。例子：一篇读书笔记只连到当天 daily note，没有连到主题笔记。 softOrphanMaxDegree = 2。适合做低优先级整理建议；不要把它解释成“这篇笔记没价值”。
S-MISSING-BACKLINKdetector 已落地 · UI 解释待加强 两篇笔记语义很近，但彼此没有链接。 missingBacklinkMinSimilarity = 0.70。先建议显式 wikilink；如果只是概念相似但写作意图不同，用户可 dismiss。
S-ISLAND-CLUSTERdetector 已落地 · 需要更好的可视化 小 community 像一座孤岛，内部有少量关系，但没有接回主图。例子：一次性导入的课程材料形成 4 篇小组，和日常研究笔记没有桥。 islandClusterMaxSize = 5。UI 上最好显示成员样本和可连接的主图候选，而不是只报 community id。
S-FRAGILE-BRIDGEdetector 已落地 · 需要图上解释 脆弱桥：community 内部连接密度太低，像靠几条细线勉强连着。例子：几篇相关笔记只通过一篇总览互相触达。 当前阈值是 internal density ≤ 0.30 且成员数 ≥ 3。处理上是补内部链接或拆分，不是直接删除。

Bridge note：它不是 detector 名字，而是一种修复产物：人为写一篇短 note，把两个 community 的核心节点连起来。它通常来自 bridge-to-main / create-hub 这类 action。

Content · 笔记本身够不够用

Signal怎么理解触发与处理
C-EMPTY / C-STUB用户可见 空笔记或只有很短 prose 的笔记。 C-STUB 默认 < 100 chars。Daily note、图片笔记、引用收集可能是假阳，适合 dismiss 或 folder-level ignore。
C-OVERSIZEDdetector 已落地 单篇笔记过长，后续搜索、阅读和维护都变重。 oversizedMinWords = 5000。处理通常是 suggest split，不是强制拆分。
C-DUPLICATEdetector 已落地 两篇笔记标题和语义都很像，可能重复。 duplicateMinSimilarity = 0.92 且 title Jaccard ≥ 0.50。处理是 merge / alias / keep-both decision，不能自动合并。
C-FRONTMATTER-MISSING / C-NAMING-VIOLATIONdetector 已落地 结构化 metadata 缺失，或标题仍是 Untitled / 前后空格这类明显命名问题。 规则驱动。适合批量 add frontmatter / rename-with-prefix；不要引入风格战，比如强制 kebab-case。

Temporal · 时间维度上腐烂

Signal怎么理解触发与处理
T-STALE-HUBdetector 已落地 曾经重要的 hub 长期未更新。 staleHubDays = 180。通常建议 review-update 或 mark-current，而不是自动重写。
T-DECAYING-BRIDGEdetector 已落地 过期桥：桥接作用的笔记太久没有维护。例子：一篇总览一年前连接过两个 topic，但两边内容已经变化，它还没有更新。 decayingBridgeDays = 365。处理是更新邻域、补 links，或确认它已经不再是桥。
T-ABANDONED-CLUSTER / T-ABANDONED-FOLDERdetector 已落地 停摆簇 / 停摆目录：一个 community 或 folder 很久没有任何成员更新。它可能是已完成项目，也可能是被遗忘的研究线。 cluster 默认 180 天，folder 默认 365 天。先判断是“已完成项目”还是“被遗忘的研究线”，再 archive 或 review。
T-RECENT-DRIFTdetector 已落地 最近新增的笔记偏离了已有主题邻域。 默认看最近 30 天 active notes 和 180 天 stale baseline。适合提示“新方向正在形成”，不适合作为错误。

Semantic · 话题结构层

Semantic 层不是纯规则判断。M-* detector 在实现里被标成需要 LLM 的候选能力，普通 Vault Lint 扫描不会执行它们；只有预算上限、节流、证据复核和 prompt 模板都准备好后，这类 finding 才适合对用户可见。

Signal产品含义和例子成形前还缺什么
M-COVERAGE-GAPLLM stub 话题地图里明显缺一块。例子：有很多 Transformer 训练笔记，但没有任何 evaluation / benchmark 笔记。 需要 topic map prompt + “缺口是否真的重要”的人工确认，不应自动创建任务。
M-LOW-COHESIONLLM stub 单篇笔记内部主题太散。例子：一篇 note 同时写面试、数据库、旅行计划。 需要 LLM 判断“混合是否有意为之”。UI 应建议 split，不应直接说这篇错了。
M-CONTRADICTIONLLM stub 两篇语义接近的笔记有事实冲突。例子：一篇写 PPR 权重 0.3，另一篇写 0.7。 需要候选对预过滤、批量上限、引用证据和用户确认；默认并发是 2，避免扫全库烧模型。
M-PHANTOM-NODELLM stub 多个文件引用同一个不存在 target。例子：很多 note 都写 [[PageRank damping]]，但没有这篇 note。 phantomNodeMinReferences = 3 只是候选门槛；LLM 要判断是创建新 note，还是 redirect typo。
M-SEMANTIC-ISOLATIONLLM stub 一篇笔记语义上找不到邻居。例子：某个新研究方向刚开始，还没有主题邻域。 需要区分“真正孤立”和“合理的新方向”。UI 更适合提示 create-hub / tag，而不是报错。
M-REDUNDANT-HUBSLLM stub 两个 hub 覆盖成员高度重叠。例子：Search Ranking 和 Retrieval Ranking 下面几乎是同一批 note。 redundantHubMinOverlap = 0.70 只是候选；最终动作可能是 merge、split、alias 或 bridge。

Tags · 标签系统的健康

Signal怎么理解触发与处理
G-UNTAGGEDinfo · 用户可见 frontmatter 与 inline tag 都为空。 可直接相信，但“是否必须有 tag”是个人策略。适合 suggest-tags 或批量 dismiss。
G-TAG-EXPLOSIONdetector 已落地 某篇 note 的 tag 数显著高于 Vault 典型值。 按有 tag 文件的 median 计算，默认倍率 5。处理是 review taxonomy，不是把 tag 自动删掉。
G-TAG-ISLAND / G-TAG-REDUNDANCY / G-NOISE-TAGS枚举预留 · 需产品设计 标签体系本身的问题：孤立标签、重复标签、噪声标签。 还缺 detector 和 UI 决策。更适合先做 taxonomy review 面板，再决定是否进入 Health score。

Hub 生成：Vault Intelligence review 的第二个能力

Hub doc（社区综述文档）和“信号细看 / 可修复建议”是并列能力：前者把 community 写成可维护的综述，后者告诉用户哪里断了、哪里该修。产品入口跟随 Vault Intelligence 的显式 review 流程，不再另建 Copilot Vault tab。

用户入口 用户通过 Quick Search → Vault Intelligence → Complete review 进入完整复核，再处理“生成 / 更新 Hub 综述”类动作。背后的实现可以调用 Curator 和 Materializer，但 UI 不应该要求用户理解这两个 agent 名字。

生成过程内部仍然分两段：Curator 先决定哪些 hub 应该存在、哪些该合并或归档；Materializer 再把单个 hub 写成一篇可维护的 Vault 笔记。

为什么不是 1-hop 拼接

Hub doc 不能只拼接 hub node 的 1-hop 邻居：那会混入“引用了但不重要”的噪声，忽略 2-hop 桥接结构，也没有中心性权重和覆盖率自检。更稳的方式是整体网络图 + PageRank/Louvain + LLM agent 自评：先由图结构筛出候选，再让 agent 判断 hub 的边界、覆盖率和合并/淘汰策略。

一次 Scan now 会发生什么

  1. 用户在 Vault Intelligence 点 Complete review。
  2. UI 通过 runVaultLintManualScan 进入 RunEnvelope，scan 有统一状态和错误出口。
  3. VaultLintService 调 getNonLlm()，只跑不需要 LLM 的 detector；M-* semantic stub 被跳过。
  4. detector 只读 adapter 给出的纯数据：Vault 文件、unresolved links、doc degree、communities、semantic neighbors。
  5. scan result 写入 VaultLintRepo；同一份 result 被 digest 和 buildVaultHealthInsights 复用。

依赖边界

边界谁负责为什么这么分
Runtime 归属 composeVaultLintRuntime → AppRuntimeRegistry runtime 在 app 层组装，service 层保持 plain class，不再加 module-scope singleton。
端口注入 VaultLintPorts 配置、Vault 读取、persistence、registry、clock、idFactory 都从构造函数进来，方便测试替换。
Obsidian / SQLite 隔离 app/lint adapters detector 本身不碰 Obsidian API，也不直接拿 sqlite manager；新增数据先扩 port。
用户可见建议 buildVaultHealthInsights finding 可以很多，用户先看聚合后的 6 类 insight；未来再做 finding-level review UI。
手动 full scan
scan.fullScanIntervalHours = 168 的意思是“如果将来做定时扫描，一周一次比较合理”。它尚未接入定时触发；用户不点 Scan now 就不会扫。
增量扫描预留
scan.incrementalDebounceMs = 30000 是未来 incremental scan 的防抖值，避免每次文件保存都触发重算。当前手动 scan 不靠它。
Detector 失败隔离
单个 detector 失败只记 warning 并返回空数组，不阻塞其他 detector。用户应该看到 partial result，而不是整次 scan 失败。
Health score 归零保护
totalNotes === 0 时每个维度返回 100（空 Vault 视为满分，避免除零）。
Signal counts
signalCounts 是每种 signal 的数量摘要。digest / dashboard 可以直接读它，不必遍历完整 findings 列表。

失效模式与恢复

Vault Intelligence 依赖索引和 Vault Lint 两条管线；两边都有会让信号“看起来不对”的失效模式。这一节告诉你怎么复位。

症状常见原因怎么恢复
Health 分数明显偏低但 Vault 看起来还行 索引深度 = fast；或 C-STUB 在 daily notes 批量触发 Index depth 升到 semantic/full；不适用的 signal 批量 dismiss（wont_fix）
S-ORPHAN 数量突增 fast 深度没有 semantic edges；或新导入了大批未链接笔记 看 orphan-reconnect insight 样本，若属导入把目录加进 search.ignorePatterns
S-BROKEN-LINK 集中在单一文件夹 该文件夹是 imported / generated 材料 Peak 会升级为 noise-source insight；采纳 “Review ignore rule”
digest 显示 stale hubs 为 0，但你认为不是 Hub 材化尚是 stub（regenerateHubByNodeId 仅 warn）；staleness 检测跑，但 hub markdown 未生成 没有自动自愈入口；digest 数字随索引重跑刷新，hub 摘要从 Vault Intelligence 的显式 review 动作处理
“Scan now” 一直转不出结果 某 detector 抛异常不阻断其他；但 getSemanticNeighbors 在 embedding 不可用时抛，orphan 分支退化。看 console 是否有 [VaultLintService] detector … failed Advanced → Diagnostics 查 embedding 连通；或临时关 semantic 深度跑一次
Dismiss 的 finding 又冒出来 Dismissal key = ${signalId}:${filePath}；移动文件即命中新路径 手动 dismiss 新路径；或标记 wont_fix
AI Search 说“没看到你的 Vault 信息” getVaultHealth() 在 loadLatestScan() 抛 / 返回 null 时 catch，报告不 fail，但 digest 少 lint 段 从 Vault Intelligence 手动运行 Complete review 后重试
不要清 vault.sqlite 来“重置”Vault Intelligence DataStore/vault.sqlite 同时装载全部搜索索引、embedding、graph、lint scan、dismissal。删掉 = 前面所有指标一起归零、下次扫全部要重算。要“重来一次 lint”，正确做法是从 Vault Intelligence 再运行一次 Complete review，会重写 latest scan 但保留 dismissal 历史。

维护规则

这条管线的形状是被“契约”和“配置文件”约束的。新增一个信号要动的地方非常多，容易漏。按下面这几条来。

加新 signal = 5 处同步。
  1. 在 lint.ts 加 LintSignalId。
  2. 在 HealthScoreEngine.ts 同步 SIGNAL_WEIGHTS 和 DIMENSION_OF。
  3. 在 signals/ 里新增对应 LintSignalDetector。
  4. 在 runtime registry 里注册 detector，确认 getNonLlm() 或 requiresLlm 语义正确。
  5. 如果要进入 Copilot 建议，在 insights.ts 加聚合逻辑，并补 prompt 模板。
漏任一步都可能造成“Health score 已被影响，但 UI 解释不出来”。
阈值要放 vault-lint-config.json，别硬编码。 项目 docs/conventions/configurability.md 明确不允许硬编码阈值。detector 从 context 拿 VaultLintConfig（content.ts 里的 buildContentDetectors(config) 就是范例：接收 config、返回按当前阈值构造的 detector）。
Detector 不许拿 AppContext / sqliteStoreManager。 当前边界要求所有 Vault / metadata / graph 访问必须走 context.detectorContext（VaultLintDetectorContextPort）。想读新的东西？先在 ObsidianVaultLintDetectorContextAdapter 加接口。test/vault-lint-contract.test.ts 会源码扫描防止回退。
新的 fix action 要落枚举，不能自由字符串。 FixActionId 是闭合联合。UI 侧根据 kind 分派动作类型。加新 action = 更新枚举 + 更新对应 insight builder + 更新 Copilot 侧的 dispatcher。
自动触发必须先进入能力契约。 VaultLintCapabilityInput.trigger 当前以 'manual' 为主；如果要加入 'startup' 或 'scheduled'，先扩展契约和 UI 说明，不要绕开它自己新起一条“自动扫描”的定时任务。
新增 detector 时同步用户说明。 每个新 signal 都可能改变 Health 分数。只要 detector 进入健康分计算，就要同步阈值、公式例子和用户解释，否则用户会以为分数突然下降是 bug。
