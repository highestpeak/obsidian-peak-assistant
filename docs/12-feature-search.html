先理解搜索意图

Obsidian 用户搜索时，经常记不住准确标题，也不一定知道某个概念被自己写在哪篇笔记里。一个只做精确关键词匹配的搜索，很快会变成“我知道它存在，但我找不到”。

Peak Assistant 的 Search 选择了多路信号融合：关键词召回负责可解释性，vector 负责概念相近，metadata/fuzzy 负责标题路径和拼写容错，PPR 和 reranker 负责图关系、最近性、hub、点击反馈。最终结果再做高亮，让用户知道为什么这条结果出现。

一句话结论 Search 是一个“多路召回 + 可降级增强”的 pipeline。任何一个 retriever、vector、PPR 或 LLM rerank 失败，都不应该让基础搜索不可用。

本文读者、目标和不做什么

对象读完应该知道什么不在这里展开什么
Obsidian 用户 为什么搜索结果不是纯关键词排序；为什么语义、模糊、图关系会影响结果。 不需要理解 SQLite FTS5、embedding 表和图算法细节。
维护者 一条 query 如何被 parse、召回、合并、rerank、highlight；哪些环节必须保持失败隔离。 不在这里重写 search index 生命周期；那属于 23-infra-search-index.html。
Coding agent 新增 retriever 时要接入 registry 和 weight，不要在 UI 或某个单一路径里 bypass RRF。 不把 Search 写成一个 LLM-only 问答功能。

入口和开始前检查

Search 的用户入口是 Quick Search。它有两个主要 tab：Vault Search 用来直接找笔记，AI Analysis 用来让 AI 围绕 Vault 做分析。

你想做什么从哪里开始开始前确认预期结果
搜索整个 Vault Command Palette → Quick Search → Vault Search。 Search service 已初始化；基础索引可用。 输入框下方出现结果数量、耗时和结果列表。
限定当前文件、folder 或行号 输入框提示支持 # in-file、@ folder、: go to line。 当前 Obsidian editor 或 folder scope 有意义。 mode label 会切到 in-file / folder / line 等状态。
让 AI 做 Vault 分析 Quick Search → AI Analysis。 需要可用 AI profile；Web Search 还需要 Web Search profile。 进入分析输入和流式结果区域。
使用语义搜索 正常输入 query；系统按条件决定是否启用 vector retriever。 Settings 里 vector search enabled，且有 embedding endpoint/model。 概念相近但不完全同词的笔记可能进入结果。

常见任务和预期结果

任务怎么做成功时应该看到什么注意
找一篇记不清标题的笔记 在 Vault Search 输入关键词或概念词。 结果列表包含标题、路径、snippet/highlight 和耗时。 排序会混合多路信号，不是纯关键词次数。
在当前文件里找内容 用 # 前缀进入 in-file 模式。 mode label 显示 in-file，结果聚焦当前文件。 如果没有活动文件，这个模式价值有限。
在某个 folder 里找内容 用 @ 前缀进入 folder 模式。 mode label 显示 folder，query 会带 folder scope。 folder scope 与全文多路召回共同作用。
从结果进入 AI 分析 切换到 AI Analysis 或用界面里的 Ask AI 入口。 AI Analysis 输入会带入相关 query。 AI Analysis 是分析 workflow，不等同于基础 Search pipeline。

用户能感知到的行为

Relevant, not literal only

结果可能来自不同信号

同一个结果可能因为正文 FTS、标题/路径 metadata、vector 相似、fuzzy correction 或 graph boost 出现。排序不是单一关键词计数。

Explainable snippets

最终结果会有高亮

高亮发生在 final topK 阶段，帮用户确认匹配点。高亮不是排序的唯一来源。

Semantic optional

语义搜索是增强，不是基础依赖

vector retriever 只有在 vector search enabled 且存在 embedding profile/model 时才启用。

Failure tolerant

单路失败不应该拖垮整次搜索

RetrieverRegistry 会捕获单个 retriever 的错误并返回空结果；PPR 失败也会回退原结果。

用户输入/场景系统会怎么找用户需要知道的限制
普通关键词 FTS、stem、metadata、fuzzy 等多路召回会参与。 排序不是“词出现次数越多越靠前”。
短 query 或拼写不准 fuzzy retriever 从 title token cache 找近似词，再查 metadata FTS。 它不是完整拼写检查器，主要依赖标题 token。
概念型长 query vector weight 会提高；如果 embedding 条件满足，vector retriever 会参与。 没有 embedding profile/model 时，语义召回不会启用。
带 -term exclude 会进入 query plan，并在排序后过滤结果。 不是每一路 retriever 都提前过滤；最终输出会过滤。
打开 LLM rerank 只有 enableLLMRerank 为 true 时才跑 LLM rerank。 基础 search 不依赖 LLM 才能返回结果。

Search Pipeline

从代码入口看，SearchClient 很薄，真正的 pipeline 在 QueryService.textSearch。它先 parse query，再并行执行 active retrievers，之后用 RRF 合并，最后叠加 PPR、ranking boost、exclude、highlight 和可选 LLM rerank。

Query Parser：先把用户输入变成计划

parseQuery 会把原始文本拆成 terms、phrases、excludes、filters，并根据 query 形态计算 retriever weights。这个 plan 是后续多路召回和 RRF 的共同输入。

输入形式处理影响
"quoted phrase" 进入 phrases。 FTS 权重上调，vector 权重下调。
-term normalize 后进入 excludes。 排序后执行 exclude filter。
tag:x / ext:x / folder:x 进入 filters。 给 retriever/query 层使用。
普通词 normalize 后生成 QueryTerm，非 CJK 计算 porter stem。 用于 FTS、stem、fuzzy 等召回。
CJK term stem 保持原词。 ftsStem weight 被压低到 0.1 倍。

Retrievers：每一路只负责拿候选，不负责最终真理

每个 retriever 都实现 shouldActivate(plan) 和 retrieve(plan)。Registry 只执行 active retrievers，并且单路失败会被捕获。

Retriever何时启用做什么注意
fts 有 terms 或 phrases。 构造 FTS5 query；BM25 归一化；多 chunk 文档用 decay 合并。 精确/前缀召回的主力。
ftsStem 按 plan 激活。 stemmed query 召回。 CJK 场景权重会显著下降。
vector vector weight > 0.1、sqlite vector enabled、存在 embedding endpoint/model。 把 raw query embed 后查相似 chunk/doc，并对多 chunk 做 decay。 没有 embedding 配置时不启用；embedding 失败返回空。
meta 按 plan 激活。 元数据召回。 适合 title/path/meta 信号。
fuzzy 有 terms。 从标题 token cache 找近似词，再用 corrected terms 查 meta FTS。 返回 fuzzyCorrection 给 UI。

Merge / Rerank / Highlight：从候选变成用户看到的结果

Search 的排序核心不是某一路 retriever 的分数，而是 RRF 合并后的路径级分数。之后才叠加图和行为信号，最后只对 final results 做高亮。

读图：RRF 是主合并点；PPR 可能扩展 graph neighbor；boost 只改变排序，不应该改变 retriever contract。

阶段规则维护边界
RRF merge 每条 result 贡献 weight / (60 + rank + 1)；同 path 合并。 新增 retriever 必须有 weight；缺省 weight 是 0.5。
PPR 由 settings 控制，query 可 force-disable；失败 catch 后回退原结果。 图排序不能成为基础 search 的硬依赖。
Ranking boosts 读取 reranker signals、current file related paths 和 click-through paths。 boost 是排序增强，不应该绕过原始召回。
Highlight 只对 final topK 结果生成 snippet/title highlight。 不要在每一路 retriever 提前做高成本 highlight。
LLM rerank 只有 enableLLMRerank 为 true 才运行。 默认 search 不依赖 LLM。

失败和降级：增强项不能拖垮基础搜索

这个 pipeline 的一个重要产品承诺是：即使语义索引、图排序或某一路召回不可用，用户仍然应该尽量得到基础结果。

读图：未初始化和空 query 是明确分支；retriever/vector/PPR 的失败要局部吸收。维护 Search 时要保住这条产品体验。

情况当前行为文档结论
SearchClient 未 init 抛出 SearchClient not initialized. Call init() first. 调用方必须保证 SQLite/store 初始化顺序。
空 query 返回空 items。 不要把空 query 偷换成 recent 或 browse。
单个 retriever 失败 Registry catch 错误，该路返回空。 多路召回必须局部失败可恢复。
Vector 条件不满足 VectorRetriever.shouldActivate 返回 false。 semantic search 是增强，不是基础 search 必选项。
PPR 失败 catch 后继续用原 resultItems。 graph rerank 不应阻断普通搜索。

排障：结果不符合预期时先看这里

现象可能原因先检查处理方式
输入后没有结果。 query 为空、索引未准备好，或当前 scope 太窄。 是否有实际 terms/phrases；Quick Search footer 是否显示搜索中；索引是否完成。 换一个更宽的 query，退出 in-file/folder scope，或先运行索引维护。
语义相关结果没有出现。 vector retriever 没有激活。 vector search 是否 enabled；embedding profile 是否有 endpoint 和 model。 配置 embedding profile，或接受基础 FTS/metadata 结果。
拼写接近但没有被纠错。 fuzzy 主要依赖标题 token cache，不是全文拼写检查。 目标词是否出现在标题 token 里。 改用更接近标题的词，或用普通关键词/语义 query 扩宽搜索。
AI Analysis 里 Web Search 不可用。 没有配置 Web Search profile。 Settings → Profiles 是否有 profile 被设为 Web Search。 配置后重试；没有 profile 时只使用 Vault/模型已有能力。
图关系排序看起来没有影响。 PPR 被关闭、没有可用 docId seed，或 PPR 失败后回退。 Search settings 的 PPR 开关；console 是否有 PPR failed 日志。 先确认基础结果可用，再检查图索引和 PPR 设置。

维护规则：新增搜索能力必须进入同一条 pipeline

不要这样做应该怎么做原因
在 UI 里单独写一个“更聪明搜索”。 新增 retriever 或 rerank/boost stage，并接入 QueryService。 否则用户会得到两套不一致的搜索语义。
让 vector/PPR/LLM rerank 成为必选路径。 保持它们 optional/failure-tolerant。 搜索是基础能力，不能因为增强项失效而不可用。
新增 retriever 但不定义 weight。 在 query plan weights 中表达它的相对重要性。 RRF 需要知道每一路信号的分量，不然排序会漂。
把高亮提前塞进每个 retriever。 最终 topK 后统一 highlight。 降低成本，也避免每一路结果展示语义不一致。
