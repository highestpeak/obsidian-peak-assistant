先理解搜索意图

Obsidian 用户搜索时，经常记不住准确标题，也不一定知道某个概念被自己写在哪篇笔记里。一个只做精确关键词匹配的搜索，很快会变成“我知道它存在，但我找不到”。

Peak Assistant 的 Search 选择了多路信号融合：关键词召回负责可解释性，vector 负责概念相近，metadata/fuzzy 负责标题路径和拼写容错，PPR 和 reranker 负责图关系、最近性、hub、点击反馈。最终结果再做高亮，让用户知道为什么这条结果出现。

一句话结论 Hyper Search 是一个“多路召回 + 可降级增强”的 pipeline。任何一个 retriever、vector、PPR 或 LLM rerank 失败，都不应该让基础搜索不可用。
和 AI Search workspace 的边界 AI Search 是 agent-driven 分析 workflow：它可以读取搜索结果、Vault Health、hub、graph 和外部工具，再生成报告。Hyper Search 只负责快速找回候选笔记和解释排序原因；它不负责写报告，也不要求 LLM 才能返回结果。
结果侧栏与 File Atlas 的边界 Vault Search 的右侧 inspector 只解释当前选中结果，并呈现 Connected、Discovered 与 AI Graph。Hub 归属、入链 / 出链和局部图谱由 File Atlas 负责；Search 通过 Open in File Atlas 交接当前结果，不再建设第二套 Hub drawer。原草图保留在 Search handoff，关闭决策见 PR-SEARCH-HUB-DRAWER。

Search Pipeline

从代码入口看，SearchClient.search() 先做可选 query rewrite；真正的召回、排序和高亮 pipeline 在 QueryService.textSearch()。它 parse query，并行执行 active retrievers，用 RRF 合并，再叠加 PPR、ranking boost、exclude、topK、highlight 和可选 LLM rerank。

Query Parser：先把用户输入变成计划

parseQuery 会把原始文本拆成 terms、phrases、excludes、filters，并根据 query 形态计算 retriever weights。这个 plan 是后续多路召回和 RRF 的共同输入。

自然语言 query parser 的当前状态 这条能力已经作为可选增强接入：SearchClient.search() 会在 settings.useAiQueryParser 开启时调用 maybeCompileWithAiParser()，把自然语言编译成 parseQuery 能吃的 Hyper Search syntax。默认关闭；没有 fast-role invoker、LLM 调用失败或 schema 校验失败时，会回退原始 query。后续产品任务是补足改写解释、bad-case 收集、本地规则 fallback 和用户可见的开关/状态。
输入形式处理影响
"quoted phrase" 进入 phrases。 FTS 权重上调，vector 权重下调。
-term normalize 后进入 excludes。 排序后执行 exclude filter。
tag:x / ext:x / folder:x 进入 filters。 给 retriever/query 层使用。
普通词 normalize 后生成 QueryTerm，非 CJK 计算 porter stem。 用于 FTS、stem、fuzzy 等召回。
CJK term stem 保持原词。 ftsStem weight 被压低到 0.1 倍。
Parser 例子：这里只产生 query plan，不解释排序
  1. 用户输入 "attention head" -draft tag:research。
  2. "attention head" 进入 phrases；-draft normalize 后进入 excludes；tag:research 进入 filters。
  3. parseQuery 只负责把输入拆成 plan，并按 query 形态计算 retriever weights。RRF、PPR、boost 和 highlight 都属于后面的 merge/rerank/highlight 阶段。

Retrievers：每一路只负责拿候选，不负责最终真理

每个 retriever 都实现 shouldActivate(plan) 和 retrieve(plan)。Registry 只执行 active retrievers，并且单路失败会被捕获。

Retriever何时启用做什么注意
fts 有 terms 或 phrases。 构造 FTS5 query；BM25 归一化；多 chunk 文档用 decay 合并。 精确/前缀召回的主力。
ftsStem 按 plan 激活。 stemmed query 召回。 CJK 场景权重会显著下降。
vector vector weight > 0.1、sqlite vector enabled、存在 embedding endpoint/model。 把 raw query embed 后查相似 chunk/doc，并对多 chunk 做 decay。 没有 embedding 配置时不启用；embedding 失败返回空。
meta 按 plan 激活。 元数据召回。 适合 title/path/meta 信号。
fuzzy 有 terms。 从标题 token cache 找近似词，再用 corrected terms 查 meta FTS。 返回 fuzzyCorrection 给 UI。

Merge / Rerank / Highlight：从候选变成用户看到的结果

Search 的排序核心不是某一路 retriever 的 raw score，而是按 path 聚合后的分数账本。维护这段时先看公式和伪代码：RRF 负责多路召回融合，PPR 把图结果作为另一种 rank source 融入，ranking boost 叠加行为/图谱信号，LLM rerank 只在显式开启时做最后一层重排。

排序公式：从多路候选到 final score
rrf(path) = Σ sourceWeight[source] / (RRF_K + rank0(source, path) + 1)
pprFuse(path) = 0.7 / (RRF_K + cmRank0(path) + 1) + 0.3 / (RRF_K + pprRank1(path))
boosted(path) = base + freq + recency + graph + anchor + click + hubDoc
llmFinal(path) = 0.7 * boosted(path) + 0.3 * normalizedRerankScore(path)
  • RRF_K = 60。普通 retriever merge 使用 0-based rank，所以代码里是 60 + rank0 + 1；人类看到的“第 1 名”对应 rank0 = 0，分母是 61。
  • cmRank0 是 PPR 前的候选排序位置；pprRank1 是 PPR 分数排序后的 1-based rank，所以 PPR 分量不再额外加 + 1。
  • freq = log1p(openCount) * 0.10；recency = max(0, 0.2 - daysSinceLastOpen * 0.005)。
  • graph = 0.2 表示当前文件 2-hop related；click = 0.15 表示 click-through 命中。
  • anchor 来自 hub/secondary/incoming signals；如果 PPR 已启用，anchor 会乘 PPR_GLOBAL_PR_DAMPENING = 0.3，避免全局 PageRank 和 PPR 双重放大。
PPR 到底在做什么 PPR 是 Personalized PageRank，不是全局“哪篇笔记最重要”的 PageRank。它把本次搜索已经找到的 top docId 当作起点，再把 FTS 命中的 query-node docId 混入一小部分 seed budget，然后沿 reference、semantic related、shared tag 和 co-citation 这些图边扩散。这样它回答的问题是：“如果用户已经在找 A/B 这些笔记，图上哪些邻近笔记也可能相关？”所以 PPR 可以把没直接命中关键词、但和强候选关系很近的 C.md 拉进候选；它不能替代关键词召回，也不能成为基础搜索的硬依赖。
PPR 步骤当前实现读结果时怎么理解
选 seed 取 RRF 后 top result 里有 docId 的前 PPR_SEED_K = 10 条；如果 FTS 有 query-node docId，再给它们 0.25 的 seed weight。 它从“这次 query 已经像样的结果”出发，不是从整个 Vault 随机找 hub。
沿图扩散 edge fetcher 混合 reference、semantic related、shared tag、co-citation 四层边，并各自归一化。 被提升的结果通常是强候选的图邻居、语义邻居或共同被引用对象。
融合排序 已有候选按 0.7 原候选 rank + 0.3 PPR rank 融合；PPR-only 邻居最多扩展 20 条。 PPR 是 rerank/expand 层。它能补相关笔记，但不应压过所有文本证据。
排序算例：RRF + PPR + boost 在这里叠加
  1. 用户搜 "attention head" -draft tag:research；Parser 先产出 phrase、exclude 和 tag filter。
  2. A.md 在 FTS 人类排名第 1、metadata 人类排名第 4：代码 rank 分别是 0 和 3，RRF 贡献约 1.0 / 61 + 0.6 / 64。
  3. B.md 在 vector 人类排名第 1，但 FTS 没命中：RRF 贡献约 0.9 / 61。它可能靠语义进入候选，但解释时要告诉用户“词不完全相同”。
  4. PPR 用 top docId 做 seed。如果 C.md 是 A/B 的强图邻居，它可能作为扩展候选进入；如果某个已有候选在 PPR 里排第 2，它的 PPR 分量是 0.3 / 62。
  5. Ranking boost 再叠加近期编辑、hub、click-through、当前文件 2-hop related 等信号。最后执行 -draft exclude、取 topK、生成高亮。
function rankSearch(rawQuery, settings):
  effectiveQuery = maybeCompileWithAiParser(rawQuery, settings)
  plan = parseQuery(effectiveQuery)
  retrieverResults = new Map()

  for retriever in registry:
    if retriever.shouldActivate(plan):
      retrieverResults[retriever.name] = retriever.retrieve(plan)

  merged = []
  for each source, results in retrieverResults:
    weight = plan.retrievers[source] ?? 0.5
    for rank0, item in results:
      contribution = weight / (60 + rank0 + 1)
      merged[item.path].rrfScore += contribution
      merged[item.path].sources.add(source)
      merged[item.path].best = maxScoreChunk(item)

  candidates = sortByScoreDesc(merged)

  if settings.pprEnabled and not plan.disablePpr:
    seeds = normalize(topWithDocId(candidates, PPR_SEED_K))
    seeds = blendQueryNodeSeeds(seeds, plan.queryNodeDocIds, fraction = 0.25)
    pprRanks = computePPR(seeds)
    candidates = fuseByRrf(candidates, pprRanks, cmWeight = 0.7, pprWeight = 0.3)
    candidates += graphNeighborsFromPpr(pprRanks, max = 20)

  boosted = candidates.map(item => {
    signal = readRankingSignal(item.path)
    base = item.score
    score = base
    score += log1p(signal.openCount) * 0.10
    score += max(0, 0.2 - daysSince(signal.lastOpenTs) * 0.005)
    score += isRelatedToCurrentFile(item.path) ? 0.2 : 0
    score += anchorBoost(signal, pprActive)
    score += wasClicked(item.path) ? 0.15 : 0
    score += signal.mobiusNodeType == "hub_doc" ? hubDocBoost : 0
    return { ...item, score }
  })

  ranked = sortByScoreDesc(boosted)

  visible = applyExcludesAndTopK(ranked, plan.excludes, plan.topK)
  visible = addHighlightSnippets(visible, plan)

  if settings.enableLLMRerank and settings.rerankModel:
    rerankScores = callRerankProvider(rawQuery, visible)
    visible = visible.map(item => {
      normalized = rerankScores[item].raw > 1
        ? rerankScores[item].raw / visible.length
        : rerankScores[item].raw
      return { ...item, score: item.score * 0.7 + normalized * 0.3 }
    })
    visible = sortByScoreDesc(visible)

  return visible
维护者读法
  1. 如果用户问“为什么这条出现”，先看 sources 和每路 RRF contribution。
  2. 如果用户问“为什么这条排这么高”，再看 PPR rank、ranking boost 分量和 LLM rerank 是否启用。
  3. 如果用户问“为什么没出现”，看 retriever 是否激活、path 是否被 exclude、是否被 topK 截断。
  4. Highlight 只解释 final result 的可见匹配片段，不应该被当成排序分数来源。
Highlight 源边界（2026-07-07 起）：Vault-first for markdown-like，chunk_raw for binary QueryService.textSearch() 在 final topK 后走 HighlightSourceResolver。按 DocumentType 分流：
  • Vault-readable（markdown / txt / csv / json / html / xml / canvas / excalidraw）：resolver 直接 vault.cachedRead(path) 拿当前文件全文，喂给 HighlightEngine.highlightSnippet()，用 hintOffset = chunkIndex / total × fileLength 让 window 落在打分 chunk 附近。这条路径**永远反映磁盘当前状态**，不会展示"已经删掉的段落"。
  • Binary / derived（pdf / docx / pptx / image / url）：resolver 从 doc_chunk.content_raw 拿索引期提取的文本。这些类型没有可 re-parse 的 Vault 源，content_raw 是它们的唯一 extracted-content 存储。
  • 降级链：Vault read 超时（SEARCH_HIGHLIGHT_VAULT_READ_TIMEOUT_MS = 200）→ chunk_raw → semantic summary → title/path 标签 → normalized。每一档在 SearchResultItem.highlightSourceKind 上留痕，Search debug trace 可读。
  • 存储变化：Vault-readable 类型的 doc_chunk.content_raw 与全表 content_fts_norm 都停写，一次性迁移 null 掉存量并 VACUUM，去掉 markdown 大约 18% 的 SQLite 文本冗余。
设计详见 2026-07-07 Vault-first spec（supersedes 2026-07-06 spec）。
阶段规则维护边界
RRF merge 每条 result 贡献 weight / (60 + rank0 + 1)；同 path 合并。 新增 retriever 必须有 weight；缺省 weight 是 0.5。
PPR 由 settings 控制，query 可 force-disable；失败 catch 后回退原结果。 图排序不能成为基础 search 的硬依赖。
Ranking boosts 读取 reranker signals、current file related paths 和 click-through paths。 boost 是排序增强，不应该绕过原始召回。
Highlight 只对 final topK 结果生成 snippet/title highlight；raw source 由 HighlightSourceResolver 决定——markdown-like 类型走 Vault 磁盘原文，binary 类走 doc_chunk.content_raw，无源时降级到 title/path 或 normalized。 不要在每一路 retriever 提前做高成本 highlight；不要为 Vault-readable 类型写回 content_raw——resolver 会实时读盘，避免 stale。新增 DocumentType 时到 isVaultReadableSource() 显式登记。
LLM rerank 只有 enableLLMRerank 为 true 才运行。 默认 search 不依赖 LLM。

失败和降级：增强项不能拖垮基础搜索

这个 pipeline 的一个重要产品承诺是：即使语义索引、图排序或某一路召回不可用，用户仍然应该尽量得到基础结果。

情况现在怎么处理
SearchClient 未 init 抛出 SearchClient not initialized. Call init() first.；调用方要保证 SQLite/store 初始化顺序。
空 query 返回空 items；不要把空 query 偷换成 recent 或 browse。
单个 retriever 失败 Registry catch 错误，该路返回空；多路召回必须局部失败可恢复。
Vector 条件不满足 VectorRetriever.shouldActivate 返回 false；semantic search 是增强，不是基础 search 必选项。
PPR 失败 catch 后继续用原 resultItems；graph rerank 不应阻断普通搜索。

失败、bad case 和处理

搜索问题不全是“故障”。有些是增强项不可用，有些是排序权重不符合直觉，有些是 query 太窄。先区分类型，再决定是修配置、改 query，还是调权重。

现象可能原因怎么判断和处理
输入后没有结果。 query 为空、索引未准备好，或当前 scope 太窄。 先看是否有实际 terms/phrases、Quick Search footer 是否显示搜索中、索引是否完成；再换一个更宽的 query，退出 in-file/folder scope，或运行索引维护。
语义相关结果没有出现。 vector retriever 没有激活。 检查 vector search 是否 enabled、embedding profile 是否有 endpoint 和 model；条件不满足时配置 embedding profile，或接受基础 FTS/metadata 结果。
拼写接近但没有被纠错。 fuzzy 主要依赖标题 token cache，不是全文拼写检查。 看目标词是否出现在标题 token 里；没有命中时改用更接近标题的词，或用普通关键词/语义 query 扩宽搜索。
AI Search 里 Web Search 不可用。 没有配置 Web Search profile。 到 Settings → Profiles 看是否有 profile 被设为 Web Search；配置后重试，没有 profile 时只使用 Vault/模型已有能力。
图关系排序看起来没有影响。 PPR 被关闭、没有可用 docId seed，或 PPR 失败后回退。 先确认基础结果可用；再看 Search settings 的 PPR 开关、console 是否有 PPR failed 日志、图索引是否可用。
标题明明很像，但结果排得低。 正文/语义分数压过了 metadata/title boost，或 query 太长稀释了标题命中。 看目标词是否在标题 token cache、metadata retriever 是否参与；用更接近标题的短 query 复测，若稳定复现再调 metadata/title boost。
CJK query 下语义相似但无关键词命中的文档排到前面，命中关键词的反而靠后（2026-07-07 遇到过：搜 英语练习，docs-表格中的Deltas和Mask插槽机制 37% 排第二，命中 英语练习 的多条只有 21%）。 title/path/content 命中 boost 用了 FTS-normalized 字段做匹配，且 CJK query 是一个整 token —— 两条都命中 → hit ratio 恒为 0 → 每条 result 的 keyword boost 都是 0，最终排序完全靠 vector base score。
失败链条：
  1. Indexer 把 title 存进 doc_chunk_meta_fts 前跑 normalizeTextForFts()，CJK 被逐字加空格、- 变空格；
  2. Retriever 直接把 normalized title 塞回 SearchResultItem.title；
  3. Boost 逻辑 title.includes('英语练习') 在 英语 需要 练习 里找不到（整串被切开了）；
  4. Query parser 按空格切 token，CJK 没空格，plan.terms 里就一个 英语练习 整块；这个整块在任何被切开的 normalized 文本里都不匹配。
 修法（rankingBoosts.ts + reranker.ts + highlight-engine.ts）：
  1. Title match 用 deriveRawFilename(item.path)（原文文件名，含 -），不要用 item.title；
  2. 用 expandQueryTokens(terms, phrases) 展开 query —— CJK 走 segmentToWhitespace 拆子 token，英语练习 → ['英语练习', '英语', '练习']；
  3. 加 pathHitRatio（含 folder segment，救 英语练习记录/foo.md）+ contentHitRatio（救正文命中但 title/path 无命中）；
  4. Snippet 高亮和 UI title 高亮也走同一套 CJK 子 token 展开（highlight-engine.cjkSubTokens / VaultSearchResult.highlightRawTitle）。
回归检查：动 rank/highlight/display 前，问自己「这个字段是否流过 normalizeTextForFts」；是的话，改用 path 派生原文。CJK query + 带 - 的文件名必须进 test case。
整个排序算法看起来"不对"——常打开的文档挤前面 / vector 相似度无关文档进来 / folder 命中的看不懂 / 百分比像随机数。 加法 boost 架构 + personalization 权重过高 + 无 relevance gate + 排序组成不可见。属于结构问题，不是单点 bug。 完整的第一性原理拆解、学术界+产业界调研（Dumais SIS / Teevan re-finding thesis / Notion 2026 blog / Elastic multiplicative boost / Slack Personalized Search 等）、所有讨论过的方案矩阵及取舍见 2026-07-07 Vault Search 排序：第一性原理拆解。
核心结论：先做诊断层（debug trace 补记每一项 boost 贡献）+ UI 暗示 filter 语法；先看清楚，再改算法。BM25F / LLM rerank / 意图分流 / 反向 personalization 全部先搁置——都是过度设计或未验证猜想。
Snippet 高亮看起来像分词后的文本，CJK 字符之间有空格。 Resolver 落到了 normalized_fallback——Vault 读文件超时或 chunk_raw 也没有。 看 SearchResultItem.highlightSourceKind / highlightVaultReadMs（debug 字段）。若是 markdown 类，通常是 Vault 慢盘或路径丢失；若是 binary 类，可能是 content_raw 索引缺失。设计和降级链见 Vault-first spec。
语义结果相关但用户不想要。 vector 召回把概念近似当成相关；缺少 folder/tag 过滤。 判断 query 是否该带 tag: / folder:，以及 vector weight 是否过高；把自然语言意图翻译成更窄的 filters，必要时降低当前 query 形态下的 vector weight。

维护规则：新增搜索能力必须进入同一条 pipeline

不要这样做应该怎么做原因
在 UI 里单独写一个“更聪明搜索”。 新增 retriever 或 rerank/boost stage，并接入 QueryService。 否则用户会得到两套不一致的搜索语义。
让 vector/PPR/LLM rerank 成为必选路径。 保持它们 optional/failure-tolerant。 搜索是基础能力，不能因为增强项失效而不可用。
新增 retriever 但不定义 weight。 在 query plan weights 中表达它的相对重要性。 RRF 需要知道每一路信号的分量，不然排序会漂。
把高亮提前塞进每个 retriever。 最终 topK 后统一 highlight。 降低成本，也避免每一路结果展示语义不一致。
