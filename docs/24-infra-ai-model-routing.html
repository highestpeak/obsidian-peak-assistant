24 · Infrastructure · AI model routing

AI 模型路由：每个用到 AI 的地方在用哪个模型，什么时候降级、什么时候升级。

这篇写给要回答“这次 AI 调用到底跑的哪个模型？为什么？”的维护者。用途槽（slot）→ 起始 tier → 可选升级 → fallback 是项目的目标模型；2026-07-28 复核发现当前生产代码仍有多条旁路，不能再写成“所有 AI 调用已经经过同一套解析”。

  • 目标解析入口：ProfileRegistry.resolveSlot(slot)；harness 的核心绑定会走它，但一次性文字、Copilot 和部分直接 provider 路径仍会绕过。
  • 唯一配置面：Settings → AI Setup 的五行（Conversation / Fast Lookup / Research / Use stronger model / Knowledge Index）。

0. 这份文档怎么读。

本文是 runtime routing map + source-code reading guide。它不解释每个功能做什么（那在各自的 feature 文档里），只回答一件事：某个 AI 触点的模型是怎么被选出来的。

本文读者

要排查“这次为什么用了 deepseek-r1 而不是 qwen”、或要改模型路由的工程师 / AI coding agent。

读完能做什么

对任意 AI 触点说清：用哪个槽、起始 tier、能不能升级、没配时降级到哪、改哪一行 Settings 生效。

本文不做什么

不讲 Provider/Profile/MCP/Skill 五层供给（见 18），不讲 Harness 运行时全貌（见 21）。

2026-07-30 当前实现校正

Claude Agent SDK 已完全退役。当前生成式调用分为三种执行形状：带多 tier 的 Peak Harness loop、固定模型的 Peak Harness run，以及少量仍直接调用 provider adapter 的单轮 helper；embedding 另走 Knowledge Index binding。用途槽、active Agent / Copilot role 与 feature-local fallback 仍未完全收敛成一个 resolver。旧 promptModelMap 虽会被加载，但主要 queryText / queryStream / queryTextStream 没有消费它，所以“逐 Prompt 选模型”现在不是可用功能。目标收敛方式和页面设计见 Prompt Control Center 设计。

1. 一张图：三层解析。

当前模型路由先解析用途 binding，再决定是多 tier Harness、固定模型 Harness，还是 feature-local provider-direct helper。Provider 只执行模型推理；Peak Harness 才拥有 agent loop、tool、permission 与 trace。

    conversation → Conversation(chat → agent)
    knowledgeIndex → Knowledge Index(embedding)
关键区分：升级 ≠ 降级。
  • 升级（cascade / escalation）是运行时行为：一次多步 agent 跑到一半，模型不确定 → 临时切到更强的 tier。只发生在拥有多个 binding 且允许升级的 TierController 上。
  • 降级（fallback）是解析时行为：某个槽没在 Settings 里配置 → resolveSlot 回退到对应 role。跟运行质量无关，纯粹是“没配就用替代”。

3. 五个槽 + 降级规则。

Settings → AI Setup 的五行是面向用户的主要配置单位。resolveSlot 是 slot-aware Harness consumer 的统一解析入口；部分 active Agent/Copilot role 与 provider-direct helper 仍有自己的兼容 fallback，见 §2.2–2.3。

fastFast LookupFast Lookup 配置 → agent-fast roleAI Analysis 后续对话、Ambient；Refine 首选此槽
researchResearchResearch 配置 → agent roleAI Analysis 主搜索、报告生成
strongerUse stronger modelStronger 配置 → Conversation(chat → agent)仅作升级兜底（见 §4）

不要把 role 当成 slot。Graph、Review、部分 Copilot / Intuition 目前仍直接读取 active Agent、Agent Fast 或 feature binding；它们已由 Peak Harness 执行，但还没有统一改成 resolveSlot。

3.1 降级规则的完整形式

resolveSlot 的 fallback 完全发生在 ProfileRegistry 内，没有额外的 SDK fallback 层：

fast           = Fast Lookup ?? active Agent Fast
research       = Research    ?? active Agent
stronger       = Stronger    ?? active Conversation ?? active Agent
conversation   = active Conversation ?? active Agent
knowledgeIndex = active Embedding

若某个 cascade tier 的 resolveSlot 返回 null，该 tier 会从 bindings 缺席，TierController 再 fall-forward 到下一个已绑定 tier。固定模型或 provider-direct feature 可以定义自己的兼容 fallback，但那不属于全局 slot contract。

降级 · 实例

你只在 Settings 里配了 Research = OpenRouter · deepseek-r1，没单独配 Fast Lookup、没配 Stronger。此时：

  • resolveSlot('research') → deepseek-r1（① 命中）。
  • resolveSlot('fast') → Fast Lookup 空 → 回退 active Agent Fast；两者都空则返回 null。
  • resolveSlot('stronger') → Stronger 空 → 回退 Conversation；Conversation 空 → 回退 agent role。

3.2 配置怎么落到槽（镜像同步）

三个 Harness tier 配置存在 settings.harnessSettings.{localFastConfig, localDeepConfig, onlineConfig}（字段名沿用旧名，不影响槽语义）。main.ts 在 bootstrap 与每次 saveSettings() 时经 ProfileRegistry.setTierConfigs() 把它们镜像进 registry，resolveSlot 才能读到当前值。保存后会立即影响所有 slot-aware 路径；仍读取 active Agent / Agent Fast / feature binding 的路径按各自 role 配置解析，不能宣称五行 AI Setup 已经覆盖所有调用面。

4. 升级规则（cascade / escalation）。

只有拥有多个 binding 的 TierController run 才可能升级。HarnessModelRunner 的固定模型调用、Chat 单 tier run 与 provider-direct helper 都不会中途换模型。

4.1 机制

  • 起步。从 policy.preferred 的 tier 开始（AI Analysis=research，后续对话=fast）；若该 tier 未绑定，fall-forward 到下一个已绑定 tier。
  • 每步自评。onStepFinish 用 scoreStep 给这一步打分（见公式）。
  • 触发升级。若 allowEscalation 且 未超本轮上限 且 score < escalationThreshold → 沿 fast → research → stronger 升到下一个已绑定 tier。
  • 模型也能自己要求。model 可调 escalate 工具（带 reason）主动升级。
  • 只升不降。升上去就不回落；每轮最多升 maxEscalationsPerLoop 次。

4.2 打分公式

score = 0.5 · schemaPassRate   # 工具调用的 schema 校验通过率
      + 0.3 · toolSuccess      # 工具执行成功率
      + 0.2 · language         # 文本确定性（对冲/不确定措辞扣分）
                               # scoreStep.ts:41 · clamp 到 [0,1]

升级条件： score < escalationThreshold

4.3 当前实际生效的参数

两条多 tier 路径当前并不使用同一组 policy：Vault Search 已接入 Settings；结果面板后续对话仍只传 preferred，其余使用 DEFAULT_TIER_POLICY。

路径policy 来源当前值
Vault Search / Continue AnalysisharnessSettingsallowEscalation、autoEscalateScoreBelow、maxEscalationsPerLoop；默认 true / 0.4 / 3
AI Analysis 后续对话DEFAULT_TIER_POLICYtrue / 0.6 / 1
升级 · 实例

Research=deepseek-r1，Stronger=qwen3-max，Vault Search 保持默认 threshold=0.4。跑 AI Analysis：起步 research（deepseek-r1）。某步一个工具 schema 校验失败 → score 掉到 ~0.35 < 0.4 → 升到 stronger（qwen3-max）跑后续步骤。若 Stronger 未绑定，则无处可升，继续用 research。默认最多允许 3 次升级，但当前只有 fast / research / stronger 三个 tier，实际次数仍受剩余已绑定 tier 数限制。

⚠ 当前不一致：后续对话尚未接入 Settings policy。

VaultSearchAgent 已把 harnessSettings 的三个 escalation 字段传给 TierController，所以 Settings 调整会改变主 AI Analysis。FollowupChatAgent 仍只传 { preferred: 'fast' }，因此结果面板的后续对话继续使用默认 0.6 / 1。要完全一致，需让 Followup 同样消费这三个字段。

5. 三条典型路径详解。

5.1 一次完整的 AI Analysis

同一次分析跨了两条解析路径，注意区分：

  • 搜索阶段（列文件夹、grep、读笔记、submit_plan）：harness agent，槽 research，可升级到 stronger。
  • 报告生成阶段（分段成文、Mermaid）：固定模型 Peak Harness，槽 research，不升级。
  • 结果面板后续对话（Topic/Graph/…）：harness agent，槽 fast，可升级。

因为搜索与报告生成都归到 research 槽，改一次“Research”对整条分析链一致生效——这是 2026-07-23 统一 resolver 之后的行为；此前报告生成走独立的 agent role，会和搜索漂移。

5.2 主 Chat 一条消息

槽 conversation（= Conversation 行）。经 harnessChatRunner 绑成单 tier、allowEscalation:false——永不升级。Assistant 指定了固定模型时以 Assistant 为准，否则 Auto 默认回到 Conversation。

5.3 报告生成 / Graph / Review（固定模型 Harness）

三者都进入 HarnessModelRunner，但 binding 来源不同：报告生成用 resolveSlot('research')；Graph 与 complete Review 用 active Agent；fast Review 优先 active Agent Fast，其次 Agent profile 的 fastModel，最后回到 Agent model。它们可以执行多轮工具调用，但每个 run 只绑定一个模型，没有 tier cascade。
