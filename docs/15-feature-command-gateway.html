15 · Feature · Command Gateway · T12 capstone

把第三方 Obsidian command 关到闸门里：AI 起草 · 用户授权 · runtime 守边界。

Command Gateway 不是又一条“让 agent 更强”的功能，它是 整个新架构最后的验收关卡。它回答一个非常具体的问题：

  • 第三方 Obsidian 插件注册了它自己的 command（比如 Calendar: open weekly note、QuickAdd: template、Advanced Tables: sort rows）
  • Peak 的 agent 能不能安全地调用它们
  • 而不用给 agent 一个 “调用一切 Obsidian API” 的口子

这份文档讲：四层概念（Command / ToolDef / Skill / Capability）为什么必须分开；AI Curator 起草到用户授权到 runtime 执行的完整流水；当前仓库里哪些零件已经在了、哪些还得补；什么样的 command 不应该被授权。

这页解决什么

Obsidian 是插件生态。用户装了几十个第三方插件，每一个都往 command palette 注册若干 command。agent 想帮用户完成一次工作流，往往需要触发这些 command 的一部分——但绝不能 任意 触发。Command Gateway 就是把 “agent 能调外部 command” 这件事关进闸门：

本篇文档同时是 说明 与 规格。Command Gateway 是 T12 capstone；当前仓库里 foundations 已在（ToolDef / PermissionGuard / Skill / RunEnvelope），但 CommandPort、Curator 的 CommandGateway schema、Settings/Tools 里的 Plugin Capabilities review 界面、command 副作用观测 都还没接上——本页 § T12 还得补的四件事 明列。
核心决策 AI 负责判断，用户负责授权，runtime 负责边界。三者缺一不可：AI 能读 command 名、插件源、用户上下文，比硬编码规则更适合分类；但 AI 不能自己写进 allowlist——必须走 Review Surface 让用户勾一次。授权后，执行阶段仍由 PermissionGuard 守 deny-first 边界——就算 AI 和用户都同意，系统级 deny rule 也 override。
本文读者 熟悉 agent / tool / policy 概念但不熟悉 Peak 新架构的工程师；正在规划 T12 交付的 coding agent；打算读懂“Peak 会不会偷偷让 agent 删我 vault”的用户。
本文不做什么 不列举 Obsidian 插件生态；不做 UI 完整视觉稿（review surface 只画一版概念图，正式设计在 T12 spec 里）；不把 command 当作 capability（这正是要避免的最深退化）；不重复 21 Agent Harness 的 tool loop 内部机制。

四层概念：Command / Tool / Skill / Capability

这是本页最重要的一段。如果这四层被拉平成同一层，整个 Command Gateway 会退化成“扫描 palette + prompt 让模型调”，那就是新架构的第二套 runtime。四层的角色完全不同：

层它回答的问题谁生成 / 决定不可混淆点
Command “Obsidian 或第三方插件暴露了什么按钮？” Obsidian core 或第三方插件 Command 可能只打开 UI；不代表 agent 能安全自动调。
ToolDef “Peak 能否把它包装成可测试、可阻断、可返回结果的工具？” Gateway 生成候选；系统实现执行器 ToolDef 必须有 schema、kind、错误归一化、policy 入口。
Skill “Agent 在什么场景下应该如何组合这些工具？” AI Curator 起草；用户或系统确认后编译 Skill 是工作手册，不是权限本身；权限来自 Policy。
Capability “Peak 产品承诺帮用户完成什么知识工作？” 产品架构定义 Capability 引用 Skill + ToolPolicy；绝不直接等于 command。
为什么 command 不能直接是 capability 举个反例：Calendar: open weekly note 是一个 command。如果直接把它注册成 capability，产品对外承诺变成 “Peak 支持 open weekly note” —— 但 用户真正想做的 是 “按当前工作状态起草这周的规划，Calendar 只是承载物”。Capability 应该是 work.plan.weekly；Calendar: open weekly note 只是这个 skill 里的一个原子操作。倒过来的分层会导致：capability 数量爆炸（每装一个插件就多几十条 capability），UI 全是命令 id，Skill 概念消失。

Draft → Authorize → Execute

Command Gateway 的完整流水是三段，每段边界清楚：AI 只在 Draft 阶段起作用；Authorize 是纯 UI + 用户判断；Execute 是运行时守边界。跨段的东西一定要落到持久化 / 可回放的记录里，不能只留在内存里。

阶段谁参与输入 / 输出硬约束
Discover Gateway service 入：Obsidian app.commands 表 + 已装插件 manifest；出：raw CommandDescriptor[] 只查、不订阅、不缓存原始 API 引用。
Enrich Gateway service 入：descriptor；出：加了 plugin source、需要的 context（active editor?）、历史使用频率 不看 command 的具体实现，只看 metadata。
Classify（AI） Curator LLM 入：enriched；出：{risk, utility, observability, notes} 输出必须走 zod schema；错误 fallback 到规则。
Draft（AI） Curator LLM 出：候选 ToolDefDraft + SkillDraft Skill 的 allowedTools 白名单必须是 已批准 的名字。
Review 用户 入：draft；出：allow / deny / edit 可以拒绝、可以修改 rationale；不能批量 “allow all” 未看的建议。
Compile Gateway service 入：approved draft；出：ToolDef 注册进 ToolRegistry；Skill 注册进 SkillRegistry 都进 quarantined 命名空间；不覆盖内置。
Runtime PermissionGuard + CommandPort + RunEnvelope 入：Skill 请求 tool；出：ToolResult + RunEvent + ArtifactRef Deny rule 永远最高优先级，即使 Skill 白名单同意也可能被拦。

AI Curator 输出规格

Curator 是本流水唯一的 AI 环节。它的输出 必须结构化 + 必须可解释 + 必须可拒绝——不能只有一句 “recommended: true”。

为什么 Curator 是 LLM 而不是规则 command id 本身就有语义（calendar:open-weekly-note 就是可读的），加上插件名和 category 提示，LLM 的分类和解释比正则准得多。但——LLM 会幻觉出不存在的 command，会给危险 command 起漂亮名字。所以必须：schema 校验 + 规则兜底 + 用户 review 三重防御。

Curator 每评估一个 command 产出这样一份 record（用当前仓库里 src/service/agents/harness/curator/ 的 zod schema 类比来写）：

{
  commandId: "calendar:open-weekly-note",
  pluginSource: "obsidian-calendar-plugin",
  risk: {
    level: "medium",              // green | amber | red | blocked
    modifiesVault: true,
    needsActiveEditor: false,
    observable: true,
    rationale: "创建或打开一个周记 note；副作用可观察"
  },
  utility: {
    intent: "work.plan.weekly",
    exampleUseCase: "把当前工作状态草稿汇进本周规划",
    evidence: ["plugin source", "command name", "recent weekly note use"]
  },
  toolProposal: {
    name: "calendar.openWeeklyNote",
    kind: "edit",                 // read | edit | destructive | meta
    inputSchema: { /* zod schema */ },
    confirmation: "per-run"       // never | per-run | per-session
  },
  skillDraft: {
    id: "work.plan.weekly.calendar",
    whenToUse: "用户想按当前状态起草本周规划时",
    allowedTools: ["calendar.openWeeklyNote", "vault.readFile"],
    outputContract: "一份 markdown 草稿 + 保存位置",
    failureMode: "无 active editor 时提示用户手动打开"
  },
  action: "suggest"               // suggest | auto-allow (never for edit+) | block
}
Curator 输出必须包含不能包含为什么
Risk finding 等级、依据、是否修改 vault、是否需要 active editor、是否可观察结果 不能只有 recommended: true 用户授权需要理由，不是相信模型一句话
Tool proposal 候选 tool name、kind、input schema、confirmation policy、preflight needs 不能直接写入 runtime registry 工具必须先过权限和 review
Skill draft 适用场景、使用步骤、allowedTools、输出契约、失败时怎么做 不能带无限制工具访问 Skill 是工作手册，不是越权口子
Rejection reason 为什么不建议开放：modal-only、unknown side effect、destructive 不能静默丢弃 用户需要理解 Peak 的安全判断
Retry + fallback：Curator 已经是这个模式 当前 src/service/agents/harness/curator/CuratorAgent.ts 已实现 LLM 试 3 次 → 失败回落到规则。Command Gateway 的 Curator 应复用同一模式；不要新起一套。用户能容忍 “这条命令我们没能自动分类，请手动查看”，不能容忍 “模型幻觉了一个不存在的 command 让我批准”。

用户 Review Surface

Review Surface 是用户心智的关键。不能只是 raw command 表。用户看到的必须是“Plugin Capabilities”——按用途聚合的能力包，每一行都带证据、风险、Skill 用途、执行策略。

读图：左侧按 用户意图 分组，右侧每条建议携带 evidence / risk / action。不出现 command id 列表；不出现 “Allow all” 按钮。

信任原则 Review Surface 不是让用户管理底层技术细节，而是让用户 相信 Peak 没有偷偷开放插件能力。用户必须能看到每个建议的 evidence、risk、Skill 用途、confirmation policy、最后一次运行 trace。做不到，就宁可不开放。
禁止的三种 UI 退化 (1) “一键 Allow all suggested” 按钮——摧毁授权语义。(2) command id 直接 checkbox 列表——用户没上下文，只会随便勾。(3) 授权后不再展示 trace——用户会以为 “只批一次” 结果 agent 反复用。任何一种都会让 Gateway 从 “安全边界” 退化成 “安全遮羞布”。

运行时合同

授权完成后，agent 请求 tool → PermissionGuard 判定 → CommandPort 调 Obsidian → RunEnvelope 记录。这条链的顺序不能变，任一环缺了都会破坏 可预检 / 可阻断 / 可观察 / 可回放。

图 4 · Runtime 时序（sequence diagram） Mermaid · runtime collaboration
sequenceDiagram autonumber participant Cap as Capability Runner participant Skill as Compiled Skill participant Tool as ToolRegistry participant Policy as PermissionGuard participant Cmd as CommandPort participant App as Obsidian App participant Run as RunEnvelope Cap->>Skill: select approved skill for user intent Skill->>Tool: request tool by name Tool->>Policy: check kind + rules + mode Policy-->>Tool: allow / deny / require-confirm Tool->>Cmd: execute(commandId, args) Cmd->>App: app.commands.executeCommandById() App-->>Cmd: side-effect happens Cmd-->>Tool: ToolResult { ok, data | error } Tool-->>Skill: result Skill->>Run: recordArtifact + recordEvent Run-->>Cap: RunEvent stream

读图：Skill 从不 直接 摸 Obsidian —— 它只跟 ToolRegistry 说话。Policy 在 tool 之前，不在 command 之前，因为 tool 层是 Peak 拥有的抽象，是加 guard 的正确层。

运行时属性由谁保证怎么验证破坏后果
可预检 CommandPort.preflight() 需要 active editor 但没有 → 直接返回 error: preconditions 无声失败；用户不知道 command 为什么没跑
可阻断 PermissionGuard deny-first golden scenario：even in bypass mode, system deny rule still blocks 用户以为 “只让 agent 读”，agent 却在改文件
可观察 RunEnvelope 记录 event + artifact trace 里能看到 ArtifactRef（新文件、diff、workspace state 变化） 用户没法回看“上次 agent 到底改了啥”
可回放 Test harness 用 fake CommandPort 用 recorded RunSession 跑一次 fake port 得到相同 artifact bug 复现只能靠原地重试
Policy 加在 Tool 层，不加在 Command 层 因为 ToolDef 是 Peak 拥有的模型——它的 name、kind、schema 都是 Peak 定义的。Command 是外部 API，可能只提供 id 和一个回调函数，没有稳定语义。在 tool 层加 guard 意味着：不管 command 长什么样，agent 请求 tool 就必然过 Policy。这是新架构 capability contract 的直接应用。

T12 还得补的四件事

下面这四件是当前仓库 没有 的，T12 交付时必须补齐。如果任何一件被 “先跳过、以后补”，那 Command Gateway 就变回了 “agent 直连 Obsidian”。

1. CommandPort 抽象（discover / preflight / execute） 现在 Peak 只 注册 自己的 command（src/app/commands/Register.ts）；调 外部 command 没有稳定入口。CommandPort 必须暴露 listCommands()、preflight(commandId, ctx)、execute(commandId, args) 三个方法；service 层 永远 不直接摸 app.commands。放在 src/core/ports/CommandPort.ts；实现在 src/app/commands/ObsidianCommandAdapter.ts。
2. Curator 的 CommandGateway schema + prompt 当前 curator/schema.ts 是 模型 curator 的（quick/deep/premium binding、cascadeEnabled）；命令 curator 需要新一份 schema：{risk, utility, toolProposal, skillDraft, action}，加对应 prompt。文件路径建议 src/service/agents/harness/curator-command/，与模型 curator 平级。
3. Review Surface：Settings → Tools → Plugin Capabilities UI 目前 没有 这一屏。放在 src/ui/view/settings/（复用现有 Tools 段）；列表按 用户意图 聚合而非 command id；每行必须显示 evidence + risk + action。没有 “Allow all” 按钮。
4. 副作用观测（Artifact for command execution） Command 执行后需要产出 可回放 的 ArtifactRef：创建了什么新文件？改了哪几行？workspace state 怎么变了？。RunEnvelope 已有 ArtifactRef 类型；补的是 CommandPort 在 execute() 后包这个 artifact 的逻辑，让 PermissionGuard 的判定和结果都被记录。
顺序有讲究：先补 1 → 4，最后才做 2 → 3 没有 CommandPort（1）和 Artifact 观测（4），Curator（2）没有稳定输入，Review（3）没有 evidence。先 把工程边界打好，再 让 AI 起草，最后 做用户 UI。反过来的顺序会把 AI 逼到 “想象一份接口来分类”，产出不可信。

Copilot Command Center meta-agent（D2 · 2026-07-03 shipped）

Command Gateway 的第一个"AI 组合器"是 Copilot Command Center——不是单一 command，而是让 meta-agent 根据用户的一句话目标 草拟一串 command 顺序，然后逐条 gateway.dispatch(commandId)。

为什么走 CommandGateway 而不是 Copilot 自己实现

  1. 不重造能力 — Copilot 想让用户"summarize this note then draft link suggestions then run vault-health"？三个 command 都已经在 CommandGateway 里注册过，直接引用 commandId。
  2. Curator/PermissionGuard 生效 — 走同一个 runCapability，manifest/permission 分级不需要额外接线。
  3. 路径统一 — palette 手动触发、Copilot meta-agent 触发、未来 Skills 触发，全部经 dispatch(commandId)；trace 里 trigger 字段区分。

数据流

plan 只引用已注册 commandId copilot-command-center-plan 系统 prompt 把 commandGateway.all() 的当前列表塞进上下文，硬约束"MUST be one of the ones listed above"。capabilityPlanStepSchema 里 readOnly: boolean 让规划器区分读 vs 写，Executor 在写-步骤失败时立即停手，避免部分 mutation 级联。

流程：用户在 CopilotCommandCenterModal 输入 goal → CopilotCommandCenterService.planOnly() 走 queryStructured 拿到 CapabilityPlan（planTitle / summary / goalRestatement / steps[1..8] / confidence）→ modal 展示 review → 用户点 Execute → executePlan() 逐条 gateway.dispatch → 每步 outcome 汇总回 stepOutcomes。

失败模式

  • 规划器凭空生成不存在的 commandId → executor 按 outcome: 'skipped' 继续下一步（不中断）
  • 写-步骤失败（readOnly: false + throw）→ executor 立即停止，保护后续写不做
  • 读-步骤失败 → 记为 failed 但继续（读失败不脏化状态）

禁止 / 阻断的场景

下列 command 类别 不进入 Curator 建议流程——直接由规则拒绝。规则永远高于 AI，AI 高于用户默认，用户显式高于 AI 默认——但系统 deny 永远最高。

Gateway 风险典型 command映射 ToolKind默认策略
Read / Navigate 打开视图、切换面板、显示搜索结果 read 或 meta 可推荐开启，但仍需授权。记录 tool_call + workspace-state artifact。
Current-note edit 插入模板、格式化当前选区、创建单个 note edit 默认关闭；per-skill 开启；preflight 需 active editor；执行前展示可读意图；执行后记录 diff。
Vault mutation 批量移动、批量重命名、批量标签修改 destructive 或 system deny 默认 deny。只能人工 review，不 作为自动 tool。
Modal-only 打开 QuickAdd modal、打开插件设置 meta 不作为自动 tool；只作为 suggested action 让用户点。
Unknown 来源不清、名称不清、副作用不可观察 system deny 阻断。需要用户手动标注或插件 manifest 补充。
Deny-first 是硬约束，不是策略偏好 PermissionGuard 的决策顺序 (1) deny → (2) mode prohibitions → (3) allow → (4) mode default 意味着：用户手动加 allow rule 也不能覆盖系统 deny。Command Gateway 依赖这条约束——否则 “允许 agent 帮我做事” 的模式随时可能被一条恶意 command 利用。

不要退化成什么

下面这几种“看起来合理但违背设计目标”的实现方式必须显式列出——每一种都会把 T12 从 capstone 变成又一层技术债。

不要：service 层直接 this.app.commands.executeCommandById() 这么做等于放弃 Port 抽象；测试无法 mock、副作用无法观测、guard 无处安放。永远 走 CommandPort。
不要：新建 CommandAgentService 或 command-only agent loop Peak 已经有 Agent Harness。Command Gateway 是 它的一种输入源——不是另一套 runtime。多一套 runtime，意味着多一份 permission gap、多一份 trace gap。
不要：把 command 直接注册进 CapabilityRegistry Capability 是 产品语义（work.plan.weekly），不是 技术能力（calendar:open-weekly-note）。混层意味着 UI 上会长出几百条“capability”，且 Skill 概念被绕过。
不要：让 Curator 直接写 allowlist AI 的产出永远只到 draft——用户 Review 才能进 quarantined registry。绕过 Review 意味着 “agent 静默给自己扩权”，是本 feature 最坏的失败模式。
不要：把 Review Surface 藏在 agent 内部 Review 属于 Settings / Tools / External capability——用户找 “插件权限” 时能找到的地方。藏在 “Chat / Advanced” 里等于没做。
不要：单元测试用 real Obsidian app 要用 fake CommandPort——golden scenario 输入一个虚拟 command 表，输出一份 recorded RunSession，能确定性验证 “curator 是否分类正确 / guard 是否阻断 / artifact 是否记录”。
验收标准（回到 spec §1） 当以下三个都为真时，T12 才算完成：(1) fake CommandPort 能跑测试并输出确定性 RunEvent + ArtifactRef + policy trace；(2) 真实插件跑 golden scenario（比如 Calendar weekly note）；(3) system deny rule 在 bypass mode 下仍能拦住 destructive command。少一样都是 “看起来能用” 而不是 “架构通过外部压力测试”。
