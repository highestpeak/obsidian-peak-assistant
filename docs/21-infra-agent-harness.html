Agent Harness：让 Peak Assistant 的多步 AI 工作可控、可停、可追踪。

这篇文档写给第一次接触 Peak Assistant 的维护者。先别把 Harness 想成一个用户功能；它更像一层运行时——上游任意能力都可以借用它，把多步 AI 工作关进同一套边界：

  • 谁会用到：Chat、Search、Review、Copilot、以及未来的 capability。
  • 做什么：分步思考、调用工具、切换模型、压缩上下文、留下 trace。

0. 这份文档怎么读。

本文是 runtime explanation + source-code reading guide，目标不是介绍所有 agent 愿景，而是让维护者能打开代码、判断边界、写新工具、审查改动。

本文读者

懂 TypeScript 和 AI tool-calling，但第一次接触 Peak Assistant 的工程师或 AI coding agent。

读完能做什么

解释一次 Harness run 怎么走，知道改工具、权限、context 或 subagent 时该先看哪些文件。

本文不做什么

不规划 Command Gateway，不替代主架构手册，不把旧 spec 里的未来能力写成现状。

  • 先看系统边界。如果只想知道 Harness 在项目里负责什么，读第 1-2 节和系统边界图。
  • 再看一次运行。如果要改代码，先读第 3 节的时序图，再打开 AgentLoop.ts。
  • 最后按合同定位改动。改工具看 ToolDef；改安全看 Permission/Hook；改长上下文看 Context；改委托任务看 Subagent。

1. 为什么这里需要一个 Harness？

Obsidian 用户真正要的是“帮我完成一个知识工作”，不是“让模型多说几句话”。

例如：用户在 Chat 里说“帮我看看 Research/AI agents 这个 folder，找出可以合并的重复笔记，并给一个整理建议”。一个普通 chat completion 可以直接生成建议，但它很难可靠地做以下决策——

  • 什么时候搜索、什么时候读文件、什么时候停？
  • 能不能写 Vault？
  • 工具结果怎么记录？
  • 上下文超了怎么办？
  • 模型不确定时是否升级？

Harness 要解决的正是这类“多步 AI 工作”的运行问题。它不是某个 prompt，不是某个 UI，也不是某个 provider wrapper——它把每一步模型调用放进外层 loop，由代码负责七件事：

  • 预算（budget）
  • 权限（permission）
  • 工具封装（tool wrapping）
  • trace
  • context compaction
  • tier escalation
  • 停止条件（stop condition）
一句话定义 Agent Harness 是 Peak Assistant 的 agent runtime：它让模型可以分步工作，但每一步都被确定性的代码边界接管。
读者问题当前事实文档里的处理方式验证入口
它和普通 Chat 有什么区别？ AgentLoop.ts 每轮只让 AI SDK 跑一步，外层 loop 决定继续、停止、升级和记录。 先用一个真实任务解释 loop，再拆合同。 harness-loop.test.ts
它真的能挡住危险工具吗？ PermissionGuard deny-first，且 wrapTool 在 hook 和 execute 前先检查权限。 把权限写成运行门，而不是 prompt 建议。 harness-permission.test.ts
它怎么处理长上下文？ ContextManager 先估 token，再丢低优先级 evictable blocks，最后滑动窗口。 单独解释 memory/context 不是“无限塞 prompt”。 harness-context.test.ts
Subagent 是另一个系统吗？ Subagent 被包装成 subagent.<name> 工具，父 loop 只看到 summary。 把 subagent 解释成统一 ToolDef 下面的隔离运行。 harness-subagent.test.ts

2. 系统边界：Feature 说“要做什么”，Harness 管“怎么安全地做”。

这条边界很重要，因为它决定后续功能不会各自长出一套小 runtime。

五类 surface 都可能需要 agent 能力——Chat、Search、Copilot、AI Analysis、未来的 Command Gateway——但它们不应该自己实现 loop、权限、工具封装、context budget、trace。分工：

  • Feature service：只声明「任务、可用工具、权限模式、预算、结果订阅」。
  • Harness：用统一合同执行上面这些声明。

3. 一次 Agent run 到底发生了什么？

核心不是“模型有多聪明”，而是每一步都先经过运行时检查。

当前实现的主入口是 runAgentLoop(cfg)。它合并默认预算，创建或复用 TraceBus，触发 session_start hook，自动把 subagent 包装成工具，然后进入 while loop。每轮开始前先检查停止条件，选择当前 tier，过滤当前 tier 可用工具，必要时压缩上下文，再调用 Vercel AI SDK 的 generateText。每次调用被限制为 stopWhen: stepCountIs(1)，所以“继续跑几步”不是模型说了算，而是外层 loop 再决定。

运行时序图一次 run 的主要控制点
sequenceDiagram autonumber participant F as Feature service participant L as AgentLoop participant H as HookBus participant P as PermissionGuard participant C as ContextManager participant T as TierController participant M as Model participant Tool as ToolDef participant Trace as TraceBus F->>L: runAgentLoop(config) L->>Trace: loop_start L->>H: session_start H-->>L: continue or block loop each step L->>L: evaluateStopConditions L->>T: current tier L->>C: compactIfNeeded C-->>L: messages and memory blocks L->>M: generateText with one-step stop M-->>L: text or tool calls alt model calls tool L->>Trace: tool_call L->>P: check tool and args P-->>L: allow or deny L->>H: pre_tool_use L->>Tool: execute Tool-->>L: ToolResult L->>H: post_tool_use L->>Trace: tool_result end L->>T: onStepFinish and possible escalation L->>Trace: step_finish end L->>H: stop L->>Trace: loop_finish L-->>F: AgentLoopResult
  • 模型每次只获得一步机会。stepCountIs(1) 让外层 loop 能在每步之间重新检查预算、权限和上下文。
  • 工具调用不是直通。tool call 先进入 trace，再过 permission、pre hook、execute、post hook，最后才把结果交回模型。
  • 状态真相在返回值和 trace。调试时先看 finishReason、steps、tool traces，不要只看最后一段文本。
illustrative 简化后的控制逻辑，来自 src/service/agents/harness/loop/AgentLoop.ts 的结构，不是完整源码。
while (true) {
  const stop = evaluateStopConditions(state, budget);
  if (stop) break;

  const tier = tierController.current();
  const tools = filterToolsForTier(effectiveTools, tier);
  const messages = await context.compactIfNeeded(...);

  const result = await generateText({
    model: tier.resolve(),
    messages,
    tools: wrapToolsWithPermissionHooksAndTrace(tools),
    stopWhen: stepCountIs(1),
  });

  recordStep(result);
  tierController.onStepFinish(step);
  if (hasFinalAnswer(step)) break;
}

为什么要一轮只跑一步？

因为多步 agent 最大的问题不是“能不能调用工具”，而是“谁负责每一步之间的安全检查”。如果一次 generateText 放任模型自己连跑很多步，预算、权限、trace、context 压缩和 tier 升级都会被动跟在后面。当前实现把模型调用切成单步，外层 loop 就能在每次 step 之间重新检查运行条件。

4. 核心合同：Harness 由四个门和三个侧车组成。

第一次读代码时，可以先把 Harness 想成一个受控管道。

四个“门”决定能不能继续：预算停止门、模型 tier 门、权限/Hook 门、最终答案门。三个“侧车”提供运行支撑：Trace 记录过程，Context 管理上下文，Subagent 把委托任务变成工具。

  • Budget gate 是第一层。超过 step、token、tool call 或收到 abort signal 时，模型不会再获得下一步。
  • Tool gate 是真实世界边界。Vault、Search、MCP 和 subagent 都要通过 ToolDef wrapper，不能裸露给模型。
  • Trace sidecar 贯穿全程。它不是可选日志，而是 UI、测试和未来 RunEvent 的共同事实来源。

4.1 Loop contract：运行一次任务需要传进什么。

AgentLoopConfig 是 Harness 的主合同。它包含 loopId、system prompt、初始消息、工具、tier controller、预算、abort signal、trace、hooks、permission、subagents、memory 和 context。默认预算当前是 5 steps、20,000 tokens、10 tool calls。

字段它回答的问题维护风险
budget这个 run 最多能走几步、花多少 token、调用多少工具。不要在 feature 里写自己的 step counter，统一传给 Harness。
tierController本轮用哪个模型 tier，是否可以升级。不要让某个 agent 私自选择 provider 后绕过 tier 记录。
permission哪些工具可用，哪些写入或危险动作必须被挡住。没有 guard 时会回到 legacy allow-all，写工具时要显式传入。
traceUI、测试或未来 RunEvent 怎么观察过程。不要只靠 console 或 UI state 当调试事实。
context + memory哪些上下文块进入 system prompt，超过预算时怎么丢弃或压缩。不要把长历史直接拼进 prompt。

4.2 Tool contract：工具必须是可审查的接口。

ToolDef 声明名称、描述、Zod input schema、可用 tier、工具风险类型和执行函数。工具结果必须回到 ToolResult envelope：成功是 { ok: true, data }，失败是 { ok: false, error, recoverable }。业务失败不要用 throw 作为主路径，因为模型需要看到可恢复错误并调整策略。

existing excerpt ToolDef 的最小心智模型，来自 src/service/agents/harness/tool/types.ts。
interface ToolDef {
  name: string;
  description: string;
  inputSchema: ZodTypeAny;
  allowedTiers?: ModelTier[];
  kind?: "read" | "edit" | "destructive" | "meta";
  execute(args, ctx): Promise<ToolResult>;
}

4.3 Permission contract：deny-first 是硬规则。

权限不是给模型的一句提示，而是工具执行前的同步检查。当前 PermissionGuard 的优先级是：显式 deny rule、read mode 禁止 edit/destructive、显式 allow rule、模式默认。代码里还明确写着：bypassPermissions 也不能越过 deny rule。

顺序规则为什么这样排
1匹配显式 deny rule项目级红线不能被用户模式或模型输出覆盖。
2read mode 阻止 edit / destructive只读运行必须真的只读。
3匹配显式 allow rule允许细粒度开放某些工具。
4模式默认 allow保持 legacy 兼容，但前面的 deny 已经先执行。
不要过度承诺 当前权限层不是完整的“弹窗询问用户授权 UI”。代码事实是同步 guard + hook blocking/modification。用户确认界面、可审阅 diff、apply/reject 仍属于上层产品能力或未来 RunEvent/Artifact 工作。

4.4 Trace / Context / Subagent：让过程能被看见、缩小和隔离。

TraceBus 记录 loop_start、step_start、tool_call、tool_result、tier_escalate、context_compacted、loop_finish 等事件。ContextManager 用与 chat token estimation 一致的 chars/4 启发式估算消息和 memory block，超过阈值时先丢低优先级可驱逐块，再保留 system 和最近消息。Subagent 则不是第二套 runtime；它被包装成 subagent.<name> 工具，子 loop 使用新的 TierController，父 loop 只接收 summary、finish reason、steps 和 token 数。

6. 当前限制和不要做的事。

这几条画出 Harness 能承担什么、不能承担什么。把愿景能力当成 runtime 合同，代码和用户预期就会立刻错位。

  • 不要把 Harness 当成用户功能。用户侧看到的是 Agent runtime、运行状态、工具授权和结果审阅；Harness 是维护者术语。
  • Command Gateway 现在不属于 Harness。Gateway 在主架构手册里仍是 T12 capstone；本页只覆盖现有 Harness 运行层的行为和边界。
  • 不要在 feature service 里复制 loop。Chat、Search、Review 需要 agent 时通过统一 runtime 合同传任务、工具、预算、权限和订阅。
  • 不要把 permission 写成 prompt。需要保证的行为必须在 PermissionGuard 或 hooks 里实现。
  • 不要让工具返回任意形状。工具必须用 ToolResult，否则模型、trace 和测试都难以判断失败是否可恢复。
  • 不要把旧 spec 里的全部愿景当成 runtime 合同。Harness 的稳定边界是 loop、tool、permission、hook、tier、trace、context、subagent；AgentBackend / RunEvent / Artifact 的汇合要看架构层的 owner 规则。

  • 调试顺序要固定。先看 finish reason，再看最后一个 step，再看 tool_result 和 context_compacted trace。

7. 怎么判断这份基础设施还能信。

Harness 的验证重点不是页面好不好看，而是运行边界有没有被测试锁住。

能力应该被保护的行为当前测试入口
Loop 最终答案停止、工具调用后继续、maxSteps、abort、trace events、工具异常被包成错误。 harness-loop.test.ts
Permission deny 胜过 allow，bypass 也不能绕过 deny，read mode 阻止 edit/destructive，denied tool 不执行。 harness-permission.test.ts
Context token estimate 增长，低优先级 evictable blocks 先丢，pinned block 保留，滑动窗口保留 system 和最近消息。 harness-context.test.ts
Subagent 子任务使用隔离 loop，父 loop 只看到 subagent tool 的 summary，子工具调用不泄漏到父步骤。 harness-subagent.test.ts
