Peak Assistant Architecture Capstone Specification

Obsidian Plugin Command Gateway：把外部插件 command 变成可授权、可审查、可回放的知识工作能力

本文是主架构现代化完成后的验收型能力规格。它不把 Obsidian command 直接交给 agent，也不新建第二套 command-agent runtime； 它用 CommandPort、ToolDef、Skill Compiler、Permission Policy、 Capability Contract 和 RunEnvelope 验证 Peak 是否真的能接住 Obsidian 插件生态。

1. 文档门槛：为什么这份文档值得存在

这不是普通 feature spec。它的价值在于给后续实现者一个清晰验收标准： 如果 Peak 能安全地把第三方 Obsidian plugin command 转成受控 tool、可审查 skill、可回放 run， 那主架构里的 ToolDef、Skill Compiler、Permission、RunEnvelope 和 Ports 才算真的通过外部生态压力测试。

Requirement Check没有这份规格，实现很容易退化成“扫描 commands + prompt 里让模型自己调用”，最后形成第二套 agent runtime。
Reader读者是熟悉 agent / 后端 / Obsidian 插件大方向，但不熟悉 Peak 新架构细节的工程师或 AI 编码代理。
Desired Output读者能判断：何时做、怎么分层、哪些 command 能进入、如何授权、怎样证明没有绕过新架构。
Delete List不写插件市场愿景、不列所有 Obsidian 插件、不做 UI 完整视觉稿、不把 command 当 capability。
Root ConstraintObsidian command 是 UI action，不是稳定 API；很多 command 无参数、无返回、依赖当前 editor，并可能有不可观察副作用。
Minimal Loop发现 commands -> AI 解释和分类 -> 用户授权 -> 编译 approved skill -> 通过 RunEnvelope 调用一个 safe command。
Bottleneck最大失败点不是发现 command，而是“用户为什么信任 AI 的建议”和“执行后如何观察副作用”。
Validation能用 fake CommandPort 跑测试，用真实插件跑 golden scenario，并输出 RunEvent、Artifact、policy trace。

2. 核心决策：AI 负责判断，用户负责授权，runtime 负责边界

用户提出“让 AI 判断哪些 command 可以进去，并让 agent 自己写 skill”是正确方向；但必须加一道产品和工程边界： AI 的判断只能生成候选，不能直接启用能力。真正进入 runtime 的必须是用户确认后的 policy + compiled skill。

Decision Command Gateway 是 T12 capstone，不是 T0-T10 的前置功能

它验证主架构，不参与旧架构扩张。

Reason 第三方 command 是最好的外部生态压力测试

它同时压测 ToolDef、Ports、Skill Compiler、Permission、RunEnvelope、Settings review surface。

Trade-off 上线会更慢，但不会制造第二套系统

不做“快接入所有 command”，先做能解释、能授权、能回放、能阻断的最小闭环。

问题决策不选什么验收方式
AI 能否决定 command 是否可用？ AI 可以分类、解释、生成候选 ToolDef / Skill。 不让 AI 直接写入 allowlist 或绕过用户授权。 所有 AI 建议都能在 review surface 被拒绝、编辑、审计。
Command 是不是 capability？ 不是。Command 是原始动作，Capability 是产品语义。 不把每个 command 注册成一个产品能力。 最终链路必须是 Command -> ToolDef -> Skill -> Capability。
是否做新 runtime？ 不做。必须复用主架构的 ToolDef、Permission、RunEnvelope。 不建 CommandAgentService 或 command-only agent loop。 golden scenario 的 trace 里能看到标准 RunEvent / ArtifactRef。

4. 概念分层：Command / Tool / Skill / Capability 的区别

这一节存在的理由很简单：如果这里混了，后面实现一定会混。AI 可以帮助写 Skill，但 Skill 不等于 Capability； Command 可以包装成 ToolDef，但 ToolDef 也不等于产品能力。

Skill “Agent 在什么场景下应该如何使用这些工具？” AI curator 可生成草稿，用户或系统确认后编译。 Skill 是工作手册，不是权限本身；权限来自 policy。
Capability “Peak 产品承诺帮用户完成什么知识工作？” 产品架构定义。 Capability 引用 Skill 和 ToolPolicy，不直接等于 command。

5. 当前代码证据：可以接，但必须等新架构收束

这一节的职责是把方案绑定到当前仓库事实，避免写成空中楼阁。结论是：项目已有工具、权限、MCP 和 Skill 的雏形； 但还缺 CommandPort、AI curation schema、用户授权 surface、command side-effect observation。

证据当前文件说明对本方案的要求
Peak 自己注册 Obsidian commands main.ts、src/app/commands/Register.ts Obsidian 插件命令已是产品入口的一部分，但当前主要是 Peak 发布自己的命令。 Gateway 需要新增 discover / preflight / execute 的 CommandPort，不能让 service 直接抓 Obsidian app。
Obsidian command 是 palette entry node_modules/obsidian/obsidian.d.ts addCommand 会把命令注册到 command palette，天然偏 UI action。 文档必须把 command 当原始动作，而不是稳定 API。
CapabilityRegistry 仍是 surface readiness src/service/capabilities/CapabilityRegistry.ts 当前 registry 注释和实现都说明它是 surface self-register adapter。 Command Gateway 不能把 command 塞进现有 registry 假装成完整 capability。
Skill 仍以 markdown workflow + tool whitelist 为主 src/service/skills/types.ts 已有 builtin / MCP tool whitelist、pipeline phases、inputs。 AI curator 可以生成 Skill draft，但必须进入 v2 compiler / quarantine，而不是直接执行。
Harness ToolDef 已有 kind 和 ToolResult src/service/agents/harness/tool/types.ts ToolDef 已支持 read / edit / destructive / meta 分类和错误归一化。 Command wrapper 应该复用这个模型，而不是继续走旧 AgentTool 直连。
PermissionGuard 是 deny-first src/service/agents/harness/permission/PermissionGuard.ts 显式 deny rule 最高优先级，即使 bypass 也不能覆盖。 高风险 command 需要默认 deny，并且用户授权也不能覆盖系统级 deny。
MCP 已可适配为 ToolDef src/service/agents/harness/tool/McpToolAdapter.ts 外部 MCP 工具已经有“发现 -> adapter -> ToolDef”的可复用模式。 Command Gateway 应该模仿 MCP adapter 的工程形状，但多加用户授权和副作用观测。
Settings 已有外部工具入口 src/ui/view/settings/settingsStrings.ts 文案已经把 MCP servers 叫作 External tools。 Command Gateway 的 review surface 应放进 Tools / External capability 语境，不应该藏在 agent 内部。

6. AI Curator：高价值在“解释和起草”，不是自动授权

AI 确实比硬编码规则更适合判断 command 的用途，因为 command id、插件名、用户近期工作状态、插件类别和历史行为都可以作为语义信号。 但 AI 输出必须可审查：每一条建议都要解释“为什么推荐、可能有什么副作用、建议归入哪个 Skill、为什么不直接开放”。

Curator 输出必须包含不能包含为什么
Risk finding 风险等级、依据、是否修改 vault、是否需要 active editor、是否可观察结果。 不能只有“recommended: true”。 用户授权需要理由，不是相信模型一句话。
Tool proposal 候选 tool name、kind、input schema、confirmation policy、preflight needs。 不能直接写入 runtime registry。 工具必须先过权限和 review。
Skill draft 适用场景、使用步骤、allowed tools、输出 contract、失败时怎么做。 不能带无限制工具访问。 Skill 是工作手册，不是越权口子。
Rejection reason 为什么不建议开放，例如 modal-only、unknown side effect、destructive。 不能静默丢弃。 用户需要理解 Peak 的安全判断。

信任原则： review surface 的目标不是让用户管理底层技术细节，而是让用户相信 Peak 没有偷偷开放插件能力。 用户必须能看见每个建议的 evidence、risk、Skill 用途、confirmation policy 和最后一次运行 trace。

8. 权限模型：比现有 ToolKind 更细，但必须兼容 deny-first

当前 Harness 已经有 read、edit、destructive、meta 的 ToolKind。 Command Gateway 需要在 curator 层做更细风险分类，最终编译时映射回 ToolKind 和 PermissionRule。

Gateway 风险典型 command映射 ToolKind默认策略执行要求
Read / Navigate 打开视图、切换面板、显示搜索结果。 read 或 meta 可推荐开启，但仍需用户授权。 记录 tool_call 和 workspace-state artifact。
Current-note edit 插入模板、格式化当前选区、创建单个 note。 edit 默认关闭；允许 per-skill 开启。 preflight 检查 active editor；执行前展示用户可读意图；执行后记录 diff。
Vault mutation 批量移动、批量重命名、批量标签修改。 destructive 或 system deny 默认 deny。 只能进入人工 review，不进入自动 agent tool。
Modal-only 打开 QuickAdd modal、打开复杂插件设置。 meta 不作为自动 tool。 作为 suggested action，让用户点击。
Unknown 来源不清、名称不清、效果不可观察。 system deny 阻断。 需要用户手动标注或插件 manifest 补充。

10. 架构验收矩阵：它到底验证主架构哪几层

这张表是本文最重要的执行工具。它把 Command Gateway 从“一个有趣功能”变成“架构验收任务”： 每一层都必须有可以测试的证明，否则这个 capstone 没有完成。

主架构层Command Gateway 验收问题通过标准失败信号
Ports service 是否能通过 CommandPort 接 Obsidian，而不是直接拿 app。 fake CommandPort 可以跑 curation 和 execution tests。 实现里到处出现 AppContext.getInstance().app.commands。
ToolDef command、MCP、本地工具是否能走同一工具协议。 obsidian.command.execute 是普通 ToolDef，带 kind、schema、ToolResult。 单独写 command tool runner。
Permission 高风险 command 是否能被 deny-first policy 阻断。 destructive / unknown command 默认 deny；bypass 也不能覆盖系统 deny。 用户一勾选就可以执行批量 destructive command。
Skill Compiler AI 生成的 skill draft 是否经过 quarantine / compile。 坏 skill 不进入 runtime；好 skill 只包含 approved tools。 curator 输出直接变成 prompt 或 runtime config。
Capability Contract 最终能力是否仍是产品语义，而不是 command 名称。 capability 是 work.plan.weekly 这类语义；command 只是实现工具。 command id 出现在产品能力列表里。
RunEnvelope 执行是否有 trace、policy event、preflight event、artifact。 golden run 能回放：为什么调用、是否确认、改了什么、结果是什么。 command 被执行了，但 UI/history 无法解释发生了什么。
No Dual System 是否绕开新 runtime。 没有 CommandAgentService；所有执行从 capability run 进入。 command gateway 自带一套 planner、store、tool runner。

11. 任务拆分：不是排期，而是依赖和验收门

这些任务应该在主架构 T10 Conformance + Golden Trace 之后执行。每个任务包都必须有测试或可观察验收，不允许只交 UI 或只交 prompt。

任务包输入产出验收门
C0 Fixture Vault + Fake Commands fake Obsidian host、3 类 command：safe、edit、destructive。 测试夹具和 golden descriptors。 不接真实插件也能测试 discovery、curation、policy。
C1 Command Discovery Obsidian command registry、enabled plugin metadata。 CommandDescriptor、source 分类、不可观察样本。 只发现不执行；能输出 unknown / modal-only。
C2 CommandPort + ToolDef T2 ports、T5 ToolDef Envelope、PermissionGuard。 CommandPort、obsidian.command.execute ToolDef。 fake port tests 通过；edit/destructive 命令可被 policy 阻断。
C3 AI Curator descriptors、curation schema、prompt fixture。 可解释 finding、candidate ToolDef、candidate Skill。 输出可 parse、可拒绝；没有自动启用路径。
C4 Review Surface Settings / Tools tab、capability readiness。 按插件和用途聚合的授权界面。 用户可以 allow / deny / edit；默认全关；展示 evidence 和风险。
C5 Skill Compile + Quarantine approved skill draft、approved tool list。 CompiledSkill，allowed tools，sourceHash，quarantine result。 坏 skill 不进入 runtime；好 skill 不包含未授权 command。
C6 Golden Scenario Calendar / Tasks / QuickAdd 中一个真实插件组合。 “把当前工作状态落到 weekly plan”的完整 run。 RunEvent trace、policy event、confirmation、artifact 全部可见。

12. 推荐 golden scenarios

Planning Calendar / Periodic Notes

从 Current Work State 生成 weekly plan，再调用用户授权的 weekly-note command。验证 active file/date、artifact trace 和 per-run confirmation。

Capture QuickAdd

QuickAdd 常见 modal/template command。适合验证 modal-only 识别，以及“suggested action, not auto-run”。

Task Work Tasks plugin

将 session thought trace 里的 todo 整理成任务草稿，但真正写入必须经过当前 note diff review。

Query Dataview / Query plugins

验证“有 command 不代表应该调用 command”。如果 SearchPort 更稳定，就不应该为了调用插件而调用插件。

Safety Bulk mutation commands

批量重命名、删除、移动应默认 blocked。这个场景用来证明 deny-first policy 生效。

Differentiation Ambient -> Plugin action

Ambient 发现用户连续写架构/商业化/任务计划，建议用已授权插件生成下一步工作区，而不是替用户思考。

13. 风险和反目标

风险 / 不要做为什么危险正确做法
不要全量开放 commands 大量 command 是 UI action 或不可观察副作用，直接开放会失控。 默认全关，AI 只生成候选，用户 allowlist。
不要让 AI 自动启用 AI 的判断可能对，但信任和授权不能外包给模型。 AI 解释，用户授权，系统执行边界。
不要把 command 变成 capability 产品能力会退化成 command palette 镜像。 Command -> ToolDef -> Skill -> Capability。
不要忽略 observable result 执行后不知道改了什么，RunEnvelope 就失去意义。 每次执行至少记录 workspace state、active file change、vault diff 或明确 no observable result。
不要建第二套 command-agent runtime 这会违反主架构手册的禁止双系统规则，并增加长期维护负担。 复用 ToolDef、PermissionGuard、Skill Compiler、RunEnvelope。
最终定位： Obsidian Plugin Command Gateway 是 Peak 架构现代化后的外部生态验收任务。 它证明 Peak 的差异化不是“也能访问目录”，而是能在 Obsidian 中把 vault、当前工作状态、插件生态和 agentic workflow 组合成可授权的知识工作能力。
