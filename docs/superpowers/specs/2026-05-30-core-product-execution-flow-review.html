Peak Assistant 核心产品能力架构与 Agent 后端 Review

这份报告面向一个“懂后端、懂 agent，但第一次读 Peak Assistant 代码”的技术人。 它先解释这个 Obsidian 插件到底由哪些服务组成，再把 Chat、Search、AI Analysis、Copilot、Knowledge、Ambient 看成一组可调度的产品能力； HermesAgent / Harness 则是为了用 DeepSeek、OpenRouter、Ollama 等低成本模型承接这些能力的自研 agent runtime。

读者: 有经验但不熟本项目 核心: 能力模型 + 后端边界 图形: sequence / state / class / stack / matrix 未修改 production src
Revision

0. 这版报告改了什么

1 Chat 不再是模式选择器 用户面应该只有一个 General Chat，内部自己判断要不要查、分析、改文档、计划或追问。
2 能力先于入口 Chat、Copilot、AI Analysis 不应该各维护一套能力入口；应共用能力说明书。
3 Harness 是主线，不是旁支 它的意义就是摆脱昂贵 SDK 后端，用便宜模型跑 vault 和 copilot agent。
4 分层边界必须硬起来 保留 AppContext，但不能让 service 反向抓 UI、core 被 service 污染、模块横向乱穿。
一句话版本： Peak Assistant 应该从“多个 UI 入口各自长出 agent 能力”，重构成“统一能力目录 + 统一运行会话 + 可替换 agent 后端”。Chat 是入口，不是模式；Copilot 是能力集合，不是孤岛；HermesAgent/Harness 是成本和模型自由度的核心工程投资。
Project primer

用你熟悉的工程类比

Peak 里的词 可以怎么理解 它不是 为什么重要
Vault 一个本地 markdown 文档库，相当于用户私有知识数据库。 不是远程 SaaS 数据库。 所有搜索、分析、copilot 都围绕 vault 文件和 metadata 发生。
Chat 用户和系统持续交互的主入口，类似一个带上下文的 agent console。 不应该只是普通 LLM chat，也不应该让用户选很多模式。 最终应该自动调度 Search、Copilot、Analysis 等能力。
General Search 本地检索服务，像内部 search service：FTS、vector、RRF、PPR、rerank。 不是 UI 搜索框本身。 它是 Chat、AI Analysis、Copilot、Ambient 的共同地基。
AI Analysis 长任务调查系统：先搜、再读、再生成 plan/report/graph。 不是一条普通 assistant 回复。 它需要 session、后台运行、HITL、报告持久化。
Copilot 围绕当前文档或整个 vault 的操作能力集合，比如审阅、补链接、提出改动。 不是一个单独聊天机器人。 它应该被 Chat 和 UI picker 共同调用，而不是孤立入口。
Knowledge vault 级结构治理：hub、cluster、结构洞、orphan、重复、stale notes。 不是单篇文档工具。 它应该进入 Knowledge Center / Vault Review，而不是散在菜单里。
Ambient 被动信号层：写作停顿、切文件时推相关笔记或轻提示。 不是主导航里的大功能。 它应该给 Chat/Knowledge/Dashboard 提供上下文信号。
AppContext 插件的 composition root / service locator，负责把 Obsidian app、settings、services 串起来。 不应该变成任何层随便穿透拿任何对象的后门。 可以保留，但要收紧成稳定 ports 和 registries。
HermesAgent / Harness 自研 agent runtime：模型 tier、tool calling、permission、hooks、memory、context compaction。 不是 Claude Agent SDK 的小 wrapper。 它是降低 agent 成本、接 DeepSeek/Ollama/OpenRouter 的核心后端。

Core diagnosis

2. 最核心判断：问题不是能力少，而是能力没有被建模

现在代码里能力很多：Chat 能上下文对话，Search 有 hybrid + PPR，AI Analysis 能做 vaultFull 报告，Copilot 有二十多个 action，Auto Review 有 structured propose 工具，Harness 也已经有 loop、tier、permission、subagent、memory。 但这些能力没有被一个统一的产品模型组织起来。

现在的形态 用户感受 工程后果 应该变成
Chat 有 chat / agent / plan 模式 用户要猜该选哪个模式 ConversationService 反向读 UI store General Chat + 内部 execution planner
Copilot actions 自己注册、自己执行 像另一个产品入口 Chat 不知道 Copilot 能力存在 能力说明书，被 Chat / Copilot / Command 共用
AI Analysis session 长在 React hook 分析和报告很强，但运行状态复杂 后台、恢复、持久化、错误处理难复用 统一 RunSession 模型
VaultFull 和 Auto Review 依赖 Claude Agent SDK MCP 功能强但贵 Harness backend 不能完整替代 MCP 工具后端中立化，Harness 也能跑
AppContext 可拿到很多东西 开发快 边界不受控，服务之间互相穿透 AppContext 作为 composition root，只暴露稳定 ports
类型守门不是第一原则。 类型检查有必要，但它是边界设计后的守门员，不是架构本身。第一步应该先决定：core/service/ui/app/context/capability/harness 各自负责什么，哪些方向的依赖被允许，哪些必须禁止。

Product capability architecture

4. 产品能力模型：先定义“系统会做什么”

用户真正关心的不是入口名，而是系统能做什么。下面这些能力应该是一等对象；UI 只是把它们以不同方式呈现出来。

Answerauto

普通回答、解释当前上下文、继续对话。默认低风险，可以自动执行。

chat.answer
Search Vaultauto read

搜索 vault、读取相关笔记、引用来源。只读能力，可以由 Chat 自动触发。

vault.search
Search Webpolicy

外部 web 搜索。可以自动或半自动，但需要受 provider、隐私、预算控制。

web.search
Analyze Vaultcost gate

全库调查、计划、报告、AI Graph。高成本，应提示范围和成本。

analysis.vaultFull
Review Current Noteread

审阅当前笔记，提出 insights、sources、changes。提出建议可以自动，应用必须确认。

doc.review
Apply Changesconfirm

修改 vault 文件、应用 Copilot diff、创建/移动/合并笔记。必须显式确认。

doc.applyChange
Knowledge Healthreview

结构洞、hub、orphan、重复、stale notes、cluster 观察。应归入 Knowledge Center。

knowledge.review
Ambient Suggestambient

写作时自动推相关笔记、早报、轻提示。不占主导航，是横切信号层。

ambient.suggest

system.readiness
设计原则： UI 不应该决定能力边界。Chat、Copilot、Command Palette、Knowledge Center 都只是 surfaces；真正的能力应该有统一 id、输入、输出、权限、成本、后端支持和验证规则。
General Chat

5. Chat 应该取消用户面模式，改成 General Chat

我同意你的判断：不要再让用户选择 Chat / Agent / Plan。用户只是在问助手；系统应该自己决定是普通回答、查 vault、跑轻量 Copilot、生成 plan、还是提示需要启动高成本分析。 但内部仍然要有 execution policy，不能让模型无限自由调用。

用户面 内部可以有 展示方式 限制
一个 Chat 输入框 intent = answer 直接回答 不调用工具或只用已有上下文。
还是同一个 Chat intent = search-vault 显示 “Using vault search” 和 sources 只读，允许自动。
还是同一个 Chat intent = doc-review 生成 Review artifacts 提出修改可以自动，应用修改必须确认。
还是同一个 Chat intent = full-vault-analysis 转入 AI Analysis / report run 高成本，先提示 scope、backend、预算。
还是同一个 Chat intent = plan 以计划形式输出 不需要用户手动切 Plan mode。
当前代码里的具体问题： ConversationService.streamChat 从 useChatViewStore.getState().chatMode 读取运行模式，这是典型 service 反向依赖 UI。重构目标不是“把模式变量搬个地方”，而是删除用户面模式，让 Chat run 自己生成 execution plan。
Prompt stack

6. Prompt / Context 应画成堆叠图，不是流程图

Chat context 的本质是“把不同来源的上下文按优先级堆进 prompt，再按 token budget 压缩”。这应该用堆叠图和预算图表达。

System Prompt 身份、边界、当前 execution policy、允许能力。 required
User Profile 用户长期偏好、写作风格、工作流规则。 small
Recent Messages 最近对话、用户当前问题、assistant 最近回复。 large
Conversation Summary 长对话压缩摘要，用于替代被丢弃的中间消息。 compress
Current File 当前 Obsidian note、selection、frontmatter、links。 policy
Resources 附件、资源摘要、direct attachment 内容。 policy
Vault Intuition folder intuition、knowledge_intuition_json、hub / graph 信号。 compress
Previous Analysis 最近 AI Analysis / report / graph 结果。 optional
Ambient Signals 相关笔记、写作上下文、近期被推送/点击的信号。 future
Budget Governor 应该回答三个问题

不是所有 context 都等价。系统需要先保 required，再压缩 compressible，最后丢 optional。

保留 压缩 丢弃

这块的设计结论

  • ContextPipeline 是正确方向。
  • 旧 ContextBuilder fallback 应该收口删除。
  • direct attachment / resource summary 的语义必须补齐测试。
  • slot 不应该直接抓 UI store；应从 ChatRunContext 读 execution policy。
具体改法： 先不要大改 prompt 内容。第一步是把 ChatProfile 和 slots 变成稳定 contract：每个 slot 声明来源、预算、是否可压缩、依赖哪个 port。然后补 fixture 测试，确保 direct attachment、current file、recent messages 不会在新旧路径里漂移。
Capability manifest

7. “Capability Manifest” 用中文说就是能力说明书

这个词听起来抽象，但意思很朴素：系统每一种能力都要有一张说明书，写清楚它叫什么、能在哪里被使用、需要什么输入、会产出什么、成本如何、能不能自动运行、用哪个 agent 后端、失败时怎么回退。

  id: "doc.review",
  label: "Review current document",
  surfaces: ["chat", "copilot"],
  requiresDocument: true,
  permission: "read",
  costLevel: "medium",
  supportedBackends: ["harness", "claude-agent-sdk"],
  outputs: ["insight", "changeProposal", "source"],
  validators: ["exactSubstringChange", "realNoteLinks"]
}
字段 通俗解释 解决什么真实问题
surfaces 这个能力能出现在 Chat、Copilot、Command、Knowledge Center 哪些地方。 Chat 不再不知道 Copilot 能做什么。
permission 只读、要确认、会写文件、危险操作。 让 General Chat 能自动调用安全能力，但不能乱改 vault。
costLevel 低成本、中等、高成本。 全库分析、长报告、web 搜索需要预算提示。
supportedBackends Harness、Claude Agent SDK、普通 Vercel chat、local-only。 让系统知道 DeepSeek 能跑什么，Claude SDK 才跑什么。
validators 输出必须满足的检查，比如 diff before 必须是原文。 便宜模型能用，但要有修复和验证层兜底。
outputs 文本回答、sources、insights、change proposals、report、graph。 UI 可以稳定渲染，不靠猜模型文字。
最小可行版本： 不需要一开始把所有功能都重写。先把现有 CopilotActionRegistry 包一层 manifest adapter，再把 buildChatTools 改为从 manifest 中挑只读能力。这样 Chat 就能先安全调用 search / current doc review / find related。
Copilot state model

8. Copilot / Auto Review 应画成状态机

Copilot Auto Review 不是普通流程。它会预检、跑一轮或多轮 agent、不断产生 structured artifacts、决定是否继续、保存历史、最后让用户选择是否应用。用 state machine 比 flowchart 更准确。 

stateDiagram-v2
  [*] --> Preflight
  Preflight --> RunningRound: build signal report
  RunningRound --> PublishingArtifacts: propose_insight / propose_change / propose_source
  PublishingArtifacts --> RunningRound: continue tool use
  RunningRound --> Submitted: submit_review
  Submitted --> Compacting: continue = true
  Compacting --> RunningRound: next round with summary
  Submitted --> ReviewReady: continue = false
  ReviewReady --> Applying: user approves selected changes
  ReviewReady --> SavedHistory: user closes or keeps result
  Applying --> Completed
  SavedHistory --> Completed
  RunningRound --> Cancelled: user cancels
  RunningRound --> Error: backend or validation failure
  Error --> ReviewReady: partial artifacts available
  Cancelled --> ReviewReady: partial artifacts available
  Completed --> [*]
当前好的地方
  • CopilotOutputCollector 是正确抽象：模型通过工具发布结构化结果。
  • propose_change.before 要求 exact substring，这对可应用修改很关键。
  • runCopilotReview 已经有多轮、snapshot、history 保存。
当前缺的地方
  • 输出工具还绑定 Claude SDK MCP 形状，Harness 不能直接跑。
  • validator / repair loop 应从 prompt 规则升级成代码层保障。
  • 普通 Copilot action、Auto Review、Vault Review 还没有统一 manifest。
Copilot 能力 应归属 Chat 是否能自动调用 是否需要确认
总结当前文档 Doc Copilot 可以 不需要
找相关笔记 / 建议链接 Doc Copilot + Search 可以 只展示建议不需要，写入 link 需要
Auto Review 当前文档 Doc Copilot 可以，但应显示 review 状态 应用变更必须确认

HermesAgent / Harness

9. HermesAgent / Harness 必须成为完整后端，不只是实验功能

你实现 Harness 的动机是对的：Claude Agent SDK / ChatGPT Agent SDK 太贵，长期跑 vaultFull 和 Auto Review 成本会压不住。 自研 HermesAgent/Harness 的产品价值，就是让这些能力能跑在 DeepSeek、OpenRouter、Ollama、本地模型上。

因此目标不是“Harness 能跑一点 agent”。 目标应该是：Claude Agent SDK 只是一个高质量可选后端；HermesAgent/Harness 是 Peak Assistant 默认 agent runtime。贵模型用于兜底、升级、关键验证，不是所有多轮 agent 的默认执行引擎。

为什么现在还没实现完整后端

缺口 现在是什么 要补什么 为什么重要
Vault tools backend-neutral vaultMcpServer 是 Claude SDK MCP server 抽 VaultToolDef，同时适配 MCP 和 Harness ToolDef 否则 vaultFull 永远只能走 Claude SDK。
Output tools backend-neutral CopilotOutputMcpServer 暴露 propose_* 把 propose tools 改成通用 tool definitions 否则 Auto Review 不能用 DeepSeek 这类模型后端。
HITL / resume 协议 VaultFull 有 submit_plan，UI plan_ready 依赖 SDK 流 Harness 中支持 tool pause、user approve、resume 全库分析不能只是一次性 final answer。
Stream adapter SDK 走 translateSdkMessage，Harness 多为 AgentLoopResult + TraceBus HarnessStreamAdapter 输出同一套 LLMStreamEvent UI 不应该关心后端是 SDK 还是 Harness。
Validator / repair 主要靠 prompt 要求模型守规则 exact substring、真实 wikilink、JSON schema、source path 验证 便宜模型更需要代码级安全网。
Model capability tests Settings 里绑定 tier，但不验证工具可靠性 每个 backend 跑 tool-call conformance tests DeepSeek 便宜，但要知道哪些任务能放心交给它。

Layer boundaries

10. 分层与 AppContext：保留模式，收紧边界

我同意你的判断：AppContext 这个设计可以保留。全局注册、static 获取、composition root 这些不是问题。问题是它现在容易变成“谁都能拿任何东西”的万能入口，导致 service、UI、core 之间互相穿透。

core 纯模型、schema、provider abstraction、storage primitives、constants。不要 import UI，不要 import service orchestration。 src/core/**
service 业务编排：chat、search、agents、copilot、ambient、usage。可以依赖 core，可以通过 ports 调 Obsidian/app 能力。 src/service/**
ui React views、stores、hooks、components。UI 可以发起 action、订阅 session，但不应把业务编排逻辑写进 hook 里。 src/ui/**
app / AppContext Obsidian integration、commands、view lifecycle、composition root。暴露稳定 services / ports，不鼓励随处拿内部实现。 src/app/**
规则 允许 禁止 原因
依赖方向 UI → service → core，app 负责装配 service → UI store，core → service/UI 避免反向依赖让业务层无法测试和复用。
跨模块共享 UI 抽到 ui/component 或 shared view components search 直接 import chat 里的 UI token 组件 模块内部 UI 自成体系，通用组件放 shared。
AppContext 使用 获取稳定 registry/service/port 在任意 service 里穿透拿 UI/runtime store 保留便利性，但限制破坏边界的自由度。
状态管理 UI store 存 UI 状态；RunSession 存运行状态 React hook 里承载完整 agent orchestration 后台运行、恢复、测试都需要 service 层 session。
类型守门 为跨层 contract 加类型和测试 把所有代码先全面类型洁癖式重写 类型服务于边界，不是反过来。
对 AppContext 的目标定义： 它应该像系统注册表和服务入口，而不是万能依赖注入黑洞。可以保留 AppContext.getInstance()，但要逐步把“拿具体实现”改成“拿稳定接口”：ChatPort、VaultPort、ProfilePort、CapabilityRegistry、RunSessionManager。
Refactor roadmap

11. 最高收益重构路线

这里按“收益最大、风险可控、能逐步验证”的顺序排。不要一上来大重写，也不要只补类型错误。

阶段 要做什么 触达文件 验收标准
0 写下目标架构规则：General Chat、Capability Manifest、RunSession、Harness backend、分层边界。 docs/superpowers/specs 团队/AI 后续写代码时有明确架构约束。
1 先建立 import boundary 守门：service 不 import UI store，core 不 import service/UI。 lint rule 或自定义 script CI 能发现新的反向依赖。
2 抽最小 CapabilityManifest，包住现有 Copilot actions 和 chat tools。 service/capability/**、service/copilot/**、service/chat/tools/** 同一个能力能被 Chat 和 Copilot 查询。
3 把 Chat 用户面模式隐藏，新增 ExecutionPlanner，先只调只读能力。 ui/view/chat-view、service/chat UI 没有 Chat/Agent/Plan 模式；service 不读 UI store mode。
4 完成 ContextPipeline 收口，删除旧 ContextBuilder fallback。 service/chat/context/** 附件、资源、当前文件、摘要都有 fixture 测试。
5 抽 RunSession，先承接 AI Analysis 与 Copilot Review 的 streaming/abort/history。 service/session/**、quick-search hooks、copilot sessions React hook 不再承载完整 agent 编排。
6 HarnessStreamAdapter：把 Harness TraceBus/steps 转成 UI 统一事件。 service/agents/harness/** UI 不区分 SDK/Harness stream。
7 适配 vault tools 和 copilot output tools 到 Harness ToolDef。 vaultMcpServer、CopilotOutputMcpServer Doc Auto Review 可用 Harness 跑只读审阅。
8 HITL/resume 协议迁移，支持 submit_plan、review continue、approval。 service/session、service/agents/harness VaultFull 可以在 Harness 后端进入 plan_ready 并继续。
9 便宜模型 conformance tests：DeepSeek/OpenRouter/Ollama tool-call、schema、validator 修复能力。 test/agents、service/agents/harness 每个 backend 有明确可用能力矩阵。

现在不要先做什么

不要先删 AppContext

它不是根问题。先限制它暴露什么，再逐步引入 ports。

不要先全量类型洁癖

先把跨层 contract 和 import boundary 守住，类型修复才有方向。

不要立刻把 vaultFull 强切 Harness

先做 tools adapter、stream adapter、HITL、validator，否则便宜模型会省钱但不可靠。
