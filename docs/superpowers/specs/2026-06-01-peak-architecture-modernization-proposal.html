Architecture Modernization Blueprint

Peak Assistant 架构现代化方案

Peak Assistant 的核心不是单个 Chat 面板，而是一组围绕 Obsidian vault 运转的知识工作能力。 架构现代化要把这些能力沉淀成稳定协议：能力契约、运行外壳、边界端口、技能包、测试合同和迁移节奏。

核心判断

当前项目最大的问题不是“代码太多”，而是 产品能力没有被编码成稳定契约。 Chat、Search、AI Analysis、Copilot、Harness、Knowledge 都已经有真实能力，但它们的入口、状态、后端、工具、输出和测试还没有被统一到可审查的工程协议里。

因此不建议先大搬目录或全量重写 service，而是先建立三条主轴： Capability Contract、Run Envelope、Ports + Adapters。

使用场景

适合读者有后端/Agent 开发经验，但不一定熟悉 Peak Assistant 代码。

主要用途快速建立系统 mental model，并判断接下来怎么重构、哪些先做、哪些不要先做。

边界范围聚焦架构和代码设计，不替代具体 PR 设计，不给每个文件逐行审查。

0. 系统阅读路径：先建立 mental model，再安排重构

Peak Assistant 不能从文件夹开始理解。正确顺序是：先看产品能力，再看用户入口，再看一次运行怎么经过 context、backend、tool、artifact 和持久化。 只有建立这套 mental model，后面的架构现代化才不会退化成搬目录、改名字或抽象层堆叠。

使用方法： 先用这一节建立系统地图，再进入证据、目标架构和迁移计划。重构时每个 PR 都应该能回答： 它改善了哪个能力契约、哪个运行外壳、哪个依赖边界，或者哪个测试合同。

Lens 1 产品能力视角

先不要从文件夹开始看。先问：用户在 Chat、Search、AI Analysis、Copilot、Knowledge 中到底想完成什么。

Lens 2 运行链路视角

再看一次请求怎么变成 context、backend run、tool call、artifact、UI 更新。这里最容易发现状态漂移。

Lens 3 代码边界视角

最后看哪个模块拥有状态、哪个模块调用宿主、哪个模块可以 fake port 测试。这里决定怎么重构。

理解系统必须回答的 8 个问题

1. Peak 是什么？不是 Chat 插件，而是一组知识工作能力。
2. Chat 怎么发送消息？用户输入经过 context、planner、backend、event、artifact。
3. Context 怎么收集？ContextPipeline 用 slots + budget 管当前文件、历史、搜索证据。
4. Copilot 怎么运行？从 document context 选 action，运行 agent，产出 diff/artifact，用户确认写回。
5. Harness 能替代什么？它是便宜模型/本地模型 agent backend，不是 UI，也不是产品能力本身。
6. Skill 有什么用？它应该变成 agent 工作手册包，被 Capability 引用，而不是孤立 picker workflow。
7. MCP 是什么位置？MCP 是外部工具协议，先转内部 ToolDef，再被 Skill/Capability 使用。
8. 先改哪里？先加 contract、RunEnvelope、ports、contract tests，再拆大 service。

1. 能力全景：Peak 不是 Chat 插件，而是一组知识工作能力

架构重构不能从 service-manager.ts 或目录结构开始。先把产品能力铺开，才能判断哪些代码应该合并、哪些应该拆开、哪些只是 UI 入口。 Peak 已经覆盖提问、搜索、研究、写作、审阅、知识维护、主动发现、工具生态和系统运营；中枢必须服务整个能力面，而不是只服务 Chat。

Conversation

Chat / Conversation

用户最常用入口。它不应该暴露一堆 ChatAgent / Client / Plan 模式，而应该是 General Chat：用户表达意图，系统内部选择搜索、分析、Copilot 或普通回答。

已存在streaming、conversation storage、ContextPipeline、follow-ups、topic aggregation、project/history。
架构问题chatMode 和工具选择仍容易被 UI store 形状影响，Chat 不知道完整 capability 目录。
目标Chat 只发 intent；ExecutionPlanner 选择 capability；结果统一成 RunEvent 和 ArtifactRef。
Retrieval

General Search

这是产品地基，不只是搜索框。它给 Chat、AI Analysis、Copilot、Ambient、Knowledge Center 提供证据。

已存在query parser、multi retrievers、adaptive RRF、PPR、rerank、highlight、click history。
架构问题IndexService 汇聚写入、graph、maintenance、embedding、配置读取等职责。
目标SearchPort + retrieval pipeline + thin IndexService facade，搜索结果能作为 artifact 被其他能力复用。
Research

AI Analysis / Vault Research

长任务能力：搜证据、生成计划、分段分析、保存报告、继续分析。它应该成为 RunSession 的样板能力。

已存在VaultSearchAgentSDK、ReportOrchestrator、plan review、sources、analysis markdown、background session。
架构问题session snapshot、persistence、UI restore 仍和 quick-search / React store shape 靠得太近。
目标AnalysisSession domain + RunSession event stream；UI 订阅状态，不拥有长任务真相。
Writing

Doc Copilot / Writing

当前文档的 polish、review、correct、suggest links、tags、split、translate、writing plan、add evidence 等能力。

已存在15+ actions、Document/Vault/Writing 三类、structured artifacts、review history。
架构问题manifest、executor、prompt、ResultPanel 混在 action registry，导致 action 同时像产品、执行器和 UI。
目标ActionManifest -> CapabilityManifest -> Executor -> UI panel binding，用户确认后才写 vault。
Knowledge

Knowledge Maintenance

这是差异化主线：Vault Lint、Structural Hole、Gap Analysis、Precompiled Knowledge、Cascade Update、Auto-tag。

已存在SQLite graph、PPR、hub regen、structural metrics、lint signals、cascade worker。
架构问题这些能力散在 search/index/lint/actions/ui 中，没有统一 readiness、artifact 和 review surface。
目标Knowledge capability family + maintenance jobs + reviewable artifacts。
Ambient

Ambient / Morning Briefing

系统主动发现相关笔记、写作提示、每日简报。它不适合硬塞进 Chat，而应该成为后台信号层。

已存在Ambient Push、gutter、Morning Briefing、反馈日志、graph neighbor/co-citation 信号。
架构问题展示位置和能力归属不清楚，容易被看成边缘 UI，而不是可复用 signal。
目标AmbientSignalService 输出 reason、source、confidence、suggested action；Chat/Knowledge/Dashboard 订阅。
Runtime

Hermes Harness / Agent Runtime

成本和模型自由度的核心。DeepSeek、OpenRouter、Ollama、本地模型需要它承接长任务、工具调用、上下文压缩和 trace。

已存在loop、tier、permission、hook、subagent、memory、context、skill lifting、tool registry。
架构问题VaultFull、Auto Review、output tools、HITL 还没有完全后端中立，部分能力仍偏 SDK 路径。
目标AgentBackend contract + HarnessStreamAdapter + backend conformance tests。
Ecosystem

Skills / MCP / Tools

插件能力市场的基础。Skill 是行为包，Tool 是可调用动作，MCP 是外接工具协议。

已存在_skills/、built-in skills、MCP stdio/SSE client、MCPToolAdapter、local tools。
架构问题Skill 没有进入 Chat/Copilot/Analysis 主调度，用户感知弱；Tool/MCP/Skill 语义容易混。
目标兼容 SKILL.md，编译成 CompiledSkill，被 Capability 引用，工具统一成 ToolDef。
Operations

Settings / Onboarding / Dashboard

这是产品支架：让用户知道系统准备好了没有、成本花在哪里、哪些能力可以跑、下一步该做什么。

已存在provider settings、Harness onboarding、index config、usage dashboard、capability readiness registry。
架构问题readiness 仍偏 surface 视角，不是完整 capability 视角；用户看到的是局部配置状态。
目标Capability readiness：provider、index、tools、permission、budget、last successful run。
架构结论： 真正的中枢不是某一个 manager、某一个 view，也不是 AppContext 本身；中枢应该是 Capability + RunSession + Backend + Ports。这样 Search 是产品能力，不只是 Quick Search； Copilot 是文档能力，不只是一个面板；Skill 是行为包，不是孤立入口。

3. 目标架构：五个工程决策，而不是十几个抽象口号

接下来的重构可以收敛到五个决策。它们的共同目标是：新增能力时先声明契约，运行时有统一外壳，底层资源通过端口进入，输出能测试、能回放、能被 UI 复用。

Decision 1 产品能力先写成 Capability Contract

Doc Review、Vault Search、AI Analysis、Knowledge Health 这类能力必须有 id、输入、输出、权限、成本、后端支持、默认 skill 和展示 surface。

Decision 2 长任务统一到 Run Envelope

统一的是状态、事件、trace、artifact、取消、恢复、历史，不是把 Search、Chat、Copilot 强行写成同一套业务流程。

Decision 3 AppContext 留在 app 层，service 依赖 Ports

AppContext 作为 composition root 可以保留；新 service 通过 VaultPort、SearchPort、ProviderPort、ToolPort、CommandPort 访问宿主能力。

Decision 4 Skill 改成工作手册包，不再只是轻量 markdown 动作

Skill 应该描述 agent 怎么做事，可以携带 examples、allowed tools、output contract、脚本资源；Capability 引用 Skill，但不等于 Skill。

Decision 5 测试从函数覆盖升级成能力合同

用 fake vault、fake search、fake model、fake tools 跑 Chat send、AI Analysis round、Copilot Auto Review、Harness backend conformance。

5. 什么叫现代、模块化、优雅：不是形容词，是验收标准

“现代化”不是把目录名改得更干净，也不是把代码抽得更抽象。对 Peak 来说，现代化就是下面六条能被代码和测试验证的标准。

1

声明式能力，而不是入口里手写流程

新增能力时先写 contract：输入、输出、权限、成本、后端支持、默认 skill、展示 surface。

现在Chat tools、Copilot actions、Skill workflow、MCP tools 各自注册。
目标CapabilityRegistry 管产品能力；SkillRegistry 管行为包；ToolRegistry 管动作。
2

统一运行外壳，而不是每个 hook 自己存状态

长任务进入 RunSession：状态、事件、取消、恢复、history、artifact 有统一模型。

现在AI Analysis session、Copilot review、Harness loop 各有状态真相。
目标ChatRun、AnalysisRun、CopilotRun、HarnessRun 都输出 RunEvent。
3

Ports and Adapters，而不是 service 到处拿 AppContext

AppContext 可以保留，但 service 不应该知道 Obsidian、React store、modal 的具体形状。

现在部分 service 直接 import UI store、AppContext、Obsidian app。
目标新 service 只依赖 VaultPort、SearchPort、ProviderPort、CommandPort。
4

后端中立，而不是 SDK 形状污染产品能力

Claude SDK、Hermes Harness、普通 provider 都是 backend adapter，不应该决定 capability 的产品语义。

现在部分复杂能力绑定具体 SDK、MCP server 或 output tool 形状。
目标统一 AgentBackend / RunEvent / ArtifactRef，工具和输出可适配。
5

资产可治理，而不是 prompt/template 越堆越多

142 个 template 是资产，不是负担。关键是每个资产要有 owner、schema、调用方、render smoke、废弃状态。

现在prompt、tool templates、config JSON、Skill markdown 分散在 templates 和 service 中。
目标TemplateManifest + PromptId + schema + unused/quarantine list。
6

测试锁行为，而不是靠手感回归

优雅架构一定容易测：输入 fixture、fake vault、fake model、fake tools，就能跑完整产品 contract。

现在已有 85 个测试文件，但核心产品能力 contract 还不够。
目标核心 capability 有 scenario、golden trace、backend conformance tests。
验收方式： 任何重构 PR 都应该能指向上面至少一条标准。否则它可能只是“看起来更现代”，但没有降低后续维护成本。

6. Pattern Atlas：设计模式不是名词，是读代码和改代码的地图

这一节的目的不是给项目贴设计模式标签，而是把“哪里该用什么结构”讲清楚。 每个模式都要回答四件事：解决哪个坏味道、项目里对应哪里、用什么图最容易看懂、落地后怎么测试。

先选问题类型，再选图型

结构关系、运行时序、状态转移、数据契约、优先级和迁移路线不是同一种问题，所以不能全部画成流程图。

Facade：保留稳定入口，不等于继续做上帝对象

Boundary
现在的问题IndexService 同时像 controller、domain service、repository、job runner、UI notifier。它越大，任何改动越难测。

9. 模块边界 Review：每个核心模块该负责什么

这一节按产品能力看边界。一个模块好不好，不看它短不短，而看它有没有清楚拥有自己的输入、输出、状态、依赖方向和第一刀改造路径。

Chat先改

Chat 应该是 General Chat，不应该继续让用户选择 Chat / Agent / Plan。

现状useChatSubmit.ts、service-manager.ts、ContextPipeline.ts 串起发送、上下文、provider 和工具。
问题模式和工具选择容易被 UI 状态影响，Chat 不知道完整 capability 目录。
目标ChatRun 交给 ExecutionPlanner，从 capability 中挑只读或审阅能力。
第一刀把 mode 变成内部 execution policy，用户面只保留一个 General Chat。
Search / Index拆 facade

Search pipeline 方向很好：parser、retriever、RRF、PPR、highlight、rerank 都有价值。

现状IndexService 同时负责读文件、chunk、embedding、FTS、graph、maintenance。
问题核心能力强，但职责汇聚，任何索引变更都可能影响多条链路。
目标保留薄 IndexService facade，拆成 writer、reader、projection、enrichment、maintenance。
第一刀先抽 DocumentIndexWriter、IndexReadService 和 GraphProjectionService。
AI Analysis解耦 UI

AI Analysis 是长任务，不应该长在 React hook 和 modal 状态里。

现状background session、report orchestration、analysis persistence 共同维护计划、报告和恢复。
问题长任务、保存、恢复、前后台切换容易被 UI shape 绑定。
目标AnalysisSession 是 domain model，UI 只订阅 session events。
第一刀把 session snapshot 从 UI store 移到 neutral contract。
Copilot能力化

Copilot 不应该只是一个单独入口，它应该是一组可被 Chat 和 Command 调用的文档能力。

现状CopilotActionRegistry / actions 同时承载 relevance、guard、execute、ResultPanel。
问题新增 action 的正确位置不清楚，UI 与执行逻辑互相靠太近。
目标Copilot actions 编译成 CapabilityManifest，panel binding 留在 UI 层。
第一刀选 Doc Review action 做 manifest / executor / panel 三段式样板。
Hermes Harness主线投资

Harness 不是旁支，它是低成本模型、可替换后端和长期 agent 能力的核心。

现状已有 loop、tier、permission、memory、hook、subagent、skill lifting、tool registry。
问题Vault tools、output tools、HITL、stream adapter 还没有完全后端中立。
目标Harness 和 SDK 都实现同一 AgentBackend，输出同一 RunEvent。
第一刀适配只读 Doc Review 和 Search tools 到 Harness ToolDef。
Knowledge Graph / Maintenance差异化

Vault Lint、Gap Analysis、Structural Hole、Hub Regen、Precompiled Knowledge 是产品护城河，不应散在搜索实现里。

现状graph、structural、hub、cascade、lint 分布在 search/index、lint、actions 和 UI view。
问题用户看到的是零散面板，代码看到的是搜索内部细节。
目标KnowledgeMaintenance capability family：diagnose、repair、regen、explain、review。
第一刀把 HubRegen / Structural / VaultLint 的结果统一成 reviewable artifact。
Ambient / Signal Layer信号层

Ambient 不是一个小侧栏，而是系统主动感知用户当前写作和 vault 变化的信号层。

现状Ambient Push、Morning Briefing、gutter、反馈日志已有实现。
问题它没有被建模成可被 Chat、Knowledge、Dashboard 复用的 signal。
目标AmbientSignal 输出 reason、source、confidence、suggested action。
第一刀把 Ambient 推荐产物统一到 artifact/event，而不是只推 UI。
Settings / Onboarding / Dashboard产品支架

这些不是边缘页面，它们是“能力准备状态”和“系统运营”的支架。

现状provider、index、MCP、Harness、usage、onboarding 各自展示局部状态。
问题用户不知道当前哪些能力 ready、哪些只是配置了但不能跑。
目标Settings 展示 capability readiness，而不是内部 routing tier。
第一刀为每个 capability 生成 readiness：provider、index、tool、permission、budget。
Templates / Prompts治理资产

Prompt、config、template 是产品能力的一部分，不是工程附属文件。

现状templates 里有 prompts、tool templates、config、agents、indexing 等多类资产。
问题文件存在不等于仍被调用；变量、schema、PromptId 和实际调用方会漂移。
目标TemplateManifest 记录 owner、schema、调用方、render smoke、废弃状态。
第一刀生成 template inventory，把 unused / unknown / active 分组。

13. 风险与开放问题

Risk 过度抽象风险

如果在没有 capability fixtures 的情况下先抽完整平台层，会产生大量类型和目录，但行为没有变得更可靠。

Risk Skill v2 兼容风险

如果直接替换现有 skill registry，可能破坏 vault skill hot reload。建议先做 compiler adapter，不删旧路径。

Needs verification RunEnvelope 对 UI store 的改造范围

AI Analysis、BackgroundSessionManager、Copilot result modal 的状态模型需要逐个确认，不应一口气迁完。

Needs verification ToolDef 与 Zod v3/v4 边界

MCP adapter 当前使用 zod/v3，后续统一 ToolDef 时要明确 schema 序列化和 provider SDK 的兼容层。

14. 不要做什么：这些看起来像重构，其实会制造更大风险

不要做为什么替代做法
不要先全仓搬目录 会产生大量 diff，但不一定让行为更可测。 先加边界检查和 capability contract，再按能力迁移。
不要把 Search 改成 agent loop Search 的核心价值是可解释、可复用、低成本 retrieval pipeline。 Search 输出 RunEvent / ArtifactRef，但内部仍保持检索 pipeline。
不要让 Capability、Skill、Tool 合成一个万能 JSON 这会把产品语义、工作流和动作权限混在一起。 Capability 引用 Skill 和 ToolPolicy，三者分层。
不要把 AppContext 直接定性为坏 它作为 composition root 有价值，问题是下层随便拿它。 保留 AppContext，新增 service 通过 ports 拿依赖。
不要先删旧 CopilotActionRegistry 它连接了很多 UI 和 action，直接删会破坏产品功能。 先加 manifest adapter，把 action/executor/surface binding 逐步拆开。
最终建议： 下一轮不要以“减少行数”为第一目标。更好的目标是：每个核心产品能力都有合同、每次运行都有 trace、每个后端都能 conformance、每个 service 都能 fake port 测。
