Architecture Atlas

Peak Assistant 现代模块化架构设计报告

日期：2026-05-30 · 范围：Chat、Search、AI Analysis、Copilot、Harness、Skills、Templates、Settings、Ambient · 目标：把现有能力重新组织成更现代、模块化、可测试、可演进的架构地图。

一句话结论

Peak Assistant 不是缺功能，而是缺一个统一的能力中枢。 现在 Chat、Copilot、AI Analysis、Search、Skills、Harness 各自长出运行逻辑； 更现代的架构应该让所有入口先进入 Capability，再由 RunSession 和可替换后端执行。

这份报告不再把问题写成一堆审计项，而是回答：系统中间层该长什么样、每个模块边界在哪里、哪些代码应该先改、哪些测试能替代手测。

1现代感
不是堆新模式，而是入口统一、能力可组合、运行时可替换。
2模块化
不是机械拆文件，而是 Surface、Capability、RunSession、Backend、Port 各司其职。
3优雅
是主路径短、边界少、测试能锁住行为，AI 继续写代码也知道落点。
1. 架构北极星先确定系统应该怎么长 2. 能力全景先把产品能力铺开 3. 现代模块中枢图最重要的一张图 4. 现代/优雅标准什么才叫好架构 5. 模块边界 Review逐模块判断问题和改法 6. 执行流图谱每条主链路怎么跑 7. Skills / Templates能力、手册、工具的层次 8. 自动化测试地图哪些不用再手测 9. 重构路线小步但有方向 10. 证据附录数字、命令、代码入口

1. 架构北极星：从“多个功能入口”改成“统一能力运行系统”

这套插件现在已经是一个完整产品：Chat、General Search、AI Analysis、Doc Copilot、Knowledge、Ambient、Settings、Onboarding、Dashboard 都存在。 架构问题不在于“功能散”，而在于这些功能没有共同的产品能力模型和运行模型。

当前更像什么

每个入口都在自己内部决定 prompt、工具、状态、保存、后端和 UI 展示。 结果是 Chat 不知道 Copilot 能力，Copilot 不知道 Chat context，AI Analysis session 长在 UI hook，Harness 不能平替 SDK。

目标应该像什么

所有用户意图先进入 Capability Registry，由 Execution Planner 选择能力、权限、预算和后端； RunSession 统一承载状态、事件、artifact、取消和历史。

1. Surface 很薄 Chat、Copilot、Search、Settings 只负责收集意图和展示结果，不拥有业务流程。
2. Capability 是产品承诺 Doc Review、Vault Search、AI Analysis、Knowledge Health 这些能力有统一 id、输入、输出、权限和后端支持。
3. RunSession 是运行真相 流式事件、步骤、取消、恢复、history、artifact 不散落在 hook、modal、service 各处。
4. Backend 可替换 Harness、Claude Agent SDK、普通 provider 都实现同一套运行接口，UI 不关心谁执行。
5. Ports 隔离宿主 Obsidian vault、SQLite、MCP、Provider、Commands 都通过 port/adapter 接入，service 不直接抓 UI 或 app。
6. Contract 可测试 核心测试不是点 UI，而是验证 capability 输入输出、event trace、artifact、permission、template render。

2. 能力全景：这不是一个 Chat 插件，而是一组知识工作能力

先把能力铺开，才能谈模块化。Peak Assistant 已经覆盖从提问、搜索、研究、写作、审阅、知识维护、主动发现到系统配置的完整产品链路。 所以架构中枢不能只服务 Chat，它必须服务整个能力面。

Conversation

Chat / Conversation

用户最常用的入口。应该从模式选择器变成 General Chat，让系统内部判断要不要查、分析、调用 Copilot 或追问。

已存在streaming、conversation storage、context pipeline、follow-ups、topic aggregation、project/history。
架构问题chatMode 在 UI store，service 读取 UI 状态决定工具。
目标Chat 只发 intent；ExecutionPlanner 选择 capability。
Retrieval

General Search

这是产品地基，不只是一个搜索框。它给 Chat、AI Analysis、Copilot、Ambient、Knowledge Center 都提供证据。

已存在query parser、5 retrievers、adaptive RRF、PPR、rerank、highlight、click history。
架构问题IndexService 汇聚写入、graph、maintenance、enrichment。
目标SearchPort + thin facade + pipeline stages。
Research

AI Analysis / Vault Research

长任务能力：搜证据、生成计划、分段分析、保存报告、继续分析。它应该是 RunSession 的样板。

已存在VaultSearchAgentSDK、ReportOrchestrator、plan review、sources、analysis markdown。
架构问题session snapshot 和 persistence 仍绑定 quick-search UI store shape。
目标AnalysisSession domain + RunSession event stream。
Writing

Doc Copilot / Writing

当前文档的 polish、review、correct、suggest links、tags、split、translate、writing plan、add evidence 等能力。

已存在15+ actions、Document/Vault/Writing 三类、structured artifacts、review history。
架构问题manifest、executor、prompt、ResultPanel 混在 action registry。
目标ActionManifest -> CapabilityManifest -> UI panel binding。
Knowledge

Knowledge Maintenance

这是差异化主线：Vault Lint、Structural Hole、Gap Analysis、Precompiled Knowledge、Cascade Update、Auto-tag。

已存在SQLite graph、PPR、hub regen、structural metrics、lint signals、cascade worker。
架构问题这些能力分散在 search/index/lint/actions/ui 中，没有统一 readiness 和 action surface。
目标Knowledge capability family + maintenance jobs + review surfaces。
Ambient

Ambient / Morning Briefing

系统主动发现相关笔记、写作提示、每日简报。它不适合塞进 Chat，而应该成为后台信号层。

已存在Ambient Push、gutter、Morning Briefing、反馈日志、graph neighbor/co-citation 信号。
架构问题展示位置和能力归属不清楚，容易被看成边缘 UI。
目标AmbientSignalService 输出 signals，Chat/Knowledge/Dashboard 订阅。
Runtime

Hermes Harness / Agent Runtime

成本和模型自由度的核心：DeepSeek、OpenRouter、Ollama、本地模型都需要它承接长任务和工具调用。

已存在loop、tier、permission、hook、subagent、memory、context、skill lifting、tool registry。
架构问题vaultFull 和 Auto Review 仍硬依赖 Claude SDK MCP 形状。
目标AgentBackend contract + HarnessStreamAdapter + backend conformance tests。
Ecosystem

Skills / MCP / Tools

插件能力市场的基础。Skill 是行为包，Tool 是原子动作，MCP 是外接工具协议。

已存在_skills/、built-in skills、MCP stdio/SSE client、MCPToolAdapter。
架构问题Skill 没进入 Chat/Copilot/Analysis 主调度，用户感知弱。
目标兼容 SKILL.md，编译成 AgentSkill，被 Capability 引用。
Operations

Settings / Onboarding / Dashboard

这是产品支架：让用户知道系统准备好了没有、成本花在哪里、下一步该做什么。

已存在provider settings、Harness onboarding、index config、usage dashboard、capability readiness registry。
架构问题当前 readiness 仍偏 surface 视角，不是完整 capability 视角。
目标Capability readiness：provider、index、tools、permission、budget、last successful run。

能力全景带来的架构结论

真正的中枢不是 AIServiceManager、不是 AppContext、也不是某个 Chat service； 中枢应该是 Capability + RunSession + Backend + Ports。 这样 Search 是能力，不是只属于 Quick Search；Copilot 是能力，不是只属于 Copilot 面板；Skill 是行为包，不是孤立入口。

4. 什么叫现代、模块化、优雅：不是口号，是可执行的架构标准

“现代”和“优雅”不能只写成形容词。对这个项目来说，它们意味着：能力声明式、运行态统一、边界可测试、后端可替换、宿主依赖被隔离、配置资产可治理。

1

声明式能力，而不是入口里手写流程

新增能力时，先写 manifest：输入、输出、权限、成本、后端支持、默认 skill、展示 surface。

现在Chat tools、Copilot actions、Skill workflow、MCP tools 各自注册。
目标CapabilityRegistry 管产品能力；SkillRegistry 管行为包；ToolRegistry 管动作。
2

运行态统一，而不是每个 hook 自己存状态

长任务都进入 RunSession：状态、事件、取消、恢复、history、artifact 都有统一模型。

现在AI Analysis session 在 UI store，Copilot review 有自己的 session，Harness 有 loop result。
目标ChatRun、AnalysisRun、CopilotRun 都输出 RunEvent。
3

Ports and Adapters，而不是 service 到处拿 AppContext

AppContext 可以保留，但 service 不应该知道 Obsidian、React store、modal 的具体形状。

现在service 直接 import UI store、AppContext、Obsidian app。
目标service 只依赖 VaultPort、SearchPort、ProviderPort、CommandPort。
4

后端中立，而不是 SDK 形状污染产品能力

Claude SDK、Hermes Harness、普通 provider 都是 backend adapter，不应该决定 capability 的产品语义。

现在vaultFull 和 Auto Review 绑定 Claude SDK MCP server 和 output MCP。
目标统一 AgentBackend，工具和输出 artifact 同时适配 SDK/Harness。
5

资产可治理，而不是 prompt/template 越堆越多

142 个 template 是资产，不是负担。关键是每个资产要有 owner、schema、调用方、render smoke、废弃状态。

现在prompt、tool templates、config JSON、Skill markdown 混在 templates 和 service 里。
目标TemplateManifest + PromptId + schema + unused/quarantine list。
6

测试锁行为，而不是靠手感回归

优雅架构一定容易测：输入 fixture、fake vault、fake model、fake tools，就能跑完整产品 contract。

现在已有 83 个测试，但 runner 卡死且部分失败不 exit 1。
目标test runner 可信；核心 capability 有 scenario + conformance tests。
PatternFacade保留 IndexService、AIServiceManager 这类入口，但把实现拆到小 service。
PatternPipelineSearch、Context、Indexing、Report generation 都用 stage + DTO + fixture tests。
PatternRegistryCapability、Skill、Tool、Provider、Template 各自 registry，职责不互相吞。
PatternState MachineCopilot Review、AI Analysis、Harness loop 明确状态和转移。
PatternPortsVault、Search、Provider、Template、Command、MCP 都通过 port 接入。
PatternManifest + Compiler用户/配置层写 source，运行时用 compiled object。
PatternContract Test每个能力有输入、事件轨迹、输出 artifact 的测试。
PatternResource Lifecycle初始化、热加载、dispose、reload 都集中到 lifecycle services。

// 调用方仍然用 IndexService；IndexService 只做分派，不再把所有逻辑写在自己身上。
class IndexService {
  constructor(
    private writer: DocumentIndexWriter,
    private reader: IndexReadService,
    private maintenance: MobiusMaintenanceService,
  ) {}

  async indexVault(input: IndexVaultInput): Promise<IndexVaultResult> {
    return this.writer.indexVault(input);
  }

  async getStatus(): Promise<IndexStatus> {
    return this.reader.getStatus();
  }

  async runMaintenance(): Promise<MaintenanceResult> {
    return this.maintenance.run();
  }
}

Facade 只协调，不直接碰 UI store、Notice、React modal。

5. 模块边界 Review：每个核心模块该负责什么

下面不是按文件大小批评，而是按产品能力看边界。一个模块好不好，不看它短不短，而看它有没有清楚拥有自己的输入、输出、状态和依赖方向。

Chat先改

Chat 应该是 General Chat，不应该继续让用户选择 Chat / Agent / Plan。

现状ConversationService.streamChat 从 UI store 读取 chatMode，再决定工具。
问题service 反向依赖 UI，Chat 也不知道 Copilot / Search 能力目录。
目标ChatRun 交给 ExecutionPlanner，从 capability 中挑只读能力。
第一刀把 mode 变成内部 execution policy，用户面只保留一个 Chat。
Search / Index拆 facade

Search pipeline 方向很好：parser、retriever、RRF、PPR、highlight、rerank 都有价值。

现状IndexService 同时负责 tenant、读文件、chunk、embedding、FTS、graph、maintenance。
问题核心能力强，但职责汇聚，任何索引变更都可能影响多条链路。
目标保留薄 IndexService facade，拆成 writer、projection、enrichment、maintenance。
第一刀先抽 DocumentIndexWriter 和 GraphProjectionService。
AI Analysis解耦 UI

AI Analysis 是长任务，不应该长在 React hook 和 modal 状态里。

现状BackgroundSessionManager、ReportOrchestrator 和 analysisDocPersistence 都碰到 UI store type。
问题长任务、保存、恢复、前后台切换被 UI shape 绑定。
目标AnalysisSession 是 domain model，UI 只订阅 session events。
第一刀把 V2SessionSnapshot 从 UI store 移到 neutral contract。
Copilot能力化

Copilot 不应该只是一个单独入口，它应该是一组可被 Chat 和 Command 调用的文档能力。

现状actions/index.ts 混合 action manifest、executor、prompt、panel map。
问题新增 action 的正确位置不清楚，UI 与执行逻辑互相靠太近。
目标Copilot actions 先编译成 CapabilityManifest，panel binding 留在 UI 层。
第一刀选 Doc Review 一类 action 做 manifest / executor / panel 三段式样板。
Hermes Harness主线投资

Harness 不是旁支，它是低成本模型、可替换后端和长期 agent 能力的核心。

现状已有 loop、tier、permission、memory、hook、subagent、skill lifting，但 vaultFull 和 Auto Review 仍偏 SDK 路径。
问题Vault tools、output tools、HITL、stream adapter 没有完全后端中立。
目标Harness 和 SDK 都实现同一 AgentBackend，输出同一 RunEvent。
第一刀适配只读 Doc Review 和 Search tools 到 Harness ToolDef。
Settings / Onboarding / Dashboard产品支架

这些不是边缘页面，它们是“能力准备状态”和“系统运营”的支架。

现状provider、index、MCP、Harness、usage、onboarding 各自展示局部状态。
问题用户不知道当前哪些能力 ready、哪些只是配置了但不能跑。
目标Settings 展示 capability readiness，而不是内部 routing tier。
第一刀为每个 capability 生成 readiness：provider、index、tool、permission、budget。
Knowledge Graph / Maintenance差异化

Vault Lint、Gap Analysis、Structural Hole、Hub Regen、Precompiled Knowledge 是产品护城河，不应散在搜索实现里。

现状graph、structural、hub、cascade、lint 分布在 search/index、lint、actions、UI view。
问题用户看到的是零散面板，代码看到的是搜索内部细节。
目标KnowledgeMaintenance capability family：diagnose、repair、regen、explain、review。
第一刀把 HubRegen / Structural / VaultLint 的结果统一成 reviewable artifact。
Ambient / Signal Layer信号层

Ambient 不是一个小侧栏，而是系统主动感知用户当前写作和 vault 变化的信号层。

现状Ambient Push、Morning Briefing、gutter、反馈日志已有实现。
问题它没有被建模成可被 Chat、Knowledge、Dashboard 复用的 signal。
目标AmbientSignal 输出 reason、source、confidence、suggested action。
第一刀把 Ambient 推荐产物统一到 artifact/event，而不是只推 UI。
Templates / Prompts治理资产

Prompt 和 config 是产品能力的一部分，不是工程附属文件。

现状97 prompts、10 tool templates、9 config、5 agents、9 indexing。
问题文件存在不等于仍被调用；变量和 schema 会漂移。
目标每个 template 有 id、category、schema、sample vars、caller、deprecation。
第一刀template-manifest.test.ts：file exists、render smoke、JSON parse、unused list。
MCP / Tools工具接入

MCP 是工具协议，不是产品能力。工具要经过 ToolRegistry、permission、schema adapter 后才能给 agent 用。

现状MCPClientManager 支持 stdio/SSE，MCPToolAdapter 能转成 AgentTool。
问题Zod v3/v4、JSON schema、SDK tool shape、Harness ToolDef 还没有统一适配层。
目标ToolDef 是内部标准；MCP、script、Obsidian command 都是 adapter。
第一刀统一 tool envelope：name、description、inputSchema、permissionKind、execute、outputSchema。
Storage / Artifacts双存储

Vault markdown + SQLite 是正确方向：可读 artifact 给用户，结构化索引给系统。

现状chat docs、analysis reports、copilot history、hub docs、SQLite index/graph/usage。
问题repo shape、DDL、Kysely type、artifact schema 没有统一 contract。
目标ArtifactStore 管 human-readable outputs；Repo 管 structured query。
第一刀AI Analysis / Copilot artifact 定义统一 metadata：capabilityId、runId、sources、usage。
AppContext / Lifecycle收紧

AppContext 可以保留，但不能再是任意模块拿任意实现的全局入口。

现状AppContext inbound import 多，service/workflow/prompt/skills 都直接取 manager/app/settings。
问题测试替换难、unload 清理难、边界不可推理。
目标AppContext 是 composition root，只暴露 stable ports 和 registry。
第一刀禁止新代码在 core 引 AppContext；service 新路径先走 ports。

7. Skills / Templates / Tools：不要混成一个概念

你前面追问的点很关键：Skill、Tool、MCP、Capability 看起来都像“能力”，但在架构里必须分层。 分清楚以后，templates 也不会再像一堆遗留 prompt 文件。

Product Capability 用户看得见的产品承诺，例如 Doc Review、Vault Search、AI Analysis、Knowledge Health。
Agent Skill / Playbook agent 做事手册：何时使用、步骤、工具白名单、输出合同、示例。
Action Tool 可调用的原子动作：读文件、搜索、生成 patch、调用 Obsidian command。
Protocol MCP 工具接入协议。它能把外部软件或内部 vault server 暴露给 agent。

Template 的正确定位

templates/ 不是垃圾堆，它应该是可治理的配置资产： prompts、tool output templates、model catalog、curator config、future capability/skill packages。

目标是 TemplateRegistry + schema + render smoke + unused/quarantine list。

Skill 的正确定位

用户/市场写 portable SKILL.md 包；Peak 编译成内部 AgentSkill； CapabilityManifest 再引用这些 skill。

不要让用户手写我们自创的一大坨 JSON，也不要把 Skill 继续做成孤立 workflow modal。

9. 重构路线：先建中枢，再迁移能力

这里不建议大重写。更稳的做法是先建立中枢接口，然后把现有功能一条一条包进去。

PR0测试可信unique temp、timeout、真实失败退出。
