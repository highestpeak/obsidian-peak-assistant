Code Design Review

Peak Assistant 全仓库代码设计与架构报告

日期：2026-05-30 · 范围：src/、test/、templates/、scripts/、关键启动/搜索/Agent/Copilot/SQLite/UI 路径 · 重点：逻辑结构、工程边界、重构优先级。

总判断

这个项目的产品方向和核心能力已经很强：它不是一个简单 Obsidian RAG 插件，而是一个围绕 Chat、AI Analysis、Copilot、Knowledge Maintenance、 Ambient Push 展开的知识工作层。

但代码设计已经进入需要主动治理的阶段：当前可维护风险不是“某个文件太长”这么简单，而是 类型守门失效、依赖方向反复穿透、服务层直接抓 UI、核心层反向依赖业务层、AppContext 成为全局服务定位器。 这些问题会让 AI 后续继续写代码时越来越难判断哪里才是正确落点。

最优先的结论

P0 先恢复 src 类型检查通过，把类型系统重新变成门禁。

P0 再治理跨层 import，尤其是 core -> service/app/ui 和 service -> ui/app。

P1 拆 IndexService、Copilot actions、BackgroundSessionManager 这三处最大架构压力点。

启动顺序设计是有经验沉淀的：AppContext 提前创建是为了解决下游 init 期间的 singleton 访问。 但这也造成一个长期成本：很多模块可以绕过构造函数直接从全局拿依赖。短期方便，长期让生命周期和测试隔离变困难。

3. 主要设计问题

P0 类型系统没有形成有效门禁

当前 tsconfig.json 开了 noImplicitAny 与 strictNullChecks，这是好事； 但真实 tsc --noEmit --skipLibCheck 仍然有 124 条 src/ 报错行。 这意味着类型系统不是“偶尔有噪音”，而是已经不能作为日常合并门禁。

错误族例子设计含义
全局上下文 API 漂移AppContext.getPluginId() 不存在；ctx.pluginId 不存在服务层对 app runtime 依赖没有稳定 port。
schema/repo shape 漂移MobiusNodeRepo 缺 structural 字段；UsageLogRepo insert shape 不匹配SQLite DDL、Kysely 类型、repo 返回 shape 没有单一真相源。
prompt/template registry 漂移hub-doc-summary-system registry mismatch；prompt variables 缺 key模板系统已经需要 manifest 校验和生成型类型。
tool schema / zod 版本漂移Zod v3/v4 类型互不兼容Agent tool adapter 层缺统一 schema adapter。
stale tests/scriptstelemetry modules missing；hub/lint tests import 旧模块测试资产没有被当前架构演进同步维护。
建议：先不要做大重构。第一步应该是新增 typecheck:src，让 src 在 skipLibCheck 下先绿； 再把 test/scripts 分到单独 tsconfig，逐步收复。否则后续重构是在没有护栏的状态下开车。

P0 依赖方向已经破坏分层模型

当前最危险的不是 UI 大，而是底层模块反向依赖上层模块。 core 里出现了对 service/chat/service-manager、service/prompt/PromptId、app/settings/types、 AppContext、甚至 ui store/type 的依赖。

反向依赖数量应对方式
core -> service56把 prompt id、AI capability、search index shared types 下沉到 core/contracts 或 service/*/contracts。
core -> app17把 settings 类型拆成纯配置 contract；Obsidian runtime 访问通过 port 注入。
core -> ui5Graph/search doc 类型不要引用 UI store 类型；建立 neutral DTO。
service -> ui55业务层不要直接读 Zustand store 或打开 modal；改为事件/adapter。
service -> app74逐步把 AppContext 改成 ports，例如 VaultPort、SettingsPort、ProviderPort。

P0 AppContext 已经从 DI root 变成 service locator

AppContext 作为插件启动时的 DI root 是合理的；问题是现在它被服务层、core、UI、工具函数大量直接调用。 这导致依赖关系从构造函数和接口转移到静态全局状态，测试时很难替换，卸载时也要靠大量手动清理。

flowchart LR Many["150+ importing files"] --> AppContext["AppContext singleton"] AppContext --> App["Obsidian App"] AppContext --> Manager["AIServiceManager"] AppContext --> Search["SearchClient"] AppContext --> Plugin["Plugin instance"] AppContext --> Settings["settings"] AppContext --> EventBus["EventBus"] AppContext --> Bridge["ClaudeAgentSDKBridge"] AppContext --> ViewManager["ViewManager"] Core["core helpers"] -.-> AppContext Service["service agents/tools"] -.-> AppContext UI["React views/stores"] -.-> AppContext

这类结构的典型后果是：一旦 AppContext 缺一个 accessor，比如当前 getPluginId，会在多条 Agent/ambient/workflow 路径同时暴露。

P0 401 文件级循环依赖连通块

依赖扫描中最大 SCC 达到 401 文件。这里不能粗暴理解为“401 个真实 runtime cycle 都会爆”，因为里面包含 type import 和 index re-export； 但从设计角度看，它已经说明模块边界不可推理：改 UI type 可能牵动 service，改 service type 可能牵动 core，再回到 app。

最先断开的环： BackgroundSessionManager 直接 import QuickSearchModal、useSearchSessionStore、eventTargetRedirect； ReportOrchestrator 直接 import useSearchSessionStore； analysisDocPersistence 直接 import UI callbacks/store types。先把 AI Analysis session domain 抽成 service-neutral 类型，会比全仓大迁移更有效。

P1 IndexService 是搜索系统的复杂度汇聚点

IndexService 现在承担太多职责：tenant resolution、文档读取、chunk、embedding、FTS、graph node/edge、cascade debt、global maintenance、pending enrichment。 这让 Search 系统虽然能力强，但任何索引变更都容易影响多个阶段。

flowchart TD IndexService["IndexService singleton\n2266 lines"] IndexService --> Tenant["Tenant resolver"] IndexService --> Crud["Document CRUD cleanup"] IndexService --> Read["DocumentLoaderManager read"] IndexService --> Chunk["Chunking + safe overlap"] IndexService --> Embed["Embedding generation"] IndexService --> FTS["FTS / stem / meta FTS"] IndexService --> Graph["Mobius graph projection"] IndexService --> Cascade["Cascade debt"] IndexService --> Maintenance["Pagerank / semantic PR / hub stats"] IndexService --> Enrich["Pending LLM/vector enrichment"]

推荐目标不是把它拆成很多同等小文件，而是保留一个薄 facade，然后把稳定阶段拆出去： IndexTenantResolver、DocumentIndexWriter、GraphProjectionService、 IndexEnrichmentQueue、MobiusMaintenanceService。

P1 Copilot action registry 把 data/action/UI 三件事混在一起

src/service/copilot/actions/index.ts 超过 1000 行，且包含 action 定义、prompt 调用、执行器、panel placeholder、custom prompt loading。 这会让新增 action 的“正确写法”越来越不明显。

当前混合内容目标拆法
Action metadataactions/manifests/*.ts，纯数据，可测试。
Action executoractions/executors/*.ts，只依赖 service ports。
React result panelsui/view/copilot/panels/panelMap.tsx，只在 UI 层绑定。
Custom prompt registry独立 registry，输出标准 action manifest，不 import UI。

P1 SQLite schema 与 repo 类型需要单一真相源

ddl.ts 过大本身不是罪，真正的问题是 DDL、Kysely Database 类型、repo insert/select shape、测试 fixture 不同步。 类型检查已经暴露 MobiusNodeRepo、UsageLogRepo、hub constituent 等漂移。

建议把 schema 分成 migration files + generated Kysely types，或者至少把 Database type 从 DDL 旁边拆成可生成/可校验层。 每次改表结构时，必须有一个 repo-level migration test 跟着改。

P1 Prompt/template registry 已经需要 manifest 校验

当前模板抽到 templates/prompts 和 TemplateRegistry 是对的，但 PromptId、PromptVariables、 TemplateRegistry、真实模板文件之间仍会漂移。

推荐建立一个 prompt-manifest.test.ts：枚举所有 PromptId，确认文件存在、registry 有 metadata、variables 类型可被 render smoke test 覆盖。

P2 UI convention、日志、any 债务需要工具化

as any、console.*、raw <button>、语义标题标签这些问题不适合靠人肉 review。 应该用 ESLint restricted imports/rules + custom script 作为轻量门禁。

5. 建议目标架构

目标不是“大重写”，而是把现在已经存在的能力按更稳定的边界重新摆放。 最小可行原则：保留现有产品功能和文件名认知，只先切断最伤人的反向依赖。

flowchart TB subgraph AppShell["app shell"] Plugin["main.ts"] Views["ViewManager"] Commands["commands/events"] AppAdapters["Obsidian adapters"] end subgraph UI["ui"] ReactViews["React views"] UIStores["UI-local stores"] UIPanels["Panels/modals"] end subgraph Domain["domain/service"] ChatDomain["chat domain"] SearchDomain["search domain"] AnalysisDomain["analysis session domain"] CopilotDomain["copilot domain"] KnowledgeDomain["knowledge maintenance domain"] end subgraph Core["core"] Contracts["contracts and DTOs"] Storage["storage repos"] Providers["provider adapters"] Templates["template engine"] Utils["pure utils"] end subgraph Ports["ports"] VaultPort["VaultPort"] SettingsPort["SettingsPort"] ProviderPort["ProviderPort"] EventPort["EventPort"] end Plugin --> AppAdapters AppAdapters --> Ports Views --> UI Commands --> Domain UI --> Domain Domain --> Ports Domain --> Core Core --> Contracts Core -. no import .-> UI Core -. no import .-> AppShell Domain -. no import .-> UI

5.1 新边界规则

层可以 import不应该 import
core纯类型、utils、storage 基础、provider 基础service、ui、app/context
servicecore、domain contracts、portsReact components、Zustand stores、modals
uiservice public APIs、UI stores、shared components直接写 SQLite、直接操纵 Agent internals
app全部组装层依赖业务细节膨胀到 commands 中

5.2 重构时最该保留的好设计

  • TemplateManager + prompt/config 外置方向正确，应继续加强。
  • Search pipeline 的多 retriever + RRF + PPR 方向正确，不要退回简单向量搜索。
  • Markdown artifact + SQLite index 的双存储策略适合 Obsidian，不要改成纯数据库产品。
  • Agent loop / tool schema / MCP 的方向正确，但 schema adapter 需要统一。
  • On unload 的资源清理意识很强，应把清理逻辑继续从 main.ts 抽成 lifecycle services。

6.2 具体任务表

优先级任务验收标准风险
P0 新增 tsconfig.src.json 与 npm run typecheck:src src 在 skipLibCheck 下通过；CI/本地 build 前可跑。 会暴露一批真实漂移，但这是必要成本。
P0 修复当前 src 类型漂移 不通过 any 糊掉；把 pluginId、PromptVariables、repo shape、EventDispatchTarget 等修到 contract 层。 如果边修边重构，容易扩大范围；建议只做类型收敛。
P0 加 import boundary 检查 core 禁 import service/ui/app；service 禁 import ui，少量例外白名单。 先只 warn/report，再逐步 fail。
P1 抽 AnalysisSession domain BackgroundSessionManager 不再 import modal/store/hook；ReportOrchestrator 不 import UI store。 AI Analysis 流程复杂，需要保留 snapshot 兼容。
P1 拆 IndexService IndexService 降到 facade，核心写入/graph/maintenance/enrichment 各有测试。 搜索/索引是核心功能，必须 test-near。
P1 拆 Copilot action system 新增 action 不需要编辑 1000 行 index；UI panel map 只在 UI 层。 涉及 15+ actions，先迁移一类 action 做样板。
P1 SQLite schema/prompt manifest 校验 DDL/repo/prompt/template 任何漂移能在测试中被抓到。 一开始会发现历史债，允许先建 quarantine list。
P2 日志与 any budget 新增 logger，限制新增 as any，把旧债做计数趋势。 不要一次性追求 0，先阻止继续增长。

6.3 不建议做的事

  • 不要一次性“重写架构”。现在系统功能多，重写会丢掉已经有效的产品路径。
  • 不要按文件长度机械拆分。拆分应该服务于依赖方向和职责边界。
  • 不要用更多 any 让 typecheck 变绿。那只是把警报器静音。
  • 不要先改 UI/产品命名。当前问题主要是工程边界，不是用户界面。
  • 不要把 AppContext 一次性消灭。先禁止它继续进入 core/service 新代码，再逐步替换已有热点。
