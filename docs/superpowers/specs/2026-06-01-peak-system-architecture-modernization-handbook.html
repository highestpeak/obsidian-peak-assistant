Peak Assistant 系统架构理解手册与现代化行动地图

Peak Assistant 不是一个 Chat 面板，也不是一堆 AI 功能入口；它是一组围绕 Obsidian vault 运转的知识工作能力。 这份手册先帮读者建立系统模型，再把架构现代化压到可执行的行动地图：能力契约、运行外壳、边界端口、技能包、测试合同和迁移节奏。

核心判断

当前项目最大的问题不是“代码太多”，而是 产品能力没有被编码成稳定契约。 Chat、Search、AI Analysis、Copilot、Harness、Knowledge 都已经有真实能力，但它们的入口、状态、后端、工具、输出和测试还没有被统一到可审查的工程协议里。

因此不建议先大搬目录或全量重写 service，而是先建立三条主轴： Capability Contract、Run Envelope、Ports + Adapters。

阅读契约

读者有后端/Agent 开发经验，知道 Peak 大概是什么，但不熟悉当前代码细节。

目标阅读后能说清系统能力、核心链路、主要坏味道、第一批重构切口和验证方式。

理解系统必须回答的 8 个问题

1. Peak 是什么？不是 Chat 插件，而是一组知识工作能力。
2. Chat 怎么发送消息？用户输入经过 context、planner、backend、event、artifact。
3. Context 怎么收集？ContextPipeline 用 slots + budget 管当前文件、历史、搜索证据。
4. Copilot 怎么运行？从 document context 选 action，运行 agent，产出 diff/artifact，用户确认写回。
5. Harness 能替代什么？它是便宜模型/本地模型 agent backend，不是 UI，也不是产品能力本身。
6. Skill 有什么用？它应该变成 agent 工作手册包，被 Capability 引用，而不是孤立 picker workflow。
7. MCP 是什么位置？MCP 是外部工具协议，先转内部 ToolDef，再被 Skill/Capability 使用。
8. 先改哪里？先加 contract、RunEnvelope、ports、contract tests，再拆大 service。

1. 能力全景：Peak 不是 Chat 插件，而是一组知识工作能力

架构重构不能从 service-manager.ts 或目录结构开始。先把产品能力铺开，才能判断哪些代码应该合并、哪些应该拆开、哪些只是 UI 入口。 Peak 已经覆盖提问、搜索、研究、写作、审阅、知识维护、主动发现、工具生态和系统运营；中枢必须服务整个能力面，而不是只服务 Chat。

1.1 产品存在理由：不是和目录聊天，而是让 vault 变成主动知识工作空间

如果 Peak 只是“在 Obsidian 里和 Markdown 文件夹聊天”，那它只是 ChatGPT / Claude Code / Codex / Cursor 的一种低摩擦平替。 这个入口有价值，尤其对不想买高价订阅、希望用 OpenRouter、DeepSeek、Ollama 或自带 API key 的用户；但它不足以成为长期护城河。 Peak 的更强定位应该是：把 Obsidian vault 从被动文件夹变成会搜索、会联想、会体检、会提醒、会审阅、会持续维护的知识工作空间。

残酷判断： Chat、Search、AI Analysis、Copilot 都必须有，但它们本身不是最终差异化。它们是让用户进入系统的基础入口； 真正差异化来自 Obsidian-native surface、长期 work state、Ambient signal、 Knowledge health、Reviewable artifact 和 低成本持续运行 的组合。
替代方案它已经能做什么Peak 不能只靠什么取胜Peak 应该赢在哪里
ChatGPT / Claude Web 强通用问答、研究、写作和文件分析；ChatGPT Plus 当前是 $20/month，API 另行计费。 不能只说“我也能和笔记聊天”。 当前文件、selection、backlink、vault graph、可审阅写入和本地知识状态都在 Obsidian 内完成。
Claude Code / Codex / Cursor 打开目录、读文件、跨文件修改、跑命令、做长任务；Claude Code 还可接 Pro/Max，但和 Claude 共用 usage limits。 不能只说“我也能访问一个目录”。 Peak 面向知识库而不是代码库：维护 link、hub、tag、source、draft、review、ambient recommendation。
其他 Obsidian AI 插件 Nexus、Gemini Helper 等已经有 native chat、RAG、MCP、workflow、diff 或 usage tracking 等能力。 不能只说“我是 Obsidian AI 插件”。 把知识图谱健康、主动发现、长期反馈学习和 review artifact 做成系统主线，而不是附加功能。
Peak 目标形态 BYOK / OpenRouter / DeepSeek / Ollama 降低成本，同时保留强模型兜底。 便宜只能带来试用，不能保证留存。 长期知道 vault 怎么变化、用户正在做什么、哪些知识关系在变差、哪些建议被接受或拒绝。
基础入口必须有 Chat 是最低摩擦入口；Search 是证据地基；AI Analysis 是长任务入口；Copilot 是从回答走向行动的入口。 没有它们，用户很难开始使用 Peak。
护城河不能停在这里 这些能力如果只是临时读取 vault、生成回答、改写文本，就会被通用 agent 吃掉。 它们必须连接长期状态、主动信号和可审阅产物。

1.2 长期 Work State：Peak 应该长期记住什么

Peak 的差异化不是“记住聊天记录”，而是把知识工作状态产品化。长期状态越明确，Chat、Search、Copilot、Ambient 就越不像一次性工具。

Vault Statehub、orphan note、broken link、stale summary、structural hole、tag gap、source gap。long term
User Focus State当前文件、selection、最近写作主题、活跃 folder/project、反复搜索的问题。session
Run StateAI Analysis 跑到哪里、Copilot 生成过哪些 artifact、哪些后台 session 可恢复。resumable
Knowledge Health State哪些地方需要补 link、合并、拆分、补证据、更新 hub、修复断链。review
Preference / Cost State用户偏好便宜模型还是强模型，哪些操作可自动，哪些必须确认，哪些建议经常被拒绝。adaptive

Decision 1 产品能力先写成 Capability Contract

Doc Review、Vault Search、AI Analysis、Knowledge Health 这类能力必须有 id、输入、输出、权限、成本、后端支持、默认 skill 和展示 surface。

Decision 2 长任务统一到 Run Envelope

Decision 3 AppContext 留在 app 层，service 依赖 Ports

AppContext 作为 composition root 可以保留；新 service 通过 VaultPort、SearchPort、ProviderPort、ToolPort、CommandPort 访问宿主能力。

Decision 4 Skill 改成工作手册包，不再只是轻量 markdown 动作

Skill 应该描述 agent 怎么做事，可以携带 examples、allowed tools、output contract、脚本资源；Capability 引用 Skill，但不等于 Skill。

Decision 5 测试从函数覆盖升级成能力合同

用 fake vault、fake search、fake model、fake tools 跑 Chat send、AI Analysis round、Copilot Auto Review、Harness backend conformance。

Decision 6 禁止双系统双代码共存

重构不是在旧系统旁边再造一套新系统。旧入口可以短暂保留为 facade，但业务实现只能有一套；每个迁移任务包必须包含旧实现删除或掏空。

硬性规则： 不接受“新架构 + 旧架构长期并行”的双系统状态。允许保留旧 public entry、command id 或 view type 作为用户不感知的稳定入口； 但这些入口只能转发到新 capability / RunEnvelope / ports 实现，不能继续拥有旧业务逻辑。 每个重构任务包的验收门都必须回答：删掉了哪个旧实现？哪个旧状态真相被移除？是否还存在同一能力的两条运行路径？

3.1 决策记录：为什么不是其他改法

这里的决策记录就是轻量 ADR：给未来改代码的人看。它不只是说“要这么做”，还记录放弃了什么方案、这条路的代价是什么、怎么证明它不是空抽象。

决策理由不选的方案代价 / 风险验证方式
先做 Capability Contract 产品能力没有合同，Chat、Copilot、Skill、Tool 会继续互相吞职责。 先拆目录或重命名 service。 会先多出一些类型；如果没有 fixture，会变成空抽象。 至少两条能力能用同一 manifest 描述输入、输出、权限和后端。
统一 RunEnvelope，不统一业务流程 需要统一状态、事件、trace、artifact、取消和恢复；但 Search、Copilot、Harness 的业务引擎不同。 把所有链路都改成 agent loop 或同一 pipeline。 不能让旧 store 和新 RunSession 同时拥有状态真相；迁移一条链路就删除这条链路的旧状态源。 Chat 或 Copilot 任一链路只有一条运行路径，且能输出标准 RunEvent 和 ArtifactRef。
Ports 优先于删除 AppContext AppContext 作为 composition root 有价值，真正问题是 service/core 直接依赖宿主细节。 把 AppContext 直接定性为坏并全仓替换。 旧入口可作为 facade 保留，但已迁移的 service 不得再直接拿 AppContext 或 Obsidian app。 新增或已迁移 service 只依赖 VaultPort / SearchPort / ProviderPort 等接口。
Skill 做编译层，并按能力替换旧执行路径 Skill 要变成工作手册包；迁移时可以保留文件格式入口，但运行时只能走新 compiled skill。 让同一个 skill 同时保留旧 registry 执行和新 compiled skill 执行。 需要 quarantine、schema、sourceHash；每迁移一个 skill family 就要删除对应旧执行逻辑。 坏 skill 不进入 runtime；好 skill 被 Capability 引用并限制 allowed tools；同一 skill 不能有双执行路径。
禁止双系统双代码共存 这次现代化的收益来自移除重复真相和重复路径；如果新旧系统长期并行，代码量、测试量和认知负担都会上升。 先搭完整新平台，旧平台继续跑，等以后再慢慢切。 迁移任务必须更克制：每次只替换一个能力族或一条链路，但替换必须闭环。 每个任务包都写清：旧入口是否只转发、旧业务实现删除/掏空了什么、同一能力是否只剩一条运行路径。

5. 什么叫现代、模块化、优雅：不是形容词，是验收标准

“现代化”不是把目录名改得更干净，也不是把代码抽得更抽象。对 Peak 来说，现代化就是下面六条能被代码和测试验证的标准。

回答问题什么叫现代、模块化、优雅，如何从形容词变成验收标准。
呈现方式每条标准都用“现在 / 目标”对照，便于审查任务包。
用来行动重构如果不能命中这里至少一条，就先不要做。
1

声明式能力，而不是入口里手写流程

新增能力时先写 contract：输入、输出、权限、成本、后端支持、默认 skill、展示 surface。

现在Chat tools、Copilot actions、Skill workflow、MCP tools 各自注册。
目标CapabilityRegistry 管产品能力；SkillRegistry 管行为包；ToolRegistry 管动作。
2

统一运行外壳，而不是每个 hook 自己存状态

长任务进入 RunSession：状态、事件、取消、恢复、history、artifact 有统一模型。

现在AI Analysis session、Copilot review、Harness loop 各有状态真相。
目标ChatRun、AnalysisRun、CopilotRun、HarnessRun 都输出 RunEvent。
3

Ports and Adapters，而不是 service 到处拿 AppContext

AppContext 可以保留，但 service 不应该知道 Obsidian、React store、modal 的具体形状。

现在部分 service 直接 import UI store、AppContext、Obsidian app。
目标新 service 只依赖 VaultPort、SearchPort、ProviderPort、CommandPort。
4

后端中立，而不是 SDK 形状污染产品能力

Claude SDK、Hermes Harness、普通 provider 都是 backend adapter，不应该决定 capability 的产品语义。

现在部分复杂能力绑定具体 SDK、MCP server 或 output tool 形状。
目标统一 AgentBackend / RunEvent / ArtifactRef，工具和输出可适配。
5

资产可治理，而不是 prompt/template 越堆越多

142 个 template 是资产，不是负担。关键是每个资产要有 owner、schema、调用方、render smoke、废弃状态。

现在prompt、tool templates、config JSON、Skill markdown 分散在 templates 和 service 中。
目标TemplateManifest + PromptId + schema + unused/quarantine list。
6

测试锁行为，而不是靠手感回归

优雅架构一定容易测：输入 fixture、fake vault、fake model、fake tools，就能跑完整产品 contract。

现在已有 85 个测试文件，但核心产品能力 contract 还不够。
目标核心 capability 有 scenario、golden trace、backend conformance tests。
验收方式： 任何重构任务包都应该能指向上面至少一条标准。否则它可能只是“看起来更现代”，但没有降低后续维护成本。

14. 不要做什么：这些看起来像重构，其实会制造更大风险

回答问题哪些“看起来现代”的动作其实会增加风险。
呈现方式用禁止清单直接约束重构冲动，比长篇解释更有效。
用来行动代码评审时先检查有没有踩这些 anti-goals。
不要做为什么替代做法
不要双系统双代码共存 新旧两套业务实现会制造两份状态真相、两套测试口径和两种调用习惯，最后比旧系统更难维护。 每个任务包都完成替换闭环：新合同、新实现、旧入口转发、旧业务删除、conformance / smoke 通过。
不要先全仓搬目录 会产生大量 diff，但不一定让行为更可测。 先加边界检查和 capability contract，再按能力迁移。
不要把 Search 改成 agent loop Search 的核心价值是可解释、可复用、低成本 retrieval pipeline。 Search 输出 RunEvent / ArtifactRef，但内部仍保持检索 pipeline。
不要让 Capability、Skill、Tool 合成一个万能 JSON 这会把产品语义、工作流和动作权限混在一起。 Capability 引用 Skill 和 ToolPolicy，三者分层。
不要把 AppContext 直接定性为坏 它作为 composition root 有价值，问题是下层随便拿它。 保留 AppContext，新增 service 通过 ports 拿依赖。
不要让 CopilotActionRegistry 和 CapabilityManifest 双源共存 它会让 action 排序、guard、execute、ResultPanel 的真实来源变成两套，后续 review 很难判断哪套才是产品合同。 按 action family 替换：旧 registry entry 只做转发，同任务包删除旧 execute / ResultPanel 业务实现。
最终建议： 下一轮不要以“减少行数”为第一目标。更好的目标是：每个核心产品能力都有合同、每次运行都有 trace、每个后端都能 conformance、每个 service 都能 fake port 测。
