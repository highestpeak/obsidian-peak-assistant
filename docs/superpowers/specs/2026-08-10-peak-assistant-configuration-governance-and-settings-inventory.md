## 0. 这份文档解决什么问题

这份文档不讨论 Settings 的具体视觉形式。它只回答四个问题：

1. Peak Assistant 到底有哪些设置和可调整能力？
2. 哪些可以让用户修改，哪些只适合高级用户，哪些应由系统自动处理？
3. 每项设置应该在哪里修改？
4. Onboarding、Settings、具体功能页面和系统各自负责什么？

本文是字段迁移、配置治理和历史模块映射的完整附录。当前产品评审先看按四个 Settings 功能组整理的[可配置能力总表](./2026-08-12-settings-configurable-capabilities-by-group.md)。UI 可以重新设计，但不能为了让页面看起来简单，就删掉用户确实需要的能力；也不能把尚未接通的功能画成已经可用。

阅读时可以分成两部分：

- 产品负责人先看第 0–6 节和第 11 节。
- 第 7、8、10、13、14 节主要供设计交接、开发和验收时查阅，不需要第一次阅读就全部看懂。

### 0.1 最终结论

- **不是所有能变化的参数都要放进 Settings。** 例如算法权重和运行限制虽然可以调整，但普通用户不需要管理。
- **不做一个覆盖全产品的“普通 / 高级”模式开关。** 每项设置自己决定是否属于高级设置，普通设置不会因此被分成两套页面。
- **同一项设置只能有一个真正的修改位置。** 其他页面可以显示它或跳转过去修改，但不能另外保存一份，避免两个页面互相冲突。
- **模型设置从用户认识的功能进入。** 用户先找 Chat Studio、Composer、File Atlas 或生成图片，再根据需要逐层查看具体动作；AI 服务商和连接信息单独管理。
- **用户决定想要什么，系统负责复杂的内部计算。** 用户可以选择默认 AI 连接、是否自动更新索引、AI 能不能修改文件，但不需要判断图算法权重或内部超时参数。
- **页面上能保存，不等于设置真的有效。** 一项设置只有在产品确实会使用它、重启后仍然保留、并且可以确认已经生效时，才算正式设置。
- **设置、状态和操作必须分开。** “自动更新索引”是设置，“索引覆盖率”是系统状态，“重新建立索引”是一次操作。
- **文档类型不是一个简单的扩展名开关。** 产品必须分别说明一种内容能否被识别、读取、全文搜索、向量化、AI 补充分析、编辑或生成。
- **知识索引不是一条短暂通知。** 首次批量索引和后续维护都需要一个可重复打开的任务入口，长期显示阶段、覆盖率、失败、成本和历史结果。
- **完成 Onboarding 不等于用户已经成功。** 完成必要设置后，还要把用户带到一个真实功能里完成第一件事。

### 0.2 明确不做

- 不规定 Settings 的具体页面布局；
- 不决定侧栏、标签页、卡片、折叠或搜索控件的视觉形式；
- 不把旧 Settings 中出现过的每个字段都默认保留为用户设置；
- 不把“源码里有默认值”误写成“用户应该看到这个默认值”；
- 不把 AI 服务商、模型、任务、工具、Agent 运行环境和图片 / 视频生成方式混为一类；
- 不把诊断、迁移、重建和删除动作伪装成普通开关；
- 不因为 Codex / Claude Code 同时具有 Agent 能力，就把它们限制为“只能运行 Agent”；
- 不在 Codex / Claude Code 的普通对话和 Agent 两条接入都完成验证前，写成已经全部可用；
- 不将本文件视为实现完成证明。

## 1. 什么内容应该成为正式设置

一项内容只有同时满足下面七个条件，才应该出现在正式 Settings 中：

1. **用户知道为什么要改。** 名称和说明能让用户理解它会影响什么。
2. **产品真的会使用这个值。** 修改后，至少有一个真实功能会发生可观察的变化。
3. **关闭再打开后仍然保留。** 不能表面上保存成功，重启后却悄悄变回旧值。
4. **不容易设置出错。** 产品知道允许填什么，也能说明它依赖哪些连接或功能。
5. **用户能看出是否已经生效。** 产品需要区分“已保存”“正在处理”“已生效”和“失败”。
6. **用户可以反悔。** 能够恢复自动选择、恢复产品默认或撤销修改。
7. **只有一个主要修改位置。** 不能让同一个设置在多个页面各存一份，最后不知道哪一份算数。

如果做不到其中任何一项，就先不要把它当作普通设置。它更可能属于：

- 尚未完成、暂时不能开放的功能；
- 系统自动检测出来的只读状态；
- 只由系统管理的内部参数；
- 重新连接、重建或清理等一次操作；
- 使用高成本或高风险功能前的一次确认；
- 只为兼容旧版本而暂时保留的数据。

### 1.1 必须区分的四种“默认”

| 类型 | 简单理解 | 用户选择“恢复”时会怎样 |
| --- | --- | --- |
| 产品内置值 | 系统没有其他信息时使用的安全起始值 | 回到产品当前版本的内置值 |
| 自动选择 | 系统根据现有连接、模型能力和当前任务自动选择 | 清除用户指定的值，以后继续由系统自动选择 |
| 用户指定的默认值 | 用户明确选定、希望以后继续使用的长期偏好 | 一直保留，直到用户再次修改或恢复自动选择 |
| 本次实际使用值 | 这一次任务最终真正使用的连接、模型、权限和参数 | 只记录本次结果，不自动变成长期默认 |

这里最容易出错的是“恢复默认”。对于支持自动选择的设置，它应该表示“取消我的手动指定，重新交给系统选择”，而不是把某个旧版本的数值永久保存下来。这样产品以后更新了更好的默认策略，老用户也能正常得到。

## 2. 本文怎样区分不同内容

后面的清单会使用下面这些中文分类。分类的目的，是一眼看出用户能不能改、应该在哪里改，而不是增加新的产品术语。

| 分类 | 用户怎么理解 |
| --- | --- |
| 自动决定 | 系统先给出可靠选择；用户可以手动指定，也可以随时恢复自动选择 |
| 普通设置 | 用户经常需要的长期偏好，影响容易理解，直接放在 Settings 中 |
| 功能内设置 | 只影响当前聊天、文档、任务或视图，在对应功能页面修改 |
| 高级设置 | 确实有用，但影响范围较大、风险较高、很少修改，或需要一定专业知识 |
| 使用前确认 | 涉及权限、费用或数据影响时的一次确认，不是假装成普通开关 |
| 操作 | 验证、重建、清理、迁移或删除等需要实际执行的动作，会显示进度和结果 |
| 只读状态 | 系统检测或计算出的事实，用户可以刷新或修复，但不能手工填写结果 |
| 系统负责 | 算法、安全限制和内部参数由产品负责，不开放给普通用户 |
| 暂不可用 | 页面或字段可能已经存在，但保存、实际使用或验证还没有完整接通 |

“高级设置”不是另一套 Settings，也不需要用户先切换整个产品模式。它只表示这一项默认可以收起，但展开后仍要说明影响、检查输入，并提供恢复方式。

## 3. 一项设置应该放在哪里

```text
用户是否需要主动决定？
  否 → 显示为只读状态，或者完全由系统处理
  是 → 产品现在是否真的会使用这个设置？
        否 → 暂不开放
        是 → 它是否只影响当前聊天、文档、任务或视图？
              是 → 放在对应的功能页面
              否 → 第一次完成目标时是否一定需要它？
                    是 → Onboarding 只询问完成任务所需的最少内容
                    否 → 放在 Settings

如果修改会产生额外费用或风险，就标为高级设置或使用前确认。如果还需要重新处理数据或迁移，则提供一项明确的操作。
```

### 3.1 五条硬规则

1. 同一个值只能有一个主要修改位置。
2. 其他页面可以跳到这个位置，但不能另外保存一份。
3. 功能页面里的临时选择不会自动变成长期默认；用户必须明确点击“设为默认”。
4. Onboarding 和 Settings 使用同一份连接、模型、索引和权限数据。
5. 保存后必须从真实功能重新确认是否已经生效，不能只因为按钮提示“保存成功”就算完成。

## 4. Onboarding、Settings、功能模块和系统的职责

### 4.1 Onboarding：负责第一次成功

Onboarding 开始时需要知道：

- 用户第一次想完成的真实任务；
- 当前有哪些连接已经可用，Vault 和知识索引是否准备好，所需工具是否能运行；
- 已保存且仍有效的用户配置；
- 上次未完成流程的进度。

Onboarding 只会修改完成第一次任务所必需的内容：

- 完成首次任务所需的新连接或认证；
- 用户尚未明确指定的任务默认值；
- 完成该任务所需的最低安全许可；
- 与首次任务直接相关的索引、媒体或 Agent 使用确认；
- 当前完成到了哪一步，以及之后应该从哪里继续。

Onboarding 不负责：

- 完整的 AI 服务商和模型列表管理；
- 逐项讲解 Peak 的所有功能；
- 模型随机程度、文档分块大小、图算法权重和超时等高级参数；
- 全部外部工具、Skills 和命令安全管理；
- 长期数据保留、目录迁移和调试记录；
- 改掉用户已经明确指定的模型或任务默认值；
- 把“设置完成”误当成“用户已经成功使用”。

为什么这样分：新用户此时没有足够上下文判断大量技术选项。Onboarding 应把“学习产品”替换成“完成一件事”，只在系统无法自动补齐阻塞依赖时提问。

### 4.2 Settings：负责长期掌控

Settings 负责：

- 当前系统是否正常，以及问题影响什么；
- AI 连接、任务默认、安全权限、索引、媒体、数据和工具的长期配置；
- 设置的保存、生效、重启、重处理和迁移状态；
- 恢复自动、恢复默认和依赖影响检查；
- 定位并进入局部修复流程；
- 高级设置、系统检查和危险操作；
- 对所有模块的可搜索入口，但不复制模块内状态。

Settings 不负责：

- 当前聊天的临时模型切换；
- 当前 Composer 动作的临时指令；
- 当前 File Atlas 视图的筛选与缩放；
- 当前媒体任务的生成要求、数量和候选预览；
- 当前 Agent 任务执行过程中的逐步确认；
- 运行历史本身的完整浏览体验。

为什么这样分：Settings 管理跨任务、跨会话的长期意图。把一次性上下文选择放入 Settings，会让用户无法判断它影响“现在”还是“以后”。

### 4.3 具体功能页面：负责这一次任务

具体功能页面负责：

- 当前任务输入；
- 当前任务临时使用的模型、生成方式或预设；
- 当前上下文范围；
- 当前视图和工作流偏好；
- 运行前确认；
- 当前结果、本次运行记录、重试和恢复；
- 明确的“设为长期默认”动作。

这里的“功能页面”也包括长期任务工作台。例如知识索引可能运行很久、可以部分成功、也可能需要稍后回来修复，因此它的运行进度、失败队列和历史结果属于知识索引工作台，而不是 Settings 中的一组开关。

为什么这样分：只有任务现场拥有足够上下文解释选择的实际影响，用户也能立即看到结果。

### 4.4 系统：负责自动处理和真实状态

系统负责：

- 判断连接、索引和工具是否真的可用；
- 识别模型支持什么，以及模型列表是否来自最新查询；
- 自动选择模型，并在首选模型不可用时按规则处理；
- 计算索引覆盖率、发现新增或变化的文件，并判断语义搜索是否可用；
- 管理数据格式、版本升级和不能绕过的安全限制；
- 管理算法权重、内部阈值、批处理大小和超时时间；
- 记录用户原本选择了什么，以及本次任务最终实际用了什么；
- 发现配置不可用时阻止假成功。

为什么这样分：这些事实不能由用户可靠填写；允许用户手工修改会破坏可信度、安全性或可支持性。

### 4.5 系统检查与维护：负责发现问题和执行修复

系统检查展示只读事实，也可以导出诊断信息；维护则会真正执行重连、重建、迁移或清理。两者都可以从 Settings 进入，但都不是普通设置。

每个维护动作必须说明：

- 准确目标；
- 影响范围；
- 是否会重处理或删除；
- 是否可取消与恢复；
- 当前进度；
- 最终结果记录；
- 完成后重新检查系统是否恢复正常。

## 5. 每个模块分别负责什么

| 模块 | 这里负责什么 | Onboarding 只做什么 | 不应该放在这里的内容 |
| --- | --- | --- | --- |
| 首次设置与可用状态 | 只记录首次设置进度，不保存长期业务偏好 | 检测已有条件、恢复进度、带用户完成第一次任务 | AI 服务商字段、索引参数、完整模型列表 |
| AI 连接 | 账户、登录、服务地址、启用状态、模型目录更新和逐项能力验证 | 只补齐第一次任务缺少的连接 | 每种任务用什么模型、Agent 流程和工具权限 |
| 任务与模型 | 产品功能层级、任务默认模型和逐级特殊指定 | 自动选择能完成第一次任务的最小方案 | API 密钥和完整模型列表的维护 |
| 权限与 Agent | Peak Hermes 流程、执行连接偏好、长期权限、升级策略和预算意图 | 只确认第一次任务所需的最低权限 | 当前这一次工具调用的确认、系统内部风险判断 |
| 知识索引设置 | 索引哪些内容、何时更新、质量层级、文件类型和长期分析策略 | 检查现状，建立完成第一次任务所需的最低策略 | 当前运行进度、失败文件和完整运行历史 |
| 知识索引工作台 | 执行首次建立、增量更新、补充分析、失败修复，并展示覆盖状态和历史 | 首次需要索引时打开同一项任务，并在达到最低可用状态后继续 | API 密钥、模型长期默认、分块参数和重复的文件类型设置 |
| Chat Studio | 当前对话的临时选择、附件和会话行为 | 打开 Chat Studio 并带用户完成第一次对话 | 管理全部 AI 服务商和长期索引策略 |
| Composer | 文档默认打开方式、Copilot 和 Intelligence 的长期偏好 | 打开 Composer 并带用户完成第一次文档任务 | 当前选区和某一次动作的临时指令 |
| AI Search / Analysis | 分析结果的保存方式和历史偏好 | 打开搜索并带用户完成第一次搜索 | 另外建立一套重复的模型设置 |
| File Atlas / Graph | 图谱长期默认和当前视图偏好 | 确认目标文档和图数据可用 | 图算法权重和当前选中的节点 |
| 工具、MCP 与 Skills | 外部工具连接、长期允许 / 禁止和 Skills 位置 | 只有第一次任务依赖时才处理 | 当前这一次运行的确认和系统安全硬限制 |
| 媒体与文件 | 各类媒体的默认生成方式、保存位置和许可 | 只配置第一次媒体任务必需的内容 | 当前生成要求、预览和生成结果 |
| 工作区与 Ambient | 启动偏好、相关内容出现的位置和 Command Center 的长期组织 | 第一次成功后推荐下一步入口 | 当前活动文档和最近文件等系统事实 |
| 数据、用量与隐私 | 数据位置、保留方式、预览、预算和隐私偏好 | 只处理第一次任务必须确认的数据影响 | 原始运行记录和内部数据库结构 |
| 外观与无障碍 | 稳定的显示和操作偏好 | 只检测系统能力，不强迫用户选择 | 产品内部设计变量和单个组件的样式 |
| 维护与开发者选项 | 高级运行、检查和修复能力，不放普通偏好 | 不进入默认首次流程 | 高频普通设置和日常状态 |

## 6. 所有设置内容

本节是目标产品清单。它规定产品需要覆盖的用户意图，不等于当前全部已经实现。

### 6.1 首次设置、可用状态与第一次成功

| 事项 | 分类 | 由谁负责 | Onboarding 怎么处理 | 默认与说明 |
| --- | --- | --- | --- | --- |
| 当前整体是否可用 | 只读状态 | 首次设置与状态汇总 | 必须读取 | 根据各项功能的真实检测结果汇总，不能让用户手填 |
| 每个工作入口是否可用 | 只读状态 | 对应功能 | 按第一次任务读取 | Chat、Search、Composer、File Atlas、Agent 和 Media 分开判断 |
| 最后检查时间与来源 | 只读状态 | 状态汇总 | 必须显示 | 用户需要知道这个结论是什么时候、根据什么得到的 |
| 首次设置进度 | 只读状态 | Onboarding | 必须恢复 | 流程走到哪一步，不代表功能已经可以使用 |
| 首次索引任务 | 操作 / 只读状态 | 知识索引工作台 | 目标需要 Vault 知识时打开 | 从 Onboarding 发起，但任务、进度和结果由可重复打开的工作台拥有 |
| 第一次想完成的任务 | 功能内设置 | Onboarding | 由用户选择或系统推荐 | 只帮助完成第一次成功，不会把产品锁定成一种模式 |
| 继续或重新运行 Setup | 操作 | 首次设置与状态汇总 | 可以执行 | 不能悄悄改掉用户已经指定的长期设置 |
| 修复某一项能力 | 操作 | 对应功能 | 可以执行 | 修复完成后必须重新检查是否真的恢复 |
| 第一次任务结果 | 只读状态 | 执行该任务的功能 | 必须观察 | 只有真实任务完成才算第一次成功 |
| “稍后再说”的时间记录 | 系统负责 | 触发提示的功能 | 不询问 | 只控制提示何时再次出现，不是业务设置 |

这里没有普通长期设置。Setup 页面主要展示当前情况并帮助用户完成必要操作，不应该把整个 Settings 再复制一遍。

### 6.2 AI 连接与服务商

本文把提供 AI 能力的公司或本地服务称为“服务商（Provider）”，把用户已经登录或配置好的一个账户 / 本地服务称为“连接（Connection）”。

#### 上线优先级

| 类型 | 产品结论 | 当前边界 |
| --- | --- | --- |
| OpenAI API | 首发重点支持 | 当前已有连接类型 |
| Anthropic API | 首发重点支持 | 当前已有连接类型 |
| OpenRouter | 首发重点支持 | 模型很多，必须在线获取最新列表并说明上次更新时间 |
| Ollama | 首发重点支持 | 必须检测本地服务，并读取这台电脑上真实安装的模型 |
| Codex | 首发双能力连接 | 既可用于普通对话 / 生成，也可承担 Agent 工作；两种能力分别检测，当前专用接入仍未完成 |
| Claude Code | 首发双能力连接 | 既可用于普通对话 / 生成，也可承担 Agent 工作；两种能力分别检测，当前专用接入仍未完成 |
| Google / Perplexity | 后续扩展 | 当前已有连接类型 |
| LiteLLM / LM Studio / vLLM / 自定义服务 | 高级扩展 | 只在高级设置中开放 |
| Simulator | 仅供开发和测试 | 不出现在普通用户的连接列表中 |

#### 用户可控内容

| 事项 | 分类 | 由谁负责 | Onboarding 怎么处理 | 默认与说明 |
| --- | --- | --- | --- | --- |
| 新增连接 | 普通设置 | AI 连接 | 缺少时才询问 | 只显示完成当前目标所需的少量推荐项 |
| 连接显示名称 | 普通设置 | AI 连接 | 先使用清楚的默认名称 | 只有多个账户时，用户才需要额外区分 |
| API 密钥或登录 | 普通设置 | AI 连接 | 任务被阻塞时输入 | 必须作为机密保存，不能出现在日志和运行记录中 |
| 服务地址 | 高级设置 | AI 连接 | Ollama 或自定义服务需要时才询问 | 已知服务商使用系统提供的默认地址 |
| 自定义请求头或环境变量 | 高级设置 | AI 连接 / MCP | 不询问 | 其中的密钥需要单独保护 |
| 启用或停用连接 | 普通设置 | AI 连接 | 复用已经验证可用的连接 | 停用前列出哪些功能会受到影响 |
| 测试或重新验证 | 操作 | AI 连接 | 保存后立即执行 | 填了 API 密钥不等于连接真的可用 |
| 删除连接 | 操作 | AI 连接 | 不执行 | 删除前列出会失去默认模型或备用方案的功能 |
| 清除本机保存的凭据 | 操作 | AI 连接 | 不执行 | 与删除列表中的连接记录分开说明 |
| 同一服务商的多个账户或地址 | 高级设置 | AI 连接 | 不询问 | 每个连接有自己的名称和验证状态 |
| 刷新模型列表 | 操作 | AI 连接 | 必要时执行 | OpenRouter 和 Ollama 优先读取最新真实列表 |
| 模型列表的来源、更新时间和错误 | 只读状态 | AI 连接 | 必须读取 | 使用内置备用列表时必须明确说明 |
| 服务商支持哪些能力 | 只读状态 | 模型能力目录 | 用于自动筛选 | 已知服务商的能力不能由用户随意填写 |
| 自定义服务的模型能力 | 高级设置 | 自定义 AI 服务 | 不询问 | 只用于系统无法识别的服务，并提示填写错误可能导致选错模型 |
| 连接编号和创建时间 | 系统负责 | 数据存储 | 不显示为设置 | 只用于稳定保存和版本升级 |

AI 连接只回答“Peak 现在可以使用哪些服务”。Chat、Composer、知识索引分别默认用哪个模型，应到“任务与模型”里管理。

#### Codex 与 Claude Code 是双能力连接

Codex 和 Claude Code 不能只被归到 Agent，也不能被当作一种无所不能的模型服务。一个连接可以同时公开两组能力：

- **普通对话与生成：** 可供 Chat Studio、Composer、AI Search 报告撰写等兼容的文字任务使用；
- **Agent 工作：** 可执行带工具、会话和任务过程的工作，并把过程交给 Peak 的权限、预算和运行记录体系管理。

两组能力必须分别验证。普通对话可用，不代表 Agent 会话已经可用；Agent 可用，也不代表知识向量、再次排序或媒体生成已经可用。模型选择仍按任务要求过滤，不使用一个含糊的“连接已就绪”覆盖所有能力。

Peak Hermes Harness（Peak 自己的 Agent 编排流程）不是服务商，也不是一个模型。它负责 Agent 的完整运行流程、安全边界和运行记录。Codex、Claude Code 以及普通 AI 服务连接提供可被它使用的模型或执行能力。

#### OpenRouter 模型目录怎样保持更新

OpenRouter 不适合长期依赖插件包内写死的模型列表。目标结构是四层来源：

```text
经过项目维护和校验的在线 JSON
  → 上次成功下载并校验的本地缓存
  → 当前插件版本自带的 OpenRouter 备用目录
  → 如果三者都不可用，明确显示目录不可用，不猜测模型
```

在线 JSON 建议放在 Peak 项目仓库中，以稳定的原始文件地址发布。与 GitHub Gist 相比，项目文件更容易经过代码审阅、保留版本历史，并与模型目录的校验测试一起修改；Gist 只适合早期试验。

插件检查更新时遵守以下规则：

1. 优先使用 `ETag`（服务端给文件的版本标记）检查内容是否变化；
2. 服务端没有 `ETag` 时，使用 `Last-Modified`（最后修改时间）检查；
3. 返回“没有变化”时继续使用本地缓存，不重复下载和解析；
4. 下载新内容后，先按允许的来源和数据格式完成校验，再替换缓存；
5. 下载失败或内容无效时保留上一份有效缓存；没有缓存时才使用插件内置备用目录；
6. 在线内容只能提供模型资料，不能修改连接凭据、Prompt 或其他运行配置。

在线 JSON 的允许内容如下：

| 内容层级 | 必须包含 |
| --- | --- |
| 整份目录 | 数据格式版本、目录版本、生成时间、服务商编号、模型列表 |
| 单个模型 | 稳定编号、显示名称、任务能力、上下文限制、价格资料、推荐状态、停用信息 |

缺少必填内容、出现重复编号或声称了无法识别的能力时，整份新目录不进入正式缓存。

模型目录状态至少记录：

| 状态内容 | 用途 |
| --- | --- |
| 当前来源 | 在线目录、本地缓存或插件内置备用目录 |
| 目录版本和生成时间 | 判断内容是否真的更新 |
| 上次检查和上次成功更新时间 | 区分“刚检查过”和“很久没有成功更新” |
| `ETag` / `Last-Modified` | 下次只检查变化，不重复下载 |
| 内容摘要 | 防止缓存内容被意外替换或损坏 |
| 最近错误 | 说明为什么继续使用缓存或备用目录 |

用户可以执行“立即检查更新”和“恢复插件内置目录”，但不需要决定缓存文件、请求头或合并算法。目录更新也不能覆盖用户已经固定的模型；如果该模型被停用或消失，产品应标记需要处理，并给出兼容替代项。

### 6.3 模型、任务默认与模型选择

模型选择器不是一个独立的 Settings 模块。它是一种被多个任务配置复用的选择能力。真正的产品配置单位是“某类任务默认使用什么”，而不是“全局选一个模型”。

#### 两张不同的地图：可用资源与使用位置

模型配置不能只从服务商开始找。AI 连接回答“Peak 现在能使用哪些服务”，产品功能回答“这些服务会用在哪些地方”。两边互相关联，但用户寻找模型设置时，应优先从自己认识的产品功能进入。

```text
可用资源池
├─ OpenAI、Anthropic、OpenRouter 等云端服务
├─ Ollama 等本地服务
├─ Codex、Claude Code 等可同时提供普通生成与 Agent 能力的连接
├─ Peak Hermes Harness 等 Agent 编排能力
└─ OpenAI、fal.ai 等图片 / 视频生成服务

        系统根据任务需要、当前可用状态和用户选择自动匹配

产品能力树
└─ 用户认识的产品入口
   └─ 一组相近能力
      └─ 具体动作
         └─ 必要时才继续查看执行步骤和 Prompt（指令模板）
```

在 AI 连接中，可以查看“这个连接正被哪些功能使用”；在具体功能中，则显示“它沿用了哪一级默认设置，这次实际会使用哪个连接和模型”。

#### 用户从产品入口逐层进入

下面是目标内容层级示例，不是具体 UI，也不是当前注册表已经完整实现的声明：

```text
通用任务默认
├─ 对话与写作
├─ 研究与网页
├─ 知识处理
├─ 理解文件
├─ Agent 任务
└─ 生成图片、视频、音乐与语音

产品功能
├─ Chat Studio
│  ├─ 普通对话
│  ├─ 改写用户问题与推荐追问
│  ├─ 计划、项目与助手
│  └─ 网页和附件任务
├─ Composer
│  ├─ Copilot
│  │  ├─ 整篇文档动作
│  │  └─ 针对内容块的动作
│  │     ├─ 正文、标题、列表、任务与引用
│  │     ├─ 表格、公式与图表
│  │     ├─ 代码、Mermaid 图与原生对象
│  │     └─ 图片与文档属性
│  └─ 文档或整个 Vault 的检查
├─ Vault Search
│  ├─ 基础搜索：不使用生成模型
│  └─ 改写搜索问题：使用模型
├─ AI Search
│  ├─ 制定搜索计划与收集证据
│  ├─ 撰写报告段落与摘要
│  ├─ 追问与综合结论
│  └─ 保存结果时的辅助
├─ File Atlas
│  ├─ 浏览、筛选与展示关系：不使用生成模型
│  └─ 总结与解释：只有真实功能接通后才能配置模型
├─ AI Graph
│  ├─ 关系图
│  ├─ 证据图
│  ├─ 思考过程图
│  └─ 节点和群组解释
├─ Ambient
│  ├─ 查找、排序和去重：不使用生成模型
│  ├─ 解释推荐原因
│  └─ 生成简报：只有真实功能接通后才能配置模型
├─ Vault Intelligence
│  ├─ 发现模式和重要内容中心
│  ├─ 检查单篇笔记或整个 Vault
│  └─ 修复发现的问题
├─ Agent / Wizard
│  ├─ 主要任务
│  ├─ 快速辅助步骤
│  └─ 需要更强能力时的升级处理
└─ 媒体生成
   ├─ 生成图片
   ├─ 生成视频
   ├─ 生成音乐

```

用户从熟悉的产品名称进入即可。内部仍然可以用“对话与写作”“研究与网页”等任务类型共享默认设置，但不要求普通用户先理解这些分类，更不能先让用户选择 `quick / deep / premium` 之类内部等级。

#### 五个配置层级

| 层级 | 用户问题 | 允许的控制 | 默认行为 |
| --- | --- | --- | --- |
| 通用任务类型 | 这一大类工作通常用什么？ | 自动选择或长期默认 | 由系统建立，普通用户不必先配置 |
| 产品功能 | Composer 或 AI Search 是否需要不同选择？ | 可选的功能级指定 | 沿用通用任务类型的设置 |
| 相近的一组动作 | Composer 的内容块动作是否统一使用另一种选择？ | 可选的动作组指定 | 沿用产品功能或通用任务类型 |
| 具体动作或执行步骤 | 是否只有这个动作需要特定模型或 Prompt？ | 高级、固定指定 | 沿用距离它最近且能力兼容的上级设置 |
| 当前这一次任务 | 这一次是否临时换模型？ | 临时选择 | 不改变以后任务的长期设置 |

上一级的指定只会影响它下面“确实能使用这个模型”的动作。例如 Composer 同时包含文字改写、图片理解和媒体生成时，一个文本模型不能被强行应用到全部动作；不兼容的动作继续使用自己所属任务类型的默认选择。

#### 解析优先级

```text
当前这一次的临时选择
  → 某个执行步骤的固定指定
  → 某个具体动作的指定
  → 一组相近动作的指定
  → 整个产品功能的指定
  → 通用任务类型的默认值
  → Peak 自动选择
```

无论最终沿用哪一级设置，都要先确认模型能力符合要求、连接当前可用，而且没有违反安全限制。如果用户固定的模型已经失效，产品要明确要求用户处理；除非用户提前允许自动改用备用模型，否则不能悄悄换掉。

#### 每项具体能力都要说明什么

| 内容 | 作用 |
| --- | --- |
| 它属于哪个产品入口 | 让用户能从熟悉功能找到它 |
| 它具体完成什么 | 不只展示只有开发者看得懂的内部编号 |
| 它是否真的使用 AI 模型 | 搜索、排序等不使用生成模型的动作，不显示假的模型设置 |
| 当前设置来自哪里 | 是系统自动选择、沿用上级、用户固定，还是只对本次临时选择 |
| 当前实际使用的连接和模型 | 告诉用户真正会用什么，而不只显示一个默认值 |
| 为什么可以使用这个模型 | 说明是否需要工具、看图、读取 PDF、长上下文或生成媒体等能力 |
| 修改会影响哪里 | 只影响当前步骤、整个动作、一组动作、整个功能，还是同类任务 |
| 相关 Prompt | 只有已经接入真实功能的动作，才能继续查看和修改指令模板 |
| 最近检查和运行记录 | 区分“已经填过设置”和“已经真实使用” |

#### Prompt 是最深一层的指令，不是寻找模型的起点

- 用户先找到产品功能和具体动作，再查看这个动作使用的 Prompt（指令模板）。
- 同一步骤配套的系统 Prompt 和用户 Prompt 共同完成一件事，不应出现两套模型设置。
- 同一份 Prompt 可能被多个动作共用，修改前必须说明会影响哪些地方。
- 模型选择属于具体动作或执行步骤，不属于某一个 Prompt 文件。
- 没有连接到真实功能的 Prompt，不进入正式配置层级。
- 系统安全指令和固定的数据格式可以查看，但不能被普通 Prompt 修改覆盖。

这样 Composer 仍然可以继续进入内容块、表格、公式和 Mermaid 等具体动作。普通用户停在 Composer 或 Copilot 层，就能理解当前整体策略，不需要浏览所有 Prompt。

#### 怎样减少选择服务商和模型的压力

模型配置的默认路径应遵循以下顺序：

1. 先检查用户已经配置并验证可用的连接；
2. 根据当前任务需要，自动排除能力不合适的模型；
3. 默认使用 Peak 自动选择，不要求用户同时理解服务商和具体模型；
4. 只给出一个推荐结果和少量已验证替代项；
5. 用户主动要求时，才进入完整兼容模型目录；
6. 保存后立即显示实际会使用的连接、模型和影响范围。

允许四种明确策略：

| 策略 | 用户承担的决定 | 适用情况 |
| --- | --- | --- |
| Peak 自动选择 | 不选服务商，也不选具体模型 | 默认；系统在所有已验证连接中自动选择 |
| 固定服务商，自动选模型 | 只指定一个连接 | 用户信任某个服务商，但不想持续管理模型更新 |
| 固定模型 | 指定连接和具体模型 | 高级用户、需要重复得到相近结果，或需要严格控制成本 |
| 不使用生成模型 | 不做模型选择 | 搜索、排序、过滤和图计算等本来就不需要生成模型的功能 |

具体规则：

- 新增连接时，只需要完成登录和真实验证，不强迫用户立刻选完所有模型；
- 选择服务商后，默认由系统在这个连接内自动选择模型；
- 直接选择某个模型时，系统自动找到它所属的连接，不再重复询问服务商；
- 推荐候选优先来自已连接、已验证且能力匹配的模型；
- OpenRouter 不默认平铺 55 个内置备用条目，只显示来自当前有效目录、适合任务且已经验证的少量模型；
- Ollama 只显示这台电脑上当前真正检测到的本地模型；
- Codex 和 Claude Code 可以出现在兼容的普通对话 / 生成任务和 Agent 任务中，但分别显示能力是否已验证；
- Codex 和 Claude Code 不进入知识向量、再次排序或媒体生成候选，除非以后为相应能力建立了独立且通过验证的接入；
- 图片、视频、音乐和语音各用自己的模型列表，不与文本模型混在一起；
- 不兼容的模型不进入默认推荐，但用户查看完整列表时能看到被排除的原因；
- 每次自动选择都记录：用户选择的策略、实际连接、实际模型，以及是否改用了备用方案。

#### 六类通用任务及其具体用途

| 通用任务类型 | 包含的具体用途 | 默认策略 |
| --- | --- | --- |
| 对话与写作 | Chat Studio、Composer Copilot、快速辅助 | 整类任务默认自动选择，单个功能可以固定 |
| 研究与网页 | 深度研究、AI Search 规划、报告撰写、网页搜索、必要时使用更强模型 | 根据工具、联网、上下文和质量要求自动筛选 |
| 知识处理 | 知识向量模型、Vault Intelligence | 向量模型和文字生成模型分开管理 |
| 理解文件 | 理解图片 / PDF / 视频、音频转文字 | 根据输入文件类型自动筛选 |

这 18 项表示产品需要负责的具体用途，不代表只有 18 个模型，也不代表页面必须同时展示 18 个选择器。每项具体用途默认沿用所属任务类型，只有用户明确要求不一样时才单独保存。

### 6.4 权限、Agent、外部工具与 Skills

#### 安全与 Agent

### 6.5 知识索引、搜索与 AI 分析

知识索引有三类内容，不能塞进同一组控件：

- **长期策略**：以后索引什么、自动做到什么程度；
- **知识库状态**：现在已经有哪些产物、覆盖是否完整、哪些内容过期；
- **一次运行**：这次正在处理什么、到哪一步、哪里失败、怎样继续。

Settings 只拥有长期策略；独立的“知识索引工作台”拥有运行、状态、问题修复和历史。Onboarding 只是根据第一次任务打开这两个模块中的必要部分。

#### 长期策略

| 事项 | 分类 | 由谁负责 | Onboarding 怎么处理 | 默认与说明 |
| --- | --- | --- | --- | --- |
| 索引深度：快速 / 语义 / 完整 | 普通设置 | 知识索引设置 | 选择能完成目标的最低层级 | 快速提供全文搜索；语义增加向量；完整再增加 AI 标签和摘要 |
| 自动增量更新 | 普通设置 | 知识索引设置 | 首次最低索引完成后说明 | 首次批量建立必须由用户明确开始；以后是否自动跟进变化仍需产品负责人确认 |
| 多久检查一次变化 | 高级设置 | 知识索引设置 | 不询问 | 当前产品内置值为 5 秒；不应作为普通用户首要决定 |
| 包含哪些用户内容类型 | 普通设置 | 知识索引设置 | 使用可靠的推荐集合 | 只对产品范围内且真实可读的类型提供开关；Office 格式不出现在产品设置中 |
| 包含或排除哪些文件夹和文件规则 | 普通设置 | 知识索引设置 | 只处理明显冲突 | 默认排除系统目录、Peak 机器数据和其他已知循环污染来源 |
| 知识向量使用哪个模型 | 自动决定 | 任务与模型 | 需要语义搜索时建立 | 只保存一份“知识向量”用途设置，不在索引页面重复保存模型 |
| AI 标签与摘要使用哪个模型 | 自动决定 | 任务与模型 | 只有首次目标依赖完整索引时建立 | 在模型层级中归属于“知识索引 → 补充分析” |
| 搜索结果再次排序 | 高级设置 | 搜索质量 | 不询问 | 当前默认开启，需要说明它会改变结果顺序 |
| 是否定期整理重要内容中心 | 普通设置 | 知识智能 | 不询问 | 当前默认关闭 |
| 多久整理一次 | 高级设置 | 知识智能 | 不询问 | 当前默认 7 天 |

#### 文档类型不能只用一个“支持 / 不支持”判断

一种文件或产品产物至少要分别说明下面七件事：

1. **识别**：Peak 知道它是什么；
2. **打开 / 预览**：用户可以查看它；
3. **读取**：Peak 能稳定提取可供处理的内容；
4. **全文索引**：可以通过普通文字搜索找到；
5. **语义索引**：可以生成向量并参加语义搜索；
6. **AI 补充分析**：可以生成标签、摘要或其他知识属性；
7. **编辑 / 生成**：Peak 能不能创建或修改它。

设置中的“包含这种类型”只控制第 3–6 项，不代表 Peak 一定能预览、编辑或生成它。反过来，Peak 能生成 Draw.io，也不代表当前就能稳定读取并索引 Draw.io。

目标上需要一份由系统维护的“文件能力目录”，而不是让 UI 自己写死扩展名。每种内容都要记录：

- 用户看到的名称和常见扩展名；
- 它是普通 Vault 文件、Peak 自有产物还是外部资源；
- 上面七种能力分别是否可用；
- 默认进入索引、默认排除，还是当前根本不能索引；
- 当前状态根据哪个真实读取器或运行功能得出，以及最后验证时间。

用户只能修改“是否把这种可读内容放进索引”；读取器、能力证明和 Peak 内部产物规则由系统负责。

#### 文件与产物类型的目标结论

| 用户认识的类型 | 当前默认 | 目标提供方式 | 当前能力边界 |
| --- | --- | --- | --- |
| Markdown | 开启 | 普通设置 | 核心文本来源，完整索引链路的基准 |
| PDF | 开启 | 普通设置 | 有专门读取流程；失败需要显示到具体文件 |
| 图片 | 开启 | 普通设置 | 依赖真实图片理解或文字识别结果，不能只凭扩展名宣称已索引 |
| Excalidraw | 开启 | 普通设置 | 可以读取 `.excalidraw` / `.excalidraw.md` 中的可提取内容，也可以生成用户产物 |
| TXT、CSV | 关闭 | 普通设置 | 已有读取入口；用户可以按需开启 |
| JSON、HTML、XML | 关闭 | 普通设置 / 高级设置 | 可以读取，但容易包含机器数据；默认关闭并继续受目录排除规则保护 |
| Canvas | 关闭 | 普通设置 | 当前可提取文字节点、文件引用和边标签 |
| URL | 关闭 | 高级设置 | 不是 Vault 文件，需要另行说明抓取、更新和隐私边界 |
| XLSX 文件 | 关闭 | 暂不可用作通用索引类型 | Peak Sheet 已能导入 XLSX，不等于通用文档索引已能读取 XLSX；当前索引读取器会拒绝它 |
| Draw.io | 关闭 | 显示能力状态，不提供索引开关 | 当前可以生成和保存，但没有通用索引读取器，不能假装已支持搜索 |
| Peak Sheet | 不进入普通文档索引 | 产品产物状态 | 数据集由 Peak Sheet 工具读取；底层 JSON 不进入知识索引。未来若需要搜索，应索引用户明确生成的摘要或可读投影，而不是整份内部数据 |
| AI Graph | 不进入普通文档索引 | 产品产物状态 | 不索引内部正式数据（manifest / version JSON）；用户显式导出的 Markdown 可以按 Markdown 规则进入索引 |
| Peak 生成的 Extract、Reminder、Dataview 等 Markdown | 跟随 Markdown | 不另设重复开关 | 它们是用户拥有的文档；仍受目录排除和防循环规则约束 |
| Folder | 关闭 | 系统负责 | 结构资源，不是可索引文件类型 |
| Unknown | 关闭 | 系统负责 | 不能让用户盲目开启未知内容 |

这里最重要的是把三件事分开：

- **XLSX 导入 Peak Sheet** 是一次导入能力；
- **搜索 Vault 中任意 XLSX** 是通用索引能力；
- **AI 读取某个 Peak Sheet** 是结构化工具能力。

三者不能因为都和表格有关，就共用一个“XLSX 已支持”的状态。AI Graph、Excalidraw、Draw.io 也要采用同样的判断方式。

当用户关闭某种已经索引过的类型时，产品必须先生成明确的维护计划：以后停止新增、现有索引何时移除、搜索结果会怎样变化。不能只保存开关，却让旧内容继续永久出现在结果里。

| 旧的思考 / 搜索模型字段 | 暂不可用 | 旧配置迁移 | 迁入任务与模型，避免同一用途出现两套设置 |

#### 知识索引工作台：为什么必须是独立 View

首次批量索引不是一次几秒钟的设置保存。它可能持续很久、产生多类结果、发生部分失败，也可能在全文搜索可用后继续生成向量、标签和摘要。因此建议把**可重复打开的独立 View**作为唯一正式运行入口；Modal 只用于开始前的范围 / 费用确认，Notice 只用于完成、失败或后台变化提醒，并提供“打开知识索引”入口。

独立 View 的行为必须满足：

- 关闭 View 不会停止索引；
- 再次打开能看到同一个活跃任务，而不是从零开始；
- Onboarding、Settings、命令或状态入口都打开同一项任务；
- 用户明确点击取消才会取消；关闭弹窗不等于取消；
- 完成、取消、部分成功和失败都有可回看的结果记录；
- 失败可以按阶段或文件重试，不必每次完整重建。

工作台需要回答五组问题，但不限定设计师采用什么具体布局：

| 内容区域 | 必须回答的问题 |
| --- | --- |
| 当前结论 | 普通搜索、语义搜索、AI 补充分析和图关系现在分别能不能用？ |
| 活跃运行 | 正在处理哪一阶段、多少文件、当前文件、速度 / 预计时间、是否可暂停或取消？ |
| 覆盖状态 | 可索引、已全文索引、已有向量、已有标签、已有摘要、图关系已更新分别是多少？ |
| 问题与待办 | 哪些文件读取失败、哪些等待模型或权限、哪些结果过期、怎样原地修复？ |
| 历史与结果 | 每次运行使用了什么范围和策略，完成了什么、花费多少、还有什么没有完成？ |

#### 一个索引任务有哪些阶段

用户不需要理解数据库名，但需要理解每一步产生了什么。目标阶段定义如下：

```mermaid
flowchart LR
    A["检查范围与文件类型"] --> B["读取内容并建立全文搜索"]
    B --> C["生成知识向量"]
    C --> D["生成标签与摘要"]
    D --> E["更新关系与知识结构"]
    E --> F["验证覆盖并生成结果记录"]
```

当前实现把文件扫描、读取和分块包含在全文索引步骤中，正式界面可以把它们显示为该阶段的子状态，而不是虚构一条不存在的独立运行链路。

每一阶段都必须有自己的状态：`等待条件`、`准备中`、`运行中`、`已完成`、`已跳过`、`部分完成`、`失败`、`已取消`。一次任务可以“全文搜索已经可用，但向量或摘要仍在继续”，不能只剩一个含义模糊的 `isReady`。

对应的用户可用状态至少分成四层：

| 可用层级 | 完成条件 | 用户现在可以做什么 |
| --- | --- | --- |
| 基础搜索可用 | 文件读取和全文索引达到最低覆盖 | 立即开始关键词搜索，不必等待后续 AI 处理 |
| 语义搜索可用 | 目标范围的知识向量完成或达到可用覆盖 | 使用相近含义搜索和相关内容发现 |
| 知识补充完成 | 标签和摘要完成或明确跳过 | 使用更完整的分类、摘要和知识维护能力 |
| 结构关系最新 | 图关系与维护步骤验证完成 | 使用依赖最新结构的 File Atlas、AI Graph 和 Vault Intelligence 结果 |

Onboarding 只等待第一次目标需要的最低层级。例如第一次任务只是搜索一个文件，基础搜索可用后就应继续引导用户完成搜索；向量、标签、摘要和图关系可以继续在后台处理。

#### 长期知识库状态与本次运行必须分开

“本次处理了 300 / 500 个文件”不等于“整个 Vault 覆盖率是 60%”，因为已有旧结果、被排除文件、失败文件和过期文件都可能影响结论。工作台必须分别保存：

- 当前策略下有多少内容符合条件；
- 每种索引产物的现有覆盖和更新时间；
- 这一次任务原计划做什么、实际做了什么；
- 哪些内容因为关闭的文件类型、排除规则、模型不可用或用户取消而没有处理；
- 哪些旧结果仍可使用，哪些已经过期或需要移除。

每次运行至少要保存：稳定任务编号、从哪里开始、当时选择的范围和文件类型、索引深度与模型、每一阶段的进度和结果、AI 阶段的预计与实际成本、开始 / 更新 / 完成时间、失败项目、建议修复方式和最终结果记录。

实时进度可以写入可重建的运行投影，但任务计划、阶段结果、失败与最终 receipt 必须在重新打开插件后仍然可恢复。View 不能成为运行状态的唯一拥有者。

#### 索引维护操作

| 操作 | 正式入口 | 执行前必须说明 |
| --- | --- | --- |
| 更新有变化的文件 | 知识索引工作台 | 预计文件数量、处理阶段、能否取消和最终结果 |
| 完整重建索引 | 知识索引工作台 | 覆盖范围、预计耗时，以及重建期间旧索引是否还能使用 |

| 刷新关系、重要内容中心和知识空缺 | 知识索引工作台 / Vault Intelligence | 会产生什么结果、影响什么，以及失败后怎样恢复 |

| 单独指定某个子目录 | 高级设置 | 对应功能 | 只有确实需要时才覆盖自动推导结果 |
| SQLite 数据库实现 | 系统负责 / 高级设置 | 开发者选项 | 默认自动选择；只有诊断问题时才允许固定 |

任何目录变更必须说明：

- 是立即生效还是只影响未来写入；
- 是否需要迁移已有数据；
- 是否会改变索引排除规则；
- 是否可能产生循环索引或重复材料；
- 失败时旧数据是否仍可用；
- 如何恢复默认派生路径。

| 事项 | 分类 | 由谁负责 | 默认与说明 |

## 8. 实现参考：Onboarding 和 Settings 怎样使用同一份数据

本节主要供开发使用。核心意思很简单：Onboarding、Settings 和具体功能页面看到的连接、模型、权限和状态，必须来自同一份记录，不能各自保存一套。

### 8.1 每项产品能力需要一份明确记录

产品功能的层级不能只写在 UI 文案里。每项能力都要记录它属于哪个产品功能、是否使用模型、可以在哪一级修改，以及是否真的有代码在使用它：

```text
capabilityId
parentCapabilityId or null
productSurfaceId
capabilityFamilyId
taskFamilyId
executionKind: deterministic | model | embedding | agent | media
executionStepIds
promptOwnerIds
requiredCapabilities
allowedOverrideScopes
productionCallerEvidence
```

当 `executionKind=deterministic` 时，表示它是搜索、排序等不需要生成模型的能力，不显示模型设置。只有已经接入真实运行代码的模型、向量、Agent 或媒体能力，才能继续配置具体执行步骤、Prompt 或单独指定模型。

### 8.2 单一配置记录

每一项长期配置至少需要：

```text
settingId
moduleOwner
value or overrideAbsent
source: compiled | auto | user | migration
scope: global | vault | connection | taskGroup | surface | capabilityFamily | action | executionStep
ownerCapabilityId
inheritsFromSettingId or null
updatedAt
schemaVersion
effectiveState
effectiveAt
requires: none | reconnect | restart | reindex | reprocess | migration
```

Onboarding、Settings 和具体功能页面不能维护三套不同的数据。它们只是从不同入口读取和修改同一条设置记录。

### 8.3 每项能力的当前状态

每项能力状态至少需要：

```text
capabilityId
status: checking | ready | degraded | action-required | unavailable | error | disabled
evidenceAt
evidenceSource
configuredState
effectiveDependencies
impact
recommendedAction
lastReceiptId
```

“已经填写配置”不等于“现在可以使用”；“可选”表示这项能力不是当前任务必需的，也不是一种运行状态；只有真实扫描任务正在运行并且能读到进度时，才能显示“正在扫描”。

### 8.4 保存与生效

```text
用户修改
  → 校验值和依赖
  → 写入唯一配置记录
  → 通知真实功能更新
  → 如果需要重连、重启、重建索引或迁移，创建一项独立操作
  → 重新读取实际生效状态
  → 返回已生效、等待处理或失败
```

数据已经写入，但真实功能还没有使用新值时，必须显示“已保存但尚未生效”，不能直接显示完成。

### 8.5 上级默认值和单独指定怎样配合

- 每类通用任务都有一个自动默认值。
- 产品功能、相近动作、具体动作和执行步骤逐级沿用上一级设置。
- 每项产品能力同时属于一种通用任务，方便不同产品功能共用可靠默认值。
- 用户明确固定某个模型后，这一项不再跟随上级变化。
- 选择“恢复自动”会清除手动固定值，重新沿用上级设置。
- Onboarding 只能补齐尚未配置的内容，不能改掉用户已经固定的设置。
- 服务商或模型失效时，系统只自动调整没有被用户固定的项目。
- 用户固定的模型失效后，必须要求用户处理，不能静默换成另一个模型。
- 当前对话或当前动作的临时选择只记录在这一次任务中，除非用户明确选择“设为长期默认”。

### 8.6 知识索引需要两份不同的数据投影

知识索引不能继续只返回“是否就绪”和“已索引多少篇”。它至少需要两份由同一运行系统维护的投影：

- **知识库覆盖投影**：当前文件策略下的可索引总量，以及全文、向量、标签、摘要和图关系各自的覆盖、过期和失败数量；
- **活跃任务投影**：当前 `indexRunId`、阶段、进度、当前文件、成本、失败项、取消能力和最后更新时间。

Settings 读取覆盖投影的简短结论；Onboarding 读取第一次目标所需的最低可用层级；知识索引工作台读取完整投影和持久运行记录。三者不得各自计算一套“Scanning / Ready”。

自动更新、用户手动更新和首次批量建立都必须创建可追踪任务。即使运行非常快，也要产生最终结果记录；这样状态不会依赖某一条 Notice 是否还停留在屏幕上。

## 9. Onboarding 完整流程

```text
1. 检查当前环境和已有设置
2. 确定第一次真实任务
3. 找出完成这个任务还缺少什么
4. 只补齐缺少的 AI 连接、最低权限或必要确认
5. 如果目标需要 Vault 知识，打开知识索引工作台并建立最低可用索引
6. 其他未固定的设置继续使用系统自动选择
7. 真实验证连接、索引、Agent、媒体或工具是否可用
8. 达到当前目标需要的最低可用层级后，打开真正执行任务的功能页面，并带入安全的预填任务
9. 观察真实结果：成功完成，或得到可以继续修复的错误
```

### 9.1 Onboarding 可以问的问题

- 第一次想完成什么；
- 完成该任务所需的登录或 API 密钥；
- 无法自动决定时，选择一个可用连接；
- 首次 Agent 任务需要的最低写权限；
- 首次媒体任务需要的成本或许可确认；
- 第一次建立索引时必须明确的内容范围或性能影响；
- 完整索引中的 AI 标签 / 摘要预计费用达到确认门槛时，是否现在继续；
- 无目标时是否接受最低摩擦推荐任务。

### 9.2 Onboarding 不应问的问题

- 所有服务商和所有模型；
- quick / deep / premium 等内部等级；
- 模型随机程度、top-p、top-k 和重复惩罚；
- 文档分块大小、重叠量、搜索排序算法和图算法权重；
- 月度预算与所有告警阈值；
- 全部外部工具、Skills 编辑和批量审批命令；
- 调试记录、数据库实现和运行 hooks；
- 每一个模块的显示偏好。

### 9.3 为什么不能用固定页数定义 Onboarding

已经有可用连接和知识索引的用户，不需要重复配置；只使用 Ollama 的用户，不需要看到云端 API 密钥；第一次生成图片的用户需要媒体生成连接，却不需要先建立语义索引。所以流程长短应该由“完成当前目标还缺什么”决定，而不是固定成相同页数。

- 当前完整索引实际按“全文索引 → 知识向量 → AI 标签与摘要 → 图关系维护”四步执行，已经具备逐文件进度和部分步骤重试的基础。
- 当前大部分索引进度仍通过 `ProgressReporterPort` 映射到 Obsidian Notice；已有的 `IndexingProgressModal` 只覆盖“待处理的 LLM 补充分析”这一小段，并且状态由弹窗内存订阅拥有。
- 当前 Settings 的维护区域同时放着更新索引、完整流程、取消、补向量、补 LLM 分析和全局维护等操作；它们尚未汇合成一项可返回的任务和历史。
- Peak Sheet 已有独立 View、JSON 数据集和 XLSX 导入能力，但数据集明确排除在普通 Peak knowledge index 之外，AI 通过结构化工具读取。
- AI Graph 已有内部正式 manifest 和不可变 version JSON；这些机器产物排除在普通知识索引之外，只有用户显式导出的 Markdown 按用户文档规则处理。
- Excalidraw 和 Draw.io 都可以作为用户产物生成；Excalidraw 有索引读取器，Draw.io 目前没有通用索引读取器。

### 10.2 不能当作正式设置的当前缺口

| 缺口 | 证据 | 产品后果 |
| --- | --- | --- |

### 10.3 上线前必须补齐的工作

1. 建立完整的产品能力目录，让每项能力都能从产品功能一路查到具体动作、执行步骤和真实代码入口。
2. 建立统一设置清单，为每项设置记录负责模块、类型、默认来源、实际使用位置、影响和恢复方式。
3. 把旧的角色、等级和全局默认模型字段，迁移到新的“任务与模型”继承体系。
4. 补齐启动恢复、旧版本迁移和重启保持测试，消灭“能保存但重启丢失”的假设置。
5. 让知识索引、AI 连接、媒体、Agent 和工具都能返回统一而真实的可用状态。
6. 在数据层明确区分设置、只读状态、使用前确认和一次操作。
7. 只有真实功能已经接入并完成验证的字段，才能进入正式 UI。
8. 为重建索引、重新连接、重启和数据迁移建立独立操作，并记录最终结果。
9. 为 OpenRouter 建立项目维护的在线 JSON、条件请求、校验、本地缓存和内置兜底链路。
10. 动态模型列表必须记录来源、版本、更新时间，以及何时使用本地缓存或内置备用列表。
11. 为 Codex / Claude Code 分别接通并验证普通生成和 Agent 能力，再按已通过验证的范围向用户开放。
12. 把 Codex / Claude Code 作为 Peak 的执行连接接入，不能另外建立一套绕开 Hermes 权限、预算和运行记录的控制体系。
13. 先迁移旧字段再退役，不能直接删除用户已有配置。
14. 建立文件能力目录，把识别、预览、读取、全文索引、向量、AI 补充分析、编辑和生成分开登记，并将现有 `includeDocumentTypes` 迁入允许用户修改的索引政策。
15. 为首次批量索引、增量更新和补充分析建立统一的持久任务记录、覆盖投影和独立知识索引 View；Notice 只保留提醒职责。
16. 为每一种 Peak 自有产物登记用户可见名称、读取方式和索引政策；Peak Sheet / AI Graph 的底层 JSON 继续排除，不能为了“支持文件类型”造成自我索引污染。

## 11. 产品负责人决策

下面是 UI 开始设计前必须由产品负责人确定的问题。D7、D9 已经确定；D10 的更新方式已经确定，但正式发布地址仍待确认；D11、D12 是本次新增建议；其余仍待确认。

### D1. 首次任务默认入口

建议：用户没有明确目标时，根据当前环境推荐最容易成功的任务。有可用知识索引时优先推荐 Vault 问答或搜索；当前正在编辑文档时优先推荐 Composer；没有文档时优先推荐 Chat。不要把用户带到空白页。

### D2. `autoIndex` 上线默认

当前产品内置值是关闭。建议第一次完整建立索引时由用户明确开始；索引成功建立后，后续的小范围增量更新默认开启，并允许用户关闭。还需要确认大型 Vault 的性能和隐私边界。

### D3. “记录用量”到底记录什么

当前默认开启，但仅看字段名无法判断数据是否只保存在本机。上线前必须明确区分：

- 安全和故障恢复必需的本地运行记录；
- 用户可以选择保留的用量历史；
- 发送到外部的遥测数据。

三者不能共用一个含糊的“记录用量”开关。

### D4. 预算到底覆盖哪些费用

需要确认三个问题：

- 40 美元是整个 Peak 的月度目标，还是只针对 Agent？
- 它是实际限制，还是仅用于显示消费进度？
- 媒体生成的单次高成本确认是否独立？

建议只设置一个总预算入口，再按 Chat、Agent 和媒体生成分类查看，而不是出现多个范围不明的“预算”。

### D5. 附件默认怎样交给模型

当前默认直接把附件交给模型。建议改成自动判断：模型和数据政策允许时直接发送；不允许时，先在本地解析成文字再发送，并在运行记录中说明实际采用了哪种方式。高级用户仍可以固定一种策略。

### D6. 首发支持哪些 AI 服务

建议首发重点支持：

- OpenAI；
- Anthropic；
- OpenRouter；
- Ollama；
- Codex；
- Claude Code。

Google、Perplexity 和其他兼容接口保留在扩展或高级范围。Codex 与 Claude Code 都是双能力连接：既能为兼容功能提供普通对话 / 生成，也能提供 Agent 执行能力。两种能力分别检测和开放；不能因为其中一条可用，就宣称整个连接全部可用。

### D7. 产品入口优先的模型配置层级（已确定）

模型配置以用户认识的产品入口作为主导航：

- Chat Studio；
- Composer 与 Copilot；
- Vault Search 与 AI Search；
- File Atlas 与 AI Graph；
- Ambient 与 Vault Intelligence；
- Agent / Wizard；
- Media。

用户需要时，可以继续进入一组相近能力、具体动作、执行步骤和 Prompt。

六类通用任务继续负责在不同产品功能之间共享自动默认值，但普通用户不需要先理解这六类。AI 服务商和连接是独立的可用资源列表，不作为产品功能导航的起点。

### D8. 用户自定义 Prompt 边界

需要确认三类边界：

- 哪些真实功能允许直接修改指令；
- 哪些只能复制成用户自己的版本后再修改；
- 哪些系统 Prompt 永远只读。

不能一次性把所有内部 Prompt 都开放编辑。

### D9. Peak Hermes 与 Codex / Claude Code 的关系（已确定）

Peak Hermes Harness 是 Peak 自己的 Agent 流程和安全控制，不是模型服务商。它继续统一负责：

- 循环和任务阶段；
- 工具调用与权限；
- 自动升级和预算；
- 人工确认；
- 运行记录、结果和失败恢复。

Codex 与 Claude Code 作为双能力连接接入。普通生成任务可以直接使用它们的生成能力；Agent 任务可以选择它们作为执行连接，但仍需进入 Peak 的权限、预算和运行记录边界。是否允许某些原生 Agent 会话保留自己的内部循环，需要实现前单独说明边界，不能静默形成第二套产品控制面。

### D10. OpenRouter 在线目录放在哪里

方向已经确定为“在线 JSON + 本地有效缓存 + 插件内置兜底”。还需要确认发布地址。

建议把文件放在 Peak 项目仓库，例如 `templates/config/models/openrouter.json`，并通过稳定的原始文件地址发布。这样目录修改可以和 schema、测试与代码审阅一起完成。GitHub Gist 可以用于短期试验，但不建议作为正式唯一来源。

### D11. 索引任务的正式入口

建议确定为：**独立的知识索引 View 是唯一正式运行入口；Modal 只做开始前确认；Notice 只做带跳转的提醒。**

原因不是视觉偏好，而是任务属性：首次建立和后续补充可能长时间运行、部分成功、在关闭界面后继续、需要按文件修复，并且必须有历史结果。把正式状态放在 Modal 或 Notice 中，会让关闭界面与取消任务混淆，也无法可靠恢复。

Settings 只显示长期策略、状态摘要和“打开知识索引”；Onboarding 在需要 Vault 知识时打开同一个 View，并在达到当前目标的最低可用层级后继续第一次任务。

### D12. 文件类型和 Peak 自有产物怎样进入索引

建议确定为：

- Markdown、PDF、图片、TXT、CSV、JSON、HTML、Excalidraw、Canvas 按真实读取能力分别开关，默认集合保持保守；DOC/DOCX、PPT/PPTX 不进入产品设置；
- “支持”拆成识别、预览、读取、全文、向量、AI 补充、编辑和生成，不能共用一个结论；
- Peak Sheet、AI Graph 等第一方产物显示自己的内容政策，不作为普通扩展名开关；
- Peak Sheet 底层数据由结构化工具读取，AI Graph 内部正式 JSON 由专用运行时读取，两者都不回流普通知识索引；
- 只有用户明确物化或导出的可读文档，才按对应文档类型进入索引；
- Draw.io 在没有稳定读取器前只显示“可生成 / 可保存，暂不可索引”。

还需产品负责人确认：关闭一种已经索引过的类型时，是立即创建清理任务，还是先停止新增并让用户稍后清理。无论选择哪种，都不能静默保留旧结果而显示“已关闭”。

## 12. 给 UI 设计师的内容约束

设计师可以自由决定视觉和布局，但必须保留：

1. 每个模块的状态结论；
2. 状态证据与最后验证时间；
3. 用户可以改变的长期意图；
4. 系统自动选择、用户长期指定和本次实际使用结果之间的区别；
5. 当前修改的保存和生效状态；
6. 修改后是否需要重新连接、重启、重建索引或迁移数据；
7. 原地修复和恢复自动 / 默认；
8. 高级项的逐模块分层；
9. 使用前确认、一次操作、危险操作和普通设置之间的区别；
10. 每项设置只有一个主要修改位置，具体功能页面和 Settings 不会各存一份；
11. Codex / Claude Code 的普通生成与 Agent 两类能力状态；
12. Peak Hermes Harness 的流程与安全状态，以及它实际使用的模型 / 执行连接；
13. OpenRouter 模型目录的来源、版本、更新时间和降级状态；
14. 文档类型的每项真实能力，以及“可生成 / 可导入 / 可索引 / 可由工具读取”的区别；
15. 知识索引四个可用层级、活跃任务、覆盖状态、问题修复和历史结果；
16. 任何索引提示都能回到同一个知识索引任务，而不是创建另一份进度。

设计师不得：

- 设计覆盖全产品的“普通 / 高级”双模式；
- 为了简洁删除本文保留的真实配置；
- 把 只读状态 画成用户可编辑值；
- 把 系统负责 机制包装成普通偏好；
- 把 暂不可用 能力画成已可用；
- 在多个模块复制同一模型、目录或权限设置；
- 用“保存成功”代替“已实际生效”；
- 让用户在 Onboarding 中浏览 113 个模型；
- 让 OpenRouter 内置备用列表看起来像刚刚在线获取的实时列表；
- 把 Codex / Claude Code 限制成“只能运行 Agent”，或用一个“已连接”状态掩盖两类能力的不同验证结果；
- 把 Peak Hermes Harness 画成服务商或具体模型；
- 把 Codex / Claude Code、Peak Hermes、网页工具、MCP 或媒体生成混成同一种资源；
- 把 XLSX 导入 Peak Sheet、搜索任意 XLSX 和 AI 读取 Peak Sheet 混成同一种“表格支持”；
- 把 Peak Sheet / AI Graph 的底层 JSON 当普通文档再次索引；
- 只用一个“Ready / Scanning”概括全文、向量、标签、摘要和图关系的不同状态；
- 让关闭 Modal 或 View 等同于取消索引任务；
- 把 Notice 当成索引进度和结果的唯一来源；
- 把 Settings 变成所有内部参数的展示柜。

## 13. 实现与验收标准

本节主要供开发和测试使用。产品负责人可以直接看 13.3 的产品验收。

### 13.1 配置注册表

每个正式设置必须登记：

- 稳定编号；
- 负责模块；
- 内容分类；
- 影响范围；
- 产品内置值和自动选择规则；
- 存储字段和数据版本；
- 真正会使用这项设置的功能；
- 校验规则；
- 实际生效状态怎样读回；
- 是否需要重新处理、重启、重新连接或迁移；
- 恢复自动或恢复默认时怎样处理；
- Onboarding 是否允许写入；
- 运行记录和敏感数据保护规则。

### 13.2 自动化验证

- 每个保存字段都有启动整理、旧版本迁移和保存后再读取测试；
- 每个用户可见设置至少有一个真实功能使用测试；
- 每个使用模型的动作只有一条可查询的“产品功能 → 相近能力 → 具体动作 → 执行步骤”路径；
- 不使用生成模型的能力不会出现模型选择器；
- 同一步骤的系统 Prompt 和用户 Prompt 只对应一套模型设置；
- 各层默认值始终优先使用距离最近且能力兼容的用户指定；
- 从 AI 连接查看使用位置，与从具体功能查看实际模型，结果一致；
- 默认推荐列表只包含已经验证且能力兼容的模型；
- Codex / Claude Code 的普通生成和 Agent 能力分别验证、分别显示，不能互相冒充；
- Agent 任务即使选择 Codex / Claude Code，也能读取 Peak 的权限、预算、工具和最终运行记录；
- 改值后可以读回真实生效状态；
- 恢复自动选择会清除用户指定，而不是写死某个旧默认值；
- Onboarding 或模型列表刷新不会覆盖用户已经固定的选择；
- OpenRouter 首次成功下载后会保存有效缓存和条件请求信息；再次检查没有变化时不重复替换目录；
- OpenRouter 下载失败、超时或校验失败时继续使用上一份有效缓存，没有缓存时才使用内置备用目录；
- OpenRouter 在线 JSON 无法修改 API 地址、密钥、Prompt、请求头或任意运行参数；
- OpenRouter 目录更新后，被停用或消失的固定模型会变成“需要处理”，不会被静默替换；
- 删除 AI 连接前可以列出所有依赖它的功能；
- 修改索引深度、文档分块和目录时，会正确创建相应处理操作；
- 文件能力目录中的“可索引”必须有真实读取器和端到端搜索测试，不能只因为存在扩展名或生成器就通过；
- PDF、图片、TXT、CSV、JSON、HTML、Excalidraw 和 Canvas 的开关分别验证新增、关闭、清理旧结果和重新开启；Office 格式不会出现在可用类型中；
- XLSX 导入 Peak Sheet、Peak Sheet 工具读取和通用 XLSX 索引分别测试、分别报告能力状态；
- Peak Sheet 与 AI Graph 内部正式 JSON 永远不进入普通知识索引；用户显式导出的 Markdown 可以按 Markdown 政策处理；
- Draw.io 在通用读取器完成前不会出现可用的索引开关；
- 每次索引运行都有稳定 `indexRunId`、阶段结果、失败项和最终 receipt，重启插件后仍可恢复；
- 关闭知识索引 View 不会取消任务；再次打开会恢复同一活跃任务；
- Notice、Onboarding、Settings 和命令入口都跳转到同一活跃任务，不会各自创建重复任务；
- 全文索引完成后可以在向量和 AI 补充分析继续运行时开始关键词搜索；
- 覆盖率按全文、向量、标签、摘要和图关系分别计算，不会用本次进度冒充 Vault 总覆盖；
- 失败文件可以单独重试，重试前会重新显示预计成本和可能的重复收费；
- 密钥不会出现在日志、运行记录和诊断导出中；
- 危险操作有明确确认和最终结果记录；
- Settings 与 Onboarding 读取同一份可用状态；
- 重启后所有正式设置保持一致；
- 当前已经发现的启动恢复问题全部有防止再次出现的测试。

### 13.3 产品验收

- 新用户只完成首次目标所需的最少决定；
- 已有连接、知识索引和用户固定的默认值会被正确复用；
- 用户从任何功能都能找到唯一的长期设置位置；
- 用户能从熟悉的产品功能逐层找到具体 AI 动作；
- 普通用户不需要先理解服务商、通用任务类型或 Prompt，也能知道当前实际会使用哪个模型；
- 不使用生成模型的能力明确写明“无需模型”，不出现假的模型选择器；
- 上一级的模型指定只影响能力兼容的下级动作，不会错误覆盖图片、音频或媒体生成等其他类型；
- 默认候选不会平铺服务商的完整模型目录；只有用户主动查看时才显示完整兼容列表；
- 用户能看出 Codex / Claude Code 当前是“普通生成可用”“Agent 可用”“两者都可用”还是“需要处理”；
- 用户能看出 Agent 当前由 Peak Hermes 怎样执行，以及实际使用了哪个模型或执行连接；
- 用户能看出 OpenRouter 当前使用在线目录、本地缓存还是插件内置备用目录；
- 每项设置都能回答“影响什么、是否保存、是否生效、如何恢复”；
- 高级能力没有被删除，也不会压过常用任务；
- 状态、设置、操作、确认和危险行为不会混淆；
- 不存在重启后丢失但 UI 仍宣称成功的设置；
- 不存在没有真实功能使用的假开关；
- 用户能分别看懂某种内容是“可索引”“只可导入”“由专用工具读取”还是“只可生成 / 保存”；
- DOC/DOCX、PPT/PPTX 不出现在产品文件类型设置中；内部 loader 的存在不会改变这一产品边界；
- 首次批量索引不依赖右上角 Notice，用户可以离开并再次打开查看同一任务；
- 用户能分别看出全文、向量、标签、摘要和图关系的覆盖与更新时间；
- 基础搜索可用后，Onboarding 不会为了等待完整 AI 补充分析而阻塞第一次真实任务；
- 某个阶段或文件失败时，用户可以在原地理解原因并只修复失败范围；
- 完成 Onboarding 后进入真实工作入口并完成第一次成功任务；
- UI 设计可以改变，但本文规定的模块所有权与配置边界保持不变。

- `templates/config/*`：产品模板配置、模型目录、媒体预设与内部机制；
- `docs/conventions/configurability.md`：模板配置、各领域内置备用值与常量的代码归属规则。

其中 `templates/config/*` 表示产品团队可以在不改业务代码的情况下调整内部配置，不代表终端用户应该在 Settings 中修改这些内容。两种“可以修改”必须始终分开。
