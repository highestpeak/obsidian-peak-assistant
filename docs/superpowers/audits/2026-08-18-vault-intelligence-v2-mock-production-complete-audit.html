原 Mock 的核心设计，不是几个页面，而是一套可信维护系统

用户心智

  • Overview 回答“Vault 现在是什么状态，我下一步最值得做什么”。
  • Vault map 回答“内容分布、知识结构和显式活动是什么”。
  • Work queue 回答“哪些事情仍需要我做决定、review 或 recovery”。
  • Scan 是一次有计划、有授权、有收据、可恢复的操作流，不是顶级栏目。

可信边界

  • Peak-owned Index / Community / lifecycle 状态可以重建或反悔。
  • Markdown、YAML、链接和新文件属于 user-file write boundary。
  • 任何文件写入都必须走：证据 → candidate → diff → revision guard → Apply → re-index → verify。
  • AI 是否调用、用哪个 provider/model、预计与实际 token/cost 都必须明确。

统一状态原子

  • 同一个维护原子必须有稳定 ID，所有分组、筛选、投影视图都只是重排。
  • 优先级：当前 owner choice ＞ 当前 Peak suggestion ＞ 历史 suggestion/evidence。
  • Apply/Verify 后，已验证结果才成为新的事实。
  • 切换 Batch/File、Target/File、Community/File 不能复制、重置或重计同一选择。

深工作去 owner surface

  • Vault Intelligence 做计划、证据、选择和返回点。
  • 真正的内容编辑在 Composer / Project / Chat / AI Graph / Proposal workspace 完成。
  • Queue 不是把所有功能复制一遍，而是保存“下一步做什么”和“何时算完成”。

交互合同：Mock 里真正需要实现的行为

Overview

  • 4 张对象摘要 hover/focus 打开对象专用 popover，不是通用 tooltip。
  • Files/Chats/Projects 使用可交互分布；Composer 指向精确 saved review checkpoint。
  • heatmap day hover/focus 显示证据，点击日同步 Activity。
  • 日期 popover 支持 7/30/365/custom，清除后回到默认。

Activity

  • 来源 picker 可搜索；Top N + Other + Unclassified。
  • 拖动窗口或两端 handle 改变选区。
  • lanes、选中期统计、sessions、event list、theme mix、等长前期对比同步。
  • Recorded activity 永远可用；AI themes 有生成/stale/confidence/citation 状态。

Vault contents / graph

  • 饼图 slice/legend 支持 hover、focus、click，筛选同一图和下方解释。
  • Community 在同一 Cytoscape 图内展开；无关项淡化；再次点击/canvas/Escape/reset 收回。
  • Shift inspect、I pin、Nodes list、四种 layout、Mermaid/image/fullscreen。
  • 选择始终同步 summary、evidence、capability、next action、AI interpretation。

Scan setup

  • scope 可加入 file/folder/Community/saved work，并自动纳入 affected closure。
  • task hover/focus 高亮它支持的 AI groups。
  • Index output 与 supporting AI operation 双向同步。
  • model picker 是真实 route；开关实时重算时间/token/cost。

Run progress

  • stage rail 可点击定位，不把四阶段当四张静态卡。
  • Build Index 有 per-file 6-step rail、队列、当前文件、速度和剩余时间。
  • vault-wide AI timeline 与 per-doc enrichment 分开。
  • operation 可独立 stop/skip；running 自动展开一次但不抢滚动。

Queue / maintenance

  • 一行只展开一个；filter/search/leave/Escape 关闭。
  • 自然语言纠偏只重算未应用 suggestion，不能覆盖 owner choice。
  • Property/Link/Community 各有专用动作，不用一套 Accept/Reject 模板。
  • 恢复 checkpoint、scroll、source revision；冲突项不能被 bulk Apply。

布局合同：哪些不是“随便排得差不多”

全局 shell

顶部两行：标题/状态/唯一主 CTA；下方只有 Overview / Vault map / Work queue。内容区最大宽度 1500px，操作页可以收紧。

Overview

对象条在最上；Continue work 为紧凑列表；随后完整年度 heatmap；Knowledge Index 是可解释的 readiness/impact，不是 2×2 的装饰数字卡。

Map

local nav 左对齐常驻。Contents 的 type distribution 在图上方；图与 Community summary/selection evidence 构成一个连续工作区，不放右侧永久 drawer。

Scan

Scan setup 的专用最大宽度 1280px。三个步骤垂直推进；Index plan 嵌套在 Step 2，AI authorization 在 Step 3，底部才给 estimate 与 CTA。

Run

先是横向总体进度带，再是阶段 rail，再是当前阶段的纵向 workbench。不是“两张 progress 卡 + 四张 stage 卡 + 一张表”。

Completed

单页决策流：完成事实 → 自动完成 → owner follow-up → 运行细节。follow-up 表格是主内容，不被大号指标卡挤到首屏下方。

Task modal

普通详情约 720px；完整维护工作区约 980px；Note split 可到 1500px。宽度跟任务复杂度走，不用一个全屏 generic modal 承载全部。

Semantic zoom

Task → group → file → atomic change。每次展开必须出现更具体对象或 diff，不能只是重复更长的解释文字。

刷新或重开仍显示同一 proposal revision；新候选不会静默替换当前审阅内容。
2. Per-file diff 与选择未实现
Mock

每个文件显示完整 combined diff 与 checkbox；可逐文件或全选，明确 unchanged/created/updated/retired。

当前

generic task dialog 没有真实 proposed bytes、file group 或 checkbox selection。

实施依据
diff 由 accepted atoms 确定性生成；selection 是 proposal review state，不改 task candidate。
通过条件
勾选数、expected writes 与实际文件集合相同；合并后 diff 不遗漏多个 atom 对同一文件的交互。
3. Source revision match / conflict未实现
Mock

每文件显示 Revision matches 或 Source changed；冲突文件不能勾选应用，可 refresh proposal。

当前

没有 per-file source hash guard 或 conflict UI。

实施依据
proposal 保存 source hash；Apply 前再次读取并比较，不依赖 UI 首次打开时的旧判断。
通过条件
审阅期间修改文件会即时或 Apply 时阻断该文件；其他 matched 文件仍可安全应用。
4. Apply safety 与写入边界未实现
Mock

明确说明 Apply 才会写用户文件；展示 selected files、expected writes、backup/receipt 与不可逆风险。

当前

generic applyTask 无独立 safety summary，用户无法确认实际写入文件和 bytes。

实施依据
Review 阶段只写 Peak-owned proposal state；user-file mutation 仅由显式 Apply command 触发。
通过条件
打开、选择、更新 suggestions 均不改用户文件；Apply receipt 精确列出 changed paths 与 source/result hashes。
5. Primary action 与零选择状态未实现
Mock

Primary action 是 Apply selected；零选择时 disabled 并解释，没有第二个含义模糊的写入按钮。

当前

没有 Proposal 页面或 selection-aware action。

实施依据
按钮 label 包含作用范围；点击后使用当前 proposal revision 与 selection snapshot。
通过条件
零选择不调用 writer；double click/idempotent retry 不产生重复写入或重复 receipt。
6. Apply 结果、re-index 与 verify未实现
Mock

Apply 后逐文件显示 Applied/Failed/Skipped；自动 re-index 并执行 task exit verification。

当前

generic runtime 暴露 verifyTask，但无 proposal-level result、re-index chain 或 per-file partial failure。

实施依据
Apply、index refresh 与 verify 是有 receipt 的连续状态机；失败不抹掉成功文件事实。
通过条件
成功文件使用新 revision 进入 index；失败文件留在 recovery；task 仅在 exit check 通过后 verified。
7. 返回 owner task 与历史未实现
Mock

完成或取消后回到来源 task/Queue/Completed，保留 checkpoint；历史 proposal 与 apply receipts 可查看。

当前

没有 proposal identity/history，因此无法恢复来源上下文或审计旧 revision。

实施依据
return checkpoint 与 proposal history 都是 canonical state；旧 proposal immutable。
通过条件
返回后原 filter/row/scroll 恢复；可从 task 打开已应用 proposal、diff、receipt 和 verify result。

为什么前一次“改了很多 CSS”仍然八竿子打不着

1. 把 parity 当成了 shell restyling

前次变更大量集中在 CSS 和同一个 865 行 workspace 组件，保留了原来的 route、snapshot、activity、graph 和 task model。结果只能让 header/card/spacing 接近，不能产生 Mock 里的对象、状态与交互。

2. 用 synthetic harness 代替真实状态契约

harness 可以喂出好看的 286 objects、5 tasks 和 running state，但真实 Vault 出现 baseline 未建立、changed 摘要、超出 discovered 的 Search ready。fixture 证明渲染，不证明事实口径和 transition 正确。

3. 测试只锁了“卡片存在和高度”

当前 parity test 主要检查 object-card class/count、CSS 顺序、78/66px 高度、overlay、Activity 2-column。它反而把错误的 2-lane/通用卡片结构固化了，没有覆盖 hover 内容、range drag、graph selection、state transitions 或 proposal diff。

4. 过早做通用化

一个 generic MaintenanceWorkspace 试图承载 11 种任务。通用外壳可以共享，但领域对象、投影、动作、diff 和退出条件不能共用一组 choice buttons。Mock 的设计正是为了避免这种“每个任务都像同一个表单”。

因此，下一轮不能从 CSS 开始

正确顺序是：锁定最终状态矩阵和 canonical atoms → 补数据端口与 routes → 实现交互闭环 → 恢复页面布局 → 最后用真实 Obsidian 做 normalized overlay/pixel diff。否则还会再次出现“截图看似整齐，但产品完全不是同一个”。

重新实现前必须写进计划的验收门

Gate 1 · State matrix

为 First setup、Changes、Recoverable、Indexing、AI work、Completed 建立明确 fixture 和 transition；Header、Overview、Queue、Scan CTA 必须从同一状态推导，不得各自猜。

Gate 2 · Screen inventory complete

9 个页面/工作区和 overlay/archetypes 都有 route、entry、back/return point；Proposal 与 Map text 不得再写成“未来 owner surface”占位文案。

Gate 3 · Data contracts before visuals

对象 popover、5-source Activity、file readiness、Community graph、maintenance atoms 都能由 production ports 提供；数量单位必须标明 files/chunks/records，不允许混用。

Gate 4 · Interaction replay

Mock 的 hover/focus/click、date range、Activity drag、graph expand/inspect/pin/Escape、Scan output sync、pause/resume、task projection 与 Apply/Verify 都有可重复脚本或明确人工录屏。

Gate 5 · Real Obsidian parity evidence

同 Vault source SHA、theme、zoom、viewport、DPR、scroll anchor、interaction state；保存 reference + real current + normalized + overlay/diff + manifest。Harness 只能做预检查。

Gate 6 · Per-screen acceptance

全局壳层、Overview、Queue、Activity、Contents、Graph、Setup、Run、Completed、Property、其余十类 maintenance、Map text、Proposal 必须逐项通过本报告的验收条目；不能用“总体更接近”掩盖任一未实现页面或任务。

Gate 7 · Claim discipline

只有页面结构、状态、数据、交互、布局和视觉都通过时才写 “parity”。若只完成 CSS 或 harness，应准确标为 shell alignment / partial implementation / interaction not verified。
