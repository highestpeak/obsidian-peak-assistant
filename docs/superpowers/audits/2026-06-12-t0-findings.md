## Top 5 findings

### Finding 1 — `service` reads and writes UI store as if it were runtime truth

**Evidence**
- `src/service/BackgroundSessionManager.ts:3` imports `useSearchSessionStore` and drives its setState from outside React.
- `src/service/chat/service-conversation.ts:38` imports `useChatViewStore` and writes streaming chat state.
- `src/service/chat/context/slots/SystemPromptSlot.ts:7` reads `useChatViewStore` to compose prompt input.
- `src/service/ambient/MorningBriefingService.ts:9` writes `useMorningBriefingStore` from a background timer.
- `src/service/lint/VaultLintService.ts:11` writes `useVaultLintStore` from a vault scanner.
- `src/service/copilot/CopilotReviewArtifactBuilder.ts:24` reuses UI display helpers from `quick-search/types/search-steps` for service-side artifact assembly.

**Why it matters**
This is the single biggest violation of "state ownership clarity" (SO dimension). The UI store is both the projection layer and the source of truth for long-running tasks, and a background service is the one populating it. Any RunEnvelope / projection split (T7) is impossible until at least one capability has a non-UI run record.

**T1/T2 input**
- Quick Search session, Chat conversation streaming, Morning Briefing run, and Vault Lint scan are the capabilities most coupled to UI stores. Pick the smallest one (Vault Lint or Morning Briefing) as the T9 pilot — the largest one (Chat) should not be the pilot.

### Finding 2 — `core` imports `service` and `app`, so `core` is not actually the bottom layer

**Evidence**
- `src/core/eventBus.ts:2` imports `ChatConversation` / `ChatProject` from `@/service/chat/types` (core depends on a business type).
- `src/core/document/loader/*.ts` (10+ files) import `AIServiceManager` from `@/service/chat/service-manager` and `ChunkingSettings` from `@/app/settings/types`.
- `src/core/providers/rerank/llm.ts:2` imports `AIServiceManager` and `PromptId`.
- `src/core/utils/{vault,obsidian,format,markdown-utils,message-preview}-utils.ts` all reach back into `service` or `app`.
- `src/core/embeddings/embedClient.ts:3` imports `AppContext` from `@/app/context/AppContext`.

**Why it matters**
The intended dependency direction (handbook §3) is `app -> service -> core/ports -> adapters`. Today `core` participates in business types and DI lookups, which means a Port-style refactor (T2) cannot rest on the current `core` shape. Either some of these modules are misclassified (`document/loader/*` is really a service concern), or `core` needs to be split into `core/contracts` vs. `core/adapters`.

**T1/T2 input**
T1 Contract Seeds should not start by adding new types into `core` until this is settled — otherwise the seeds will inherit `core`'s wrong-direction dependencies. First decision a T1 prompt has to force: *do `core/document/loader/*` and `core/providers/rerank/llm.ts` belong in `core` or `service`?*

### Finding 3 — Concrete Obsidian side effects inside `service`

**Evidence (12 distinct service files)**
- `Notice` calls inside business code: `BackgroundSessionManager.ts:1`, `copilot/CopilotReviewHistoryService.ts:14`, `copilot/vault/VaultReviewReportService.ts:14`, `search/analysisDocPersistence.ts:10`, `search/support/progress-tracker.ts:1`, `search/index/indexInitializer.ts:1`.
- `MarkdownView` inside `service/ambient/ContextExtractor.ts:1` (reads the active editor to extract context).
- Concrete Obsidian symbols in service edges total **23** in the scan (`Notice`/`Modal`/`MarkdownView` etc.).

**Why it matters**
Each of these is a fakeability blocker. None of them can be exercised under a Node test runner today (no Obsidian app handle). They are the natural first **Port** candidates:
- `NotificationPort` (a wrapper around `new Notice(...)`).
- `ActiveDocumentPort` (replaces `MarkdownView` peek inside `ContextExtractor`).
- `ProgressReporterPort` (wraps `progress-tracker.ts` Notice usage).

**T2 input**
The number is small enough (12 files) that T2 Port Sketches can cover all current concrete side-effect symbols in one pass. This is a high-leverage, low-blast-radius first port.

### Finding 4 — `AppContext.getInstance` is the de-facto runtime locator across every layer

**Evidence**
- 88 references in `service`, 110 in `ui`, 3 in `core`, 21 in `app`.
- CLAUDE.md (Code Conventions) explicitly prefers `AppContext.getInstance` over passing context as a parameter. This means the *style* is intentional — but every reference is also an undeclared dependency that a Capability Contract cannot describe.

**Why it matters**
Capability Contract (T1) needs explicit inputs. Anything resolved via `AppContext.getInstance()` is invisible to the contract. If we run T1 without surfacing what each capability actually pulls from `AppContext`, the contract will look clean while the runtime stays opaque.

**T1 input**
T1 should produce, per pilot capability, a "what does this capability resolve from `AppContext`?" inventory. The scanner's per-file count is the cheap first cut; the next step is opening the worst offenders and writing the resolved-dependency list as part of the contract.

## Suggested first-capability candidates for T4 / T9

Ranked by leverage (low blast radius × high boundary-clarification value):

1. **Vault Lint** — small surface, single store (`vaultLintStore`), single service file (`VaultLintService.ts`). Good T9 pilot.
2. **Morning Briefing** — also single store, lives in `service/ambient/` but is independent of the Ambient Push spec; lets us prove RunEnvelope on a real long-running job without touching Ambient itself.
3. **Quick Search session** — bigger, but `BackgroundSessionManager.ts` is the clearest exhibit of service-writes-UI-store, so the boundary win is high.
4. (Defer) **Chat conversation streaming** — largest blast radius; should be one of the *last* capabilities migrated, not the pilot.
5. (Defer) **Ambient Push** — gated by the handbook anyway; should not start before T10.

## What was intentionally NOT changed in T0

The script is dependency-free and does not require Obsidian. It walks `src/**/*.{ts,tsx}` with a tolerant regex import parser and classifies each edge against the layer model in CLAUDE.md.

## Limitations

- The scanner uses regex import parsing, not a real TS AST. Edge cases (dynamic `import()`, conditional re-exports, decorators) may be missed. Counts are floors, not ceilings.
- Type-only imports are counted as imports because they still pin architectural shape; this slightly inflates the layer matrix relative to a runtime-only count.
- "Suspected dual paths" (Finding 5) is hand-curated, not auto-detected. T1/T2 should confirm or reject each row before acting on it.
- The Obsidian side-effect symbol set is fixed in the script. Adding a new symbol there will retroactively re-classify existing edges; that is intentional — the symbol list is the audit's policy surface.
