Composer 文档主题：从结构到阅读节奏

              
Composer 不是富文本画布的仿制品，而是一张可直接工作的 Markdown 文档。主题需要让 写作状态、已撤回判断、AI 新建议、外部链接、[[Theme Boundary]]、#design-system、行内 semantic-token 与公式 E = mc² 各自可辨认，但不制造一排彩色徽章。


              
1. 标题建立层级，不制造卡片

              
H1–H6 使用稳定比例和统一上边距。字号可以随 preset 改变，但标题的职责始终是组织文档，而不是模拟 Dashboard 模块。

  • 无序列表保留清楚的悬挂缩进。
  • 嵌套关系只增加层级，不增加容器。
    • 第二层仍然与正文共享字体和颜色。
  • 长列表切换到 Research Compact 后应明显增密。

              
  • 网络结构：承接滑箱笔记、论文旁批与临时判断。
  • 树形结构：承接系统学习、技术专题与项目文档。

Executive Summary
Peak 的界面需要共享一套可切换主题，同时保持与 Obsidian 宿主样式的明确边界。组件只消费语义角色，Theme Pack 决定具体颜色与层级。
设计系统的目标不是让每个页面完全相同，而是让相同动作、状态和信息层级保持一致。

                  
视觉角色与主题边界
Canvas、Surface、Raised 与 Overlay 组成深度顺序；Accent 只表达选择、主动作与 AI 身份，不承担所有装饰。
Obsidian UI Defensedocs/conventions/ui-design.md · cited section 4.3.1Source 2

                  
组件状态与可达性
每个可点击控件都要拥有 Rest、Hover、Focus、Selected、Disabled，以及必要时的 Loading 和 Error。Focus 不能只依赖颜色差。
同一主题下，正文阅读表面应该比 Dashboard 更安静，比浮层更平。

                  
可执行的下一步
先覆盖共享 primitives，再迁移产品组合；新增 UI 时必须把新状态补到视觉覆盖板和自动校验里。
