目标设计契约 · 2026-08-10

Peak 被 Obsidian 承载，
但不被 Obsidian 设计。

这套系统统一颜色、字体、密度、间距、圆角、阴影、动画、组件和 Graph 语义；同时建立独立 Theme Engine 与 Theme Boundary，让 Peak 的每一个界面在任意 Obsidian 主题下保持可预测。

阅读约 20 分钟 面向产品、设计与工程 现有资产 目标约束 待收敛
一个视觉真源

所有 Peak 管理的 DOM 只消费 Peak semantic tokens。颜色名描述角色，不描述某个固定色值。

Theme 是参数，不是补丁

Theme Pack、Light/Dark、Density、Accessibility 和字体覆盖共同解析成一个完整主题。

共享行为，保留领域语义

共享外壳、状态和交互；Composer、Graph、Streamdown 等复杂领域保留自己的渲染内核。

层当前事实本系统的目标约束
Tokenspeak-tokens.css 已有 Light/Dark、type、spacing、radius、shadow 与 transition。继续作为 Peak Default 真源；全部产品 CSS 只消费 semantic roles。
Components已有 primitives 与 Result Browser，但 Button、局部 controls 和 surface CSS 仍有并行实现。每个公共 intent 只有一个组件族；产品表面只组合，不复制内部视觉与行为。
Host isolation当前依赖 scoped root、reset 与 !important 对抗 Obsidian，历史上多次出现 geometry 回归。Theme Boundary 覆盖普通 DOM、Portal 与 popout；Shadow Root 是长期硬边界。
Theme现有 token 会跟随宿主 Light/Dark class，Appearance 里主要只有 code theme。Peak 自主 Theme Pack 可注册、验证、预览、切换；非法 pack 原子回退 Peak Default。
GraphResult Browser 与 File Atlas 有结构图；AI Graph 使用独立多 Lens 内核。保留两个 renderer，统一 View / Scope / Layout / Lens 词汇和 Graph chrome。
不是组件画廊

设计系统只有在真实产品里被约束才有意义。因此下文既展示组件，也规定 Composer 属性建议、Chat、Search、File Atlas、AI Graph、Settings、Onboarding 与 Usage Dashboard 应怎样组合它们。

Theme Boundary

宿主可以提供运行环境，但它的视觉变量、裸标签规则和第三方主题样式不能成为 Peak 的输入。

01 · Boundary
输入环境信号

ownerDocument、viewport、DPR、reduced motion、forced colors；只有用户选择“跟随”时才读取宿主明暗信号。

解析Theme Resolver

验证 Theme Pack，叠加 mode、density、accessibility 和 font overrides，生成完整 resolved theme。

隔离Peak Boundary

普通 UI、Portal、Modal、Popover 与 popout window 都挂载同一作用域；长期以 Shadow Root 为硬边界。

输出Peak UI

组件只读取 Peak semantic tokens。主题缺失、非法或加载失败时回退 Peak Default。

Obsidian Host

  • 允许：窗口与辅助功能信号
  • 拒绝：颜色与字体变量
  • 拒绝：button / input 裸标签样式
  • 拒绝：圆角、阴影、动画和 focus
→

Peak Theme Boundary

  • 内部完整定义颜色、排版、形状、层级与 motion。
  • Portal 必须回到同一个 themed portal host。
  • popout 在所属 ownerDocument 重新挂载主题。
  • light DOM reset 只是迁移防线，不是最终架构。
明确的失败策略

任何缺 token、非法值或不兼容版本的 Theme Pack 都不得部分生效。系统必须原子回退到 Peak Default，而不是穿透到 Obsidian 变量。

Theme Engine

页面顶部的 Theme Lab 正在用同一套概念切换本页。Quiet Moss 只是展示“换主题不换组件行为”的示例，并非正式内置主题承诺。

02 · Theme

Resolved Theme

Theme Pack + Appearance + Density + Accessibility + Font overrides

  • Appearance：Light / Dark / Follow preference
  • Density：Comfortable / Compact
  • Accessibility：Normal / High contrast / Reduced motion / Forced colors
  • Fonts：界面与等宽字体可独立覆盖

Theme 可以改变什么

  • 语义颜色、字体家族与字重
  • 经过设计系统允许的 shape、elevation、motion preset
  • Light 与 Dark 两套完整模式
  • 不能改变键盘、命中区、组件状态机和信息层级

1 · Define从 versioned Theme Pack 模板开始，只填写语义 token 与允许的 presets，不写组件 selector。
2 · Validate检查 schema、Light/Dark 完整性、值类型、contrast、未知 token 和版本兼容。
3 · Preview在隔离 Boundary 同时预览组件状态、产品样例、Compact 与 Reduced Motion。
4 · Apply一次性发布 resolved theme；任何步骤失败都保持当前主题并回退 Peak Default。
5 · Persist保存 Theme Pack id、版本和用户 overrides，不保存展开后的易漂移 CSS。
6 · Migrateschema 升级走显式 migration；不认识的新字段不能静默吞掉。

Color

现有 peak-tokens.css 是 Peak Default 的起点。组件引用角色名；Theme Pack 为每个角色提供 Light 与 Dark 值。

Motion

动画用于解释状态如何变化，而不是装饰。上方可切换 Reduced Motion；它必须保留最终状态和可理解性。

06 · Motion
100ms · Fasthover、pressed、颜色和微型 icon 反馈。交互开始时不应等待动画。
150ms · BasePopover、AI 属性建议、行展开与轻量 panel 出现。
300ms · SlowModal、sidecar 与大面积布局变化。禁止串联多段无意义过场。
Spring · Shared thumb只用于视图、密度、lens 等连续互斥切换；统一 stiffness 500 / damping 34。
Streaming · 连续稳定Chat 与 AI candidate 追加内容时固定已渲染前缀，避免整个 surface 跳动。
Reduced Motion移除 spring、位移和呼吸效果；保留 opacity 或瞬时切换与完整 focus 反馈。

Components

按交互意图选择组件，不按外形猜。下列是全产品共享的核心组件族；展开查看示例和适用边界。

07 · Components
Buttons & actionsPrimary、Secondary、Ghost、Danger、IconButton；同一动作在所有 surface 保持状态和命中区。
每个区域最多一个 Primary主动作竞争时必须先解决信息架构。
固定命中区是组件契约宿主 reset 不得改变 32 / 36 / 40px 目标。
IconButton 必须有名称用 aria-label 与 tooltip 说明行为。
Segmented, tabs & toggle视图、密度、时间范围、模式和布尔设置；不能把三个普通按钮拼成 Button Group。
Segmented同一层级、即时生效、互斥选项，通常 2–5 项。

哪些共享，哪些不抽象

抽象目标是降低视觉与行为分叉，而不是制造一个吞掉领域语义的万能组件。

怎么改

先建立边界与真源，再迁移组件和产品表面。不能继续按“哪里坏了补哪里”的顺序推进。

11 · Adoption

冻结契约与基线

确认 token roles、Theme Schema、Boundary、primitive inventory、Graph vocabulary 和例外登记。记录 hostile-theme computed styles 与视觉基线。

建立主题运行时

实现 Theme Resolver、Peak Default、preview、validation、atomic fallback、Portal host 和 popout ownerDocument 传播；Settings 提供主题入口。

收敛共享组件

合并并行 Button；统一 Segmented、Input、Row、Overlay、AI state 与 Graph chrome。所有固定尺寸 primitive 建立宿主防御测试。

按 surface 整体迁移

顺序建议：Settings/Onboarding → Search/Result Browser → Chat → Composer chrome/sidecar → File Atlas/Graph → Dashboard。每个 family 一次迁完。

迁移优先级

优先改共享频率高、宿主侵入风险高、视觉分叉明显的层：Theme Boundary、Button/Segmented、Overlay/Portal、SearchInput、Result Browser。复杂编辑器和 Graph renderer 只替换外壳，不在同一波重写内核。

以后怎么不再出现

设计系统不是文档约定，而是“设计评审 + 静态门禁 + hostile host 测试 + 真实 Obsidian 验收”的组合。

12 · Enforcement

自动门禁

  • Peak scope 内禁止新增 Obsidian visual vars
  • 禁止未登记 literal color / radius / shadow / z-index
  • 禁止新 raw button、重复 Segmented 与 surface-local Button Group
  • Theme Pack schema、完整 token、contrast 与 fallback 测试
  • Portal scope、fixed geometry、focus 与 reduced-motion 测试
  • 扫描基线只降不升；新增例外必须有 owner 和删除条件

真实宿主验收

  • 准备 hostile Obsidian theme：夸张按钮、字体、圆角与 input 规则
  • 在 Light/Dark、Compact/Comfortable、Reduced Motion 下核对 computed style
  • 在真实 Obsidian 中验证 Button geometry、Popover、Modal、Portal 与 popout
  • 键盘验收读取 activeElement；hover 验收走真实 pointer path
  • 截图只证明最终视觉；交互状态需 DOM/CDP 证据
新界面进入开发前先完成 Surface Contract，不允许边写 JSX 边决定 token 和组件。
1 · 任务用户在这里做什么？默认信息密度与主要状态是什么？
2 · 组件映射逐项映射到已有 primitive；缺口先补公共组件。
3 · 视觉角色列出 surface、text、border、radius、elevation、motion 与 graph semantics。
4 · 边界确认 root、Portal、popout、Shadow DOM 与第三方 renderer 的主题传播。
5 · 状态empty、loading、streaming、ready、stale、error、disabled、focus、selected。
6 · 证据focused test、build、real host computed style、交互与截图证据分开记录。
Definition of Done

一个 surface 只有在 Peak Default Light/Dark、自定义 Theme Pack preview、hostile Obsidian theme、Compact、Reduced Motion、键盘与 Portal 场景都通过后，才算完成设计系统迁移。Build 通过不等于真实宿主视觉通过。

本页是产品级 Design System 入口，描述目标契约并引用当前代码事实；工程细节继续由 UI Design System convention、迁移决策 与各产品 spec 承载。
