这页解决什么

Peak Assistant 现在的代码规模已经不小：Chat / Search / AI Analysis / Copilot / Ambient / Knowledge / Harness 每条链路都有独立的 service、UI 和 stores。新读者若直接从任一 feature 入手，会在“service 到底是不是可以随便拿 AppContext”、“runtime 应该长在哪一层”、“这个 Runtime 是不是又一个 singleton”这类问题上反复踩。这页把当前已经落地的架构地基摊平，再把仍在路线图上的部分标出来，让读代码时能一眼判断“这段是现状还是目标”。

本文读者 刚加入的工程师；即将改动跨模块 API、runtime 生命周期、port 定义的维护者；正在写新 feature、需要知道“service 层能拿什么、不能拿什么”的人。
本文不做什么 不重复代码目录（那是 02 Code Organization）；不重复各 feature 的用户流（那是 11/12/13/16）；不重复配置项（那是 04）；不列 provider/模型的接线细节。

四层架构：app · service · core · ui

Peak 的顶层结构是四层：app 拥抱 Obsidian，service 做业务编排，core 只放框架无关的抽象与类型，ui 是 React 层。依赖方向单向向下：app → service → core、ui → service → core；app 组装并把 service/ui 拼起来。反向依赖是硬错误——core 不认识 Obsidian，service 不认识 React store，ui 不直接读 SQLite。

为什么没有 service-side singleton CLAUDE.md 的 “Runtime ownership” 规则显式禁止两件事：一是在 service 层用模块级 let currentRuntime = null 加 set/getRuntime 做单例；二是把 AppContext.getInstance() 当依赖捷径。原因是 Obsidian 热重载会保留旧闭包引用，service-side singleton 会持续持有已 dispose 的 sqlite 句柄 / event listener，导致隐蔽的内存泄漏和事件重复触发。所有 capability runtime 必须由 app/ 层拥有和释放。

Capability Contract

“Capability”在 Peak 里有一个非常具体的含义：一个产品能力承诺——它给用户什么、需要什么输入、产出什么 artifact、有什么权限约束、可以在哪些 surface 出现、可以用哪些后端跑。它不是一个 tool，不是一段 prompt，也不是一条 agent loop——它是这些东西的组织单位。

但代码里现在并没有这样一个完整的"能力对象"。src/service/capabilities/CapabilityRegistry.ts 只兑现了其中最小的一块——让每个 UI surface 声明自己此刻是否 ready，供 Settings 面板渲染 readiness 灯。对比一下"现在"和"目标"的形状：

// 现在（landed）
type Capability = {
  surfaceId:       'Conversation' | 'Research' | 'Fast Lookup'
                 | 'Knowledge Index' | 'Web Access' | 'Safety'
  surfaceLabel:    string
  getStatus():     'ready' | 'needs-attention' | 'not-ready' | 'optional'
}

// 目标（roadmap · handbook §3 决策 1、§8）
type Capability = {
  id:              string          // 'doc.review.current' 之类的稳定标识
  inputContract:   Schema          // 需要什么输入
  outputContract:  Schema          // 产出什么 artifact
  permissionKind:  'read' | 'acceptEdits' | 'bypassPermissions'
  costTier:        'fast' | 'deep' | 'premium'
  backendPolicy:   BackendPolicy   // Hermes / Claude SDK / provider
  skillRef:        SkillId         // 挂哪本工作手册
  surfaceBinding:  SurfaceId[]     // 允许出现在哪些 surface
  // + 上面三个 (surfaceId / surfaceLabel / getStatus)
}

目标形状里的每个字段其实都在代码里，只是散着——backend 选择混在 agentBackend setting、权限混在 harness 的 permissionMode、skill 直接从 service/skills 拿，都还没被合同化成 Capability 的一个字段。下表把每个属性映射回它现在藏在哪里、以及归属哪个 Roadmap 任务包（源头见 系统架构现代化手册）。

关键 mental model 读 feature 代码时不要把 CapabilityRegistry.register(...) 误当成“能力全景注册”——它现在只表达“surface 是否 ready”。真正的产品能力（“Doc Review”、“Vault Search”、“Analysis Round”）目前散落在 ChatAgent / CopilotActionRegistry / VaultSearchAgent / ReportOrchestrator 里，尚未被合同化。2026-07-02 T1 已落地 CapabilityManifest 类型 + doc.review.current fixture——契约形状已锁，等 T4 CapabilityRunner 消费。这是 handbook 里最大的一块地基，从"未开工"变成"合同已定，等消费"。
写新 feature 时的临时约束（T1 后仍适用）

T1 落地了 CapabilityManifest 类型和一份 fixture，但还没有 CapabilityRunner 消费它。所以新 feature 仍然应该：

  1. 通过 CapabilityRegistry 声明 surface readiness（service/capabilities/CapabilityRegistry.ts）。
  2. 把 backend 选择、tool policy、artifact shape 集中写在一个 service/<feature>/ 目录下，而不是塞进已有的 CopilotActionRegistry 或 service-manager。
  3. 每个新加的运行时状态优先走 Owned Runtime 而非 singleton。
  4. 如果你在写"新 capability"，可以顺手写一份 CapabilityManifest fixture 放到 test/fixtures/capabilities/——T4 落地后能直接接入。

这样后续 T4 Capability Replacement 只需换 registry 引用，不用重写业务。

RunEnvelope：统一外壳，不统一业务流程

当 Chat、Search、Copilot、AI Analysis、Harness、Knowledge Jobs 各自跑长任务时，它们业务引擎不同——Chat 是 stream+context assembly，Search 是 retrieval+rerank，Copilot 是 review+propose+apply，Harness 是 agent loop——但它们对 UI、测试、历史、debug 的外部形状应该一致：可观察、可取消、可恢复、可回放。这个共享外壳就是 RunEnvelope。

RunEnvelope 由三个类型组成：

  • RunSession——一次运行的状态柄：runId / capabilityId / status / trigger / startedAt。
  • RunEvent——有序事件流，discriminated union 五个变体：status、progress、artifact、error、log。
  • ArtifactRef——对产物的稳定引用（pointer-only，body 存在生产 capability 自己的 store 里），kind 包含 result / report / trace / source / diff / file / custom。
层负责状态
RunSession / RunEvent / ArtifactRef 纯 type 模块 src/service/run-envelope/types.ts，无 class、无 top-level statement，形状由 test/run-envelope-core.test.ts 源码扫描锁定。 landed：T3A Core
InMemoryRunRecorder per-instance recorder（InMemoryRunRecorder.ts），无 module 单例；时钟 / ID 工厂由构造注入，事件轨迹可字节级复现。 landed：T3A Core
首个 adopter：VaultLint VaultLintRun.ts 是 T3B 首条走完整 envelope 的链路——起 run、发 progress、写 artifact、finish。 landed：T3B 首条链路
全量推广 Chat streaming / Search retrieval / Copilot review / AI Analysis / Harness agent loop / Knowledge Jobs 尚未接入。目前它们各自跑独立的 stream / session / trace 雏形（下一行"局部先例"）。 roadmap · T3 剩余
UI RunEvent projection UI store 只订阅 RunEvent、不拥有运行真相。 roadmap · T7
局部先例 LLMStreamEvent（provider 层归一化流式事件）、service/agents/harness/loop（AgentLoopResult + trace）、service/search/background/QuickSearchBackgroundRuntime（session 存活/取消）。 landed：三处独立雏形，未收敛到 RunEnvelope
为什么“统一外壳、不统一业务流程” 这条边界是 handbook §7 的核心判断。把所有链路强行改成同一 pipeline（例如“万物皆 agent loop”）会让 Search 被 agent overhead 拖慢、让 Chat 被 tool policy 复杂化、让 Copilot 丢掉 review-before-write 的语义。RunEnvelope 只承诺“可观察协议一致”——事件形状、cancel 语义、artifact 引用——业务流程各自保留。
当前的“状态真相分散”问题

读 feature 代码时会发现同一个 feature 的运行状态被切在多处：

  • AI Analysis session——一部分在 ReportOrchestrator、一部分在 ui/store/searchSessionStore。
  • Copilot review——在 action registry + panel props。
  • Chat streaming——在 chatDataStore。

这是 RunEnvelope 尚未推广的直接后果。RunEnvelope 核心类型 + InMemoryRunRecorder 已在 master（src/service/run-envelope/），但目前只有 VaultLint 接入。改这类 feature 时，尽量让 UI store 只做"投影"，把业务真相留在 service——T7 UI RunEvent Projection 会正式收敛这一层。

Ports：service 与宿主之间的窄接口

Peak 现在有一批 core/ports/* 接口，它们的形状不是随意的：每个 port 描述 service 需要的“一个能力”，不是把 Obsidian App 直接暴露给 service。这样做的直接收益是——service 可以在 Node 单测里跑（fake port），也可以在 desktop / mobile 两个 build 里换实现，同时不会把 Obsidian 特定 API 泄漏进 service 逻辑。

Editor-shaped port EditorCommandsPort、ChatRuntimeStatePort、ChatNavigationPort UI 状态与 editor 命令的窄适配；service 不再 import useChatViewStore。
Read/write split AmbientBriefingReadPort、SemanticGraphTraversalReadPort、SemanticLinkReadPort、AnalysisDocVaultWriterPort 读接口与写接口分开——只读消费者不会被误用为写入通道。
Ports vs Services Service 是行为，port 是接口。SearchClient 是 service（它内部有 SQLite + rerank + AI 拼接），AmbientSearchPort 是 port（它只是一个 search(context, ...) 契约）。同一个 SearchClient 可以被多个 port 用不同姿势包装（Ambient 用 AmbientSearchPort，Vault Lint 用另一个），这是 port 让 feature 之间保持独立演化的关键。

Owned Runtimes：谁拥有长期状态，谁负责释放

Peak 里“runtime”一词专指一段长期活着的、跨调用共享状态的执行单元：Ambient 的编辑器订阅、Vault Lint 的 SQLite 视图、QuickSearch background session、CopilotAction 的 custom prompt 缓存、VaultReview 的 fingerprint 缓存。它们不是 pure function，需要显式的 start() / dispose()。所有这类 runtime 都必须由 app 层拥有，通过 AppRuntimeRegistry 绑定和释放。

Runtime ownership 规则（CLAUDE.md） 这条规则是硬约束：capability 运行时必须在 app 层（main.ts / AppContext / app-owned runtime registry）组合和拥有。禁止在 service 层新增模块级 let currentRuntime = null + set/getRuntime；禁止把 AppContext.getInstance() 用作 service 层的依赖捷径。依赖只能通过 app composition、构造函数、port、或 RunEnvelope 边界传递。违规会在 code review 阶段被驳回。
fail-loud vs try-get 每个 runtime 在 AppRuntimeRegistry 上都有一对访问器：getXxxRuntime()（未绑定即 throw，用于“只应该在 runtime up 之后才被调用”的 service 消费者）和 tryGetXxxRuntime()（未绑定返回 null，用于可能在早期 boot 就 mount 的 UI provider）。选错一个会导致要么 UI 崩溃、要么静默失效。规则：service 层用 hard get，UI provider 用 try get。

Trace / Artifact / Usage：可观测性边界

Peak 的可观测性分三块，落地程度各不相同：

  • Trace——一次运行的事件流，用于 debug 和 golden test。当前在 Agent Harness 内部有雏形，尚未归一到 RunEvent 合同。
  • Artifact——产物的稳定引用，用于 review-before-write 和历史检索。当前只有局部实现（Copilot review history）。
  • Usage——成本 / token / 耗时的账本，用于预算与 dashboard。landed：UsageTrackingService + UsageOutcomeService + UsageOptimizationService 三件套 + Dashboard。
类别目标当前状态为什么值得单独一层
Usage 记录 provider / model / feature / cost / tokens / duration；驱动预算 alert 与 Dashboard。 landed：UsageTrackingService + chat.sqlite + 3 屏 Dashboard 成本可见性是产品差异化的一部分（BYOK 场景），必须在 core 就干净。
Artifact Answer / sources / report / patch / trace 的稳定引用与存储，供 review 与历史检索。 partial：CopilotReviewHistoryService、AI Analysis 结果落 Vault、Chat message 落 SQLite；无统一 ArtifactRef Copilot / AI Analysis 都需要“review-before-write”，没有统一 artifact 时每个 feature 各自写一套。
Trace 一次 run 的完整事件序列，含 tool call、backend 选择、context stack；供 golden test 与 UI trace inspector。 partial：service/agents/harness/trace；无跨引擎统一格式 没有 trace，Chat / Copilot 回归只能靠“手感”；有 trace 后可以 pin fixture + golden trace 进 CI。
为什么这三块不能塞进 core Usage / Artifact / Trace 都是可选能力：mobile 上 Usage 只记 in-memory，Trace 在生产可以关，Artifact 只有 review-heavy 的 feature 需要。它们的接线属于 service+app 层的 concern。core 只提供类型和 port（UsageRecordedViewEvent、ProgressReporterPort），实现和存储由 service+app 层完成。这条边界不遵守，会把 SQLite 依赖打进 core。

No Dual System：重构的硬约束

Handbook §3 决策 6 定死了一条规则：禁止双系统双代码共存。旧入口（Command id、view type、public API 名字）可以短暂保留为 facade，但业务实现只能有一套。每次重构任务包都必须回答：删掉了哪个旧实现？哪个旧状态真相被移除？同一能力是否还有两条运行路径？

这条规则不是洁癖，是成本控制——Peak 的代码库已经足够大，双系统状态会让 test 数量翻倍、认知负担翻倍、bug fix 需要在两处同步。以下是历史上最常见的两种违反姿势，读代码时警惕这些反模式。

反模式典型触发正确做法
“新架构 + 旧架构并跑” 先搭一套新 RunSession，让新 feature 走新架构；旧 Chat/Copilot 继续走 service-manager，说“等重构完再切”。 选一条链路（handbook 建议 doc.review.current 或 vault.search）先完整迁移，旧实现同任务包内删掉或掏空。
“旁挂 registry” 已有 CopilotActionRegistry，又新起一个 CopilotCapabilityRegistry，两个各自注册一半。 先在旧 registry 上加“capability manifest”字段，让新 feature 用同一入口注册；旧字段最后统一迁除。
“service 层 singleton + app 层 runtime 双持有” Owned runtime 落地后，service 里还留一个 Xxx.getInstance() 作“兼容层”。 Owned runtime 落地当次就必须删旧 singleton 或改成薄壳 forwarder；不允许两条状态真相长期并存。
当前的诚实状态（T13 之后） 上一代 service-side singleton 已在 2026-07 一次性清完：IndexService、MCPClientManager、SkillRegistry、CapabilityRegistry、UsageTracking/Outcome/Optimization 全部由 AppRuntimeRegistry 拥有并在 clearForUnload 里释放。service-manager.ts（AIServiceManager）从来就不是 singleton；旧版这段文字把它误列了。当下不存在"service 层 singleton + app 层 runtime 双持有"的兼容层——每个 runtime 只有一条状态真相。

维护规则

这页容易变成“架构名词表”，然后半年后跟代码脱钩。改架构级 API 时按下面几条来。

新增 runtime = 5 处同步。
  1. Port 接口 — 定义在 core/ports/<Xxx>Ports.ts。
  2. Runtime 类 — service/<xxx>/<Xxx>Runtime.ts，只 impl 接口，不 import 任何 app-shell。
  3. Compose 站 — app/<xxx>/compose<Xxx>Runtime.ts，装配 adapter。
  4. AppRuntimeRegistry — 加 set / get / tryGet / clear 四件套。
  5. main.ts — onload 绑定 + onunload clear。
任何一处漏掉，热重载会泄漏或用户看到 fail-loud。
新增 port 前先问“它是不是又是一个 App 转发”。 Port 必须用 feature 词汇描述能力，不是 Obsidian API 换个名字。若发现自己写的 port 有 getApp() / getWorkspace()，退一步——你想暴露的是 feature-shaped 能力，不是 host。
加 service 层新代码前问三件事。
  1. 我要不要 getInstance()——如果要，先看能不能改成 Owned Runtime。
  2. 我要不要 AppContext.getInstance()——如果要，改成构造函数注入或 port。
  3. 我要不要 useXxxStore——如果要，改成 UI 投影 port（参考 AmbientUiProjectionPort）。
动 CapabilityRegistry / SurfaceCapability 时同步 vocabulary。 当前六个用户词汇（Conversation / Research / Fast Lookup / Knowledge Index / Web Access / Safety）与 Settings / Onboarding / templates/config 深度耦合。加第七个 capability 意味着 Settings Overview、AI Setup、Setup Wizard、templates/config/settings.json 同时长格子；不能只在 service 侧加。
No Dual System 检查清单。 每次 PR 自问：这次改动是否新起了一套并行 registry / runtime / state 真相？如果是，旧的删了吗？如果 partial 迁移，能否保证下一次 PR 立刻收口？把答案写进 PR description。
路线图状态推进要同步这页 §roadmap。 当某个任务包从 planned → landed，回本文件更新对应行；status pill 从 gold 改成 green，evidence 列补上具体 file。否则新读者会以为架构还停在半年前。
