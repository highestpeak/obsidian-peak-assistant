这页解决什么

Peak Assistant 的搜索表面上是一套东西——用户按 Cmd+P 敲 Quick Search，Chat 里 @ 引笔记，Ambient Push 冒相关卡片，都指向“找到相关文档”。但底下有六层：文档扫描 → chunk 拆分 → FTS 索引 → 向量索引 → 图关系 → hub / community 补图。这份文档把这六层一次讲清楚，让改索引结构 / 加文档类型 / 排障的人有一张摊平的物理地图。

本文读者 要改 chunk 大小 / 加代码块处理 / 接入一种新文档类型（PDF、Excalidraw、Canvas…）的维护者；诊断“搜不到 / 只出关键词 / semantic 档不可用”的排障者；准备迁移 SQLite schema 的人。
本文不做什么 不讲查询侧：query parser、weighted RRF、rerank、highlight——那是 12 Search。不讲 Settings UI 的档位开关、AI Analysis 保存路径——那是 04 Configuration。不讲 provider embedding endpoint 怎么绑定——那是 04 的 activeEmbeddingConfig 章节。

两个 SQLite 库

Peak Assistant 在 <Vault>/A-control/PeakAssistant/DataStore/ 下开两个文件：vault.sqlite 和 chat.sqlite。名字暗示了业务分工，但表的分布并没有“搜索全在 vault、聊天全在 chat”那么干净。

vault.sqlite search store

常量
VAULT_DB_FILENAME（constant.ts）
Tenant

装什么
Vault 内所有被扫描笔记的 FTS / chunk / embedding / graph / hub / lint / ambient log / structural analysis——即“用户笔记体”索引。

chat.sqlite meta store

常量
CHAT_DB_FILENAME
Tenant
tenant = 'chat'
装什么
Chat project / conversation / message / star / resource；AI analysis 记录；query pattern；tag suggestion；usage_log + usage_daily + usage_outcome；harness_reflection；以及 chat tenant 的一整套 index 表（chunk / embedding / mobius_node / mobius_edge）。
与 04 的 Vault layout 对照 04 的 Vault 里长出什么 把 vault.sqlite 描述成“搜索 / embedding / graph”、chat.sqlite 描述成“会话历史 / usage log”。这是简化说法：chat.sqlite 里也带一整套索引表（doc_chunk、embedding、mobius_node、mobius_edge 都在 SqliteStoreManager.init() 里以 chat tenant 起了一份），用于把聊天历史当成“可以被搜索的文档”接入 hub / cross-search。tenant 是运行时切换（getIndexedDocumentRepo('chat')），schema 是同一份 Database interface。

为什么不合并？分库是为了让用户笔记的重建和聊天历史 + 用量数据的保留解耦。Rebuild vault 索引不会踩 chat.sqlite；反过来用户删除会话不会触发 vault 索引重扫。两库之间没有 foreign key，跨库的引用（比如“某条 message resource 指向 vault 里的笔记路径”）用字符串路径连——不做 join，只做 lookup。

<Vault>/A-control/PeakAssistant/DataStore/ ├── vault.sqlite # 用户笔记全部索引；tenant='vault' ├── vault.sqlite-journal # SQLite 事务日志（正常） ├── vault.sqlite-shm/-wal # WAL 模式副产品（若启用） ├── chat.sqlite # 会话 + 用量 + chat tenant 索引 └── ...

读图：fast 挡完全不出网——纯本地 FTS + 图构建，是所有档位的地基。semantic 才开始调 embedding endpoint。full 再加两轮 LLM 富化（tags + 长短摘要）+ hub 发现 + 全量 Mobius 维护 + structural analysis。cascade_debt 是三档共通的机制：fast 挡把“待补语义边 / 待重算 hub”写进 debt 表，semantic / full 挡的定时任务负责消费。

Reason vs Level 两个维度。indexDocument() 收的是 IndexDocumentOptions，但常用入口有两个：一个是运行时的 IndexDocumentReason（listener_fast / startup_scan / manual_full / hub_maintenance / vector_enrich_only / llm_enrich_only），一个是 Settings 里的 IndexLevel（fast / semantic / full）。前者是为什么这次索引，后者是用户当前的档位。defaultIndexDocumentOptionsForLevel('semantic') 就是在 listener_fast 基础上打开 includeEmbeddings；'full' 直接等价 manual_full。

为什么要 markPending 标志。当档位是 fast 但用户可能升到 semantic / full，索引跳过 embedding / LLM 时会在 mobius_node.attributes_json 上标 vector_pending / llm_pending。之后 Advanced 面板执行 “Update index” 或 IndexInitializer.performStagedFullIndexing() 时，IndexService.runPendingVectorIndexEnrichment() / runPendingLlmIndexEnrichment() 就按这个标志扫过一遍，只补需要补的文档，避免全量重跑。

Full 挡的 4 步流水线（IndexInitializer.performStagedFullIndexing()）：Step 1 FTS（listener_fast options 跑所有文档）→ Step 2 Vector（runPendingVectorIndexEnrichment 消费 vector_pending）→ Step 3 LLM（runPendingLlmIndexEnrichment 消费 llm_pending）→ Step 4 Graph maintenance（runMobiusGlobalMaintenance 跑 tag_doc_count → degree → PageRank → semantic PageRank → semantic edges → folder hub stats）。任一步都可以带 IndexErrorHandler，返回 continue / retry / cancel——错误从 embedding 报出来一次不至于把整轮索引废掉。

Chunking 细节

Chunking 有两层保护：loader 层用 LangChain 的 RecursiveCharacterTextSplitter，IndexService 侧再用 enforceChunkLengthWithOverlap 做最终守门。Loader 层意图是“按语言 / 段落切”，safeChunking 意图是“embedding input 不能超”。

字段（ChunkingSettings）默认作用UI 露出
maxChunkSize 1000 单 chunk 字符上限（loader + safeChunking 都用这个）。 Knowledge Index tab
chunkOverlap 200 chunk 之间的重叠字数，保证跨 chunk 的语义连续。safeChunking 会 clamp 到 [0, maxChunkSize - 1]。 Knowledge Index tab
minDocumentSizeForChunking 1500 文档小于这个字数直接整篇当一个 body_raw chunk，不走 splitter。 不露出（data.json）
skipCodeBlocksInChunking false true 时会用 codeBlockPlaceholder 替换 fenced code block，避免代码文本污染 embedding。 不露出
codeBlockPlaceholder "\n\n[code omitted]\n\n" 替换字符串。 不露出
maxCodeChunkChars 0 0 = 完全省略；>0 = 保留前 N 字符后截断。 不露出
embeddingModel — legacy 遗留；现在真正生效的是 activeEmbeddingConfig（04 定义）。 不露出

Loader 侧的两条路径。BaseDocumentLoader.chunkContent()（src/core/document/loader/BaseDocumentLoader.ts）是通用路径：new RecursiveCharacterTextSplitter({ chunkSize, chunkOverlap }).createDocuments([content])，得到 body_raw 类型的 chunks。MarkdownDocumentLoader 走 RecursiveCharacterTextSplitter.fromLanguage('markdown', ...)，多一层 markdown 结构感知（headers / lists 优先作为切点）。JsonDocumentLoader 用普通 splitter，但 loader 里把 JSON 结构先扁平化成文本。所有 loader 最终都调 assembleIndexedChunks()（src/core/document/loader/helper/assembleIndexedChunks.ts），把 body_raw 主体 + LLM 短摘 + LLM 长摘（可能切片） + TextRank 显著句合并成最终 chunk 数组。

safeChunking 是 embedding 侧的最终守门。enforceChunkLengthWithOverlap()（src/service/search/index/helper/safeChunking.ts）遍历 loader 返回的 chunks，超长的用 findSplitPoint()（优先落在 \n / 空格 / \t）+ overlap 二次切。每个切片重新生成 chunkId，之后统一 reindex chunkIndex。这一步确保 embedding provider 不会因为单个巨型 chunk 崩掉（尤其是 Markdown 内嵌 base64 图片、超长 code block 时）。

加新文档类型时的最小工作量 继承 BaseDocumentLoader；实现 getSupportedExtensions()、readFile()；如果源是二进制（PDF、图片、Word），override getContentForChunking() 用 cacheFileInfo.content（缓存的文本表示）。chunkContent() 不用重写——只要 chunk 长度守门跑到位，safeChunking 会兜。然后：注册到 DocumentLoaderManager；在 SearchSettings.includeDocumentTypes 加一个开关；settings.json 里加对应的 vocab；ignorePatterns 判断是否需要默认排除。

Embedding 与 sqlite-vec

Embedding 从两条视角看：调 provider 的 embedClient，和 写入 vec_embeddings 虚表。前者是 OpenAI 兼容的 POST {endpoint}/embeddings；后者是懒建维度的 sqlite-vec 虚表。

调用侧：embedClient.ts

入口 embedTexts(texts: string[]): Promise<number[][]>（src/service/search/embeddings/embedClient.ts）。它做四件事：从 ProfileRegistry.getActiveEmbeddingProfile() 取 profile（fallback 到 getActiveAgentProfile()）；toEmbeddingConfig() 生成 { endpoint, model, apiKey }；POST 到 ${endpoint}/embeddings body { model, input: texts }；把 data.data[].embedding 拆成 number[][] 返回；顺带把 token 用量通过 setEmbeddingUsageReporter 注册的 reporter 上报（feature: 'indexing', action: 'embed'）。

Reporter 是 late-bound sink。main.ts 在 boot 时调 setEmbeddingUsageReporter(...)，reporter 里的 report() 会把用量写进 usage_log（chat.sqlite），进而累计到 Usage Dashboard 的 “indexing / embed” 行。没绑 reporter 时 embed 仍然工作，只是不上报。

存储侧：embedding + vec_embeddings

embedding 表是普通 SQLite 表，存 BLOB 副本 + 元数据（doc_id、chunk_id、chunk_type、content_hash、embedding_model、embedding_len）。vec_embeddings 是 sqlite-vec 提供的vec0虚表，只有 rowid + float[N]。两张表通过共享 rowid 关联——vec_embeddings.rowid 就是 embedding.rowid，避免映射表。

为什么需要虚表。SQLite 的 B-tree / Hash 索引只能处理标量。多维距离（cosine / euclidean）+ HNSW/IVF 近似最近邻只有虚表能提供。ddl.ts 里那段长注释（“VEC0 VIRTUAL TABLE EXPLANATION”）就是说这件事，代码在 src/core/storage/sqlite/repositories/EmbeddingRepo.ts。

维度懒建。vec_embeddings 不在 migrateSqliteSchema() 里创建——因为不能 hardcode 一个维度（openai-embedding-3-small 是 1536，bge-m3 是 1024，其它 provider 各异）。EmbeddingRepo.ensureVecEmbeddingsTable(dim) 在第一次插入时才 CREATE VIRTUAL TABLE vec_embeddings USING vec0(embedding float[${dim}])。

换 embedding 模型 = 重建 vec_embeddings 当写入维度和已存在的 vec_embeddings 不一致（比如从 1536 换成 1024），recreateVecEmbeddingsTable(newDim) 会 DROP TABLE vec_embeddings 重建。vec 表数据丢失，但 embedding 元数据留着——之后需要用户走一次“Rebuild vector”把 BLOB replay 回 vec 表。这是有意的取舍：BLOB 是安全网，vec 表是可再生的索引。

Chunk 类型冗余。embedding.chunk_type 冗余了 doc_chunk.chunk_type，理由写在 ddl.ts 注释里：Redundant copy of chunk_type for fast KNN filtering; SSOT is doc_chunk。SearchClient 在做 semantic doc→doc 查询时按 SEMANTIC_CHUNK_TYPE_ORDER（summary_short > summary_full > salient_textrank_sentence > body_raw）优先返回摘要类命中；SEMANTIC_EDGE_CHUNK_TYPE_WEIGHT（1.25 / 1.15 / 1.1 / 1.0）给不同 chunk 类型的 KNN 分加权，生成 semantic edges。

来源

写入

何时算

PPR（Personalized PageRank）是查询时的，不是索引时的。SearchSettings.enablePPR 默认 true。查询时 SearchClient 拿 query 命中的 seeds 做一次 personalized walk，把图上强相关但 keyword / vector 都没命中的笔记加权提升——这是读侧的行为，索引期间只保证 pagerank / semantic_pagerank 列已经算好，PPR 本身不写库。

Semantic edges 是 KNN 的物化视图。SemanticRelatedEdgesRebuildService（helper/semanticRelatedEdges.ts）走 vec_embeddings 的 KNN，按 SEMANTIC_EDGE_CHUNK_TYPE_WEIGHT 加权聚合到 doc→doc 边。为什么物化？因为查询时反复做 KNN 不划算；把结果写成边之后，PPR / rerank / semantic PageRank 全都能只读边就能算。mobius_node.semantic_edges_version 是幂等标记，每次某个 doc 的 semantic edges 被重建就 += 1。

Tenant 与 ignore 规则

IndexTenant = 'vault' | 'chat'（src/core/storage/sqlite/types.ts）。tenant 决定 SqliteStoreManager 返回哪个数据库的同名 repo（getIndexedDocumentRepo(tenant) / getDocChunkRepo(tenant) / getEmbeddingRepo(tenant) / getMobiusNodeRepo(tenant) 等）。schema 完全一致，只是文件不同。

路径 → tenant 的判断

getIndexTenantForPath(path)（indexService.ts）逻辑非常小：

  1. 如果路径落在 getAIHubSummaryFolder(rootFolder) 之下（Hub-Summaries），tenant 是 vault——即使它物理位置在 ChatFolder/ 之内。理由是 hub 摘要虽然写在 chat 根目录下面，但功能上是 vault 索引的一部分。
  2. 否则如果路径以 settings.ai.rootFolder（默认 ChatFolder）为前缀，tenant 是 chat。
  3. 其它路径都是 vault。

Ignore patterns 是是否入库的开关

SearchSettings.ignorePatterns（默认包含 .git/、node_modules/、.obsidian/、A-control/、*.tmp、*.log、.DS_Store 等）由 DocumentLoaderManager.shouldIndexDocument() 消费。命中的路径连 chunk 都不生成，也不入 mobius_node。

A-control/ 默认排除意味着 DataStore 不会自己吃自己 A-control/PeakAssistant/DataStore/*.sqlite 是二进制文件，一旦被误当 markdown 扫，chunking 就会跑出天量垃圾 chunk。默认 ignorePatterns 里的 A-control/ 就是防这个。改 dataStorageFolder 到别的位置时必须给新位置加对应 ignore，否则 rebuild 会崩。

AI Analysis 文件夹的选择性 exclude。aiAnalysisAutoSaveFolder（默认 ChatFolder/AI-Analysis）在 aiAnalysisExcludeAutoSaveFolderFromSearch=true（默认）时不参与 Local Search / Graph 的召回——避免 AI 分析结果反过来污染下一次分析。它跟 ignorePatterns 的区别是：AI Analysis 文件夹依然被索引（chunk / embedding / node 都会建），只是查询侧过滤掉。这个区别很重要——不然重启后 hub 引用就断了。

增量、Rebuild、Cascade

索引不是一次性事件，是一个持续跑的反应系统。文件改动、Obsidian 重启、用户点 “Rebuild index” 都会触发不同粒度的重扫。

增量：checkAndUpdateIndex()

Obsidian 启动时 IndexInitializer.checkAndUpdateIndex() 跑一次（04 里说的 “Auto-index on startup”）。逻辑：

  1. 查 index_state：如果没建过 index，autoIndex 开着就跑 performFullIndexing()；关着就弹提示让用户手动跑 Rebuild。
  2. 建过：scanForIndexChanges() 扫 vault，用 IndexedDocumentRepo.batchCheckIndexed() 比 mtime；mtime 不同的用 contentHash 再核一次——因为 Obsidian 的 mtime 有时会因为 sync 抖动，hash 才是权威。
  3. 命中变更的进入 performIncrementalIndexing()；同时并发跑 checkAndDeleteRemovedFiles()（vault 里没了但 index 里还在的路径调 IndexService.deleteDocuments()）。
  4. 如果没有增量且 isMobiusMaintenanceRecommended() 说该维护了，跑 runMobiusGlobalMaintenance(['vault', 'chat'])。
  5. Startup 尾巴：HubRegenService 检查 hub_regen_queue.pendingCount()，非零就后台清。

indexRefreshInterval（默认 5000ms）是运行时的 debounce——用户在编辑器里输入时不至于每敲一个字就 reindex。

Rebuild：performStagedFullIndexing()

Advanced tab 的 “Rebuild index” 或用户显式选 full 挡时调 performStagedFullIndexing(level='full', onError?)。4 步流水线（见 上一节）。可以中途取消——IndexService.isCancelled() 被观测就退出；onError handler 决定 continue / retry / cancel。fast 挡的 rebuild 只跑 Step 1 + Step 4（graph 维护）。

Cascade：文档变更的副作用债

CascadeChangeDetector（service/search/index/cascade/）在 indexDocument() upsert 之后跑一次差量比较（对比 PreIndexSnapshot）。检测到的变化按类型入队 cascade_debt：

debt_type触发Worker 动作
semantic_edgedoc 内容或 embedding 变了。SemanticRelatedEdgesRebuildService.rebuildIncrementalFromDocIds([...])。
degree_refreshdoc 的 references 数量变了。重算 doc_incoming_cnt / doc_outgoing_cnt。
mermaid_overlay被 mermaid 图引用的 doc 变了。让 mermaid overlay 重画。
hub_invalidatedoc 是某 hub 的 member。把 hub_regen debt 入队（延迟消费）；hub_stale_since 打时间戳。
folder_statsdoc 所在文件夹发生结构变化。重算 folder_cohesion_score。

UNIQUE INDEX (tenant, target_id, debt_type) WHERE processed_at IS NULL 是天然去重——同一 doc 短时间内改多次只会入一次 debt。CascadeWorker 按 priority 排空。这套设计让 fast 挡的 indexDocument() 保持轻量：昂贵的语义边、hub 重算不阻塞主索引，进 debt 表异步跑。

1. better-sqlite3 加载失败

症状：启动时弹 “Peak Assistant: SQLite component failed to load. Search and indexing features are unavailable.”（unavailableReporter 触发）。SqliteStoreManager.isInitialized() 返回 false，任何 getXxxRepo() 都抛 “SqliteStoreManager not initialized”。

原因：better-sqlite3 的 native binding 与当前 Electron ABI 不匹配。BetterSqliteStore.checkAvailable() 先跑 NativeModuleManager.ensureCompatible() 尝试自动下载对应版本；失败后按 getPossiblePaths() 列的多路径 fallback 加载；全都失败才报 Notice。修复：npm install better-sqlite3 后 electron-rebuild（或 README 里的对应脚本），重启 Obsidian。

2. sqlite-vec 扩展未加载

症状：insert 到 vec_embeddings 时报 no such table: vec_embeddings；isVectorSearchEnabled() 返回 false；semantic / full 挡不可用但 fast 挡照跑（因为 FTS 不依赖 vec）。

原因：BetterSqliteStore.tryLoadSqliteVec()（better-sqlite3-adapter/BetterSqliteStore.ts）尝试 require('sqlite-vec')；失败时 console 会 warn “sqlite-vec extension is not installed / Failed to load”。sqlite-vec 依赖平台特定 package（sqlite-vec-darwin-arm64 / sqlite-vec-darwin-x64 / sqlite-vec-linux-* / sqlite-vec-windows-x64），未安装或安装错平台包都会挂。修复：npm install sqlite-vec 让它自动装对应平台 package。

3. Embedding provider 不可用

症状：embedTexts() 抛 “No embedding profile configured”（未绑 activeEmbeddingConfig）、“Embedding endpoint not configured on active profile”（profile 没 embedding endpoint）、或者 Embedding API error 401 / 429 / 500。Vector enrichment 时进入 onError handler，用户选 continue / retry / cancel。

修复：Settings → AI Setup → Knowledge Index 换 profile；或到 Advanced tab 直接看 profile 定义；如果是 Ollama 本地，确认 ollama serve 起了。选 retry 时 runPendingVectorIndexEnrichment 会重跑，只重跑还未标记为已完成的 doc。

4. Embedding 维度不匹配

症状：切了 embedding model（比如 openai text-embedding-3-small 1536 → bge-m3 1024）后，写 vec_embeddings 抛 Expected 1536 dimensions。

修复：EmbeddingRepo.recreateVecEmbeddingsTable(newDim) 会 drop 重建 vec 表（embedding BLOB 元数据保留）。之后跑 runPendingVectorIndexEnrichment() 或 performStagedFullIndexing() 让所有向量重新写入新维度。

5. Hub 陈旧 / 结果不更新

症状：Hub summary 里显示的相关笔记还是老的，或搜索结果里 hub 相关笔记权重不对。

诊断：SELECT COUNT(*) FROM hub_regen_queue WHERE status='pending'；或 SELECT hub_path, hub_stale_since FROM mobius_node WHERE hub_stale_since IS NOT NULL。修复：HubRegenService.getInstance().processQueueNow()（Advanced 面板 Diagnostics 或 devtools console）。或走一遍 Rebuild。

6. DataStore 文件损坏

症状：open db 直接抛 “database disk image is malformed”，或搜索永远转圈。

修复：先备份 vault.sqlite / chat.sqlite（含 -journal / -wal / -shm）。删除 vault.sqlite：下次启动 autoIndex=true 会全量重建（大 vault 需要数分钟）；autoIndex=false 会提示手动。删除 chat.sqlite 会丢会话 metadata + 用量 log，但对话本体（markdown）在 ChatFolder/ 里，可以按需重扫恢复元数据。删之前想清楚 usage_log 是不是要留——那是 Budget 阈值和 Dashboard 唯一的历史。

不要直接手改 SQLite 文件 用外部 SQLite CLI 打开 vault.sqlite 只读查表是可以的（诊断很有用），但 写入 会破坏 FTS5 / vec0 虚表的一致性、破坏 Kysely 的 statement cache。所有变更必须走 SqliteStoreManager 提供的 repo。
