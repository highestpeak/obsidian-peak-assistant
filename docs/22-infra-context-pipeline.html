22 · Infra · Context Pipeline · 让四个 surface 说同一种上下文

Chat、Agent、Ambient、Command Gateway 在同一份原语上装配上下文。

这份文档回答一个问题：如果你要新加一个 AI surface，怎么让它跟已有的 Chat / Agent / Ambient 用同一套上下文规则，而不是重新发明一套 prompt 系统？

结论前置：Peak 目前没有一个叫 ContextPipeline 的共享大模块，而是一组共享原语 + 每个 surface 自己的装配器。共享原语有五件：

  • PromptService
  • LLMStreamEvent
  • SessionContextService
  • templates/config
  • ModelCapabilities

这份文档把共享的和分歧的部分摊开。

这页解决什么

Peak Assistant 里“把东西喂给模型”的地方不止一处。Chat 视图有 ContextPipeline；自研 Agent Harness 有 ContextManager 加 MemoryBlock；Ambient Push 只是渲染两条 prompt 模板；Command Gateway 还没落地。四个 surface 都自己写自己的装配逻辑，但它们必须落到相同的下游：同一份 provider adapter、同一份 LLMStreamEvent、同一份 templates/config/、同一个 SessionContextService。这页就是把这条“共同下游”和四条“各自上游”摊开。

本文读者 正在设计新 AI surface 的维护者（Copilot lane、Vault Intelligence、Command Gateway、未来任何 headless job）；要改动跨 surface 原语（Prompt、LLMStreamEvent、SessionContextService）的人；想搞清楚“为什么 Chat 有 8 个 slot，Agent 有 MemoryBlock，Ambient 却只有两条 prompt”的人。
本文不重复解释 Chat 侧的 slot 顺序、预算细节、mode 分支 — 那是 11 Chat Context。Agent 的 tool loop、tier escalation、hook 生命周期 — 那是 21 Agent Harness。Provider SDK 接线、模型注册表、Vercel adapter — 那放在 24 Provider Model Runtime（未写）。这里只讲跨 surface 的形状。
形态诚实：目前没有单一 ContextPipeline 拥有者 早期 spec 曾设想 Chat / AI Analysis / Copilot / Followup / Ambient 都统一走一个 ContextPipeline.assemble(profile, ctx)。当前形态更稳的是：Chat 用 slot pipeline，其它 surface 走各自装配器，并共享 PromptService / RunEnvelope / LLMStreamEvent 等原语。所以本文描述的“共享”是共享原语，不是共享装配器。设计边界见 § 设计边界。

共享原语：所有 surface 都得走这条底盘

虽然装配器各写各的，但四个 surface 最终喂给模型的东西必须落到一组共享原语。改这些原语就是在改所有 surface 的语言。

装配好之后怎么进模型

Chat、Agent 与 Ambient 都由 Peak Harness 拥有运行语义，但输出形状按 surface 不同：Chat / streaming caller 消费 LLMStreamEvent，AgentLoop 保留 step + trace，Ambient 只取最终文本。Provider adapter 只执行模型推理。

Chat 把 ContextPipeline.assemble 的最终消息、buildChatTools 生成的工具与 output control 交给 harnessStreamChat。它用单 tier TierController 调 runAgentLoop，当前固定 Conversation 选中的 model 且关闭 escalation；Vercel provider factory 只创建底层 LanguageModel。

Agent Harness 直接走 generateText({ model, system, messages, tools, stopWhen: stepCountIs(1) }) — 一次 step 一个 generateText 调用；tool 用 ai-sdk 的 tool() 包装，返回值是 ToolResult envelope 的 JSON。TraceBus 把 step / tool_call / tool_result / context_compacted / escalate emit 出去。

Ambient Explanation 走最短路径：adapter 先 resolveSlot('fast')，再调用 runHarnessText(..., maxSteps: 1)，最后向 AmbientExplanationService 返回 string | null。它不需要 tool 或多轮历史；PushCard 再负责 line-clamp。

每个 surface 的隔离：session / conversation / push / capability

四个 surface 有不同的“单位”。Chat 的单位是 conversation（用户视角是一段对话）；Agent 的单位是 loop run（用户视角是一次分析）；Ambient 的单位是 push（一次 trigger 一条建议）；Command Gateway spec 里是 command invocation。四个单位各自的存储、TTL、并发规则都不一样。

这里最容易踩的一坑是：Ambient 不能塞进 Chat 的 conversation 里。它没有 conversation id、没有历史 message 列表，也不该被 Chat prompt picker 看到。反过来，Chat 也不应该直接读 push 表；如果 Chat 想知道“最近推了什么”，应该走 SessionContextService 的 WorkingContext.recentActivities，而不是绕过它去读 SQLite。

SessionContextService.getInstance() 是 singleton — 不是每 surface 一个 这个 singleton 是四个 surface 共享的“最近工作现场”。它读 mobius_operation 表、订阅 MESSAGE_SENT / SEARCH_QUERY / AI_ANALYSIS_COMPLETE event、监听 file-open。新 surface 想产生活动，请 emit event（走 eventBus）或调 recordActivity()，不要再实例化第二个 SessionContextService。

典型失败模式

跨 surface 上下文问题一半来自新加装配器时忘了对齐共享原语，另一半来自模型能力和预算不匹配。

Over-budget: 明明模型上下文很大，还是被截断。 Chat：ContextPipeline.resolveBudget 需要 modelCapabilities.maxCtx。如果新加的 provider 忘了填 maxCtx，会 fallback 到 200000 — 对小模型可能爆窗口。Agent：ContextManagerConfig.maxTokens 传的是当前 tier 的窗口；tier 切换时要重建 ContextManager，不然会用旧窗口。
Missing prompt template：surface 起来了但模型静音。 PromptId 找不到 template 时，TemplateManager.render() 抛错。Ambient 的 AmbientExplanationService 会 catch 并返回 null（用户看不到解释，但也不 crash）；Chat 的 SystemPromptSlot 会让 build 失败并被 Promise.allSettled 吞掉（slot 内容为空）。新增 PromptId 一定要在 templates/ 里放对应文件 + fallback。
Provider capability mismatch：模型不支持 tool call。 Chat agent mode 会仍然把 tools 传给 vercelStreamChat，能不能用取决于 provider 的 tool-call 支持。Agent Harness 更明确：generateText({ tools }) 在不支持 tool 的 provider 上直接 fail。更稳的做法是在装配层先做 capability probing，再决定是否把工具交给 provider。
SessionContext 未初始化：新 surface 装配时 slot 建不起来。 SessionContextService.getInstance() 首次调用需要 app + eventBus + themeQueryText。主 main.ts 已经在启动时 init 一次；如果新 surface 在 main.ts 之前的启动阶段跑，会抛 “requires app, eventBus, and themeQueryText on first call”。解决：装配前保证 AppContext 已就绪。
LLMStreamEvent 不被 UI 认识：加了新 tool-call 但 ToolCallSummary 空白。 ToolCallSummary.tsx 有一份 label + icon 的字典（例如 context-pipeline:assemble）。加新 tool 名字要同步这份表；否则 UI 会显示空白 pill。

设计边界：哪些不应统一

本页所有代码事实都来自 src/。下面列的是容易误读的边界：哪些只是背景设计，哪些是当前维护时应该遵守的形态。

为什么不立刻统一 Chat 用 slot、Agent 用 MemoryBlock、Ambient 用直接 render — 这些差异不是历史包袱，是形态不同。Chat 需要多 slot，因为它要装 conversation history + focus folder + resource；Agent 需要 MemoryBlock，因为它要在 loop 每一步动态注入；Ambient 只需要两条 prompt，因为它不做对话。强行统一到一个 assemble(profile, ctx) 会引入抽象税。当前立场：把原语做扎实（PromptService / LLMStreamEvent / SessionContext / templates/config），装配器保留形态自由。Command Gateway 也保持 routing 层，不在 gateway 层装 context。

为什么不收敛成一个 ContextPipeline

Chat / Copilot / Analysis / Harness 都可以接上 RunEnvelope 记录 observability，但这不代表它们应该共用同一个 context 装配器。RunEnvelope 解决“运行中发生了什么”，Context assembly 解决“模型这一步该看什么”。这两件事的边界要分开。

Surface装配范式（保留）为什么不能变成 slot-based
Chat 8 slots @ ChatProfile · SlotBuildContext.sessionContext 基线，不动。
Agent Harness MemoryBlock[] + ContextManager.compactIfNeeded（每步注入） Agent 每步都可能新增 block（tool result、subagent 结论），slot 模型的 "一次组装" 不适配 loop 结构。硬套只会把 SlotBuildContext 改成动态可变，等于重写 slot 模型。
Ambient 2 条 prompt 模板 + 段落/链接直接 render 没有对话、没有历史消息、没有 tool call。装 slot pipeline 只是把 200 字 prompt 塞进 8 slot 框架，抽象税 > 收益。
Command Gateway Per-CapabilityManifest（surfaceOpenStrategy 或 backend adapter） Gateway 是命令→能力→backend 三段映射器，不做装配。产 token 的 capability 由 backend adapter 走自己那条形态（Chat slot / Agent block / Ambient render）。Gateway 层强行装 context 会绕开 backend 契约。
Decision 我们收敛的是 observability（RunEnvelope + RunEvent + Artifact 记录方式统一）和 原语（PromptId / LLMStreamEvent / SessionContextService / templates/config）；我们不收敛装配器，因为 4 种形态本质不同。判断标准：如果两个 surface 的差异需要在 slot 模型上加 "特殊 flag"，那它们就不应该共用 slot。当前 4 种形态各自的 flag 全是特殊 flag。

维护原则是保持原语原地更新：新 prompt 进 PromptId，新 event 进 LLMStreamEvent，新 tenant 进 SessionContextService。不要为了“统一”把四种装配形态塞进同一个巨大参数对象。

影响到你的两种场景：写一个第 5 种 surface 时，别先问 "能不能复用 Chat pipeline"；先判断它更像 slot-based、memory-block、direct-render，还是 manifest-driven routing。看到旧 spec 里的 "Unified ContextPipeline" 字眼时，把它当成背景设计，不要等它变成共享大模块。

加新 surface 时的规则

如果你在写一个第五个 AI surface（例如 Copilot lane 想脱离 Chat 自己起一套、或者 headless job 想跑 agent），按这套规则来。

1 · 先判断形态：conversation / loop / one-shot。 多轮对话 → 复用 Chat 的 ContextPipeline，加一个 Profile（不是加 slot 到 ChatProfile）。多步 tool call → 复用 Agent Harness 的 runAgentLoop，塞 MemoryBlock。单次 render → 直接 PromptService.chatWithPrompt(PromptId.X, vars)，不要装 pipeline。
2 · 所有 prompt 走 PromptId / TemplateManager。 不要在 surface 代码里写 "You are an AI that..."。这违反 docs/conventions/configurability.md，也会绕开用户的 vault override 机制。新 prompt = 新 PromptId + templates/prompts/<id>.md + 代码里的 fallback 字符串。
3 · 所有流式产出走 LLMStreamEvent。 即使你的 surface 最终只想要一段字符串（像 Ambient），底下也要用 LLMStreamEvent — 让 adapter 折成字符串是 adapter 的事，不是 surface 的事。理由：trace / observability / UI 全部读这个类型。
4 · 用 ModelCapabilities 定预算，不要硬写数字。 无论走 Chat pipeline 还是 Agent ContextManager，预算都得从 modelCapabilities.maxCtx（或 tier 决定）来。硬写 maxTokens: 100000 会在用户切小模型时爆窗口。
5 · 想知道“最近做了什么”，走 SessionContextService。 不要 scan file-open、不要重扫 chat.sqlite。SessionContextService.getInstance() 已经维护了带 30 分钟衰减窗口的 WorkingContext.recentActivities；你要就直接读。要产生活动，emit ViewEventType 或调 recordActivity()。
6 · Capability run 记录走 RunEnvelope，但装配上下文不走 RunEnvelope。 看它的名字容易被误导。RunEnvelope 只装 “一次 run 的状态和产物”；prompt / messages / slots 不是它的职责。装配上下文用 PromptService + Slot / MemoryBlock，run 结果用 RunEnvelope。
7 · runtime 在 app 层拥有，不要在 service 层放模块 singleton。 见 CLAUDE.md § Runtime ownership。新 surface 的 runtime 要通过 AppContext / AppRuntimeRegistry 组装（参考 src/app/ambient/composeAmbientRuntime.ts）；不要在 service 里搞 let currentRuntime = null。
Anti-pattern：绕过 PromptService 直接调 provider 过去有几次“为了快”，surface 直接调 vercelStreamChat(messages, { system: 'hardcoded system' })。结果：用户改 vault prompt override 不生效、Curator 更换模型时这条路径没跟着切、i18n 契约破裂。所有走模型的路径都必须先经过 PromptId + TemplateManager；一个 PromptService.chatWithPrompt 的调用是最低门槛。
