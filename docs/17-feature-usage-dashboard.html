17 · Feature · Usage Dashboard · AI 用量 · 预算 · 有效性

看清 AI 花了多少 token / 多少美元 / 有没有真的帮上忙。

Usage Dashboard 是 Peak 唯一 回答“AI 到底给我带来了什么” 的界面。它把六件事放在同一个面板：

  • 每次 AI 调用的原始记录（token / 成本 / 时延 / feature 归属）
  • 按月 / 周 / 天的预算 pace，逼近上限时的告警
  • Provider × Model 的分布，看是不是被某个昂贵模型吃掉一半
  • Outcome funnel：调了 → 有下文 → 真被采纳，MPG（Model Per-Get）指标
  • History：可回溯的调用明细，能翻到“上次那笔 $0.4 是干什么的”
  • Optimization：curator 推的模型路由 / 阈值 / 静音建议，一键 Preview / Apply

这份文档讲 数据从哪来（AIServiceManager.emitUsage）、三张表怎么存（usage_log / usage_daily / usage_outcome）、六屏各自看什么、Optimization curator 的规则 vs LLM 双路径、以及 关掉这个功能的正确方式。

这页解决什么

Peak 有 6 个 feature 会主动调 LLM（chat、search_analysis、copilot、graph、indexing、internal，加上 skill agent 调用与 media_generation 媒体产物调用共 8 类）。用户一天下来 不知道 这些调用累计花了多少 token、多少钱、有没有真正落进笔记。Usage Dashboard 把这层黑盒打开：

核心结论 这个面板 只读——它从不主动调 LLM，也不改动任何 vault 文件。它做三件事：(1) 订阅 event bus 收 usage 事件写 SQLite；(2) 定时把 usage_log 的详情行汇总进 usage_daily；(3) 用聚合数据给六屏提供查询结果。Optimization 那屏是唯一可选调 LLM 的地方，规则 fallback 保证不联网也能出建议。
MPG（Model Per-Get）：这个面板最重要的一族指标 单看 token / 美元只回答“花了多少”；MPG 类指标回答 “这些钱换来了多少真正保存到笔记里的产出”。核心一条 cost per saved artifact：Σ(以 vault_save / copilot_accept / agent_file_emit 结尾的调用成本) ÷ 保存事件数。这条指标出现在 Overview 的 KPI 条，也出现在 Outcome Value 屏。
本文读者 想知道 Peak 有没有偷偷烧钱的 Obsidian 用户；正在调 Overview / Budget 屏 UI 的前端；想搞明白 为什么某个 feature 的调用没进 dashboard 的排障 agent。
本文不做什么 不重复 04 里 Budget / Safety 的设置界面说明；不覆盖模型定价（那是每个 provider 各自的事）；不讲 Agent Harness 的 trace UI（这里只用 sessionId 关联）。
规格有历史坍塌，本文写当前实现 2026-05-29 那一版 insights 认为“一板 BI dashboard 打不了 9 个 JTBD 中的 7 个”，主张把用量情报拆到 inline receipts / status bar / callout 多处。当前代码是 六屏 + inline receipt + status bar 混合的落地版本，本页按 代码事实 描述现状；未来 UI 变化在 roadmap 里追踪。

六屏各自看什么

Command Palette → Open Usage Dashboard 打开 UsageDashboardView。顶栏有时间范围切换（Today / 7d / 30d / All）和六个 tab。六屏不是六份数据——底层是同一份 usage_log + usage_outcome，只是切面不同。

屏回答什么核心组件数据来源
Overview
默认打开		 “今天 / 本周有没有异常？” 一屏见分晓 KPI 条（Budget pace + Context risk + Cost/saved + Calls）+ 推荐动作卡 + This week 三小图 useOverviewSnapshot()：getMonthlyPace + getCostPerSavedArtifact + getThisWeekTrio
Provider-Model “钱都去了哪个 provider / model？” Cost breakdown × 分布图 + model popularity 表 getModelDistribution / getCostBreakdown
Outcome Value “调用 → 有下文 → 真被采纳，漏斗窄不窄？” 三段 funnel + 每 feature MPG 分解 UsageOutcomeService.adoptedMessageIds + getCostByFeature
Budget Alerts “按当前 pace，月底会不会超预算？” Monthly pace bar + 阈值告警 getMonthlyPace(monthlyUsd, resetDayOfMonth)
History “上次那笔 $0.4 是干什么的？” 分页明细表 + feature 筛选 + expandable row getRecentCalls(range, feature, limit, offset)
Optimization “下个月省钱的行动清单？” Recommendation 列表 + Preview/Apply + scenario 选择 UsageOptimizationService.run(opts)
Overview 的四个 KPI 是可点的 Budget pace 点进去 = 跳 Budget Alerts；Context risk 点进去 = Chat Studio 打开 compact 面板；Cost per saved 点进去 = 跳 Outcome Value；Calls 点进去 = 跳 History。这不是装饰性 KPI，是 “看到不对劲就能直接跳到详情” 的入口。
Overview 的推荐动作卡 = Optimization 的前 3 条 推荐动作 这张卡不是新算的——它调 useOptimization() 拿全量建议，只显示前 3 条 impact = high 的。所以“看到卡 → 点 Optimization → 看到相同 3 条”不是 bug，是同一份数据的两个入口。

Media generation · run detail（Outcome Value 屏专段）

除了 LLM token / 美元，Chat 内媒体调用（image / image edit / video / music / TTS / transcription）也会以 feature='media_generation' 打进 usage_log。Outcome Value 屏底部的 Media generation · run detail 段把这些行渲染成一张明细表——每次调用一行。

字段来自哪里渲染语义
kind / outcome usage_log.action（image.success、video.failure、music.success、tts.success、transcription.success …）split 出来 outcome 三态：success / failure / unknown；failure 行展开显示 errorMessage。
route metadata.route（native / fal / auto→…） 缺失时显示 unknown——不静默假设。
provider / model usage_log.provider + usage_log.model 与 LLM 侧同 catalog；Sora native 显 openai + sora-2，fal veo 显 fal + fal-ai/veo3.1，等。
operation metadata.presetId / billingUnit image generate vs image edit、video vs music 通过 preset + kind 区分。
Estimated cost usage_log.cost_usd；metadata.costConfidence 恒 'estimated' 永远标 estimated——presets 是本地价格快照，不是 provider 结算账单。字段级不变量在 src/app/media/composeMediaGenerationService.ts 与 src/ui/view/usage-dashboard/hooks/useMediaLogs.ts 里锁死。
Job id metadata.jobId（async video / music / Sora） 点开可跳到 ChatArtifactReceipt 或 History 屏对应行。
"Cost is a preset estimate — never a settled bill" 这行文案是 media run detail 段的 header 副标题（src/ui/view/usage-dashboard/UsageDashboard.tsx L300 附近）。它防止用户把 preset 快照当成 provider 真实账单——preset 价可能过期、可能不含隐藏 fee、可能与 tier 折扣无关。要看真实账单必须去 provider dashboard。只有 未来某个 preset 显式把 costConfidence 翻成 'provider-reported' 时该行才不再打 estimated 徽标。
空态行为 当前时间范围内无 feature='media_generation' 的行时，媒体段显示 No media generation runs recorded in this range——不显示假 spinner，也不把 image / video / music 的 0 值堆成柱图假装有数据。要过滤 kind / route，暂时用 History 屏（Feature filter = Media generation）。

Music licensing 首次确认

music 生成的第一次 Confirm 前，ArtifactReceiptCard 出 licensing checkbox（Lyria SynthID 水印 + 分发平台 AI 披露 + USCO 版权口径 + fal ToS 链接）。确认写两处：

settings.ai.mediaDefaults.musicLicensingAccepted
包含 policyVersion + confirmedAt；同 policy version 内后续 music 请求不再重复弹窗。
ChatArtifactReceipt.metadata.musicLicensing
该 receipt 上标记接受时的 policyVersion，便于事后审计。policy version 若变（例如新加一条 SynthID 说明），下次 music 请求会重新弹窗。

关联入口 Settings 侧的媒体能力矩阵（Route × Kind × Operation 三维 + Validate 时间戳）在 Chat Studio UI/UX · Composer 与 Chat Context · 能力不可用时用户看到什么 里详解——Usage Dashboard 只展示结果，不承担配置界面。

谁在写 usage 记录

所有写入都走 event bus——service 层不直接摸 SQLite。这让 UsageTracking 能作为 可选 服务：关掉后调用方仍能正常跑，只是没人订阅事件。

emitUsage 的四种调用点

主要写入源在 AIServiceManager，每次 LLM 请求结束时打一条：

queryText()
一次性文本请求。成功后 emitUsage(usage, startMs, false, feature, action, sessionId)。
queryTextStream()
流式文本。最后一个 chunk 的 usage 累加后打点，isStreaming = true。
queryStream()
包含 tool use 的完整 stream；同样最后打一次点。
queryStructured()
结构化 output（zod 校验）。action 里带 schema 名，方便 History 屏识别。

Agent 调用（SDK harness）在 sdkAgentPool.ts L344 有独立 emit，feature: 'skill'。媒体调用（image / image edit / video / music / TTS / transcription）由 src/app/media/composeMediaGenerationService.ts 的组合根 emit，feature: 'media_generation'；成功 / 失败双路径都打点，成本恒标 metadata.costConfidence='estimated'。embedTexts（embedding 客户端）目前 没有 手动 emit——insights spec 里列作已知 gap，需要在 T13 之前补上。

成本是本地算的，不是 provider 传的 emitUsage 里的 costUsd 走 computeUsdFromUsage() + 本地模型 catalog 定价，所以：(1) 断网时也有成本估算；(2) provider 涨价 / 降价必须更新 catalog；(3) 缓存 token 与 reasoning token 的价格差异需要 catalog 支持——如果 catalog 里没写就按 input token 价近似。这条口径在 21 Harness 的 model catalog 里维护。

三张 SQLite 表

Dashboard 依赖三张表，属于 vault.sqlite（不是 chat.sqlite）。schema 在 src/core/storage/sqlite/ddl.ts L981-1031。

usage_log — 每一次调用的原始记录

写频繁读稀疏；带三个 index（created_at / feature / session）。compactBefore(cutoffMs) 定期把过期行汇进 usage_daily 后 DELETE。

usage_log (
  id                INTEGER PRIMARY KEY,
  session_id        TEXT,
  feature           TEXT,          -- chat | search_analysis | copilot | graph | indexing | internal | skill | media_generation
  action            TEXT,          -- 'queryText' | 'stream' | schema name for structured
  provider          TEXT,
  model             TEXT,
  input_tokens      INTEGER,
  output_tokens     INTEGER,
  cached_tokens     INTEGER,
  reasoning_tokens  INTEGER,
  cost_usd          REAL,
  duration_ms       INTEGER,
  is_streaming      INTEGER,
  created_at        INTEGER,       -- monotonic ms
  metadata_json     TEXT
);

usage_daily — 每日聚合

写稀疏读频繁；unique constraint (date, feature, action, provider, model) + index date。History 屏之外的所有屏都是从这张表查——它是 dashboard 的 “热数据”。

usage_daily (
  date              TEXT,          -- YYYY-MM-DD
  feature           TEXT,
  action            TEXT,
  provider          TEXT,
  model             TEXT,
  call_count        INTEGER,
  total_input_tokens    INTEGER,
  total_output_tokens   INTEGER,
  total_cached_tokens   INTEGER,
  total_reasoning_tokens INTEGER,
  total_cost_usd    REAL,
  avg_duration_ms   INTEGER,
  max_duration_ms   INTEGER
);

usage_outcome — 后置事件

与 usage_log 的关联是 message_id（弱关联，不做外键；outcome 可能没有对应 log）。5 种事件类型闭集：

vault_save
用户把 AI 回复保存 / 复制到笔记（Save to note 按钮）。
copilot_accept
用户接受了 Copilot 内联建议（Apply changes）。
search_click
Quick Search 结果被点开。
agent_file_emit
Agent 直接产出了一个 vault 文件。
continuation
用户在 10-60s 内继续发送下一条消息且没有拒绝关键词——弱信号：至少没被拒绝。
Adoption vs Useful 的区别 Useful = 有 ≥ 1 条 outcome 事件（任一种）。Adopted = 有 vault_save | copilot_accept | agent_file_emit 中至少一种（不含 search_click 与 continuation）。所以 useful ⊇ adopted。Cost per saved 分母是 adopted 事件数；Cost per useful click 分母是 useful message 数。
Compaction：默认 30 天详情 → 之后仅存 daily usageDetailRetentionDays（默认 30）到期后 compactBefore 把详情行汇进 daily 并 DELETE。History 屏只能查 30 天内的明细——超出后仍能看聚合统计，但看不到单条调用了。要看更长历史，把设置调大；代价是 usage_log 表体积随时间增长。

六个核心指标

Dashboard 上有几十个数字，但真正决策用的就下面这六个。每个都来自明确的 service 方法，不是 UI 拼算的。

指标怎么算来自哪个方法看到不对劲时看哪
Budget pace 当月已花 / 当月预算，按线性外推到月底 UsageTrackingService.getMonthlyPace(monthlyUsd, resetDayOfMonth) Budget Alerts 屏
Context risk 当前 chat session token 占 auto-compact 阈值的百分比 useCurrentContextUtilization()（前端 hook，走 SessionContextService） Chat Studio 的 compact 按钮
Cost per saved artifact Σ以 vault_save / copilot_accept / agent_file_emit 结尾的调用成本 ÷ 保存事件数（默认 7d 窗口） getCostPerSavedArtifact(range, outcome) Outcome Value 屏
Cost per useful click Σ search + rerank 调用成本 ÷ search_click 事件数 组合调用 Outcome Value 屏（每 feature 分解）
Total calls 期内 usage_log 行数 getKPIs(range) History 屏
Outcome funnel Total calls → Useful（≥1 outcome）→ Saved（adoption 类） UsageOutcomeRepo.countUsefulMessages / adoptedMessageIds Outcome Value 屏
为什么 “calls” 不是最有用的数字 用户 本能 会去看“今天 AI 被调了几次”，但那个数没有决策价值——分母是使用意愿，不是浪费。真正有决策力的是 cost per saved：如果它异常高，要么模型选错了（Optimization 会建议 route_to_cheaper），要么调用没落地（Outcome funnel 会显示 useful 但没 adopted）。所以 Overview 把 Cost per saved 放在第三个 KPI，比 Calls 更显眼。

Optimization：规则 vs LLM 双路径

Optimization 是这个 dashboard 里唯一 会调 LLM 的通路——但只在你手动打开 Optimization tab 且当前 Optimization Curator 设置了 provider 时才发生。规则路径始终作为兜底，保证离线也能出建议。

能推的建议种类（action）

action触发信号预估影响
route_to_cheaper_model 某 feature-model 的 no-outcome 率 > 50% 且 cost per call > $0.05 预估月省，按建议 model 的价格差 × 调用次数外推
lower_compact_threshold 长 session 数量 > 阈值，session 平均 token 占比接近上限 压 chat context 让 compact 提前发生
review_no_outcome 某 feature 的 useful rate 特别低 不省钱，但值得排查：feature 是不是给了坏 prompt
silence_low_cost_pip 某 feature 频繁但单价很低（例如 embedding 心跳） 不省钱，只是提示别在 Overview 焦虑这类噪声
set_budget 用户还没设 monthly budget 预算是 pace 的分母；没设的话所有告警都不起作用
Scenario：保守 / 均衡 / 激进 Scenario = conservative | balanced | aggressive 只影响 过滤——保守模式只保留 impact = high 且 investigate 类的建议；激进保留全部。UI 右侧的 projection summary 会随 scenario 变——你能在真的 Apply 之前看到 “选保守能省多少 vs 选激进能省多少”。
Apply 会真的改设置吗？ 会——但走的是 建议对应的具体 action：route_to_cheaper_model 修改 04 profiles 里的 role → model 映射；lower_compact_threshold 改 chat 的 compact 阈值；set_budget 写 monthly budget。都是 settings 层的修改，不改 vault，不 evict 已有 chat 上下文。想撤销：Preview 阶段可以退出；Apply 后到 Settings → Restore 或用 Obsidian 的 File Recovery 找 data.json。

隐私 / 关掉它 / 数据保留

用户对 usage tracking 的三个疑问：数据发出去了吗、能不能关、存多久。答案：本地保存，可关，默认 30 天。

问题实际行为控制项
会不会把我的 prompt / response 传到 provider 之外 不会。UsageTracking 只订阅 usage 事件——input/output tokens 数、cost、duration。调用内容 从来不写进 usage_log。Prompt/response preview 是可选的（Storefront 那栏 metadata），默认关。 usagePreviewEnabled: false（默认）
数据存哪里 本地 vault.sqlite；从不发送到 Peak 服务端（Peak 没有服务端）；也不发到 provider。 —
能全关吗 能。usageTrackingEnabled: false 后 UsageTrackingService.init 跳过订阅——从此 event bus 上的事件全丢。dashboard 打开会显示空数据。 usageTrackingEnabled: false
历史明细存多久 默认 30 天详情；到期后 compact 进 daily。daily 长期保留（用户几乎不会主动清）。 usageDetailRetentionDays
outcome 事件呢 存在 usage_outcome，不受 detail retention 影响；outcome 分析要跨窗口，不宜按 30 天砍。 手工清 SQLite
Optimization LLM 呢 只有你打开 Optimization 屏且配置了 curator LLM 才调用；每次点 Refresh 才请一次。发的是 聚合 signals（feature-model stats、cost 分布），不发 prompt/response 原文。 不配 curator LLM = 规则路径
Prompt preview 打开前请三思 usagePreviewEnabled: true 会把 prompt/response 的前几百字符写进 metadata_json——之后 History 屏的 What was this about 会有内容，但 usage_log 表变大且带上你与 AI 的对话内容。误开 → 忘了关 → 分享 vault backup 时会带出对话历史。只在排障时临时开，排完关掉。

技术附录 · 运行时装配

Usage Dashboard 是 Peak 里 装配最简单 的 feature 之一——两个 singleton service + 一个 Obsidian View。装配全在 main.ts。

失败与降级

当 Dashboard 里数字对不上、屏空、或告警不出，按下面顺序排。

屏空 — usageTrackingEnabled 关了。 症状：所有六屏都空，Cost per saved 显示 —。修：Settings → AI → Usage tracking → Enable；打开后 只对之后 的调用生效——之前的记录已经没写。
某个 feature 从来不在 Provider-Model 屏出现。 症状：明明在用 embedding / graph，dashboard 却没有 graph / indexing 分布。原因：该 feature 的调用路径 没有 调 emitUsage。目前已知 gap：embedTexts()。修：在该 feature 的调用结束点补一次 emitUsage(usage, startMs, false, 'indexing', 'embed')。
Cost 显示 $0.00 但明明调了 provider。 症状：History 屏 cost 列 0。原因：模型 catalog 里没有该 model 的定价条目。修：在 Harness 的 model catalog 加一条；之前 的行 cost 不会补算，只有之后的新行按新价。
Budget alert 从来不响。 症状：明明月底了、pace 明显超支，Budget Alerts 屏没有告警。原因：monthly budget 未设 或 resetDayOfMonth 不对。修：Settings → AI → Budget → 设 monthly $ 上限；Optimization 屏也会推 set_budget 建议。
Outcome funnel 一直显示 0 saved。 症状：明明常在用 Save to note，Outcome Value 屏的 saved 分子是 0。原因：这些 UI 动作没有触发 UsageOutcomeService.recordVaultSave()。修：找该 UI 组件，在保存成功后调 recordVaultSave(messageId, sessionId)。
Optimization 屏建议全是 “Set a monthly budget”。 症状：只出一条 set_budget，别的建议都没有。原因：signals 里 monthlyBudgetUsd = 0，规则引擎因为 不知道要省什么 没法推别的。修：先设预算，再回来看建议。
History 表分页“下一页”不响应。 症状：翻到第 3 页后卡住。原因：getRecentCalls 的 offset 超过留存窗口（30 天前的行已被 compact 掉）。修：把 usageDetailRetentionDays 调大；或接受 “30 天前只有 daily 聚合可看”。
event bus 上的 usage 事件被跨插件其他订阅者读到？ USAGE_RECORDED 是 Peak 内部 event bus，不进 Obsidian 的公开 event 通道，其他插件读不到。如果你另外写了 vault-level Obsidian event，要小心别把 usage 数据带出去——本 dashboard 的 event 类型永远只在 src/core/eventBus.ts 里。
