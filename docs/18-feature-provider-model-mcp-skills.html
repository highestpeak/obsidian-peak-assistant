18 · Feature · Provider · Model · MCP · Skills · 五层 AI 供给的用户视角

Provider 是账户；Profile 是账户 + 模型；Role 是任务；MCP 是外部工具；Skill 是工作手册。

Peak 里 “配置 AI” 涉及五个概念——它们容易混，因为供应商常把账户、模型、工具和工作手册混着叫。这份文档把每一个说清楚：

  • Provider：Anthropic / OpenAI / Google / Perplexity / Ollama / LiteLLM / 自定义。选谁提供 AI 服务。
  • Profile：一个 Provider + API key + 一组模型偏好。它是“账户”的技术叫法。
  • Role：一次“任务用哪个 Profile 的哪个模型”。Chat / Copilot / Agent / Fast / Embedding / Web Search 六种任务。
  • MCP：Model Context Protocol。第三方进程暴露的工具集，AI 可以调用（读文件、搜网、控制 IDE 等）。
  • Skill：工作手册，告诉 AI “在 X 场景下用哪几种工具、什么步骤、产出什么”。

这份文档讲清楚这五个概念的 责任分工、怎么在 Settings 里配、Curator 怎么替你选、加一个新 MCP server / 一份新 skill 走什么路径。

这页解决什么

在 04 · Configuration 里，Provider / Profile / Role / MCP / Skills 各占一节——但 它们之间的关系 分散在各段，第一次读的用户很难拼出全景。这页把五个概念放到 一张地图 上：

核心结论：AI 供给分两条独立通路 (1) 模型能力通路：Provider → Profile → Role → 具体调用；(2) 工具与工作流通路：MCP servers 暴露工具，Skills 组织成工作手册，Agent 从 Skill 拿白名单再从 ToolRegistry 拿工具。两条通路只在 Agent 里汇合——Chat / Copilot 走通路 1，Agent / Skill 调用需要通路 1 + 2 一起。
本文读者 刚装 Peak 想搞清楚要不要填 6 个 API key 的新用户；想给团队接入自建 LiteLLM 的管理员；要加一个自定义 MCP server 的 tinker；打算发布 skill 到 marketplace 的 skill 作者。
本文不做什么 不重复 04 里 Settings tab 逐字段的说明；不覆盖 21 Agent Harness 的 tool loop 内部；不讲每个 provider 的定价历史；不写 “Ollama 本地跑 llama3 vs qwen” 这类模型选择建议——那属于 Curator。
Curator 与本文关系 你不需要理解五层就能用 Peak：Curator 会读你的环境（有没有 Ollama / 有没有 API key / 内存多少 / 语言偏好），推荐一套 Recommended Setup。本文是给那些想手动 override Curator 建议的用户——正常情况下走 Settings → AI Setup → Apply recommended 就够了。

五个概念的分工

同一张“AI 服务” 概念被不同人切成不同层。Peak 的分层如下——每一层回答一个不同的问题，重叠越少越健康。

图 1 · 五层概念的责任边界 Mermaid · semantic stack
flowchart TB Prov["Provider
Anthropic / OpenAI / Ollama / ..."] --> Prof["Profile
Provider + API key + 模型偏好"] Prof --> Role["Role
Chat / Copilot / Agent / Fast / Embedding / WebSearch"] Role --> Call[["实际 AI 调用"]] MCP["MCP Servers
外部进程暴露工具"] --> Tools["ToolDef
标准化工具"] Skill["Skill
工作手册: allowedTools + phases"] --> Tools Tools --> Agent[["Agent 执行"]] Role -. Agent role .-> Agent

读图：Chat / Copilot 只需要走 左半 的 Provider→Profile→Role→Call。Agent / Skill 类调用需要走 左半 + 右半——Role 提供模型，Skill 提供剧本，MCP 提供额外工具。五个概念都可以独立配、独立测。

层它回答的问题谁生成 / 决定不可混淆点
Provider “AI 服务来自哪家？” 用户选：Anthropic / OpenAI / Google / Perplexity / Ollama / LiteLLM / 自定义 Provider 只是 “vendor 名”，不带 key、不带模型选择。
Profile “我这个账户上有哪些模型可用？” 用户配 API key + baseUrl；系统从模型 catalog 挑该 vendor 下的所有模型 可以同一 Provider 有多个 Profile（例如个人账号 + 公司账号）。
Role “这次 Chat / Copilot / Agent 用哪个 Profile 的哪个模型？” 用户在 AI Setup 绑定每个 Role → (Profile, modelId) Role 是产品概念（任务），不是技术概念（vendor）。
MCP Server “外部工具从哪个进程 / URL 来？” 用户加 MCP config（stdio 命令 或 SSE url） MCP 不是模型，是 工具集；AI 不 成为 MCP，AI 调用 MCP。
Skill “AI 在 X 场景下应该怎么工作？” 作者写（vault 目录里的 markdown 或内置代码） Skill 白名单里可以包含 MCP 工具；Skill 本身不带模型，跑时用当前 Role 的模型。
常见误解 1：Provider = Model 用户常说 “我要用 OpenAI” —— 但 OpenAI 是 Provider（vendor），gpt-4o-mini 才是 Model。同一 Provider 下有几十个 Model，每一个价钱、能力都不同。“绑了 API key” = Profile 就绪，还没决定 Role 用哪个 Model。
常见误解 2：Skill = Prompt Skill 不只是一段 prompt——它包含 allowedTools 白名单、phases（如果是 pipeline）、outputTemplate、inputs schema。“把 prompt 存起来” 属于 Chat 的 System Prompt / Copilot 的自定义 action；skill 是完整的工作手册。
常见误解 3：MCP = 插件 MCP 是 协议——一个外部进程用 stdio 或 SSE 暴露工具。Obsidian 插件是 插件——同一个进程里注册 command。两者边界完全不同，见 15 · Command Gateway。

Provider & Profile

Provider 是 vendor 类型；Profile 是 用户配好的 vendor 实例。当前 Peak 支持 7 种 Provider kind，每一种都有对应的 SDK adapter。

Provider kind典型 modelsProfile 需要填的字段特点
anthropic claude-opus-4 / claude-sonnet-4 / claude-haiku-4-5 apiKey 官方 Anthropic API；maxOutputTokens 可能需要额外配。
openai gpt-4o / gpt-4o-mini / o3 / o3-mini apiKey，可选 baseUrl 官方 OpenAI 或 Azure OpenAI；baseUrl 兼容 OpenAI 格式的都能用。
google gemini-1.5-pro / gemini-2.5-pro-exp / gemini-flash apiKey Google AI Studio 或 Vertex AI（后者需要更多字段）。
perplexity sonar / sonar-reasoning / sonar-pro apiKey Web-native 模型；有内置检索。Web Search Role 常用这里。
ollama llama3.1 / qwen2.5 / deepseek-r1 / phi4 / ... baseUrl（默认 http://localhost:11434） 本地跑；无 API key；模型必须先 ollama pull。
litellm 用户自建 gateway 路由的一切 baseUrl + apiKey 典型企业接入：一个 LiteLLM 后端后面接多家 provider。
custom OpenAI-compatible 的任何后端（LM Studio / vLLM / TGI / ...） baseUrl + apiKey（可选） 走 createOpenAI({ baseUrl })——只要接口兼容就行。
Profile 与 Provider 是多对一 同一个 Provider kind 可以有 多个 Profile。典型场景：anthropic-personal（你的个人 key）+ anthropic-work（公司报销的 key）——两个 Profile 都是 kind=anthropic，但 apiKey 不同，Role 可以分别绑到不同 Profile。“换公司账号” 就是切 Role 到 anthropic-work。

Provider 全景 · 支持的 vendor 与选择规则

Peak 支持的所有 provider 都列在这里。三张表分工：LLM/embedding 一张、多模态生成一张、rerank/向量一张。表下的选择规则是 Curator 内置的推荐逻辑——用户可以手动 override 但默认走这份判断。

LLM / Embedding Provider（Profile.kind）

createLanguageModel(profile, modelId)（src/core/providers/vercel/provider-factory.ts）目前接受 8 种 kind。前 4 种是原生 API，中间 2 种是聚合/开源，最后 2 种是 OpenAI-兼容的兜底：

kindCatalog成本梯度能力亮点典型用途 · 建议 Role 绑定
anthropic claude.json · 11 model 中-高 Reasoning 强、Tool use 稳、200k ctx、Vision Chat 主推、Agent Deep tier、Copilot Research；写作、结构化 JSON、长上下文工程都优先它
openai openai.json · 18 model 低-高 覆盖最广（gpt-5-nano 到 gpt-5-pro）、原生 embedding、Vision、Reasoning Fast tier（gpt-5-nano 便宜）、Embedding Role（text-embedding-3-small）、Copilot Fast Lookup；catalog 最全，作为 fallback 也稳
google（gemini） gemini.json · 8 model 低-中 1M ctx（gemini-2.0-flash）、PDF input 原生、多模态、便宜 长文档 chunk 处理、Ambient LLM 摘要（成本敏感 + 内容长）、Auto-tag / DocSummary 类高频调用
perplexity perplexity.json · 5 model 中 原生 web search、citation 返回、实时新闻 Web Search Role 专用；不推荐做 chat 主 provider（一般对话它算贵）
openrouter 动态（走 OR 的 model list API） 低-高 400+ 模型聚合、单 key 走遍 open-source + 闭源、有 free tier 层 试用新模型（先在 OR 上跑 3 天决定是否单独接原生 provider）、成本压缩（用 OR 的 discount 版路由）、兜底（原生 provider 都挂时切它）
ollama ollama-families.json（families 而非单模） 0（本地） 本地推理、无网络依赖、隐私 vault 场景 移动/离线、敏感 vault 强隐私、Local Fast tier；缺点：延迟高、tool use 表现不稳，不推荐做 Agent Deep
litellm 用户自己填（走 OpenAI 兼容 API 层） 视代理商而定 企业内部 LLM 代理常用、把私有云 model 暴露成 OpenAI shape 企业 vault 走 LiteLLM 代理；配置 baseUrl + apiKey，其它跟 openai 无差别
custom 用户填（OpenAI-shape 兼容） 取决于服务 任何 OpenAI-兼容 endpoint（Deepseek / Groq / Together / Mistral 等） Groq（超低延迟 chat）、Deepseek（性价比 reasoning）、Together（社区开源 model）——它们目前没独立 kind，走 custom + baseUrl
为什么 8 种够用 LLM 生态本质上是"闭源 4 家（Anthropic / OpenAI / Google / Perplexity 特色场景）+ 聚合器 1 家（OpenRouter）+ 本地 1 家（Ollama）+ OpenAI-shape 兜底 2 种（LiteLLM / custom）"。每加一个原生 kind 都要写一个 ai-sdk provider 依赖 + provider-factory case + catalog JSON。新兴 vendor（如 Groq）先走 custom；如果长期活跃再独立成 kind。

多模态生成 Provider（MediaGenerationPort）

跟 LLM 是独立的抽象轴：不进 Profile / Role 系统，只需要 API key + 端点。当前默认实现走一家聚合器，备选 adapter 只在默认路径不满足时出现。

Adapter角色覆盖类型推荐理由 · 备胎位置
FalMediaAdapter 默认适配器 TTS · 图像 · 视频（音乐放弃） 主推：985 endpoints，image API 市场 50%、video 44%，比 Replicate 便宜 30–50%、快 10×，一个 key 覆盖四类
ReplicateMediaAdapter 备选适配器 预期覆盖同上 fal.ai 挂/涨价时的备胎；社区自定义模型比 fal.ai 更多
ElevenLabsMediaAdapter 专项备选 只 TTS 用户对 fal.ai 的 Kokoro TTS 声音质量不满时的升级路径；成本 3–5×
OpenAIMediaAdapter OpenAI-only 备选 DALL-E 3 图像 + TTS 用户只有 OpenAI key、不想再注册 fal.ai 时的最小配置路径
ComfyUILocalAdapter 本地 GPU 备选 图像（视用户装的 workflow） 本地 GPU 用户；成本 0 但需自己起 ComfyUI 服务

Rerank / Vector Provider

Rerank（src/core/providers/rerank/）目前有 2 层实现：

  • RankGPT（走上表的 Rerank Role 绑定 LLM Profile）——用 LLM 自身对搜索结果打分。适合精细但慢+贵。
  • Cohere Rerank API（Backlog）——独立 rerank service，性价比高。当前用 RankGPT 替代。

Vector store 直接用 sqlite-vec（不走 provider 抽象）；用户不需要选。

Curator 推荐规则

Curator 拿到用户环境（有哪些 provider key + 优先级 = 便宜 / 快 / 高质）后走这份 hard-coded 优先级：

Role用户偏好：quality用户偏好：cost / speed
Chat / Agent Deep anthropic claude-opus-4-x → anthropic claude-sonnet-4-x → openai gpt-5-pro openai gpt-5-mini → google gemini-2.0-flash → ollama llama-3.x-8b
Agent Fast / Copilot Fast Lookup anthropic claude-sonnet-4-x → openai gpt-5 openai gpt-5-nano → google gemini-2.0-flash-lite → ollama llama-3.x-8b
Embedding openai text-embedding-3-large openai text-embedding-3-small → ollama nomic-embed-text
Web Search perplexity sonar-large-online perplexity sonar-small-online → 关闭
Rerank 与 Agent Fast 同 Profile（RankGPT） 关闭 rerank，用 RRF 兜底
Media (TTS) fal.ai Kokoro（默认可用）→ ElevenLabs（专项备选） fal.ai Kokoro
Media (Image) fal.ai Flux dev（override styleHint） fal.ai fast-sdxl（默认）
推荐规则是 hard-coded 不是 LLM 决定的 Curator 本身用 LLM 是为了"环境检测"（有没有 key 有效、哪些模型响应通）——最终 Role → Provider 绑定的选择规则写死在代码里（src/service/agents/harness/curator/），确保结果 deterministic。用户可以在 Onboarding wizard 点Apply recommended 一键套用，也可以手动 override 到 Provider 列表里的任何可用项。

Provider 扩展边界

Provider 扩展要先判断它属于 LLM provider、media provider，还是 OpenAI-shape 兼容 endpoint。不同类型进入不同抽象轴，不要把所有外部服务都塞进 Profile / Role。

  • LLM provider：进入 Provider/Profile/Role；只有长期稳定、能力差异明显的 vendor 才值得独立成 kind。
  • Media provider：进入 MediaGenerationPort，与文本模型选择解耦。
  • OpenAI-shape endpoint：优先走 custom 或 litellm，等到有明确产品理由再独立成 provider。

六种 Role

Role 是 任务，不是 vendor。同一个 Chat Role 可能今天用 Claude 明天换到 Gemini。Peak 里有 6 种 Role，每种都是 (profileId, modelId) 的绑定。

Role什么时候用选模型时的偏好
Chat
最常用		 用户和 AI 对话；Chat view 里那些消息 能力强 + 上下文长；一般选 Opus 级 或 GPT-4o 级
Copilot Document Copilot 的 17 条 action（polish/review/tags/...） 结构化输出稳 + 中等价位；Sonnet 级 或 gpt-4o-mini 常见
Agent Vault Intelligence 的多步 agent（find-related / extract-todos / ...） tool use 好 + 推理强；Opus / Sonnet / o3
Agent Fast agent 循环里的快速中间步骤（planner / router） 便宜 + 快；Haiku / gpt-4o-mini / gemini-flash
Embedding Search Index 的 chunk 嵌入 + 查询嵌入 专用 embedding 模型（text-embedding-3-small / nomic-embed-text for Ollama）
Web Search Chat 里 “搜网” 触发的检索 web-native 模型；sonar-pro 或 gpt-4o + web tool
Copilot 回落到 Chat 如果没绑 Copilot Role，ProfileRegistry.getActiveCopilotConfig() 返回 null；Copilot action 会回落到 Chat Role。这意味着 “不配 Copilot 也能用”——但 Chat 模型往往过强 / 过贵，Copilot 应该显式绑到 Sonnet 级 或更便宜的模型。
Embedding Role 不能用普通 LLM Embedding 是专用模型（输出向量而非文本）。绑到 Chat / Reasoning 模型会 直接报错。合法选择：OpenAI text-embedding-3-small/large、Voyage voyage-3、Ollama nomic-embed-text、Google text-embedding-004。没有 embedding = 语义搜索不可用——见 12 · Search。
Role 到底怎么设置 Settings → AI → AI Setup → AI behavior 里每个 Role 都有一个 inline picker——先选 Profile，再从该 Profile 下的模型 catalog 里选一个 Model。点 Recommended Setup 一键应用 会跳 Curator，由 curator 根据你的环境推荐。

Model catalog

Peak 里的所有价格 / token 上限 / 能力标注都来自一份中央 catalog：templates/config/models/model-catalog.json。它是 Provider / Profile / Role / Usage Dashboard / Curator 五方共用的真实源。

Catalog 里每条模型的字段

id / apiModelId
用户看的 id vs API 用的字符串（有时会 diverge，例如别名迁移）。
modelType
llm | embedding | image | video | sound——不同类型进不同 Role 的 picker。
icon
Simple Icons slug 或 vendor 官方 mark 引用；不能 用 emoji 或手写通用图。
costInput / costOutput
USD per 1M tokens，字符串（"2.50"）。Cached / reasoning token 若 vendor 有独立价，可加额外字段。
tokenLimits
maxTokens（单次输出上限）、maxInputTokens（context 窗口）、recommendedSummaryThreshold（compact 触发点）。
capabilities
vision / pdfInput / tools / webSearch / reasoning / maxCtx——布尔或 tier；Role picker 会按这些字段过滤（Embedding Role 不显示 llm）。
releaseTimestamp
用于按 recency 排序；老模型排后面。
Catalog 变化会立即生效 重启插件（或 ModelRegistry.reload()）后：新价格 应用到新调用（历史 usage_log 不追溯）；新能力标注 立即影响 Role picker；新模型 出现在下拉里。反过来——catalog 里没有 的 model id 用户填了，Peak 会用 fallback 定价（按 input token 单价近似），并在 17 Usage Dashboard 上体现为不准确。
Catalog 有历史演化：多 provider 单文件 → 按 provider 拆 当前 catalog 的读法是按 provider 查模型能力、价格和 recency。无论物理文件是单一 model-catalog.json 还是按 provider 拆分，Settings 和 Role picker 都只依赖 ModelRegistry 暴露的同一份查询接口；扩展作者不应该绕过 registry 直接读 JSON。

Curator 怎么替你选

Curator 是 Peak 里 唯一会 “替你决定 AI 用哪个模型” 的 agent。它读你的环境 + 你的预算/速度偏好，产出 推荐 Role 绑定。用户在 Onboarding 或 AI Setup 里点 Apply recommended 就是调它。

读图：Curator 不 执行 绑定——它 推荐；用户 Apply 才写进 ProfileRegistry。LLM 失败时规则兜底 保证离线也能出建议。

Curator 的三档：quick / deep / premium 对应 Agent Fast / Agent / Chat（大致）——但更细：quick 是 “便宜快”，deep 是 “有推理能力”，premium 是 “最强给关键场景”。Curator 会把 6 个 Role 分别落到这三档里，例如 Copilot → deep, Chat → premium, Agent Fast → quick。
Curator 需要 LLM Curator 本身也是 agent——需要一个 provider + model 才能跑。这带来 鸡生蛋 问题：Onboarding 第一次跑 Curator 时用户还没配 provider。解决：Onboarding wizard 先要求配一个（最快的路径通常是 Anthropic 或 OpenAI 的 API key，或本地 Ollama），然后用它跑 Curator 推荐其他 Role。

媒体生成 provider（TTS / 图像 / 视频）

LLM provider 只覆盖文本+embedding；音频 / 图像 / 视频生成走一条独立的抽象轴——MediaGenerationPort（src/core/ports/MediaGenerationPort.ts）。它的形状比 LLM provider 简单：不需要流式、不需要工具调用、不需要 profile 组合，只需要 请求 → 二进制字节 + 扩展名 + MIME。

抽象层选择

不为每个 vendor 写 adapter，用聚合器 调研（docs/research/2026-07-01-multimodal-generation-studio/）明确否决"为 ElevenLabs / OpenAI / Midjourney / Runway 各写一个"，选择用聚合器作为主 adapter：一家聚合了图/音/视/TTS 四个方向、单一 API key、单一账单。这样多家 vendor 的选型不落到 Peak 用户身上，只在 styleHint = "model:..." override 那一层暴露。

Shipped adapter：fal.ai

当前默认的 MediaGenerationPort 实现是 FalMediaAdapter（src/app/platform/media/FalMediaAdapter.ts）。选它的原因：

  • 覆盖广 — 985 个 endpoint，image API 市场占有率 50%、video 44%，一家搞定四大类
  • 价格 & 速度 — 比 Replicate 便宜 30–50%、速度快 10×
  • API 模式统一 — 全部走 queue.fal.run 提交-轮询，指数退避 1.5s → 5s，超时 5min；无需为每类媒体单独学 SDK
  • Key 单一 — 用户在 Settings → AI → fal API key 填一次就都能用

类别默认 model选择理由

换 provider 的成本

要接入 ElevenLabs / OpenAI TTS / Replicate / 本地 ComfyUI 等，只需要实现 MediaGenerationPort 的两个方法（generate + isConfigured），其他代码零改动：MediaRingService 只识别 port，命令层通过 getOrBuildMediaRing 拿到 service，谁都不 import 具体 adapter。

媒体成本不能套用 LLM 定价 媒体生成的定价模型可能按秒、按图、按 token 或按队列任务计费，不能直接复用 LLM 的 input/output token catalog。接入 Usage Dashboard 时应给 Media provider 单独的 catalog 和 usage event shape。

MCP 外部工具

MCP（Model Context Protocol）让 AI 调用 另一个进程 里的工具——文件系统、Slack、GitHub、你自己写的服务。Peak 的 MCP 集成分三步：连接 → 发现工具 → 包装成 ToolDef 供 Agent 调用。

图 3 · MCP 集成链路 Mermaid · MCPClientManager
flowchart TB Cfg["MCPServerConfig
id · transport (stdio | sse)
command/args (stdio) 或 url/headers (sse)"] Mgr["MCPClientManager
connect() · listTools() · callTool()"] Discover["Discovered tools
Record{serverId, tools[]}"] Adapter["MCPToolAdapter
mcpToolToAgentTool()"] ToolDef["AgentTool / ToolDef

读图：连接是 可选 的——用户 disable 某个 MCP server 后它不 connect，tools 不出现在 registry；Skill 白名单里的 mcp_x_y 也就找不到，agent 会跳过或报错。

transport: stdio
用 本地 command + args 起一个子进程；典型：npx mcp-server-filesystem /path。
transport: sse
用 远端 SSE endpoint；典型：远程部署的 MCP server 通过 auth header 访问。
enabled
UI 上的 toggle；关掉后不 connect。加了 config 但没启用 = tool 不会出现在 registry。
status
disconnected | connecting | connected | error；UI 上以徽章显示；错误 message 保留在 MCPConnectionInfo.error。
Tool 名字空间 工具名是 mcp_<serverName>_<toolName>——避免不同 server 的同名工具冲突。Skill 里的 allowedTools 白名单必须写全名。
MCP 工具不走 15 Command Gateway 的 review 当前 MCP 集成是 直接把 tool 交给 agent——没有 Curator 审查、没有用户 review。这是因为 MCP config 是用户自己写的 stdio 命令——用户已经默认信任这个进程。但：Command Gateway 是给 Obsidian 插件生态 用的（不是 MCP）；MCP 的信任模型是 “你敢加就假定你懂”。生产环境应用 MCP 时要谨慎。

Skills 工作手册

Skill 告诉 AI “在 X 场景下，用哪几种工具，按什么步骤，产出什么”。它 不是 一段 prompt，也 不是 一段代码——是一份结构化的工作手册。

SkillDefinition 的字段

id / name / version / author
唯一标识 + 元信息；vault 里的 skill 从 markdown frontmatter 读。
type
simple（一个 prompt + output）或 pipeline（多 phase，前一步输出是后一步输入）。
tools
{ builtin: string[], mcp: string[] }——两类白名单。不在这里的工具 agent 不能用。
model
{ recommended, minCapabilities, outputControl }——建议的模型能力，跑时 Peak 用当前 Agent Role 的模型，如果不满足会 warn。
inputs
用户提供什么：file | text | selection | active-note；UI 会渲染对应的 picker。
phases（pipeline 才有）
多步执行顺序；每步一份 prompt + tools 子集。
systemPrompt / outputTemplate
系统提示；产出的 markdown 模板。
source / filePath
builtin（打包在插件里）或 vault（用户 ChatFolder/Skills/ 目录里的 markdown）。
Skill 的 hot-reload SkillRegistry 监听 ChatFolder/Skills/ 目录变化——用户改 markdown 保存后立即生效，不用重启插件。Built-in skill 需要重启。
invocation: model-first vs user-only model-first：agent 在生成响应时可以主动调用；user-only：只有用户显式选“运行这个 skill”才跑。破坏性 skill（会改 vault 的）默认走 user-only，防止 agent 幻觉调用。
License 与 marketplace（roadmap） 当前 license: free | community | premium 只是标签——没有真正的 marketplace 或订阅。Skill Marketplace 的产品形态放在 roadmap；无论安装源来自哪里，vault skill 都应落到用户配置的 Skills folder，默认是 ChatFolder/Skills/。

失败与降级

五层任何一层出问题都可能让 “AI 不响应”——诊断顺序从最简单往最复杂。

1. Profile 缺 API key / baseUrl 错。 症状：Chat 里点发送后一直转圈，最后报 “Provider not configured” 或 401。修：Settings → AI Setup → Providers，检查 key。Anthropic key 以 sk-ant- 开头，OpenAI 以 sk- 开头——粘错格式会立即报错。
2. Role 没绑 model。 症状：Chat 直接说 “No model configured for Chat role”。修：AI Setup → AI behavior → Conversation 选一个。Copilot 缺 会回落 Chat（安静发生），Embedding 缺 会导致 Search 语义档不能用。
3. Model ID 在 catalog 里不存在。 症状：调用能过（用 provider 原样接收），但成本显示为 fallback price（Usage Dashboard 上表现为 Cost ≈ 0 或明显不对）。修：升级插件（catalog 更新）；或手动在 templates/config/models/model-catalog.json 加条目重启。
4. Ollama baseUrl 不对 / 模型没 pull。 症状：报 connection refused 或 model not found。修：确认 Ollama 在跑（curl http://localhost:11434）；确认模型 pulled（ollama list）；模型不在必须 ollama pull <model>。
5. MCP server 状态 error。 症状：Settings → Tools → 该 server 徽章红色；agent 请求 mcp_x_y 工具时 tool not found。修：查 error message——stdio 常见是 command not found（npx / uvx 路径），SSE 常见是 auth 或 CORS。改完 disable + enable 触发重连。
6. Skill 白名单里的工具不存在。 症状：跑 skill 时 agent 说 “Tool X not available”。可能原因：写错 tool 名（拼写 / 缺 mcp_ 前缀）；MCP server 未连接；Peak 版本升级去掉了某个 built-in tool。修：改 Skills folder 里的 markdown，重新保存触发 hot-reload。
7. Curator 推的模型没在 catalog。 症状：Apply recommended 后 Chat 报 error。Curator schema 校验 就是防这个的——若发生说明 catalog 与 curator prompt 不同步，是 bug；报 GitHub issue。
“换 provider 后 chat 记忆丢了” 是预期行为 切换 Chat Role 到另一 Profile 不会 迁移 conversation history——上下文仍在 SQLite 里，但新 provider 用新的 tokenizer 计 context 窗口。历史消息 会在下次发送时按新模型的 context limit 重新截断，可能触发 auto-compact。没丢，只是重装了。
