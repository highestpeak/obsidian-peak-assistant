这页解决什么

Peak Assistant 的配置面很宽，但它不是十几个并列开关的清单。读这页时先把配置分成四组：

模型与角色 Provider、Profile、Role 绑定，决定“谁来回答”和“不同任务用哪一档模型”。
知识与工具 Knowledge Index、Web Access、MCP，决定 Chat / Search / Agent 能拿到哪些外部线索。
运行与安全 Agent runtime、permission policy、budget alert，决定 agent 能跑多远、何时提醒、何时收手。
文件与模板 ChatFolder、Prompts、Skills、DataStore、Inbox、templates/config，决定 Vault 里长出什么。

这页把整个配置面的“形状”摊平，让改东西的时候有一张地图。

本文读者 正在配置插件的用户；正在改 Settings UI、加新开关或调整默认值的维护者；想搞清楚“为什么我在 Vault 里看到 ChatFolder/、DataStore/ 或 Inbox/”的人。
本文不做什么 不重复功能怎么用（那是 11/12/13/16）。不讲 Search / Chat / Agent 内部实现（那是 22/23/21）。不涉及具体 provider SDK 的接线（那放在 24-infra-provider-model-runtime）。

配置入口在哪

同一份 MyPluginSettings，用户从三个不同 surface 触碰它：Settings tab、Setup Wizard、Command Center。三者共享同一份持久化，只是场景不同。

入口什么时候用能改什么持久化在哪
Settings tab
主入口		 已经上手的用户想改绑定、切索引深度、加 provider、调 safety。 五个 tab 覆盖 provider、role 绑定、index、tools、advanced（storage / runtime / dev tools）。 Obsidian 的 data.json；由 PluginSettingsLoader.normalizePluginSettings() 读取。
Setup Wizard
首次 / re-run		 第一次装，或想让 Curator 根据当前环境重新推荐一次。 7 步引导：环境探测 → Curator 推荐 → 用户接受/编辑 → 写入 profile + role 绑定。 同一份 MyPluginSettings.profileSettings；Curator 只是一次性写入。
Command Center / status bar
运行时轻量调整		 写作过程中要换模型、切 role、临时改 run mode。 覆盖“下一次运行”的 run settings（role / model routing / tools）；不改持久化。 Chat 视图的临时 store；退出会话即失效。
不要混淆持久化和临时覆盖 Command Center 里改的 “Auto model / Manual override / Agent / Plan” 只影响下一条消息。要让绑定永久生效，得回到 Settings → AI Setup。这是 Chat run chip 的设计约束，不是 bug。

字段与用户术语对照

Settings 现在跑一份统一的用户词汇，把内部技术术语一层层翻译。改 UI 文案时必须尊重这份契约，否则 AI Setup、Setup Wizard、Advanced tab 会互相打架。

这份契约由 templates/config/settings.json 和 templates/config/onboarding.json 强制。两个文件顶部都有 _doc 说明当前 vocabulary contract；只有 Advanced tab 允许出现“Harness”这类内部词。

Profile（Profile 数据结构）ProviderAI Setup · Providers；Setup Wizard 前 3 步
Quick tier / fastModelFast LookupAI Setup · AI behavior；Advanced · Tier bindings
Deep tier / primaryModel（agent 场景）Research同上
Premium / online tierUse stronger model when neededAI Setup；Advanced · Escalation policy

如果你要加新配置项：先在这张契约里给它一个用户术语，再决定它出现在哪个 tab。契约里没有的词，绝大多数情况下就是这个开关不应该暴露给用户，而应该留在 templates/config 或 Advanced tab。

5 个 Settings tab

Settings 由 5 个 tab 组成：Overview / AI Setup / Knowledge Index / Tools / Advanced。每个 tab 只负责一类用户任务；越靠后越偏运行时和排障。

Overview · 一眼看 Peak 是否可用

五张卡片：Providers、AI behavior、Knowledge Index、Web Access、Safety。每张卡片是“Ready / Needs attention / Not ready / Optional”四态之一。它不直接改设置，而是把用户导向其它 tab；卡片下面挂 4 个 Actions（Run setup / Test providers / Check index / Try Chat）。

AI behavior 摘要块 (overview.aiBehaviorSummary) 是只读的：Conversation / Fast Lookup / Research / Use stronger model when needed 各自绑定的模型。想改绑定要跳到 AI Setup。

AI Setup · Provider 和 Role 的主编辑面

4 个 section：

  • Recommended setup — Balanced / Lowest cost / Research quality / Local & private 四个预设，一键改绑定。
  • AI behavior — Conversation / Fast Lookup / Research / Use stronger model when needed / Knowledge Index，每个 role 单独选 provider + model。
  • Providers — 列出 profile，Test / Edit / Add Provider。
  • Safety — 默认 permission mode。

这 tab 是 Profile v2 的门面。它不直接编辑 Profile 对象，而是让用户看到“角色 → provider + modelId”的一对映射，中间转换由 ProfileRegistry 负责。

Knowledge Index · 索引深度与质量

5 个 section：

  • Knowledge Index status — vector store / indexed files / index depth 只读快照。
  • Indexing — index depth、Auto-index on startup、Document types、Ignore patterns、Rebuild index。
  • Search quality — Personalized PageRank 开关。
  • Chunking — Max chunk size、Chunk overlap。
  • AI Analysis — Auto-save results、Save folder、Recent history limit。

详细的深度区别放在 Knowledge Index 深度。

Tools · Web Access 与 External Tools

两个 section：External tools（挂 MCP server），Web Access（选一个 profile 作为 web search provider；显示会被哪些 surface 使用，例如 Chat、Research）。Web Access 是 optional，没配也不影响其它功能，只是 Chat / Research 无法调 web search 工具。

Advanced · 运行时、存储、诊断

用户不常动的一层：Re-run setup wizard、Diagnostics（agent runtime + backend health）、Storage（Data storage folder + Chat root folder）、General（Attachment handling、DevTools graph inspector）。“Harness”这个词只允许在这个 tab 出现；Tier bindings、Escalation policy、Hooks 也在这里。

为什么 5 tab 而不是一大坨 这次分 tab 是 2026-05-30 design-system-unification 的结果。核心判断：Overview 服务“Peak 现在有没有问题”这一个问题；AI Setup 服务“我要换模型 / 换 provider”；Knowledge Index 服务“搜索为什么不准”；Tools 服务“我想加 MCP / Web”；Advanced 服务“运行时 / 排障 / 我知道自己在做什么”。原先所有配置堆在一个 tab 时用户根本找不到入口。

Provider、Profile 与 Role

Profile v2 是当前的模型配置数据模型。用户看到的是“Provider”和“Role”；底层结构是 Profile + 6 个 RoleConfig。

Profile 是一次能通所有 SDK 的凭据 + 模型 bundle：kind（anthropic / openai / google / perplexity / ollama / openrouter / litellm / custom）、baseUrl、apiKey、primaryModel、fastModel、可选 embeddingEndpoint / embeddingModel。用户在 Settings 里看到的“Provider 卡片”，一张卡就是一个 Profile。

RoleConfig 是一次“角色需要哪个 profile 的哪个 model”的绑定，只有 profileId + modelId 两个字段。整个插件目前用 6 个 role：

Role 字段用户术语谁在读不配时会发生什么
activeChatConfig Conversation Chat 视图默认回答；Fast Lookup / Copilot 未绑定时回落到它。 Chat 拒答；Overview 卡片显示 Needs attention。
activeAgentFastConfig Fast Lookup（local） Agent Harness 的 fast tier；Ambient Push / 短回复。 Harness 跳过该 tier，进入 escalation。
activeAgentConfig Research（local） Vault 分析、多步 agent、长文档处理。 回落到 Conversation；agent 质量下降但仍能跑。
activeCopilotConfig Copilot（继承 Research 命名） Copilot Document lane：polish / review / links / tags。 回落到 Conversation。
activeEmbeddingConfig Knowledge Index Search 索引写入时用它算 embedding。 semantic / full 深度不可用；Search 只能跑 fast。
activeWebSearchConfig Web Access Chat + Research 里的 web search 工具。 Chat / Research 无 web search；其它功能不受影响。

Curator 只写这一层：Setup Wizard 里 Curator 推荐的结果，最后落成的就是这 6 个 RoleConfig。Curator 不能创建新的 role，也不改 Profile 结构；它只是根据 templates/config/curator-catalog.json 里 22 个模型的元数据挑选。

Harness 那三个 tier 又是什么 harnessSettings.localFastConfig / localDeepConfig / onlineConfig 是 Advanced tab 里的“Tier bindings”。它们和上面 6 个 role 是同类型 RoleConfig，但用途不同：这 3 个是 Agent Harness 内部 tier；上面 6 个是产品级 role。分开是因为 harness escalation 逻辑独立，允许 local-fast 走本地小模型、online 走云端强模型，而 Conversation / Research 的 role 绑定不必跟着切。

Knowledge Index 深度

Knowledge Index tab 最重要的一件事是 Index depth：fast / semantic / full。三档不是“质量高低”，而是“索引管线跑到哪一步”。用户看到的搜索质量、AI Analysis 能力、Ambient Push 精度都会跟着变。

深度索引跑到哪用得上的功能代价
Fast
默认		 标题、路径、文本分片、关键词。 Quick Search 关键词 + 标题匹配；不含语义。 无 embedding 成本；重建快。
Semantic Fast 全部 + embedding + 语义边。 Search 支持向量召回；AI Analysis 可用；Ambient Push 更准。 需要 Knowledge Index role；首次索引消耗 embedding token。
Full Semantic 全部 + hub 发现 + structural 补图 + 更多 enrichment。 Vault Intelligence（13）全量能力；更好的相关推荐。 索引周期显著变长；后台 job 更多。

Auto-index on startup（search.autoIndex）默认 关。开启后 Peak 每次 Obsidian 启动都会跑一遍当前深度的索引。ignore patterns 也在这个 tab 编辑（search.ignorePatterns），默认过滤 .git/、node_modules/、.obsidian/、当前 dataStorageFolder/ 等；如果你把 ChatFolder 也想排除，得手动加。

Search quality 里的 Personalized PageRank（search.enablePPR，默认开）会在每次查询时做一次图 walk，把 keyword / vector 搜不到但图上强相关的笔记提升排名。这跟深度无关，fast 深度也能开，代价是每次查询多几十 ms。

Chunking 有两条最常改的参数：maxChunkSize（默认 1000）和 chunkOverlap（默认 200）。剩下的（skipCodeBlocksInChunking、codeBlockPlaceholder、maxCodeChunkChars）不在 UI 露出，只能通过 data.json 改；它们更接近 23 Search Index 的话题。

AI Analysis 区块决定“分析结果要不要保存回 Vault”：aiAnalysisAutoSaveEnabled（默认开）+ aiAnalysisAutoSaveFolder（默认 ChatFolder/AI-Analysis）+ aiAnalysisExcludeAutoSaveFolderFromSearch（默认开，避免分析结果反过来污染下次搜索）。

Web Access 与 External Tools

Tools tab 是“把外部能力接进来”：Web Access 让 Chat / Research 可以查最新信息；External tools 让 agent 可以调 MCP server。两个都是可选。

Web Access 通过 activeWebSearchConfig 绑定到一个 profile。当前 UI 只显示“Web search provider”一栏；如果没配，Chat 里的相关能力开关会显示 “Web search not configured”，但不会阻塞普通对话。触发 web search 的判断散落在 CapabilitySuggestion.tsx：Chat 会根据用户输入匹配 CAPABILITY_SUGGESTION_PATTERNS.webSearch，在合适时提示。

External tools 是 MCP（Model Context Protocol）server 列表，持久化在 settings.mcpServers。UI 目前给的能力是“加 / 删 tool server”，具体连接生命周期由 MCP 客户端管。这块和 21 Agent Harness 的 tool 权限模型直连：agent 拿到的工具集 = 内置 tools + MCP-registered tools。

为什么放在一个 tab Web search 和 MCP 从用户角度都是“外部能力入口”。放一起让用户在同一处 review 自己“开放”了哪些外部依赖，也让排障时能一次看清 Chat 为什么会去联网、agent 为什么会调外部命令。

Safety、Runtime 与预算

Safety / Agent runtime / Budget 三块合起来决定 “agent 能不能改我的 Vault、跑多少钱、跑什么引擎”。它们分别在 AI Setup（Safety 简版）、Advanced tab（全部）和 Usage Dashboard（预算显示）三处露出，但读同一份 harnessSettings。

Safety · 三档 permission mode

模式Agent 可以Agent 不可以默认？
read
Read only		 读 Vault、搜索、调只读工具。 写文件、删除、跑 shell / MCP 副作用。 不是默认。
acceptEdits
Accept edits		 自动执行写入类工具（含 Vault 写）。 无。适合已建立信任的场景。 默认
bypassPermissions
Bypass safety		 跳过所有 permission gate，甚至不弹确认。 UI 标红：unsafe。 不是默认。

Runtime · 谁在跑 agent loop

Advanced · Agent runtime 里的 agentBackend 有三种取值：auto（默认；有能力时用自研 Harness，个别 agent 仍走 Claude Agent SDK）、harness（强制自研；跑在 Vercel AI SDK 上，支持任何 provider）、claude-agent-sdk（走 Anthropic 官方 SDK，仅 Anthropic 模型）。

Escalation policy 是 Harness 特有的：allowEscalation（默认开）+ maxEscalationsPerLoop（1–3，默认 3）+ autoEscalateScoreBelow（0–1，默认 0.4）。当 self-score 低于阈值时，Harness 会尝试升到下一 tier（fast → deep → online）。详细语义放在 21 Agent Harness。

Budget · 4 条 alert rule

Budget 现在直接持久化在 harnessSettings.budget：monthlyUsd（默认 40 美元；0 表示无预算）+ resetDayOfMonth（1–28）+ 4 条 alertRules。Settings tab 可以改，Setup Wizard / onboarding 也可以在首次配置时写入一组可接受的预算默认值。每条 rule 有独立 kind：

Kind触发条件用户看到的载体
budget_threshold月度花费 ≥ threshold × 预算（默认 40%）。Dashboard 通知。
context_compactcontext ratio ≥ threshold（默认 0.7）。Chat 内 inline 提示，让用户压缩。
agent_receipt单次调用花费 ≥ 阈值美元（默认 0.15）或 token ≥ 5 万。Post-task receipt。
silence_low_cost_pipcall cost < 阈值时压制 per-message pip（默认关）。Chat 消息旁的 pip 隐藏。

为什么 alert rule 是闭合枚举：每条 rule 都对应一个已经写好的 UI 载体（通知 / 内联提示 / receipt / 消息 pip）。PluginSettingsLoader.sanitizeBudget() 用 ALERT_RULE_KINDS 白名单过滤持久化数据，未知 kind 一律丢弃。改这里前请先确认对应载体已经存在，否则 sanitize 会把新 kind 静默清掉。

templates/config 分工

除了 Settings 面板里能改的开关，剩下影响用户体验的配置都在 templates/config/。这层不叫“数据”，叫“可编辑的配置”：随插件发货，但也允许用户覆盖。

文件ownsLoader / 消费者
settings.json Settings UI 全部用户字符串 + vocabulary contract（5 tabs / Harness 词汇 / External tools）。 TemplateManager.loadJson(ConfigTemplateId.Settings)；渲染前 fallback 到 settingsStrings.ts。
onboarding.json Setup Wizard 全部 7 步字符串 + Curator 提示 + welcome / capabilities 文案。 TemplateManager.loadJson(ConfigTemplateId.Onboarding)；fallback onboardingStrings.ts。
chat.json Chat 视图所有 header / composer / runSettings / capability suggestion 用户字符串。 TemplateManager.loadJson(ConfigTemplateId.Chat)。
dashboard.json Usage Dashboard 三屏字符串 + preset alert rules 显示。 TemplateManager.loadJson(ConfigTemplateId.Dashboard)。
curator-catalog.json 22 个可选模型的元数据（benchmark、cost、language、tier 适配）。Curator 推荐来源。 Setup Wizard；validation.ts 做硬约束校验。
*.json 各 provider 的 model catalog（claude.json / openai.json / ollama-families.json 等）+ _defaults.json。 Provider 服务启动时加载，供 model picker 展示。
vault-lint-config.json Vault Intelligence 的维度权重、阈值、时间衰减系数。 13 · Vault Intelligence；lint pipeline。
time-within-normalize.json 时间归一化字典（“昨天 / 上周” 等自然语言 → 时间窗口）。 Search / Ambient Push 的时间感知逻辑。

bridge-note-template.hbs Bridge note 的 handlebars 模板。 Copilot / Vault Intelligence 生成 bridge note 时。
Configurability 原则 docs/conventions/configurability.md 定死了一条：以下七类都不许硬编码在逻辑文件里，必须走 templates/config/ 加一个文档化的 domain fallback——
  • i18n
  • regex
  • label maps
  • 颜色
  • 阈值
  • 权重
  • timing
加新配置项时先决定它属于哪个已有 JSON；只有当没有归属时才开新文件。

Vault 里长出什么

默认布局遵循一个原则：Peak Assistant 自己生成和管理的东西，尽量收在同一个 ChatFolder 下面分层。目录可以被 Advanced setting 覆盖，但默认心智模型不应该把用户带到一堆散落的根目录。

  1. 用户会读会写 — Chat root、Prompts、Skills、Inbox。
  2. Peak 自己管理但用户会看到 — Hub-Summaries、AI-Analysis、Attachments。
  3. 纯数据 / 缓存 — DataStore、resources-summary-cache。

全部路径来自 settingsTypes.ts 的 DEFAULT_SETTINGS 和 folderPaths.ts。

<Vault>/ ├── ChatFolder/ # settings.ai.rootFolder（可改） │ ├── Prompts/ # prompt override 与 prompt 工作区 │ │ └── Custom/ # 用户自建 Copilot prompt action │ ├── Skills/ # 用户导入 / 自建 skill；默认也收在 ChatFolder │ ├── Inbox/ # quick capture / 写作计划默认保存处；可高级覆盖 │ ├── Attachments/ # Chat 里粘/传的附件落地 │ ├── Hub-Summaries/ # Vault Intelligence 生成的 hub 摘要 │ │ └── Manual/ # 用户手写 hub note │ ├── AI-Analysis/ # AI Analysis 自动保存结果（可关） │ ├── resources-summary-cache/ # 资源摘要缓存；用户通常不用看 │ ├── DataStore/ # settings.dataStorageFolder 默认值；纯数据 │ │ ├── vault.sqlite # 搜索 / embedding / graph（vault tenant） │ │ ├── chat.sqlite # 会话历史 / usage log + 会话的独立索引 tenant，见 23 │ │ └── ... # backup / journal 等 SQLite 附属文件 │ └── system/ │ └── User-Profile.md # AI 记住的用户偏好；用户可改
高级覆盖 Prompts、Skills、DataStore、Inbox 都可以暴露成 Advanced setting。默认文档只描述低心智成本布局：插件所有目录先聚到 ChatFolder/ 下，再按用途分层；如果用户希望 Inbox 像独立收集器，也可以把它改到别处。
路径谁写谁读删了会怎样
Prompts/ Prompt override；用户也可以直接维护 prompt 工作区。 PromptService；Chat prompt picker。 丢失 prompt override；插件回到内置默认。
Prompts/Custom/ 用户手写 Copilot prompt action。 Copilot custom prompt source。 自建 Copilot prompt action 消失；内置 Copilot action 不受影响。
Skills/ 用户导入或手写 skill 定义。 Skill runtime；Copilot / Agent Harness。 自定义 skill 全部丢失；内置能力不应依赖这里。
Attachments/ Chat 附件上传。 Chat 历史消息渲染。 历史消息里附件链接失效。
Hub-Summaries/ Vault Intelligence 的 hub summarizer。 Chat / Search / Ambient 引用 hub 时。 下次索引重建时会重生成；Manual/ 里的手写笔记不会自动补回。
AI-Analysis/ AI Analysis 自动保存（可关）。 用户回顾；默认 不纳入搜索（aiAnalysisExcludeAutoSaveFolderFromSearch）。 历史分析结果丢失；不影响下次分析。
User-Profile.md AI 摘要 / 用户手写。 Chat 上下文装配时可被注入。 下次生成 profile 时会重建，但历史偏好丢失。
summary-cache/ Peak 内部资源摘要缓存。 Peak 内部；用户不需要直接看。 重新触发摘要时会重建；只是一次性变慢。
DataStore/ 两个 SQLite 引擎写入。 Search / Chat / Ambient / Usage 都读这里。 危险：搜索索引 + 全部聊天历史 + 用量数据全部丢失。删前请手动备份。
Inbox/ Quick capture。 用户日常整理；Peak 一般不主动写这里。 Quick capture 记录丢失；插件不受影响。
DataStore 不进 Search Index 无论默认放在 ChatFolder/DataStore/，还是用户通过 Advanced setting 把它改到别处，当前 DataStore 目录都必须进入 search.ignorePatterns。否则 SQLite 文件会被 Search 当成笔记扫，轻则污染结果，重则拖垮索引。

Settings 如何读写

PluginSettingsLoader.normalizePluginSettings() 是唯一把 data.json 转成运行时 MyPluginSettings 的入口。它有三个非明显规则，改配置结构前必须理解。

1 · Whitelist over spread
Loader 不做 { ...raw, ...defaults }。它显式抽出每个字段，未知字段直接被丢。加新字段时必须在 loader 里补 normalize 分支，否则用户 data.json 里的值读不出来。
2 · Defaults 分层
三层默认：字段层（DEFAULT_SEARCH_SETTINGS / DEFAULT_AI_SERVICE_SETTINGS / DEFAULT_HARNESS_SETTINGS）、块层（promptModelMap 是所有 PromptId 的默认 map）、结构层（DEFAULT_SETTINGS 组合前两层）。加字段前先看它属于哪一层。
3 · 只 clamp 边界
数值字段基本都夹一次上下界：shortSummaryLength 50–500、fullSummaryLength 500–10000、aiAnalysisHistoryLimit 1–50、maxEscalationsPerLoop 1–3、autoEscalateScoreBelow 0–1、resetDayOfMonth 1–28、Ambient 的各种 cooldown 至少 1000ms。用户输错也不会崩，但 UI 组件也要跟这份界一致。
4 · Legacy migrate
Settings loader 负责把无效值收敛到当前 schema。目录相关字段只认当前新布局和合法 Advanced override；旧默认目录不作为 fallback。
5 · Budget sanitize
sanitizeBudget() 用一个 ALERT_RULE_KINDS 白名单过滤 alertRules。未知 kind 一律丢弃、保留默认 rule 集。加新 alert kind 前必须同步 white list。
Settings 写入 插件运行时不再直接改 data.json，写入走 PluginSettingsLoader 反向序列化 + Obsidian saveData()。Setup Wizard、Command Center 的临时覆盖、Settings tab 三个入口都收敛到这一个 write path。

维护规则

04 最容易变成“把每个字段抄一遍”，然后半年后就跟代码脱钩。维护时按这些规则来。

加新 Settings 字段 = 4 处同步。 settingsTypes.ts（interface + DEFAULT）→ PluginSettingsLoader.ts（normalize + clamp）→ 对应 tabs/*.tsx（UI）→ templates/config/settings.json（用户文案 + vocabulary contract）。任何一处漏掉，用户就会遇到 “设置了但没生效”。
加新 Role 前先想它的 vocabulary。 Role 是 6 个（Chat / Agent / Agent-Fast / Copilot / Embedding / Web Search），已经吃掉了字段和用户看到的名字里的 5 个用户术语 + Web Access。加第 7 个 Role 意味着 Setup Wizard、AI Setup、Overview、StatusBar 都要同时长出对应格子。别绕开 ProfileRegistry 单独引一份新的绑定。
加新 templates/config JSON 前先找归属。 已有的 9 个 JSON 各有 owner 注释和 _doc 声明。加新文件时先确认现有 JSON 装不下再开；开了之后必须补 _doc + fallback + TemplateRegistry 注册。
改 Vault 路径 = 改用户心智模型。 ChatFolder 结构或 DataStore 路径变，会直接改变用户在哪里找 Prompts、Skills、AI-Analysis 和数据文件。默认逻辑只保留当前新布局；不要在代码里继续挂旧默认路径 fallback。
Advanced tab 才是排障入口，不是隐藏抽屉。 不要把“找不到位置的开关”丢进 Advanced。Advanced 只放：Re-run wizard、Diagnostics、Storage、Attachment handling、DevTools 这种明确“运行时 / 调试”的字段。产品级开关必须待在前 4 个 tab。
